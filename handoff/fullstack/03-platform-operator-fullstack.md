# MiriYum 플랫폼 운영자 풀스택 구조·연결 인계서

## 1. 현재 런타임 결론

플랫폼 운영자 기능은 고도화 로드맵에 설계되어 있으나, 현재 확인된 계정 유형·인증 namespace·OpenAPI·Controller·Service·테스트에는 플랫폼 운영자 계정, 권한, 관리 기능이 없다. 현재 실제 구현은 일반 사용자와 매장 운영자 경계만 제공한다.

이 부재 결론은 영구 지원표가 아니다. 향후 작업자는 매 작업 시점의 Issue, 활성 계약, OpenAPI, Controller·Service, 호출 가능 증거와 릴리스 승인을 다시 확인한다.

따라서 **플랫폼 운영자 전체 셸은 숨긴다.** 로그인 진입, 내비게이션, 라우트 등록, 탭, 버튼과 기타 제어 요소, 데이터 요청, 조치, 코드 분할 진입점, production bundle 및 production mock을 모두 포함하지 않는다. 디자인 문서나 로드맵의 존재는 런타임 capability가 아니다.

`1차 MVP`, `2차 MVP`, `고도화`라는 표기는 로드맵 소통에만 사용한다. 어느 단계 이름도 셸 또는 기능의 런타임 결정이 될 수 없다.

## 2. 금지되는 우회

- 일반 사용자나 매장 운영자 계정에 `ADMIN` 역할을 덧붙이거나, 클라이언트 입력·저장 값·role injection으로 플랫폼 권한을 만들지 않는다.
- 일반 사용자 또는 매장 운영자 로그인, principal, 토큰, 쿠키, 계정 저장소를 플랫폼 운영자 로그인에 재사용하지 않는다.
- 하드코딩 계정, 가짜 endpoint, 가짜 성공 응답, 임의 enum·권한·상태값을 만들지 않는다.
- 테스트 경계를 벗어난 mock, 데모 데이터를 실제 운영 데이터처럼 보이게 하는 흐름, production mock을 만들지 않는다.
- CSS만으로 감추거나 직접 주소 접근만 막는 방식은 충분하지 않다. 미지원 모듈은 navigation, route registration, tabs/controls, requests/actions, production bundles에서 함께 제거한다.
- 일반 매장 운영자의 예약·웨이팅·매장·메뉴·재고 일상 업무를 플랫폼 권한으로 확대하거나, 플랫폼 사건 조치를 매장 운영자의 통상 권한으로 누출하지 않는다.

## 3. 향후 활성화 공통 게이트

플랫폼 기능을 한꺼번에 또는 일부만 연결하기 전에, 해당 기능마다 다음 교집합을 확인한다.

1. 현재 Issue의 소유자, 정확한 허용 경로, 인수 조건, 검증 계획 및 필요한 contract-first 의존 관계
2. 활성 제품·보안·개인정보·UI 기준과 현재 발표·배포 범위
3. 플랫폼 운영자 전용 계정, 인증 namespace, principal, 토큰·세션 격리 계약과 실제 구현
4. 플랫폼 권한 모델과 슈퍼관리자 전용 경계의 승인된 계약 및 실제 서버 인가
5. 대상 기능의 OpenAPI, 상태 전이, 오류 의미, 사유와 감사, 개인정보 최소화·열람 경계
6. 승인된 계약과 일치하는 Controller 및 Service 구현
7. 권한 거부, 동시 조치, 이미 처리된 대상, 부분 실패를 포함한 실제 backend 검증과 현재 release 범위의 승인

하나라도 없거나 서로 충돌하면 해당 기능은 연결하지 않고 전체 셸 또는 해당 독립 모듈을 계속 숨긴다. OpenAPI만 있거나 Controller만 있는 경우, 혹은 제품 단계만 앞서는 경우도 활성화 근거가 아니다.

## 4. 독립된 미래 셸과 가드

조건이 충족된 뒤에도 플랫폼 운영자는 일반 사용자·매장 운영자와 독립된 로그인 진입점, 인증 bootstrap, principal 해석, 토큰·쿠키 namespace, 라우트 가드, 오류 경계, 내비게이션을 사용한다.

- 셸 가드는 서버가 검증한 플랫폼 인증 맥락 없이는 셸 자체를 로드하지 않는다.
- 라우트 가드는 각 업무의 실제 권한과 대상 범위를 다시 확인한다. 셸 접근이 특정 조치 권한을 뜻하지 않는다.
- 슈퍼관리자 가드는 운영자 관리 모듈과 그 계정 발급·중지·권한 관리 요청을 별도로 막는다.
- 권한 거부·세션 만료·동시 변경·이미 처리됨·부분 실패는 임의 성공으로 전환하지 않고, 승인된 오류 의미와 재조회 경계를 사용한다.
- 미지원 모듈은 route 등록이나 lazy import로 남기지 않아 production bundle에 포함되지 않게 한다.

## 5. 기능별 계약 경계

### 회원 관리

일반 사용자와 매장 운영자의 계정 유형, 조회 가능 정보, 제한·해제 가능 조치, 민감 정보 접근 범위가 명시된 계약과 구현이 있어야 한다. 플랫폼 관리 화면이 기존 계정의 일상 프로필 수정이나 다른 계정 유형의 데이터를 우회해 수정해서는 안 된다.

### 입점 신청과 제출 자료 심사

신청, 제출 자료, 승인·반려, 사유, 감사, 동시 처리와 종결된 신청의 상태 전이가 계약·구현·검증으로 제공된 뒤에만 연결한다. 이는 1차 MVP의 승인 대기 없는 매장 등록 흐름과 별개의 고도화 모듈이며, 기존 등록 응답을 클라이언트에서 심사 상태로 바꾸지 않는다.

### 매장 관리

정보 정정, 비활성화, 운영 중지는 플랫폼 전용 권한·사유·감사·영향 처리 계약이 필요하다. 매장 운영자의 일상 매장 관리 기능이나 서비스 재고를 플랫폼 API로 우회하지 않는다.

### 예약 및 웨이팅 사건 관리

예약과 웨이팅 각각에 플랫폼 사건 조회·조치 권한, 대상 범위, 상태 전이, 이유, 감사, 동시성·이미 처리된 결과를 갖춘 계약과 실제 구현이 필요하다. 매장 운영자의 일상 예약 처리나 웨이팅 호출을 같은 endpoint·버튼·권한으로 합치지 않는다. 웨이팅의 실시간 전달은 SSE의 승인된 계약, 인증·인가와 재연결 의미, 실제 Controller·Service 또는 stream 구현, 호출 가능한 성공·실패·재연결 증거, 현재 릴리스 승인이 모두 있을 때만 연결하는 독립 capability다. 하나라도 없으면 이 전달 기능의 내비게이션, 라우트 등록, 탭, 카드, 데이터 요청, 액션, production bundle과 production mock을 함께 제거한다.

### 대표 메뉴·추천 메뉴 운영 검토

대표 메뉴와 추천 메뉴의 플랫폼 경계 조치는 공개 영향, 사유, 감사, 개인정보·권한 경계가 있는 계약으로만 연결한다. 매장 서비스의 메뉴 편집 또는 메뉴 홀드·다른 재고를 직접 변경하는 기능은 이 모듈에 포함하지 않는다.

### 슈퍼관리자 운영자 관리

플랫폼 운영자 계정 발급, 중지, 권한 관리에는 슈퍼관리자만의 서버 인가, 사유·감사, 상태 전이, 경쟁 조치 처리와 실제 backend 검증이 모두 필요하다. 일반 플랫폼 운영자에게 이 권한을 묶어 주거나 권한 이름을 프론트에서 추측하지 않는다.

## 6. 구현 전후 확인 목록

연결을 검토할 때는 기능별로 다음을 실제로 확인하고 결과를 기록한다.

- 현재 Issue와 허용 경로, 활성 기준 문서, 발표 범위가 해당 기능을 승인하는가?
- OpenAPI와 Controller·Service가 같은 인증 namespace, 권한, 대상 범위, 상태 전이, 오류·사유·감사를 제공하는가?
- 실제 테스트가 플랫폼 인증의 교차 사용 거부, 일반 운영자와 슈퍼관리자 분리, 민감 정보 최소 노출, 동시 조치·이미 처리됨, 부분 실패를 검증하는가?
- shell guard와 route guard가 독립적으로 동작하고, 미지원 모듈이 navigation, routes, tabs/controls, requests/actions, production bundles에 없는가?
- 일반 사용자·매장 운영자 기능을 재사용하거나 플랫폼 기능을 다른 역할에 노출하지 않았는가?

현재는 이 목록을 만족하는 플랫폼 계약과 실제 구현이 확인되지 않았으므로, 플랫폼 운영자 런타임은 absent이며 전체 셸을 계속 숨긴다.
