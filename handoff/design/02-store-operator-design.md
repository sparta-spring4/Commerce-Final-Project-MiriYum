# MiriYum 매장 운영자 UI 디자인 인계서

## 1. 목적과 역할 경계

이 문서는 매장 운영자 전용 관리 경험을 설계하는 독립형 요구사항이다. 일반 사용자 탐색·예약 화면과 플랫폼 운영자 심사·관리 화면을 섞지 않는다. 한 대표 운영자가 한 매장을 관리하는 1차 MVP를 기본 구조로 삼고, 공동 관리자·직원 권한·매장 전환은 만들지 않는다.

모든 단계의 화면을 설계하되 단계별 모듈을 독립적으로 둔다. 이후 어떤 모듈이 빠져도 핵심 관리 흐름에 빈 자리, 비활성 버튼, 또는 임시 안내가 남지 않아야 한다.

## 2. 단계별 정보 구조

| 단계 | 설계 범위 |
| --- | --- |
| 1차 MVP | 운영자 계정·내 정보, 매장 등록과 기본정보, 운영 설정, 메뉴, 예약, 두 서비스의 재고, 픽업 운영 |
| 2차 MVP | 자연어 검색·개인화·대체 메뉴·주변 매장·지도는 일반 사용자 탐색 중심이다. 운영자 추천 관리 화면은 설계하지 않는다. |
| 고도화 | 운영 대시보드, 웨이팅, 결제·환불, 알림, 이미지, 통계, 체크인·노쇼, 대표·추천 메뉴 3~5개 관리 |

## 3. 공통 셸과 상태

- 상단에는 현재 매장명과 계정 메뉴를, 본문에는 매장 정보·운영 설정·메뉴·예약·픽업의 독립 내비게이션을 둔다.
- 각 화면은 제목, 목적 설명, 최근 저장 상태를 제공한다. 기본, 로딩, 빈 목록, 입력 오류, 권한 없음, 네트워크 실패, 최신 상태 충돌, 재시도, 저장 성공을 설계한다.
- 저장하지 않은 변경은 이탈·탭 이동 전에 명확히 알리고, 처리 중에는 같은 의도를 중복 제출하지 않게 한다.
- 모바일은 목록에서 상세로 이어지는 단일 열 구조, 태블릿과 데스크톱은 목록·필터·상세 정보를 함께 비교할 수 있는 구조로 조정한다.

## 4. 계정과 매장 시작 흐름

### 4.1 운영자 계정과 내 정보

- 운영자 전용 회원가입과 로그인은 일반 사용자와 분리해 보이게 한다. 이메일, 비밀번호, 표시 이름, 신뢰 연락처, 오류와 요청 제한 상태를 제공한다.
- 신뢰 연락처는 1차 MVP의 연락 수단 입력이다. 이메일 또는 휴대전화 소유 인증이 완료되었다고 표현하지 않는다.
- 내 정보 화면에서는 표시 이름을 조회·편집·저장하고, 최초 등록 신뢰 연락처를 확인한다. 신뢰 연락처의 자유 변경이나 소유 인증 흐름은 만들지 않는다. 비밀번호 재설정, 소셜 로그인, 직원 계정은 고도화 계약이 생기기 전에는 넣지 않는다.

### 4.2 매장 등록과 즉시 관리 진입

가입 후 매장 등록으로 바로 이어지고, 등록이 끝나면 승인 대기 없이 매장 관리 첫 화면으로 이동한다. 별도 입점 신청서, 심사 진행, 승인 대기, 자동 승인 메시지는 만들지 않는다.

등록 화면은 다음의 사용자가 이해할 수 있는 입력으로 구성한다.

- 사업자등록번호, 사업 유형, 매장명, 소개, 지역, 주소, 시간대
- 매장 주 분류와 선택 태그
- 예약·메뉴 홀드·픽업 운영 여부
- 신청자 사업 정보 자기 확인과 필수 입점 약관 동의

수정 화면은 매장명·소개·지역·주소·분류·태그·운영 모드·영업 상태처럼 바꿀 수 있는 값과, 사업자등록번호·사업 유형·시간대처럼 등록 후 일반 수정 대상이 아닌 값을 시각적으로 구분한다. 사업자등록증, 매장 이미지, 고객 공개 준비 심사 화면은 여기에 넣지 않는다.

## 5. 1차 MVP 운영 설정

### 5.1 운영시간과 예약 접수 시간대

운영시간과 예약 접수 시간대는 서로 다른 화면 또는 분리된 탭으로 설계한다. 각각 요일별 여러 구간을 관리하며, 초안 저장 후 즉시 게시하거나 미래 시점 게시를 선택할 수 있다.

- 초안, 예약 게시, 게시됨, 실패 상태와 각 상태의 설명을 보여 준다.
- 게시 전에 예약 게시를 취소할 수 있게 하고, 충돌·검증 실패는 해당 요일과 시간 구간에 안전하게 표시한다.
- 영업시간에는 브레이크타임을, 예약 접수에는 영업시간 밖 또는 브레이크타임과 겹치는 구간을 구별해 안내한다.
- 저장하지 않은 변경, 저장 중, 저장 완료, 저장 실패, 다른 변경과의 충돌을 일관되게 처리한다.

### 5.2 정기·임시 휴무

정기 휴무는 요일·반복 조건을 초안으로 만들고 즉시 또는 예약 게시하며, 게시 전 취소할 수 있는 흐름으로 구성한다. 임시 휴무는 시작과 종료, 사유, 현재 적용 상태, 종료 시각 변경, 취소를 별도 목록으로 제공한다. 휴무 설정이 기존 예약을 자동으로 옮기거나 취소한다고 단정하지 않는다.

### 5.3 예약 시간 정책

예약 시간 정책 화면은 예약 슬롯 간격, 서비스 제공 시간, 정리·회전 시간을 한 정책으로 묶어 보여 준다. 초안 작성, 즉시 게시, 예약 게시, 게시 취소, 활성·실패 상태를 제공하고, 운영시간·휴무·다른 정책과의 모순은 사용자가 안전하게 수정할 수 있는 메시지로 표시한다. 이전에 확정된 예약을 임의로 변경하는 기능은 넣지 않는다.

### 5.4 예약 수용량

날짜와 예약 시간 구간마다 최대 인원, 최대 팀 수, 최소·최대 일행 인원, 영유아 허용 여부를 관리한다. 현재 사용량과 남은 수용량을 함께 보여 주며, 현재 사용량보다 낮게 바꾸려 할 때는 기존 확정 예약은 바뀌지 않고 이후 가용성에만 영향을 줄 수 있음을 안내한다. 날짜 전체 설정의 저장·충돌·실패 상태를 제공한다.

## 6. 메뉴와 두 서비스 재고

### 6.1 메뉴 관리

메뉴 목록과 상세에는 메뉴명, 소개, 가격, 주·보조 분류, 태그, 대표 메뉴 표시, 예약 메뉴 홀드 허용, 픽업 허용을 둔다. 메뉴 내용은 생성·수정·초안·즉시 또는 예약 게시·게시 취소·운영 종료의 흐름을 갖는다.

- 노출 여부, 판매 여부, 게시·운영 종료 상태를 서로 독립된 상태 축으로 표시한다.
- 대표 메뉴 표시와 함께 알레르기 정보, 원산지 정보, 주류 여부를 구조화해 입력·검토할 수 있게 한다.
- 매장과 메뉴 이미지는 고도화 모듈로 분리한다. 대표·추천 메뉴 3~5개를 별도로 선정·노출 관리하는 기능도 고도화 모듈로 분리한다.

### 6.2 예약 메뉴 홀드 재고

`예약 메뉴 홀드 재고`는 일반 좌석 예약에서 선택한 메뉴를 확보하는 전용 영역이다. 메뉴·서비스 날짜·시간 구간별 총량, 사용량, 가용량, 품절 제어를 표시하고, 취소된 일반 예약의 수량은 이 영역의 같은 재고로만 복원된다는 정보를 준다.

### 6.3 픽업 재고

`픽업 재고`는 픽업 주문 전용 영역이다. 메뉴·픽업 날짜·시간 구간별 총량, 사용량, 가용량, 품절 제어를 예약 메뉴 홀드 재고와 나란히 보이되 합산하지 않는다. 취소된 픽업의 수량은 픽업 재고로만 복원된다.

두 영역은 수량, 품절, 사용량, 가용량, 취소 복원이 서로 독립적이다. 한 서비스의 품절·복구·수량 조정이 다른 서비스에 영향을 주지 않으며, 두 재고 사이에 이전·공유·자동 보정 제어는 제공하지 않는다.

## 7. 예약과 픽업 운영

### 7.1 일반 예약

예약 관리에는 날짜·상태 필터, 목록, 상세, 예약자 최소 식별정보, 방문 일시, 인원 구성, 선택 메뉴와 수량, 매장 사유 취소를 둔다. 취소의 결과와 같은 예약 메뉴 홀드 재고 복원 여부를 예약 상세에서 이해할 수 있게 보여 준다.

`방문 완료`은 1차 MVP 흐름으로 디자인하되 독립 모듈이다. 버튼·상태·완료 확인은 예약 조회·상세·취소 화면이 없어도 배치할 수 있게 분리한다.

### 7.2 픽업

픽업을 켠 매장은 사업 유형과 무관하게 픽업 관리 흐름을 설계한다. 픽업 날짜·시간·상태 필터, 목록, 상세, 예약자 최소 식별정보, 메뉴·수량, 매장 사유 취소를 둔다. 취소는 픽업 재고만 복원한다.

`수령 완료`도 목록·상세·취소와 분리된 모듈로 설계한다. 픽업 기능을 켜지 않은 매장에서는 전체 픽업 내비게이션과 화면 흐름이 남지 않게 한다.

## 8. 고도화 모듈

다음은 1차 MVP 기본 화면을 침범하지 않는 독립 모듈이다.

- 오늘 예약·품절·웨이팅 사건을 요약하는 운영 대시보드
- 웨이팅 사용 설정, 대기·호출 목록, 입장 완료·미응답 처리
- 결제·예약금·취소·환불 상태와 내역
- 예약·취소·품절·방문 시간·웨이팅 알림
- 매장과 메뉴 이미지 관리
- 예약률·취소율·노쇼·웨이팅의 기간별 운영 통계
- 체크인과 노쇼 처리
- 대표·추천 메뉴 3~5개 관리

이 문서에 없는 플랫폼 운영자 기능이나 2차 MVP의 운영자 추천 관리 기능은 추가하지 않는다.

## 9. 화면별 산출 기준

각 화면은 목적, 필수 정보와 행동, 기본·로딩·빈·오류·완료 상태, 모바일·데스크톱 정보 구조, 적용 단계, 독립적으로 제거 가능한 미래 모듈, 그 모듈을 제외한 MVP 구성을 함께 제시한다.
