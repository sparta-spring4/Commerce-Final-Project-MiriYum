# 기능 명세: 인증·계정·마이페이지

> 문서 상태: 4단계 승인
> 적용 단계: 1차 MVP
> 도메인 소유자: 1번 팀원 — 인증·계정
> 협업 검토: 3번 팀원 — 마이페이지 예약 상태·조회 DTO
> 관련 정책 ID: AUTH-001, AUTH-002, AUTH-003, AUTH-006, AUTH-007, AUTH-008, AUTH-009, S-006, D-002~D-007, C-001~C-013
> OpenAPI: `docs/specs/auth-account/openapi.yaml`
> 최종 승인일: 2026-07-28

## 범위

### 포함

- 일반 사용자와 매장 운영자의 분리된 이메일·비밀번호 가입·로그인
- Access JWT 발급, Refresh JWT 재발급과 클라이언트 로그아웃
- 계정 유형별 본인 정보 조회·기본 표시 정보 수정
- 일반 사용자 마이페이지의 예약 내역 조회

### 제외

- 플랫폼 운영자 가입·로그인·API
- 그 밖의 소셜 로그인(카카오 외 제공자)
- Valkey Refresh Token 회전·폐기·재사용 탐지
- 활성 로그인 목록·기기별 종료·전체 로그인 종료
- 비밀번호 재설정·수동 복구·회원 탈퇴
- 프로필 이미지 업로드
- 결제·환불·노쇼 정보

## API 경로 결정과 이유

일반 사용자와 매장 운영자의 인증 경로를 각각 `/api/v1/consumers/auth`와 `/api/v1/store-operators/auth`로 분리한다. 계정·인증·거래 경로는 같은 plural audience namespace 아래에 두며, 요청 본문의 `role`로 계정 유형을 선택하는 단일 로그인 API는 사용하지 않는다.

| 결정 | 채택안 | 대안 | 선택 이유 |
| --- | --- | --- | --- |
| 가입 | `POST .../accounts` | `/sign-up` 동사 경로 | 계정 collection 생성이라는 HTTP 의미를 유지한다. |
| 로그인 | `POST .../sessions` | `/login` 동사 경로 | 현재 브라우저 인증 상태 생성으로 표현한다. |
| 재발급 | `POST .../token-refreshes` | `/refresh` 동사 경로 | 재발급 명령의 결과가 새 토큰이라는 의미를 명시한다. |
| 로그아웃 | `DELETE .../sessions/current` | `/logout` 동사 경로 | 현재 브라우저 shell의 인증 상태 제거로 표현한다. |
| 내 정보 | `GET/PATCH .../me` | 요청에 accountId 전달 | JWT subject가 소유자를 결정해 수평 권한 상승을 막는다. |
| 내 예약 내역 | `GET /api/v1/consumers/me/reservations` | 예약 도메인이 API 제공 | 예약 HTTP 경계와 조회 계약을 예약 도메인이 함께 소유한다. |

이 경로는 C-008의 소문자·kebab-case·리소스 중심 원칙을 적용한다. 클라이언트가 계정 유형, 역할이나 accountId를 본문으로 보내 인증 주체를 바꾸지 못한다.

## 계정과 가입

- 일반 사용자는 `consumer_accounts`, 매장 운영자는 `store_operator_accounts`에 생성한다.
- 두 테이블은 같은 이메일·휴대전화 값을 각각 가질 수 있지만 각 테이블 내부에서는 정규화 값이 유일하다.
-- 비밀번호는 AUTH-006을 따라 NFC 정규화 뒤 8~64 Unicode code point이며, 영문 대문자·소문자·숫자·특수문자 중 3종 이상을 포함해야 한다. 이모지와 이모지 조합에 사용되는 제어 문자는 허용하지 않는다. 일반 사용자와 매장 운영자 모두 같은 기준을 적용한다.
- 비밀번호 해시는 `{sha256-bcrypt}` 식별자를 포함한 형식으로만 저장한다. 접두사가 없는 순수 BCrypt 해시와 `{bcrypt}` 형식은 레거시 fallback으로 매칭하지 않으며, 이러한 값으로 로그인하면 일반 비밀번호 불일치와 같은 `AUTH_005`로 실패한다.
- 1차 MVP의 일반 사용자와 매장 운영자 가입은 이메일·휴대전화 소유 인증을 수행하지 않는다. 사용자가 직접 입력한 값을 `MVP 신뢰 연락처`(실제 소유 인증은 생략했지만 1차 MVP에서 사용할 수 있다고 간주한 연락처)로 저장하되, 실제 인증 완료라고 표시하지 않는다.
- 일반 사용자와 매장 운영자의 휴대전화는 공백과 하이픈을 제거한 `010` 시작 11자리 숫자로 정규화한다. 다른 형식은 임의 변환하지 않고 `COMMON_001`로 거절하며, 정규화 값은 같은 계정 유형 테이블에서 유일해야 한다.
- 일반 사용자 가입자는 만 14세 이상임을 직접 확인한 값을 제출해야 한다. 이 값은 실제 연령 인증이 아니며 생년월일 원문은 수집하지 않는다.
- 운영 공개 전에는 일반 사용자와 매장 운영자의 이메일·휴대전화 소유 및 일반 사용자의 연령 확인을 승인된 인증 결과로 교체할지 별도 결정한다. 1차 MVP의 신뢰 연락처는 실제 인증 완료로 승격하지 않는다.
- 매장 운영자의 연락처 정책과 매장 입점의 사업자등록증·운영 승인 절차는 별개다. 연락처를 MVP 신뢰 연락처로 저장해도 매장 입점 승인이나 사업자 자격 확인을 대신하지 않는다.

### 1차 MVP 계정 연락처 경계

- “입력값을 인증된 것으로 간주한다”는 말은 원문 형식을 그대로 저장한다는 뜻이 아니다. 전화번호는 숫자 정규화 값만 저장하고 응답·운영 화면에는 `010-****-5678`처럼 마스킹(일부를 가려 표시)한다.
- 기존 `phone=null` 일반 사용자는 `/api/v1/consumers/me/contact`에서 번호를 한 번 등록할 수 있다. 같은 정규화 번호의 반복 요청은 멱등(같은 요청을 반복해도 한 번 처리한 것과 결과가 같음)하게 처리하고, 다른 번호로 변경하는 기능은 1차 MVP에서 제공하지 않는다.
- 기존 `phone=null` 매장 운영자는 `/api/v1/store-operators/me/contact`에서 번호를 한 번 등록할 수 있다. 매장 운영자도 같은 정규화·중복·변경 금지 규칙을 적용하지만, 예약 알림 대상이 아니므로 이 등록으로 예약용 opaque reference를 생성하지 않는다.
- 기존 DB에 전화번호 값은 있지만 새 알림 대상 참조가 없는 계정은 자동으로 신뢰 연락처로 승격하지 않는다. 마이페이지에서 기존 번호와 같은 정규화 값을 한 번 다시 제출하면 참조를 함께 확정하고, 다른 번호를 제출하면 변경 요청으로 보아 `ACCOUNT_007`로 거절한다.
- 정규화 번호 중복은 `ACCOUNT_002`, 활성 계정의 예약 연락처 미등록은 `ACCOUNT_006`, 최초 등록 뒤 다른 번호로 변경하려는 요청은 `ACCOUNT_007`, 가입·최초 등록 요청의 누락·형식 오류는 `COMMON_001`을 사용한다.
- 일반 사용자의 자동 비밀번호 재설정과 보안 알림은 이메일 소유 인증이 도입되기 전까지 해당 이메일을 “확인된 채널”로 사용하지 않는다. 현재 로그인 수단을 잃은 계정은 정책에 승인된 별도 복구 경계가 없으면 자동 복구하지 않는다.

### 예약 알림 대상 참조

- Auth는 일반 사용자의 예약 연락처에 한해 전화번호와 별도로 opaque reference(내부 구조나 실제 전화번호를 알 수 없는 무작위 참조값)를 생성하고 DB 유일성 제약으로 보호한다. 매장 운영자 연락처는 예약 스냅샷 대상이 아니므로 이 참조를 생성하지 않는다.
- 참조는 UUID v4(충분한 무작위성을 가진 식별자 표준)처럼 예측하기 어려운 값이어야 하며 전화번호 원문, 계정 ID, 단순 해시·Base64 인코딩이나 본인확인 참조를 사용하지 않는다.
- 같은 연락처 버전에는 같은 참조를 반환한다. Auth 또는 승인된 알림 어댑터만 참조를 실제 번호로 해석하고 Reservation은 해석하지 않는다.
- 계정 부재는 `AUTH_003`, 비활성 계정은 `AUTH_011`, 활성 계정에 전화번호 또는 예약 참조가 준비되지 않았으면 `ACCOUNT_006`으로 실패한다. 참조가 준비된 뒤 참조 저장소를 사용할 수 없는 실제 서버 장애만 `COMMON_012`로 구분한다. 빈 참조나 `contactAvailable=false`인 성공 결과를 반환하지 않는다.
- 공개 Service·DTO 이름은 실제 인증 완료를 뜻하는 `Verified...` 대신 `ReservationContactResult`, `getReservationContact`처럼 중립적인 이름을 사용한다.

### 매장 운영자 연락처 경계

1차 MVP 매장 운영자는 일반 사용자와 동일하게 직접 입력한 정규화 휴대전화를 `MVP 신뢰 연락처`로 저장한다. 이 값은 실제 이메일·휴대전화 소유 인증 완료를 의미하지 않는다. 매장 입점의 사업자등록증 업로드·검토·승인은 별도 Store 정책과 API 계약을 따른다.

실제 인증 제공업체를 연동하는 단계에서는 `emailVerificationReference`, `identityVerificationReference` 같은 공급자 중립 참조를 다시 도입할 수 있다. 제공업체 토큰 구조, callback payload(외부 업체가 되돌려주는 응답 본문)와 비밀 키는 MiriYum 공개 API로 노출하지 않는다. 이 단계의 인증 실패 우회 금지는 별도 고도화 계약으로 관리한다.

### 고도화 확인 계약

실제 이메일·휴대전화·연령 확인을 도입할 때는 공급자 중립 어댑터(외부 업체별 차이를 Auth 내부 계약으로 감추는 연결 계층)가 다음을 증명해야 한다.

- 성공 결과의 서명 또는 서버 대 서버 진위
- 대상 이메일·휴대전화와 가입 namespace의 결합
- 만료·일회성 소비·중복 콜백 멱등성
- 만 14세 이상 여부만 보존하고 생년월일 원본을 저장하지 않는 경계
- 연락처 변경 시 기존 또는 새 연락처 소유 확인과 새 참조 버전 발급

1차 MVP의 일반 사용자 임시 신뢰 정책을 고도화 인증으로 교체할 때 기존 값을 일괄 인증 완료로 승격하지 않는다. 사용자가 실제 인증을 통과한 값만 확인된 연락처로 전환한다.

## 토큰과 브라우저 계약

| 항목 | 일반 사용자 | 매장 운영자 |
| --- | --- | --- |
| Access JWT namespace | `consumer` | `store-operator` |
| subject | `consumer:{id}` | `store-operator:{id}` |
| Access JWT 수명 | 15분 | 15분 |
| Refresh JWT 수명 | 14일 | 14일 |
| Refresh 쿠키 | `MIRIYUM_CONSUMER_REFRESH` | `MIRIYUM_STORE_OPERATOR_REFRESH` |
| Refresh 쿠키 Path | `/api/v1/consumers/auth` | `/api/v1/store-operators/auth` |
| CSRF 쿠키 | `MIRIYUM_CONSUMER_XSRF_TOKEN` | `MIRIYUM_STORE_OPERATOR_XSRF_TOKEN` |
| CSRF 쿠키 Path | `/api/v1/consumers/auth` | `/api/v1/store-operators/auth` |
| CSRF 헤더 | `X-CSRF-TOKEN` | `X-CSRF-TOKEN` |

- Access JWT는 로그인·재발급 성공 응답의 `data.accessToken`으로 전달하며 프론트엔드는 계정 shell 메모리에만 보관한다.
- Refresh JWT는 `HttpOnly`, `Secure`, `SameSite=Lax`, host-only 쿠키로만 전달하고 JSON 응답·Web Storage·로그에 넣지 않는다.
- CSRF 쿠키는 프론트엔드가 헤더로 되돌려 보내야 하므로 Refresh 쿠키와 달리 JavaScript 읽기를 허용한다. 인증 토큰으로 사용하거나 서버 로그에 기록하지 않는다.
- 재발급은 namespace별 Refresh 쿠키, `POST` JSON, 같은 Origin을 요구한다. `Origin`이 없으면 `Referer`를 확인하고 둘 다 없거나 허용 Origin과 다르면 실패 폐쇄한다.
- 로그아웃은 namespace별 Refresh 쿠키와 `X-CSRF-TOKEN`을 검증하고 같은 이름·Path로 쿠키를 만료시킨다.
- 1차 MVP 로그아웃은 서버에 저장된 Refresh 상태를 폐기했다고 응답하지 않는다.
- 일반 보호 API는 Refresh 쿠키를 Access JWT 대체 수단으로 사용하지 않는다.

### CSRF 토큰 준비

각 shell은 `GET .../csrf-tokens/current`로 namespace별 CSRF 토큰을 준비한다. 응답 `data.token`과 같은 값이 해당 namespace의 CSRF 쿠키에 설정된다. CSRF 토큰은 인증 자격이나 비밀 값이 아니며 Refresh JWT와 분리한다.

## 멱등성과 요청 제한

- 본인 정보 `PATCH`는 C-006의 `Idempotency-Key`를 요구한다.
- 가입·로그인·재발급·로그아웃은 인증 전 또는 무저장 토큰 경계이므로 C-006의 “인증 주체 namespace + 주체 ID” 업무 멱등 레코드를 적용하지 않는다.
- 가입 중복은 계정 유형별 정규화 이메일·휴대전화 유일 제약과 확인 참조의 일회성 소비로 막는다.
- 로그인·재발급·CSRF 준비는 계정·IP 등 활성 보안 정책 기준으로 요청 제한할 수 있으며 초과 시 `AUTH` 오류가 아니라 공통 `COMMON_010`을 사용한다.
- 가입·로그인·재발급·CSRF 준비 4개 요청은 IP 기준 고정 윈도우로 요청을 제한한다. 로그아웃과 마이페이지 등 나머지 요청은 대상이 아니다. 요청 성격별로 한도가 다르다(2026-07-30 팀 결정, `miriyum.rate-limit.*` 프로퍼티로 조정 가능):
  - 회원가입: IP당 10분에 5회 — `SCALE-005` "로그인·인증번호 요청" 등급을 재사용한다(대량 계정 생성 방지).
  - 로그인: IP당 10분에 5회 — `SCALE-005` "로그인·인증번호 요청" 등급.
  - 토큰 재발급: IP당 1분에 30회 — `SCALE-005`에 없던 신규 수치다. 정상 브라우저가 자동으로 자주 호출하므로 10분당 5회는 너무 엄격해 반복 남용만 막을 수 있는 별도 값을 정했다.
  - CSRF 토큰 준비: IP당 1분에 60회 — `SCALE-005` "공개 조회" 등급을 재사용한다(비용이 낮고 페이지 진입·새로고침 시 호출될 수 있음).

  카운터는 `rate_limit_windows` MySQL 테이블에 원자적 upsert로 저장해(이슈 #63) 여러 인스턴스가 같은 카운터를 공유하며, `SCALE-005`의 "로컬 메모리만으로 최종 판정하지 않는다" 요구를 만족한다. 검증은 Testcontainers MySQL로 동시 요청 시나리오를 재현해 확인했다(H2는 이 원자적 upsert의 MySQL 전용 문법을 지원하지 않아 증거로 쓰지 않는다).

  남은 알려진 한계 2가지: (1) 클라이언트 IP를 `getRemoteAddr()`로만 판단해 리버스 프록시·로드밸런서 뒤에서는 프록시 IP로 뭉뚱그려질 수 있다(배포 구조가 정해지면 `X-Forwarded-For` 등을 반영해야 한다), (2) 만료된 윈도우 행을 정리하지 않아 서로 다른 키 수만큼 테이블이 계속 늘어난다(개발 단계에서는 무시할 만한 수준이며, 필요해지면 배치로 정리한다).
- 로그인과 재발급의 성공 응답 유실 뒤 같은 요청을 다시 보내면 새 JWT가 발급될 수 있다. 1차 MVP는 중앙 토큰 상태가 없으므로 이전 JWT를 폐기했다고 표시하지 않는다.

인증 endpoint에 억지로 업무 멱등 저장소를 적용하는 대안은 인증 전 주체 식별과 무저장 JWT 정책을 왜곡하므로 채택하지 않았다.

## 로그인 실패 시 계정 단위 지연

위 IP 기준 요청 제한과 **별개로 중첩 적용**하는 계정 단위 지연이다. IP 제한은 한 출발지의 요청량을 막고, 이 지연은 한 계정을 겨냥한 비밀번호 추측을 늦춘다. 기준은 `AUTH-006` 확정 정책을 그대로 따른다.

- 같은 계정에서 이메일·비밀번호 로그인에 연속 5회 실패하면 1분 지연한다. 지연이 끝난 뒤 다시 실패하면 5분, 그다음 실패하면 15분으로 단계를 올린다.
- 15분 단계에 도달한 뒤의 추가 실패에는 15분 지연을 반복 적용하며 영구 잠금으로 전환하지 않는다. 공격자가 고의 실패로 남의 계정을 영구히 막을 수 없어야 하기 때문이다.
- 단계는 **지연이 끝난 뒤의 실패에만** 올린다. 아직 지연이 유효한 동안 도착한 실패는 실패 횟수와 단계를 바꾸지 않는다. 동시 요청이 지연 여부 확인을 함께 통과한 뒤 순서대로 기록되면, 이 규칙이 없을 때 한 번의 지연 구간에서 1분 → 5분 → 15분으로 연속해 뛸 수 있다.
- 로그인에 성공하면 해당 계정의 연속 실패 횟수와 지연 단계를 초기화한다.
- 지연 중에는 비밀번호를 검사하지 않고 거절하되, 응답은 평소 실패와 같은 `AUTH_005`다. 실패 횟수·지연 단계·다음 시도 가능 시각은 물론 계정 존재 여부도 응답으로 구분할 수 없어야 한다. 지연 여부를 알려주는 별도 오류 코드나 `Retry-After` 헤더를 쓰지 않는 이유가 이것이다.
- 지연 대상은 이메일·비밀번호 로그인뿐이다. 비밀번호 재설정·계정 복구는 `AUTH-006`에 따라 지연 중에도 허용한다(1차 MVP 범위 밖이라 아직 API가 없다).

연속 실패 횟수·지연 단계·다음 시도 가능 시각은 `login_failure_delays` MySQL 테이블에 계정 유형(namespace)과 계정 ID를 키로 저장한다. 여러 인증 인스턴스가 동시에 실패를 기록해도 5회 기준과 단계가 우회되지 않아야 하므로(`AUTH-006`의 원자적 갱신 요구), 행을 배타 잠금으로 잡은 뒤 갱신한다. 잠금은 `INSERT ... ON DUPLICATE KEY UPDATE`로 잡는다. `INSERT IGNORE` 뒤 `SELECT ... FOR UPDATE`로 잡으면 이미 있는 행에서 공유 잠금이 배타 잠금으로 승격되며 같은 계정 동시 실패 시 교착이 발생한다.

실패 기록은 자격 증명 오류를 던지기 전에 커밋해야 하므로 로그인 흐름과 분리된 트랜잭션에서 처리한다. 이때 로그인 처리 자체에는 바깥 트랜잭션을 두지 않는다. 두면 요청 하나가 커넥션을 두 개 잡아 동시 로그인 실패가 몰릴 때 커넥션 풀이 고갈된다.

지연 판정과 실패 기록은 **비밀번호 비교 앞에서 한 번에** 처리한다. 판정만 먼저 하고 기록을 비교 뒤로 미루면, 동시 요청이 모두 "지연 아님"을 보고 통과한 뒤 비교까지 마쳐 지연이 걸린 뒤에도 추측이 계속된다. 그래서 판정을 통과한 시도는 그 자리에서 실패로 먼저 기록해 슬롯을 예약하고, 비밀번호가 맞은 경우에만 그 기록을 되돌린다.

반대로 **비밀번호 해시 비교는 트랜잭션 밖에서** 수행한다. 해시 계산을 트랜잭션 안에서 하면 계산이 끝날 때까지 DB 커넥션과 행 잠금을 함께 쥐게 되고, 서로 다른 계정을 동시에 시도하면 각 요청이 다른 행을 잠근 채 나란히 계산에 들어가 커넥션 풀 전체를 점유한다. 이 경우 인증과 무관한 DB 요청까지 지연되므로, 계정 단위 진입 제어(짧은 DB 연산)와 해시 계산(CPU 연산)을 분리한다.

알려진 한계: 계정이 없는 이메일로는 지연 기록을 만들지 않는다. 존재하지 않는 계정까지 기록하면 표가 공격자 입력만큼 늘어나기 때문이다. 응답은 계정 존재 여부와 무관하게 동일하지만, 처리 시간 차이로 계정 존재를 추정할 여지는 남는다. `AUTH-006`이 기기 지문·유료 봇 방어를 범위에서 제외했으므로 1차 MVP는 이 한계를 수용한다.

## 본인 정보

- 일반 사용자는 이메일, 휴대전화, 공개 닉네임과 계정 상태를 조회한다.
- 1차 MVP의 일반 사용자 수정은 닉네임만 지원한다. 닉네임은 NFC 정규화 후 2~20자, 허용 문자·예약어·7일 변경 제한을 적용한다.
- 매장 운영자는 이메일, 휴대전화, 표시 이름과 계정 상태를 조회하고 표시 이름만 수정한다.
- 이메일·비밀번호 변경과 이미 등록된 휴대전화의 교체는 이번 팀 분담의 명시적인 1차 API에 포함하지 않는다. 다만 기존 `phone=null` 일반 사용자는 `/api/v1/consumers/me/contact`, 매장 운영자는 `/api/v1/store-operators/me/contact`에서 각각 최초 1회 등록을 별도 목적 API로 제공하며, 범용 PATCH로 임의 변경을 열지 않는다.
- 프로필 응답의 accountId는 문자열이며 다른 계정 유형의 ID로 변환하지 않는다.

## 마이페이지 예약 내역

- `GET /api/v1/consumers/me/reservations` 경로와 페이지 응답은 `reservation.controller.consumer`가 관리한다.
- `auth-account`는 인증 principal과 계정 상태를 제공하며 예약 내역 HTTP DTO나 조회 흐름을 소유하지 않는다.
- 예약 도메인은 상태·날짜 필터, 정렬, 예약 스냅샷 DTO와 개인 자원 404 규칙을 소유한다.
- 다른 사용자의 예약이나 매장 전체 예약을 이 경로로 조회할 수 없다.
- 결과가 없으면 `200 OK`, `items: []`와 페이지 메타데이터를 반환한다.
- `status` 필터는 1차 MVP의 영속·공개 상태인 `CONFIRMED`, `CANCELLED`, `FULFILLED`만 공개한다.
- 결제·환불·노쇼·체크인 필드는 포함하지 않는다.

## 트랜잭션과 동시성

- 일반 사용자 가입은 정규화 연락처·만 14세 이상 자기 확인값·계정 생성·무작위 알림 대상 참조 생성을 하나의 트랜잭션에서 확정한다. 매장 운영자 가입은 정규화 연락처와 계정 생성만 하나의 트랜잭션에서 확정하며, 예약용 알림 대상 참조는 생성하지 않는다. 사업자등록증·입점 승인 상태는 별도 Store 흐름에서 확정한다.
- 같은 정규화 식별자로 동시에 가입하거나 기존 일반 사용자·매장 운영자가 연락처를 동시에 최초 등록해도 DB 유일 제약과 조건부 갱신으로 계정 유형별 하나의 값만 확정한다.
- 본인 정보 수정은 현재 계정 상태와 프로필 버전을 조건부로 확인한다.
- 마이페이지 조회는 예약 상태나 거래를 변경하지 않는다.
- 인증 도메인은 예약 entity·repository를 직접 조회하지 않는다.

## Migration·호환성 요구

- 공통 `users` 테이블이나 `role` discriminator를 만들지 않는다.
- 계정 유형별 같은 숫자 ID를 하나의 전역 ID로 해석하지 않는다.
- Reservation의 기존 연락처 스냅샷 컬럼은 재사용하고 Reservation migration(DB 스키마 변경 파일)은 추가하지 않는다. 일반 사용자 계정에는 무작위 알림 대상 참조와 유일성 제약을 추가하는 Auth 소유 migration을 사용한다.
- 2차·고도화에서 Valkey를 도입해도 공개 계정 ID, 인증 namespace와 경로는 유지한다.
- Refresh Token 회전을 추가할 때 쿠키 이름·Path를 유지할 수 있으나 서버 저장·폐기 의미 변경은 별도 계약 변경으로 기록한다.

## 인수 조건

- 일반 사용자와 매장 운영자 가입·로그인 경로, 테이블, subject와 Refresh 쿠키가 분리된다.
- 요청 본문의 역할 값으로 다른 계정 유형을 생성하거나 로그인할 수 없다.
- 일반 사용자는 정규화된 신뢰 연락처와 만 14세 이상 자기 확인값 없이 활성 계정이 생성되지 않는다. 매장 운영자는 정규화된 MVP 신뢰 연락처 없이 활성 계정이 생성되지 않으며, 사업자등록증·입점 승인 조건은 별도 Store 정책을 따른다.
- 로그인·재발급 응답 본문에 Refresh JWT가 없다.
- Access JWT는 응답 본문과 Bearer 헤더, Refresh JWT는 namespace별 쿠키에만 존재한다.
- 다른 namespace 쿠키·JWT로 갱신하거나 보호 API를 호출하면 `401`이다.
- 로그아웃의 CSRF 검증 실패와 재발급의 교차 Origin 요청은 `403`이다.
- 일반 사용자 닉네임 수정과 매장 운영자 표시 이름 수정이 상대 계정 테이블을 변경하지 않는다.
- 마이페이지 예약 내역이 예약 도메인의 공개 조회 계약을 사용하고 빈 결과를 200으로 반환한다.
- 1차 MVP OpenAPI와 코드에는 플랫폼 운영자·결제·노쇼 API가 없고, 카카오 로그인과 Valkey Refresh Token은 고도화 분기에서만 추가한다.
