# 기능 명세: 이력 기반 결정적 매장 추천

> 문서 상태: Human 설계 승인
> 적용 단계: 2차 MVP
> 도메인 소유자: 2번 팀원 — 매장·검색·추천
> 협업 계약: 3번 팀원 — 예약 이력, 4번 팀원 — MenuHold 스냅샷
> 내부 개인화 규칙 버전: `history-v1`
> 공개 검색 랭킹 버전: `food-evidence-v1+history-v1`
> 최종 승인일: 2026-08-06

## 사용자 관점의 기능 동작

통합 검색 결과는 사용자가 현재 입력한 음식 근거와 검색 의도를 가장 먼저 반영한다. 로그인 사용자의 유효한 과거 이용 이력이 있으면 현재 요청의 필수 조건을 모두 통과하고 구조화 음식 관련도와 기존 관련도 tier가 같은 후보 그룹 안에서만 익숙한 매장과 메뉴 취향을 가산한다. 개인 이력은 더 낮은 음식 관련도 그룹을 더 높은 그룹 위로 올릴 수 없다.

- 현재 검색 의도 점수는 최대 70점, 개인 이력 점수는 최대 30점이다.
- 광고비, 광고 계약, 구독 상태와 비공개 결제 규모는 후보·점수·동점 규칙의 입력이 아니다.
- 이력이 없거나 안전하게 읽을 수 없으면 추가 개인정보를 요구하지 않고 개인 이력 점수 0의 결과를 반환한다.
- 추천 이유는 실제로 점수에 기여한 요인 중 하나만 템플릿으로 설명하고 내부 점수와 이용 횟수는 노출하지 않는다.

## 권한

- 공개 검색 후보 생성과 비개인화 정렬은 비회원도 사용할 수 있다.
- 개인 이력 가산은 인증된 소비자가 자기 Reservation 공개 이력 계약을 조회할 수 있을 때만 적용한다.
- 추천 도메인은 Reservation 또는 MenuHold의 Entity·Repository를 직접 참조하지 않고 각 도메인의 공개 Service·DTO만 사용한다.
- 운영자, 광고주 또는 구독 상태가 일반 추천 순서를 바꾸는 관리 권한은 제공하지 않는다.

## 정상 흐름

1. 통합 검색이 같은 요청의 정규화 조건과 visible·non-retired·current published 메뉴 한 행의 음식 근거, 공개·최신 상태를 통과한 후보를 만든다.
2. 후보는 `구조화 음식 관련도 → 기존 관련도 tier`의 정적 그룹을 가진다.
3. 랭커는 전체 bounded 후보 집합, 요청에서 고정한 `asOf`, 후보 스냅샷과 `history-v1`을 입력으로 요청당 한 번 호출된다.
4. 현재 검색 의도를 최대 70점으로 계산한다.
5. 인증된 소비자이면 최근 `FULFILLED` 예약 최대 20건을 읽고, 그중 최근 5건에 연결된 MenuHold 스냅샷만 조회해 개인 이력을 최대 30점으로 계산한다.
6. `history-v1` 결과에 안정 정렬을 적용해 정적 그룹 순서를 먼저 복원하고 같은 그룹 안에서만 총점과 기존 동점 순서를 유지한다.
7. 실제 최고 기여 요인과 고정 우선순위로 템플릿 이유를 선택한다.
8. 표시 직전 최신 영업·판매·예약 가용성 검증은 기존 통합 검색 계약을 그대로 적용한다.

## 점수 계약

### 현재 검색 의도 — 최대 70점

| 요인 | 점수 | 상한 |
| --- | ---: | ---: |
| 키워드 관련도 tier | `0..4 × 8` | 32 |
| 요청한 매장 주 카테고리 일치 | +12 | 12 |
| 요청한 메뉴 주 카테고리 일치 | +10 | 10 |
| 메뉴 보조 카테고리 일치 | 각 +4 | 8 |
| 요청 태그 일치 | 각 +2 | 6 |
| 예약 가용성 | `AVAILABLE +2`, `NOT_REQUESTED +1`, 그 외 0 | 2 |

관련도 tier의 숫자 방향은 검색 후보 계약의 관련도 순서와 일치해야 한다. 구현은 가장 관련도 높은 후보가 32점, 구조화 조건만 일치한 후보가 0점이 되도록 명시적으로 변환하며 enum ordinal에 의존하지 않는다.

이 70점 의도 점수와 30점 개인 이력 점수는 같은 정적 음식 그룹 안의 순서만 정한다. 그룹 간 순서는 `구조화 음식 관련도 → 기존 관련도 tier`가 항상 우선한다.

### 개인 이력 — 최대 30점

| 요인 | `asOf` 기준 기간별 점수 | 상한 |
| --- | --- | ---: |
| 동일 매장의 `FULFILLED` 예약 | 30일 이내 +10, 90일 이내 +6, 180일 이내 +3 | 18 |
| 위 유효 예약에 연결된 동일 메뉴 MenuHold | 30일 이내 +6, 90일 이내 +4, 180일 이내 +2 | 12 |

- 기간 구간은 서로 중복 가산하지 않는다. 한 이력 사건에는 가장 가까운 하나의 기간 점수만 적용한다.
- 180일을 초과한 이력은 0점이다.
- 예약 이력은 `startAt`을 사건 시각으로 삼아 최신 순으로 최대 20건, MenuHold 스냅샷 조회는 그중 최신 5건으로 제한한다. 같은 예약 스냅샷에 같은 `menuId`가 중복되어도 해당 예약에서는 한 번만 가산한다.
- `CANCELLED`, 실패, 노쇼, 미래 `CONFIRMED`, 단순 조회는 0점이며 개인 취향 신호로 변환하지 않는다.
- 동일 메뉴는 MenuHold 공개 스냅샷의 `menuId`가 현재 후보의 게시·공개·판매 가능한 메뉴 ID와 같은 경우에만 인정한다. 과거 이름 문자열만으로 동일 메뉴를 추측하지 않는다.

## 동점·설명·결정성

동점은 다음 순서로만 해소한다.

1. 총점 내림차순
2. 요청한 매장 주 카테고리 일치 후보 우선
3. 메뉴 보조 카테고리 일치 수 내림차순
4. 가용성 우선순위 `AVAILABLE → NOT_REQUESTED → UNAVAILABLE`
5. 허용된 저장 좌표 기준 거리값이 입력에 있을 때 가까운 순
6. `storeId` 오름차순

사용자 현재 위치는 요청·저장·사용하지 않는다. #113 입력에 허용된 거리값이 없으면 5번을 건너뛴다.

추천 이유는 후보에 실제로 양의 점수를 기여한 요인 중 점수가 가장 큰 하나를 사용한다. 동률 이유는 `현재 키워드 관련도 → 명시 카테고리 → 명시 태그 → 예약 가용성 → 동일 매장 이용 → 동일 메뉴 이용` 순서로 고른다. 어떤 개인 이력 요인도 기여하지 않았으면 개인화된 문구를 표시하지 않는다.

같은 후보·이력 스냅샷, `asOf`, 규칙 버전은 같은 점수·순서·이유를 만든다. 시스템 현재 시각을 계산 중간에 다시 읽거나 DB 기본 정렬, 컬렉션 순회 순서, enum ordinal에 의존하지 않는다.

## 오류 흐름

- Reservation 이력이나 MenuHold 공개 계약이 실패하거나 응답 소유권·식별자가 맞지 않으면 그 요청의 개인 이력을 버리고 0점 콜드스타트로 축소한다. 오래된 개인화 결과를 대신 반환하지 않는다.
- 최신 Store 상태나 필수 후보 데이터가 누락되면 해당 후보를 실패 폐쇄한다.
- 최신 예약 가용성을 확인할 수 없고 요청이 `availableOnly=true`이면 가용을 추측하지 않고 기존 통합 검색 계약대로 후보를 제외한다.
- 점수 상한 위반, 알려지지 않은 규칙 버전 또는 비결정적 입력은 성공 결과로 숨기지 않고 구현 오류로 탐지한다.

## API·데이터 계약

- 이 기능은 #112의 통합 검색 공개 경로와 정규화 조건·후보 계약 위에 재정렬 계층으로 연결한다. 별도 AI 검색 API를 만들지 않는다.
- Reservation 입력은 소비자 자신의 공개 예약 이력 DTO만 사용하며 상태·서비스 시각·매장 ID를 읽는다.
- MenuHold 입력은 유효 예약 ID에 대한 공개 스냅샷 DTO만 사용하며 메뉴 ID만 취향 매칭에 사용한다.
- `history-v1` 입력은 후보 ID, 현재 명시 조건의 일치 값, 최신 가용성, 선택적 허용 거리, 이력 사건, `asOf`와 규칙 버전을 불변 값으로 전달한다. 구조화 음식 그룹은 공통 랭커의 입력·점수 상한을 바꾸지 않고 검색 서비스가 랭커 결과에 적용하는 상위 정렬 계약이다.
- `recommendation,desc` 응답은 `rankingRuleVersion=food-evidence-v1+history-v1`과 각 항목의 실제 최고 양의 기여 요인 `recommendationReason(code, message)`을 반환한다. 다른 정렬은 두 추천 필드를 `null`로 반환한다. 내부 음식 점수, 개인화 점수, 가중치, 예약·홀드 횟수와 원본 이력은 공개하지 않는다.

## Migration·호환성 요구

- 새 영속 테이블이나 사용자 프로필을 만들지 않는다. Reservation과 MenuHold 원본을 추천 도메인에 복제하지 않는다.
- 1차 MVP 검색과 `searchInput`이 없는 기존 페이지 계약은 변경하지 않는다.
- 규칙의 요인·가중치·동점 또는 이유 우선순위가 바뀌면 기존 버전을 조용히 덮어쓰지 않고 새 규칙 버전과 고정 평가셋 승인을 만든다.
- 혼합 배포 동안 요청 하나에는 하나의 규칙 버전만 적용한다.

## 고정 평가셋

- 현재 의도 점수 차이가 개인 이력 최대 30점을 초과하는 신규 매장이 과거 방문 매장보다 앞서는 사례
- 검색 의도 점수가 같은 두 후보에서 유효한 동일 매장·메뉴 이력이 순서를 정하는 사례
- 30일·90일·180일 경계와 180일 초과 이력이 정확히 한 구간에만 포함되는 사례
- 취소·미래 확정·노쇼·단순 조회가 순위와 이유에 영향을 주지 않는 사례
- 이력 없음과 이력 계약 실패가 같은 비개인화 순서·이유를 만드는 사례
- 광고비·구독·결제 규모 값을 바꾸거나 주입해도 순위가 변하지 않는 사례
- 모든 점수·동점 요인이 같은 후보가 `storeId` 오름차순으로 고정되는 사례
- 실제 최고 기여 요인과 이유 코드가 일치하고 내부 수치를 노출하지 않는 사례

## 인수 조건

- 현재 의도 점수는 최대 70점, 개인 이력 점수는 최대 30점을 넘지 않는다.
- 같은 입력 스냅샷·`asOf`·`food-evidence-v1+history-v1`은 같은 순서와 이유를 만든다.
- 개인 이력 점수가 높은 낮은 음식 그룹이 더 높은 음식 그룹을 추월하지 않는다.
- 광고비·광고 계약·구독 상태·비공개 결제 규모가 일반 추천 입력에 존재하지 않는다.
- 이력이 없거나 안전하게 읽지 못한 사용자는 추가 개인정보 없이 비개인화 결과를 받는다.
- 표시된 추천 이유가 해당 결과의 실제 양의 기여 요인과 일치한다.
- 최신 가용성 검증과 원 도메인의 최종 거래 검증을 우회하지 않는다.
