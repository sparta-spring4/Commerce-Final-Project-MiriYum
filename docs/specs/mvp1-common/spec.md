2026-07-28 팀 승인으로 `1. 팀 결정 목록`을 마감한다.

- 공통 성공·예외·검증 응답, 페이지네이션, 날짜·시간·타임존과 멱등성의 구체 계약은 `4. 공통 계약과 API 명세`에서 확정한다.
- 코드·GitHub·AI 규칙과 문서 담당자 표시는 `5. 코드·GitHub·AI 규칙`에서 저장소 활성 정책을 기준으로 확정한다.
- 통합 `USER`를 사용한 기존 ERD·API 초안은 삭제하지 않고 충돌·구버전으로 식별한 뒤 3·4단계에서 승인된 분리 구조로 정비한다.

## D-001 1차 MVP와 후속 단계의 기능 경계

### 1차 MVP

- 예약은 결제·예약금·보증금·환불 없이 생성·변경·취소한다.
- 예약과 선택 메뉴 홀드는 하나의 MySQL 트랜잭션에서 전부 확정하거나 전부 반환한다.
- 메뉴를 건너뛴 예약은 예약 인원·팀 수 자원만 확정한다.
- 결제 상태, `PAY-*` 정책 참조, 체크인·노쇼 상태를 1차 MVP 예약·메뉴 홀드 상태 전이와 API 계약에 넣지 않는다.

### 후속 단계

- `2차 MVP`: 지도 고도화, 개인화 추천, 품절 대체 추천
- `고도화`: 결제·예약금·보증금·환불, 체크인·노쇼

후속 단계의 기존 상세 정책은 삭제하지 않는다. 각 기능의 단계 진입 조건이 승인될 때까지 `1차 MVP`의 상태, API, 데이터 모델과 인수 조건으로 활성화하지 않는다.

### 문서 적용 규칙

- 예약·메뉴 홀드 정책의 본문에서 `1차 MVP` 정상 흐름과 `고도화 전용` 연결을 별도 하위 절로 구분한다.
- 결제 성공·실패·결과 불명확·승인 취소·환불 흐름은 `고도화 전용`으로만 표기한다.
- 1차 MVP의 원자성·동시성·실패 복구 검증은 외부 결제 없이 예약 자원과 메뉴 수량 원장만 대상으로 한다.

### 인수 조건

- 1차 MVP 예약·메뉴 홀드 상태 전이표와 OpenAPI에 결제 상태, `PAY-*` 참조, 체크인·노쇼 상태가 없다.
- 후속 단계 정책 문서는 삭제되지 않고 단계 표기와 활성화 조건을 유지한다.
- 예약과 선택 메뉴 홀드의 일부 성공 상태가 남지 않는다.

## D-002 JWT 유효기간

### 확정값

- Access JWT 유효기간은 발급 시각부터 1시간이다.
- Refresh JWT 유효기간은 발급 시각부터 14일이다.
- 일반 사용자·매장 운영자·플랫폼 운영자의 분리된 토큰 namespace에 같은 유효기간을 적용한다.
- 로컬·개발·운영 런타임 프로필은 같은 유효기간을 사용한다. 만료 경계 검증을 위한 테스트 설정만 더 짧은 값을 주입할 수 있다.

### 변경하지 않는 정책

- 1차 MVP의 무저장 Access JWT·Refresh JWT 구조를 유지한다.
- 1차 MVP 로그아웃은 클라이언트가 보유 토큰을 제거하는 경계를 유지한다.
- Refresh Token 회전·폐기·재사용 탐지와 Valkey 상태 관리는 기존대로 고도화 범위에 둔다.
- 브라우저 전달·저장 방식과 CSRF 경계는 이 결정에 포함하지 않는다.

### 참고 기준

- Agora 운영·Docker 프로필의 Access Token 1시간과 Refresh Token 14일 설정을 수치 참고 기준으로 사용했다.
- Agora 로컬 프로필의 Access Token 10시간 값은 환경별 계약 불일치를 만들기 때문에 적용하지 않았다.

## D-003 브라우저 토큰 전달·저장과 CSRF 경계

### 배포와 계정 shell 전제

- `1차 MVP`는 하나의 Vite 빌드와 하나의 Spring Boot 애플리케이션을 같은 Origin에서 제공하고 API 경로는 `/api` 아래에 둔다.
- 일반 사용자·매장 운영자·플랫폼 운영자 shell은 하나의 프런트엔드 빌드 안에 둘 수 있지만 로그인 진입점, 라우트 가드, principal 해석과 토큰 namespace를 공유하지 않는다.
- 계정 유형별 Refresh Token 쿠키는 이름과 `Path`를 분리한다. 정확한 쿠키 이름과 인증 경로는 `auth-account` OpenAPI에서 함께 확정하되, 한 namespace의 쿠키가 다른 namespace의 갱신·로그아웃 경로로 전송되지 않게 한다.

### Access Token

- 로그인과 토큰 재발급 성공 응답은 Access JWT를 응답 본문으로 전달한다.
- 프런트엔드는 Access JWT를 계정 shell별 메모리에만 보관하고 `localStorage`, `sessionStorage`, IndexedDB 또는 일반 쿠키에 저장하지 않는다.
- 보호 API는 `Authorization: Bearer {accessToken}`으로 호출한다.
- 새로고침으로 메모리 상태가 사라지면 Refresh Token 쿠키를 사용하는 재발급 요청으로 인증 상태를 복구한다.

### Refresh Token

- Refresh JWT는 JavaScript에서 읽을 수 없는 `HttpOnly`, `Secure`, `SameSite=Lax` 쿠키로만 전달한다. 로그인·재발급 응답 본문에 원문을 포함하지 않는다.
- 프런트엔드는 인증 요청에서 필요한 경우 동일 Origin 자격 증명만 전송하고 Refresh Token 원문을 애플리케이션 상태나 로그로 복사하지 않는다.
- 로그아웃은 shell 메모리의 Access JWT를 제거하고 해당 namespace의 Refresh Token 쿠키를 만료시킨다. `1차 MVP`에는 서버 저장 상태가 없으므로 복제된 JWT의 중앙 폐기를 의미하지 않는다.

### CSRF와 요청 경계

- Access JWT만 사용하는 보호 API는 브라우저가 자동 첨부하는 인증정보에 의존하지 않으므로 Bearer 토큰 검증 경계를 사용한다.
- Refresh Token 쿠키가 관여하는 토큰 재발급은 `POST`와 JSON 요청만 허용하고 요청 `Origin`을 우선, 없으면 `Referer`를 검증하여 서비스 Origin과 다르면 거부한다. 브라우저 요청에 두 헤더가 모두 없으면 실패 폐쇄한다.
- Refresh Token 쿠키를 제거하는 로그아웃 요청에는 Spring Security CSRF 보호를 적용한다. CSRF 토큰은 인증 토큰과 분리하고 요청 헤더로 검증한다.
- 교차 Origin 자격 증명 요청은 허용하지 않는다. 배포 구조를 분리해야 하는 근거가 생기면 CORS, 쿠키와 CSRF 계약을 함께 재검토한다.

### 단계 경계와 인수 조건

- Access JWT는 1시간, Refresh JWT는 14일의 기존 D-002 수명을 유지한다.
- `1차 MVP`의 Access·Refresh JWT는 서버 정상 목록·폐기 목록 없이 검증한다. Refresh Token 회전·폐기·재사용 탐지와 Valkey 상태 관리는 기존대로 `고도화` 범위다.
- 로그인·재발급 응답과 브라우저 저장소에 Refresh Token 원문이 노출되지 않는다.
- 페이지 새로고침 뒤 유효한 Refresh Token 쿠키로 같은 계정 shell의 Access JWT만 복구된다.
- 다른 계정 namespace의 쿠키, 교차 Origin 재발급, 허용되지 않은 요청 형식과 유효한 CSRF 토큰이 없는 로그아웃은 거부된다.
- 로그아웃 뒤 해당 shell의 Access JWT 메모리와 Refresh Token 쿠키가 제거되지만, 서버가 이미 발급된 JWT를 폐기했다고 응답하거나 기록하지 않는다.

## D-004 1차 MVP 동시 로그인 정책

### 확정 사항

- `1차 MVP`에는 계정별 동시 로그인 개수 상한을 두지 않는다.
- 서버가 로그인·Refresh JWT 목록을 저장하지 않으므로 활성 로그인 목록, 로그인 개수 조회, 오래된 로그인 자동 종료와 기기별·다른 로그인 전체 종료를 제공하지 않는다.
- 같은 브라우저·계정 namespace에서는 D-003의 같은 이름·경로를 사용하는 Refresh Token 쿠키가 새 로그인·재발급 값으로 교체될 수 있지만, 이는 다른 브라우저나 복제된 토큰을 종료하는 전역 로그인 제한이 아니다.
- 과거 중앙 세션 정책의 일반 사용자 5개·매장 운영자 3개·플랫폼 운영자 1개 제한을 `1차 MVP` JWT에 변환하거나 적용하지 않는다.
- 로그인 수 상한과 상한 초과 시 종료 순서는 Valkey 로그인 상태를 도입하는 `고도화` 활성화 전에 별도 결정한다.

### 인수 조건

- 같은 계정으로 여러 브라우저에서 로그인해도 유효한 각 JWT는 서명·만료·발급자·대상·토큰 종류·계정 namespace 검증 결과에 따라 독립적으로 처리된다.
- 새 로그인 때문에 다른 브라우저의 Refresh JWT가 자동 폐기되거나 가장 오래된 로그인이 종료됐다고 응답하지 않는다.
- `1차 MVP` API와 UI에는 활성 로그인 목록, 로그인 개수, 기기별 종료 또는 전체 로그인 종료 기능이 노출되지 않는다.

## D-005 정상 비밀번호·이메일 변경 시 로그인 유지

### 확정 정책의 단계 적용

- 2026-07-21에 확정한 “정상 비밀번호·등록 이메일 변경 시 기존 로그인 유지” 정책을 변경하지 않고 `1차 MVP`의 무저장 JWT 구조에 적용한다.
- 정상 변경이 성공해도 현재 브라우저와 다른 브라우저에 이미 발급된 Access JWT·Refresh JWT를 서버에서 폐기하거나 종료됐다고 표시하지 않는다.
- 기존 JWT는 각 토큰의 서명·만료·발급자·대상·토큰 종류·계정 namespace와 현재 계정·권한 검증 경계를 통과하는 동안 사용할 수 있다.
- 비밀번호 재설정, 수동 계정 복구, 탈취 신고, 보안 잠금, 계정 정지와 권한 회수는 정상 정보 변경에 포함하지 않으며 해당 기존 정책의 단계 경계를 그대로 따른다.
- Valkey 로그인 상태를 도입하는 `고도화`에서도 정상 변경의 기본값은 다른 로그인 유지다. 사용자가 명시적으로 로그인 종료를 요청하거나 별도 보안 사건이 발생한 경우에만 해당 고도화 정책을 적용한다.

### 인수 조건

- 인증된 사용자가 정상 비밀번호 또는 등록 이메일을 변경한 뒤 현재 Access JWT로 허용된 요청을 계속할 수 있다.
- 다른 브라우저의 유효한 JWT가 정상 정보 변경만을 이유로 폐기되거나 로그아웃됐다고 응답하지 않는다.
- 정상 변경 응답은 전체 로그인 종료나 중앙 토큰 폐기가 완료됐다고 표시하지 않는다.

## D-006 Access JWT 만료 전 중앙 재검증 경계

### 기존 정책 유지

- `1차 MVP`에는 새로운 공통 `auth_time`, 최근 로그인 유효시간 또는 추가 인증 토큰을 도입하지 않는다.
- Access JWT 만료 전이라는 이유만으로 모든 중요 명령에 현재 비밀번호 확인이나 공통 추가 인증 절차를 새로 요구하지 않는다.
- 보호 명령은 기존 정책대로 현재 계정 상태·계정 유형·권한, 매장 운영자와 대상 매장의 소속, 대상 자원의 소유권과 매장 승인·운영 상태를 필요한 범위에서 MySQL로 다시 검증한다.
- 개별 활성 정책에 이미 재인증이 명시된 작업만 해당 정책의 절차를 적용한다. 플랫폼 운영자의 중요 작업 재인증은 플랫폼 운영 기능이 활성화되는 `고도화` 경계에 그대로 둔다.
- 계정 정지·권한 회수·매장 소속 해제처럼 중앙 상태가 바뀌면 서명과 만료가 유효한 Access JWT만으로 명령을 허용하지 않는다.

### 인수 조건

- 유효한 Access JWT라도 현재 계정이 정지됐거나 필요한 권한·매장 소속·자원 소유권이 없으면 보호 명령이 거부된다.
- 개별 정책 근거가 없는 요청에 최근 로그인 시각이나 새 공통 추가 인증 토큰을 요구하지 않는다.
- `1차 MVP` API에 구현하지 않는 플랫폼 운영자 추가 인증 경로를 노출하지 않는다.

## D-007 계정 유형별 물리 테이블 분리

### 기존 정책의 구현 적용

- [사용자와 권한](../../02-users-and-permissions.md)의 물리적 계정 분리 정책과 [데이터·API 계약](../../07-data-and-api-contracts.md)의 계정 물리 분리 계약을 그대로 적용한다.
- 일반 사용자, 매장 운영자와 플랫폼 운영자를 공통 `users` 테이블의 `role`·`account_type`으로 구분하지 않는다.
- 일반 사용자는 `consumer_accounts`, 매장 운영자는 `store_operator_accounts`, 플랫폼 운영자는 `platform_operator_accounts`를 사용하고 각 유형은 별도 PK·principal·토큰 namespace를 가진다.
- `1차 MVP`에는 `consumer_accounts`와 `store_operator_accounts`를 구현한다. `platform_operator_accounts`와 플랫폼 운영자 API·UI는 해당 기능이 활성화되는 `고도화`에 구현한다.
- 회원가입·로그인·재발급·로그아웃은 계정 유형별 진입 경로와 스키마를 사용하고 클라이언트의 `role`·`accountType` 입력으로 계정 유형을 선택·전환·승격하지 않는다.
- 예약·예약 결합 메뉴 홀드·사용자 픽업 예약은 `consumer_account_id`, 매장 소속은 `store_operator_account_id`를 참조하며 범용 `user_id` FK를 사용하지 않는다.

### 인수 조건

- `1차 MVP` 스키마와 JPA 모델에 공통 `users` 계정 엔티티나 계정 유형 discriminator가 없다.
- 일반 사용자 토큰으로 매장 운영자 API를 호출하거나 매장 운영자 토큰으로 일반 사용자 거래의 소유자가 될 수 없다.
- 플랫폼 운영자 기능을 추가할 때 일반 사용자·매장 운영자 테이블에 역할 열을 추가하거나 기존 PK를 바꾸지 않는다.
