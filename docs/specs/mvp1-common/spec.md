# 1차 MVP 공통 명세

> 문서 상태: 4단계 공통 계약 완료 (1~3단계 완료)
> 추적 Issue: [#25](https://github.com/sparta-spring4/Commerce-Final-Project-MiriYum/issues/25)
> 최종 변경일: 2026-07-28

이 문서는 1차 MVP 구현 전에 팀이 승인한 공통 결정을 순서대로 기록한다. 승인되지 않은 선택지는 확정 계약으로 사용하지 않는다.

## 1단계 마감

2026-07-28 팀 승인으로 `1. 팀 결정 목록`을 마감한다.

- `D-001`~`D-007`은 아래 결정 기록과 상세 절을 따른다.
- 매장 정상 입점의 자동 확인, 예약의 인원·팀 수 이중 수용량, 날짜·시간대별 메뉴 수량, 예약과 선택 메뉴 홀드의 단일 트랜잭션, 사용자 현재 위치 미사용은 최신 활성 정책에서 이미 확정된 기준을 유지한다.
- 화면 담당자와 도메인·파일·API 소유권은 `2. 도메인·담당자 소유권`에서 확정한다.
- 논리 ERD와 상태 전이는 `3. 상태 전이와 논리 ERD`에서 계정 물리 분리와 단계 경계를 반영한다.
- 공통 성공·예외·검증 응답, 페이지네이션, 날짜·시간·타임존과 멱등성의 구체 계약은 `4. 공통 계약과 API 명세`에서 확정한다.
- 코드·GitHub·AI 규칙과 문서 담당자 표시는 `5. 코드·GitHub·AI 규칙`에서 저장소 활성 정책을 기준으로 확정한다.
- 통합 `USER`를 사용한 기존 ERD·API 초안은 삭제하지 않고 충돌·구버전으로 식별한 뒤 3·4단계에서 승인된 분리 구조로 정비한다.

## D-001 1차 MVP와 후속 단계의 기능 경계

### 1차 MVP

- 예약은 결제·예약금·보증금·환불 없이 생성·변경·취소한다.
- 예약과 선택 메뉴 홀드는 하나의 MySQL 트랜잭션에서 전부 확정하거나 전부 반환한다.
- 메뉴를 건너뛴 예약은 예약 인원·팀 수 자원만 확정한다.
- 결제 상태, `PAY-*` 정책 참조, 체크인·노쇼 상태를 1차 MVP 예약·메뉴 홀드 상태 전이와 API 계약에 넣지 않는다.

### 후속 단계

- `2차 MVP`: 지도 고도화, 개인화 추천, 품절 대체 추천
- `고도화`: 결제·예약금·보증금·환불, 체크인·노쇼

후속 단계의 기존 상세 정책은 삭제하지 않는다. 각 기능의 단계 진입 조건이 승인될 때까지 `1차 MVP`의 상태, API, 데이터 모델과 인수 조건으로 활성화하지 않는다.

### 문서 적용 규칙

- 예약·메뉴 홀드 정책의 본문에서 `1차 MVP` 정상 흐름과 `고도화 전용` 연결을 별도 하위 절로 구분한다.
- 결제 성공·실패·결과 불명확·승인 취소·환불 흐름은 `고도화 전용`으로만 표기한다.
- 1차 MVP의 원자성·동시성·실패 복구 검증은 외부 결제 없이 예약 자원과 메뉴 수량 원장만 대상으로 한다.

### 인수 조건

- 1차 MVP 예약·메뉴 홀드 상태 전이표와 OpenAPI에 결제 상태, `PAY-*` 참조, 체크인·노쇼 상태가 없다.
- 후속 단계 정책 문서는 삭제되지 않고 단계 표기와 활성화 조건을 유지한다.
- 예약과 선택 메뉴 홀드의 일부 성공 상태가 남지 않는다.

## D-002 JWT 유효기간

### 확정값

- Access JWT 유효기간은 발급 시각부터 1시간이다.
- Refresh JWT 유효기간은 발급 시각부터 14일이다.
- 1차 MVP의 일반 사용자·매장 운영자 토큰 namespace에 같은 유효기간을 적용한다. 플랫폼 운영자 인증은 고도화 구현 시 같은 기본 수명을 적용한다.
- 로컬·개발·운영 런타임 프로필은 같은 유효기간을 사용한다. 만료 경계 검증을 위한 테스트 설정만 더 짧은 값을 주입할 수 있다.

### 변경하지 않는 정책

- 1차 MVP의 무저장 Access JWT·Refresh JWT 구조를 유지한다.
- 1차 MVP 로그아웃은 클라이언트가 보유 토큰을 제거하는 경계를 유지한다.
- Refresh Token 회전·폐기·재사용 탐지와 Valkey 상태 관리는 기존대로 고도화 범위에 둔다.
- 브라우저 전달·저장 방식과 CSRF 경계는 이 결정에 포함하지 않는다.

### 참고 기준

- Agora 운영·Docker 프로필의 Access Token 1시간과 Refresh Token 14일 설정을 수치 참고 기준으로 사용했다.
- Agora 로컬 프로필의 Access Token 10시간 값은 환경별 계약 불일치를 만들기 때문에 적용하지 않았다.

## D-003 브라우저 토큰 전달·저장과 CSRF 경계

### 배포와 계정 shell 전제

- `1차 MVP`는 하나의 Vite 빌드와 하나의 Spring Boot 애플리케이션을 같은 Origin에서 제공하고 API 경로는 `/api` 아래에 둔다.
- 일반 사용자·매장 운영자·플랫폼 운영자 shell은 하나의 프런트엔드 빌드 안에 둘 수 있지만 로그인 진입점, 라우트 가드, principal 해석과 토큰 namespace를 공유하지 않는다.
- 계정 유형별 Refresh Token 쿠키는 이름과 `Path`를 분리한다. 정확한 쿠키 이름과 인증 경로는 `auth-account` OpenAPI에서 함께 확정하되, 한 namespace의 쿠키가 다른 namespace의 갱신·로그아웃 경로로 전송되지 않게 한다.

### Access Token

- 로그인과 토큰 재발급 성공 응답은 Access JWT를 응답 본문으로 전달한다.
- 프런트엔드는 Access JWT를 계정 shell별 메모리에만 보관하고 `localStorage`, `sessionStorage`, IndexedDB 또는 일반 쿠키에 저장하지 않는다.
- 보호 API는 `Authorization: Bearer {accessToken}`으로 호출한다.
- 새로고침으로 메모리 상태가 사라지면 Refresh Token 쿠키를 사용하는 재발급 요청으로 인증 상태를 복구한다.

### Refresh Token

- Refresh JWT는 JavaScript에서 읽을 수 없는 `HttpOnly`, `Secure`, `SameSite=Lax` 쿠키로만 전달한다. 로그인·재발급 응답 본문에 원문을 포함하지 않는다.
- 프런트엔드는 인증 요청에서 필요한 경우 동일 Origin 자격 증명만 전송하고 Refresh Token 원문을 애플리케이션 상태나 로그로 복사하지 않는다.
- 로그아웃은 shell 메모리의 Access JWT를 제거하고 해당 namespace의 Refresh Token 쿠키를 만료시킨다. `1차 MVP`에는 서버 저장 상태가 없으므로 복제된 JWT의 중앙 폐기를 의미하지 않는다.

### CSRF와 요청 경계

- Access JWT만 사용하는 보호 API는 브라우저가 자동 첨부하는 인증정보에 의존하지 않으므로 Bearer 토큰 검증 경계를 사용한다.
- Refresh Token 쿠키가 관여하는 토큰 재발급은 `POST`와 JSON 요청만 허용하고 요청 `Origin`을 우선, 없으면 `Referer`를 검증하여 서비스 Origin과 다르면 거부한다. 브라우저 요청에 두 헤더가 모두 없으면 실패 폐쇄한다.
- Refresh Token 쿠키를 제거하는 로그아웃 요청에는 Spring Security CSRF 보호를 적용한다. CSRF 토큰은 인증 토큰과 분리하고 요청 헤더로 검증한다.
- 교차 Origin 자격 증명 요청은 허용하지 않는다. 배포 구조를 분리해야 하는 근거가 생기면 CORS, 쿠키와 CSRF 계약을 함께 재검토한다.

### 단계 경계와 인수 조건

- Access JWT는 1시간, Refresh JWT는 14일의 기존 D-002 수명을 유지한다.
- `1차 MVP`의 Access·Refresh JWT는 서버 정상 목록·폐기 목록 없이 검증한다. Refresh Token 회전·폐기·재사용 탐지와 Valkey 상태 관리는 기존대로 `고도화` 범위다.
- 로그인·재발급 응답과 브라우저 저장소에 Refresh Token 원문이 노출되지 않는다.
- 페이지 새로고침 뒤 유효한 Refresh Token 쿠키로 같은 계정 shell의 Access JWT만 복구된다.
- 다른 계정 namespace의 쿠키, 교차 Origin 재발급, 허용되지 않은 요청 형식과 유효한 CSRF 토큰이 없는 로그아웃은 거부된다.
- 로그아웃 뒤 해당 shell의 Access JWT 메모리와 Refresh Token 쿠키가 제거되지만, 서버가 이미 발급된 JWT를 폐기했다고 응답하거나 기록하지 않는다.

## D-004 1차 MVP 동시 로그인 정책

### 확정 사항

- `1차 MVP`에는 계정별 동시 로그인 개수 상한을 두지 않는다.
- 서버가 로그인·Refresh JWT 목록을 저장하지 않으므로 활성 로그인 목록, 로그인 개수 조회, 오래된 로그인 자동 종료와 기기별·다른 로그인 전체 종료를 제공하지 않는다.
- 같은 브라우저·계정 namespace에서는 D-003의 같은 이름·경로를 사용하는 Refresh Token 쿠키가 새 로그인·재발급 값으로 교체될 수 있지만, 이는 다른 브라우저나 복제된 토큰을 종료하는 전역 로그인 제한이 아니다.
- 과거 중앙 세션 정책의 일반 사용자 5개·매장 운영자 3개·플랫폼 운영자 1개 제한을 `1차 MVP` JWT에 변환하거나 적용하지 않는다.
- 로그인 수 상한과 상한 초과 시 종료 순서는 Valkey 로그인 상태를 도입하는 `고도화` 활성화 전에 별도 결정한다.

### 인수 조건

- 같은 계정으로 여러 브라우저에서 로그인해도 유효한 각 JWT는 서명·만료·발급자·대상·토큰 종류·계정 namespace 검증 결과에 따라 독립적으로 처리된다.
- 새 로그인 때문에 다른 브라우저의 Refresh JWT가 자동 폐기되거나 가장 오래된 로그인이 종료됐다고 응답하지 않는다.
- `1차 MVP` API와 UI에는 활성 로그인 목록, 로그인 개수, 기기별 종료 또는 전체 로그인 종료 기능이 노출되지 않는다.

## D-005 정상 비밀번호·이메일 변경 시 로그인 유지

### 확정 정책의 단계 적용

- 2026-07-21에 확정한 “정상 비밀번호·등록 이메일 변경 시 기존 로그인 유지” 정책을 변경하지 않고 `1차 MVP`의 무저장 JWT 구조에 적용한다.
- 정상 변경이 성공해도 현재 브라우저와 다른 브라우저에 이미 발급된 Access JWT·Refresh JWT를 서버에서 폐기하거나 종료됐다고 표시하지 않는다.
- 기존 JWT는 각 토큰의 서명·만료·발급자·대상·토큰 종류·계정 namespace와 현재 계정·권한 검증 경계를 통과하는 동안 사용할 수 있다.
- 비밀번호 재설정, 수동 계정 복구, 탈취 신고, 보안 잠금, 계정 정지와 권한 회수는 정상 정보 변경에 포함하지 않으며 해당 기존 정책의 단계 경계를 그대로 따른다.
- Valkey 로그인 상태를 도입하는 `고도화`에서도 정상 변경의 기본값은 다른 로그인 유지다. 사용자가 명시적으로 로그인 종료를 요청하거나 별도 보안 사건이 발생한 경우에만 해당 고도화 정책을 적용한다.

### 인수 조건

- 인증된 사용자가 정상 비밀번호 또는 등록 이메일을 변경한 뒤 현재 Access JWT로 허용된 요청을 계속할 수 있다.
- 다른 브라우저의 유효한 JWT가 정상 정보 변경만을 이유로 폐기되거나 로그아웃됐다고 응답하지 않는다.
- 정상 변경 응답은 전체 로그인 종료나 중앙 토큰 폐기가 완료됐다고 표시하지 않는다.

## D-006 Access JWT 만료 전 중앙 재검증 경계

### 기존 정책 유지

- `1차 MVP`에는 새로운 공통 `auth_time`, 최근 로그인 유효시간 또는 추가 인증 토큰을 도입하지 않는다.
- Access JWT 만료 전이라는 이유만으로 모든 중요 명령에 현재 비밀번호 확인이나 공통 추가 인증 절차를 새로 요구하지 않는다.
- 보호 명령은 기존 정책대로 현재 계정 상태·계정 유형·권한, 매장 운영자와 대상 매장의 소속, 대상 자원의 소유권과 매장 승인·운영 상태를 필요한 범위에서 MySQL로 다시 검증한다.
- 개별 활성 정책에 이미 재인증이 명시된 작업만 해당 정책의 절차를 적용한다. 플랫폼 운영자의 중요 작업 재인증은 플랫폼 운영 기능이 활성화되는 `고도화` 경계에 그대로 둔다.
- 계정 정지·권한 회수·대상 매장의 대표 운영자 변경처럼 중앙 상태가 바뀌면 서명과 만료가 유효한 Access JWT만으로 명령을 허용하지 않는다.

### 인수 조건

- 유효한 Access JWT라도 현재 계정이 정지됐거나 필요한 권한·대상 매장의 대표 운영자 FK 일치·자원 소유권이 없으면 보호 명령이 거부된다.
- 개별 정책 근거가 없는 요청에 최근 로그인 시각이나 새 공통 추가 인증 토큰을 요구하지 않는다.
- `1차 MVP` API에 구현하지 않는 플랫폼 운영자 추가 인증 경로를 노출하지 않는다.

## D-007 계정 유형별 물리 테이블 분리

### 기존 정책의 구현 적용

- [사용자와 권한](../../02-users-and-permissions.md)의 물리적 계정 분리 정책과 [데이터·API 계약](../../07-data-and-api-contracts.md)의 계정 물리 분리 계약을 그대로 적용한다.
- 일반 사용자, 매장 운영자와 플랫폼 운영자를 공통 `users` 테이블의 `role`·`account_type`으로 구분하지 않는다.
- 일반 사용자는 `consumer_accounts`, 매장 운영자는 `store_operator_accounts`, 플랫폼 운영자는 `platform_operator_accounts`를 사용하고 각 유형은 별도 PK·principal·토큰 namespace를 가진다.
- `1차 MVP`에는 `consumer_accounts`와 `store_operator_accounts`를 구현한다. `platform_operator_accounts`와 플랫폼 운영자 API·UI는 해당 기능이 활성화되는 `고도화`에 구현한다.
- 회원가입·로그인·재발급·로그아웃은 계정 유형별 진입 경로와 스키마를 사용하고 클라이언트의 `role`·`accountType` 입력으로 계정 유형을 선택·전환·승격하지 않는다.
- 예약·예약 결합 메뉴 홀드·사용자 픽업 예약은 `consumer_account_id`를 참조하고, 1차 MVP의 `stores`는 `store_operator_account_id`를 직접 참조한다. 범용 `user_id` FK는 사용하지 않는다.

### 인수 조건

- `1차 MVP` 스키마와 JPA 모델에 공통 `users` 계정 엔티티나 계정 유형 discriminator가 없다.
- 일반 사용자 토큰으로 매장 운영자 API를 호출하거나 매장 운영자 토큰으로 일반 사용자 거래의 소유자가 될 수 없다.
- 플랫폼 운영자 기능을 추가할 때 일반 사용자·매장 운영자 테이블에 역할 열을 추가하거나 기존 PK를 바꾸지 않는다.

## C-001 공통 성공 응답

### 결정

일반적인 JSON 성공 응답은 다음 세 필드를 항상 사용한다.

| 필드 | 규칙 |
| --- | --- |
| `code` | 성공 시 모든 기능에서 문자열 `SUCCESS`를 사용한다. |
| `message` | 사람이 읽는 안내 문구다. 클라이언트의 분기 조건으로 사용하지 않는다. |
| `data` | 기능별 실제 결과를 담는다. 반환할 결과가 없으면 빈 객체 대신 `null`을 사용한다. |

```json
{
  "code": "SUCCESS",
  "message": "요청 성공",
  "data": {
    "reservationId": 123
  }
}
```

반환할 데이터가 없는 JSON 성공 응답은 다음과 같다.

```json
{
  "code": "SUCCESS",
  "message": "요청 성공",
  "data": null
}
```

성공 여부의 HTTP 의미는 응답 본문이 아니라 HTTP 상태 코드로 구분한다. 조회·수정 등의 성공에는 `200 OK`, 생성 성공에는 `201 Created`처럼 유스케이스에 맞는 상태 코드를 유지한다.

### 페이지 응답

목록과 페이지 정보는 모두 성공 응답의 `data` 안에 둔다. 목록 필드명은 `items`를 사용하고 페이지 메타데이터는 별도 객체로 묶는 방향으로 한다. 페이지 번호, 크기, 전체 개수 등 페이지 메타데이터의 정확한 필드와 인덱스 기준은 후속 공통 계약 결정에서 확정한다.

### 적용 예외

다음 응답에는 JSON 성공 응답 봉투를 적용하지 않는다.

- `204 No Content`: 응답 본문을 보내지 않는다.
- 파일 또는 바이너리 다운로드: 해당 미디어 타입과 본문을 그대로 사용한다.
- SSE 스트림: 이벤트 스트림 규격을 그대로 사용한다.

### 오류 응답과의 경계

성공 응답은 `ApiResponse<T>`와 같은 공통 타입으로 구현하는 방향을 사용한다. 오류 응답은 성공 봉투에 `ERROR` 같은 포괄 값을 넣지 않고 별도의 `ErrorResponse` 계약으로 관리한다.

활성 저장소 정책에 따라 오류 응답에는 기계 판독 가능한 `code`, 사람이 읽는 `message`, 필요한 경우 필드별 `details`가 있어야 한다. 구체적인 오류 코드 체계와 `details` 형식은 C-001에서 확정하지 않고 후속 결정에서 다룬다.

### 근거

참고 저장소의 공통 응답처럼 성공 결과를 일관된 봉투로 감싸되, 필드명은 `status` 대신 사용자가 제시한 `code`를 사용한다. 또한 모든 오류를 일반 문자열 `ERROR`로 표현하면 프론트엔드가 실패 원인을 안정적으로 구분할 수 없으므로, 오류 계약은 성공 계약과 분리한다.

### 수용 조건

- 모든 일반 JSON 성공 응답은 `code`, `message`, `data`를 같은 깊이에 둔다.
- 성공 `code`는 기능과 관계없이 `SUCCESS`다.
- 클라이언트는 `message` 값으로 비즈니스 로직을 분기하지 않는다.
- 반환 데이터가 없는 JSON 응답의 `data`는 `null`이다.
- 성공 HTTP 상태 코드는 각 유스케이스의 의미를 보존한다.
- `204`, 파일·바이너리 다운로드, SSE에는 JSON 성공 응답 봉투를 강제하지 않는다.
- 페이지네이션 세부 필드와 오류 응답 세부 구조는 후속 승인 전까지 확정된 것으로 간주하지 않는다.

## C-002 공통 오류 응답과 ErrorCode

### 오류 응답

오류 응답은 성공 응답 봉투와 분리하고 다음 필드를 사용한다.

| 필드 | 규칙 |
| --- | --- |
| `code` | 클라이언트가 분기에 사용하는 안정적인 외부 오류 코드다. |
| `message` | 클라이언트에게 전달할 수 있는 사람이 읽는 문장이다. 분기 조건으로 사용하지 않는다. |
| `details` | 요청값 검증처럼 필드별 설명이 필요한 경우에만 포함하는 배열이다. |

일반적인 도메인 오류는 다음과 같이 응답한다.

```json
{
  "code": "RESERVATION_003",
  "message": "예약 가능한 수용량을 초과했습니다."
}
```

요청값 검증 오류는 필요한 경우에만 `details`를 포함한다.

```json
{
  "code": "COMMON_001",
  "message": "입력값이 올바르지 않습니다.",
  "details": [
    {
      "field": "partySize",
      "reason": "1명 이상이어야 합니다."
    }
  ]
}
```

`details`에는 비밀번호, JWT, Refresh Token을 비롯한 민감 정보와 클라이언트가 제출한 거절 입력값을 싣지 않는다.

### 외부 오류 코드 형식

- enum 상수명은 `CAPACITY_EXCEEDED`처럼 오류 의미가 드러나는 이름을 사용한다.
- 외부 `code` 값은 `{DOMAIN}_{3자리 숫자}` 형식을 사용한다.
- 1차 MVP 도메인 접두사는 `COMMON`, `AUTH`, `ACCOUNT`, `STORE`, `RESERVATION`, `MENU_HOLD`, `PICKUP`이다.
- 외부 코드의 의미는 한 번 공개한 뒤 다른 의미로 재사용하지 않는다.
- 프론트엔드는 enum 상수명이나 `message`가 아니라 외부 `code` 값으로 분기한다.
- 실제 코드 목록과 각 코드의 HTTP 상태 매핑은 공통 오류 카탈로그 및 기능별 OpenAPI에서 검증·확정한다.
- 결제 관련 오류 코드는 1차 MVP 오류 카탈로그에 추가하지 않는다.

### Java 타입과 패키지 구조

`global.exception.ErrorCode`는 enum이 아니라 공통 인터페이스로 둔다. 공통·기술 오류와 도메인 오류 enum이 이 인터페이스를 구현하여 `ServiceException`과 공통 처리기가 같은 방식으로 다룰 수 있게 한다.

```text
global/
 └─ exception/
      ├─ ErrorCode.java
      ├─ CommonErrorCode.java
      ├─ ServiceException.java
      └─ GlobalExceptionHandler.java

domain/
 ├─ auth/exception/AuthErrorCode.java
 ├─ store/exception/StoreErrorCode.java
 ├─ reservation/exception/ReservationErrorCode.java
 ├─ menuhold/exception/MenuHoldErrorCode.java
 └─ pickup/exception/PickupErrorCode.java
```

```java
public interface ErrorCode {
    HttpStatus getHttpStatus();
    String getCode();
    String getMessage();
}
```

```java
@Getter
@RequiredArgsConstructor
public enum ReservationErrorCode implements ErrorCode {

    CAPACITY_EXCEEDED(
        HttpStatus.CONFLICT,
        "RESERVATION_003",
        "예약 가능한 수용량을 초과했습니다."
    );

    private final HttpStatus httpStatus;
    private final String code;
    private final String message;
}
```

`ServiceException`은 `ErrorCode` 인터페이스를 받는다.

```java
throw new ServiceException(
    ReservationErrorCode.CAPACITY_EXCEEDED
);
```

### HTTP 상태와 보안 예외

- `HttpStatus`는 서버가 HTTP 응답 상태를 결정할 때 사용하며 오류 응답 본문에 정수 상태를 중복해서 넣지 않는다.
- Spring MVC에서 발생한 예외는 `GlobalExceptionHandler`가 공통 오류 응답으로 변환한다.
- Spring Security 필터 구간에서 발생하는 인증·인가 실패도 동일한 오류 응답 직렬화기를 사용한다.
- 예상하지 못한 `500 Internal Server Error`는 내부 예외명, 스택 추적, SQL, 시스템 경로를 응답에 노출하지 않는다.
- 참고 예시의 개별 오류명과 HTTP 상태는 그대로 복사하지 않고 기능별 정책과 HTTP 의미를 검증한 뒤 오류 카탈로그에서 확정한다.

### 소유권

- `CommonErrorCode`와 공통 오류 응답 직렬화기는 공통 계약 소유 범위다.
- 도메인별 ErrorCode enum과 오류 추가·변경은 2단계에서 정한 해당 도메인 소유자가 관리한다.
- 다른 팀원은 소유자 협의 없이 타 도메인 ErrorCode enum에 코드를 추가하거나 기존 코드의 의미를 변경하지 않는다.

### 수용 조건

- 공통·기술 오류와 도메인 오류가 모두 `ErrorCode` 인터페이스를 구현한다.
- 모든 오류 응답은 성공 응답 봉투와 구분되는 `code`, `message`, 선택적 `details` 구조를 따른다.
- 외부 오류 코드는 `{DOMAIN}_{3자리 숫자}` 형식이며 한 번 공개한 의미를 재사용하지 않는다.
- 클라이언트는 외부 오류 코드만 업무 분기에 사용한다.
- 민감 정보와 거절 입력값은 `details`에 노출하지 않는다.
- MVC와 Security 필터 구간의 오류 응답 형식이 동일하다.
- 결제 오류와 결제 전이는 1차 MVP 계약에 포함하지 않는다.

## C-003 요청값 검증

### 검증 책임

- Controller는 영속성 Entity가 아니라 유스케이스별 요청 DTO를 입력으로 받는다.
- 필수 여부, 문자열 길이, 숫자 범위, 형식처럼 외부 입력만으로 판단할 수 있는 조건은 Bean Validation으로 검증한다.
- 검증기는 fail-fast로 중단하지 않고 발견한 모든 위반 항목을 수집한다.
- 날짜·시간·enum·숫자 등 JSON 타입 또는 형식이 잘못된 요청도 공통 `400 Bad Request` 오류 응답으로 변환한다.
- 예약 수용량 부족, 중복 예약, 메뉴 재고 부족처럼 저장된 상태를 조회해야 판단할 수 있는 조건은 요청값 검증으로 처리하지 않는다. 해당 조건은 도메인 정책 검증과 도메인 오류 코드를 사용한다.

### 검증 오류 응답

Bean Validation 실패는 enum 상수 `VALIDATION_FAILED`, 외부 오류 코드 `COMMON_001`을 사용한다.

```json
{
  "code": "COMMON_001",
  "message": "입력값이 올바르지 않습니다.",
  "details": [
    {
      "field": "partySize",
      "reason": "1명 이상이어야 합니다."
    },
    {
      "field": "menuSelections[0].quantity",
      "reason": "1개 이상이어야 합니다."
    }
  ]
}
```

`details[].field`는 Java 필드명이 아니라 공개 JSON 요청 필드 경로를 나타낸다.

- 단일 필드: `partySize`
- 중첩 목록 필드: `menuSelections[0].quantity`
- 특정 필드 하나로 표현할 수 없는 요청 전체의 교차 검증: `$`

`details[].reason`은 클라이언트에게 전달 가능한 문장으로 작성한다. `details`에는 거절된 실제 값, 비밀번호, JWT, Refresh Token 및 그 밖의 민감 정보를 포함하지 않는다.

### 엄격한 요청 계약

- 요청 DTO에 선언되지 않은 JSON 필드는 조용히 무시하지 않고 `400 Bad Request`로 거절한다.
- enum은 OpenAPI에 공개한 값만 허용하며 임의의 별칭이나 대소문자 보정을 적용하지 않는다.
- 새 요청 필드는 OpenAPI와 백엔드 요청 DTO를 먼저 같은 계약으로 맞춘 뒤 클라이언트에서 사용한다.
- 알 수 없는 필드, 읽을 수 없는 JSON, 타입 불일치 등 파싱 오류에 사용할 외부 코드 번호는 공통 오류 카탈로그에서 별도로 확정한다. 승인 전까지 임의의 새 코드 번호를 만들지 않는다.

### OpenAPI 동기화

요청 DTO의 다음 제약은 기능별 `openapi.yaml`에도 같은 값으로 작성한다.

- 필수값: `required`
- 숫자 범위: `minimum`, `maximum`
- 문자열 길이: `minLength`, `maxLength`
- 문자열 형식: `format`, `pattern`
- 허용된 값: `enum`
- 목록 크기: `minItems`, `maxItems`

코드와 OpenAPI의 제약이 다르면 승인된 공통·기능 명세를 기준으로 둘을 함께 수정한다. 구현만 완화하거나 문서만 강화하지 않는다.

### 수용 조건

- Controller 요청 DTO와 영속성 Entity가 분리되어 있다.
- 하나의 요청에 여러 필드 오류가 있으면 가능한 오류를 모두 `details`에 반환한다.
- 필드 경로는 공개 JSON 이름과 중첩 구조를 따른다.
- 요청 전체 오류는 필드 경로 `$`를 사용한다.
- 거절된 실제 값과 민감 정보가 오류 응답에 포함되지 않는다.
- DB 상태가 필요한 업무 규칙 위반은 `COMMON_001`로 변환하지 않는다.
- 알 수 없는 요청 필드는 `400 Bad Request`로 거절된다.
- DTO 검증 제약과 OpenAPI 스키마 제약이 일치한다.

## C-004 날짜·시간·타임존

### 업무 타임존

- 1차 MVP의 업무 타임존은 `Asia/Seoul`로 고정한다.
- 서울, 부산, 대구, 대전, 광주의 영업일·예약일·픽업일은 모두 `Asia/Seoul`의 현지 날짜를 기준으로 판단한다.
- `오늘`, 예약 마감 시각, 지난 시간 여부는 클라이언트 시계가 아니라 서버가 조회한 `Asia/Seoul` 현재 시각으로 판단한다.
- 1차 MVP API는 클라이언트로부터 임의의 타임존을 입력받지 않는다.
- 애플리케이션 코드는 운영체제나 JVM의 시스템 기본 타임존에 의존하지 않고 명시적인 `Asia/Seoul`을 사용한다.

### API 표현

| 의미 | 형식 | 예시 |
| --- | --- | --- |
| 달력 날짜 | `YYYY-MM-DD` | `2026-08-24` |
| 영업·예약·픽업 시간 | `HH:mm` | `14:00` |
| 특정 시점 | ISO 8601 및 UTC 오프셋 | `2026-08-24T14:00:00+09:00` |

- 예약과 픽업 시간 입력은 분 단위까지만 허용한다.
- 초 또는 소수 초가 포함된 예약·픽업 시간 입력을 임의로 절삭하거나 반올림하지 않고 요청값 검증 오류로 거절한다.
- 생성일·수정일처럼 사건이 발생한 절대 시각은 서버 내부에서 `Instant`와 UTC 기준으로 저장하고, API가 현지 시각을 제공할 때는 명시적인 오프셋을 포함한다.
- OpenAPI에는 날짜를 `format: date`, 특정 시점을 `format: date-time`으로 선언한다. `HH:mm` 현지 시간은 정규식과 설명으로 분 단위 형식을 명시한다.

### 시간 구간 경계

영업시간, 예약 시간대 및 픽업 시간대의 구간은 시작 포함·종료 제외인 반개구간 `[start, end)`로 판단한다.

예를 들어 `14:00`부터 `15:00`까지인 구간은 `14:00`에 시작하고 `15:00`에는 종료된 상태다. 따라서 끝 시각과 다음 구간의 시작 시각이 같은 두 구간은 그 사실만으로 서로 겹치지 않는다.

### 확장 경계

향후 해외 지역을 지원할 때 Store별 IANA 타임존을 추가할 수 있다. 이때도 공개 날짜·시간 형식과 `[start, end)` 경계 규칙은 유지하며, 1차 MVP 데이터와 API가 시스템 기본 타임존에 묶이지 않게 한다.

### 수용 조건

- 서버와 테스트가 시스템 기본 타임존과 관계없이 같은 예약일·픽업일을 계산한다.
- 날짜, 현지 시간, 특정 시점이 각각 승인된 형식으로 직렬화·역직렬화된다.
- 예약·픽업 시간 입력에 초 또는 소수 초가 포함되면 검증 오류가 발생한다.
- 끝 시각과 다음 시작 시각이 같은 인접 구간을 중복 구간으로 판정하지 않는다.
- 생성·수정 시각은 절대 시점으로 보존된다.
- 클라이언트가 임의의 타임존을 제출하여 업무 날짜 판정을 바꿀 수 없다.

## C-005 페이지네이션과 빈 결과

### 요청 규칙

페이지네이션을 지원하는 목록 API는 다음 쿼리 파라미터를 사용한다.

```http
GET /api/v1/stores?page=0&size=20&sort=name,asc
```

| 파라미터 | 규칙 |
| --- | --- |
| `page` | 0부터 시작하며 기본값은 `0`이다. |
| `size` | 기본값은 `20`, 최대값은 `100`이다. |
| `sort` | `{공개 정렬 필드},{asc|desc}` 형식이다. |

- 음수 `page`, `size=0`, 음수 크기 및 최대 크기 초과는 서버가 임의로 보정하지 않고 `400 Bad Request`로 거절한다.
- 1차 MVP에서는 한 요청에 하나의 공개 정렬 조건만 허용한다.
- 각 API는 허용할 공개 정렬 필드와 기본 정렬을 기능 명세 및 OpenAPI에 명시한다.
- 공개 정렬 필드는 내부 Entity 필드명을 직접 노출하지 않고 서버의 허용 목록을 통해 실제 정렬 기준으로 변환한다.
- 정렬값이 같은 행 사이에는 해당 리소스의 ID를 최종 보조 정렬로 적용하여 페이지를 이동할 때 순서가 불안정해지지 않게 한다.

### 응답 규칙

페이지 응답은 C-001 성공 응답의 `data` 안에 `items`와 `page`를 둔다.

```json
{
  "code": "SUCCESS",
  "message": "요청 성공",
  "data": {
    "items": [],
    "page": {
      "number": 0,
      "size": 20,
      "totalElements": 0,
      "totalPages": 0,
      "hasNext": false
    }
  }
}
```

| 필드 | 규칙 |
| --- | --- |
| `items` | 현재 페이지의 결과 배열이다. 결과가 없으면 빈 배열이다. |
| `page.number` | 현재 0 기반 페이지 번호다. |
| `page.size` | 요청에 적용된 페이지 크기다. |
| `page.totalElements` | 조건에 맞는 전체 결과 수다. |
| `page.totalPages` | 전체 페이지 수다. 빈 결과이면 `0`이다. |
| `page.hasNext` | 다음 페이지 존재 여부다. |

### 빈 결과와 프론트엔드 표시

- 조건에 맞는 목록이 없는 것은 오류가 아니며 `200 OK` 성공 응답을 반환한다.
- 빈 결과를 `404 Not Found` 또는 별도 오류 코드로 변환하지 않는다.
- 빈 결과는 `items: []`, `totalElements: 0`, `totalPages: 0`, `hasNext: false`로 표현한다.
- `items`와 페이지 메타데이터로 이미 판별할 수 있으므로 중복된 `empty` 필드를 추가하지 않는다.
- 프론트엔드는 `items.length === 0` 또는 `totalElements === 0`을 기준으로 목록 대신 별도의 빈 결과 화면이나 안내 문구를 표시한다.
- 프론트엔드는 성공 응답의 `message` 값으로 빈 결과 여부를 판단하지 않는다.

### 적용 범위

페이지네이션은 매장 검색, 내 예약 내역처럼 결과가 증가할 수 있고 기능별 명세에서 페이지 응답으로 선언한 목록 API에 적용한다. 예약 가능 시간대, enum 값처럼 크기가 제한된 목록에는 공통 페이지네이션을 강제하지 않는다.

### 수용 조건

- 기본 요청은 0번 페이지와 20개 크기로 처리된다.
- 100을 초과하는 크기와 유효하지 않은 페이지 값은 자동 보정 없이 거절된다.
- 기능별 OpenAPI가 허용 정렬 필드와 기본 정렬을 명시한다.
- 동일한 데이터와 조건으로 조회할 때 ID 보조 정렬을 포함한 순서가 결정적이다.
- 빈 목록은 `200 OK`와 빈 배열·0개 메타데이터를 반환한다.
- 프론트엔드는 빈 목록을 일반 목록과 구분되는 빈 결과 UI로 표시한다.

## C-006 상태 변경 명령 멱등성

### 기존 승인 정책과의 관계

이 결정은 3단계 E-005의 상태 변경 명령 멱등 처리와 고정 잠금 순서를 변경하지 않는다. 4단계에서는 E-005가 남긴 HTTP 헤더, 키 형식과 1차 저장 방식을 확정한다.

### 1차 MVP 적용 범위

- 예약 생성·취소·상태 변경, 픽업 예약 생성·취소·수령 완료, 수용량 설정 및 메뉴 수량 조정처럼 재전송으로 거래·상태·자원이 중복 변경될 수 있는 명령에 `Idempotency-Key` HTTP 헤더를 필수로 사용한다.
- 메뉴 홀드는 일반 예약 생성·취소 조정 트랜잭션에 참여하므로 별도 키를 요구하지 않고 해당 예약 명령의 키를 공유한다.
- 키는 클라이언트가 생성한 하이픈 포함 표준 UUID 문자열이며 하나의 사용자 명령을 재시도하는 동안 같은 값을 유지한다.
- `Idempotency-Key`는 ASCII 36자로 제한하고 UUID가 아닌 값, 중괄호가 붙은 값과 앞뒤 공백이 있는 값을 거절한다.
- 조회 요청에는 멱등성 키를 사용하지 않는다.
- 같은 리소스를 최종 표현으로 맞추고 반복 실행해도 추가 부작용이 없는 단순 수정 API는 기능별 명세가 별도로 요구하지 않는 한 멱등성 키를 필수로 하지 않는다.
- 키가 필수인 명령에 헤더가 없으면 `400 Bad Request`로 거절하며 서버가 임의의 키를 대신 만들지 않는다.

### MySQL 최소 구현

1차 MVP는 이미 사용하는 Spring Boot, JPA, MySQL만으로 공통 `idempotency_commands` 기록을 구현한다.

```text
idempotency_commands
- principal_namespace
- principal_id
- command_type
- idempotency_key
- request_fingerprint
- processing_status
- result_http_status
- result_response_code
- result_resource_type
- result_resource_id
- result_payload
- created_at
- updated_at
```

- 인증 주체 namespace, 주체 ID, 명령 유형, 멱등성 키의 조합에 데이터베이스 유일 제약을 적용한다.
- 멱등 기록을 예약·홀드·픽업·수량 자원보다 먼저 선점하고 E-005의 고정 잠금 순서를 이어서 적용한다.
- 같은 주체·명령·키·전체 요청 지문의 재전송은 자원을 다시 변경하지 않고 먼저 확정된 HTTP 상태·응답 코드·결과 payload를 반환한다.
- 같은 주체·명령·키를 다른 요청 지문에 사용하면 새 명령으로 처리하지 않고 `409 Conflict`로 거절한다.
- 처리 결과는 전체 업무 트랜잭션과 함께 확정한다. 일부 자원만 변경되거나 결과 연결이 실패하면 전체를 롤백한다.
- 멱등성 키는 수용량·재고 조건부 갱신, 데이터베이스 유일 제약과 행 잠금을 대신하지 않는다.

`request_fingerprint`는 HTTP method, 정규화된 route, 실제 path parameter, 정렬·정규화한 승인 query와 예약일·시간대·매장·인원·선택 메뉴·수량 같은 승인 body field를 결합해 만든다. 같은 route template이라도 대상 리소스 ID가 다르면 다른 지문이어야 한다. 비밀번호, JWT, Refresh Token과 원본 JSON 전체를 그대로 보관하지 않는다.

`result_payload`는 최초 성공 응답의 승인된 `data` 필드를 정규화한 불변 결과다. `result_http_status`, `result_response_code`, 리소스 type/id와 함께 업무 트랜잭션에서 확정하며 인증 헤더, 전송 시각과 직렬화된 HTTP 원문 바이트는 보관하지 않는다.

### 반복 실행과 결과 범위

- 일반 예약 취소의 수용량·메뉴 수량 복구는 실제 취소 상태 전이가 성공한 한 번에만 실행한다.
- 픽업 취소의 메뉴 수량 복구와 수령 완료 상태 전이도 같은 명령 결과를 중복 적용하지 않는다.
- 성공 커밋 뒤 HTTP 응답이 유실되어도 같은 키와 전체 요청 지문의 재시도는 저장된 최초 HTTP 상태·응답 코드·결과 payload를 재생한다.
- 결과 리소스가 이후 취소·완료·수정되어도 재시도 응답을 현재 표현으로 다시 만들지 않는다. 1차 MVP는 최초 결과의 의미적 필드만 보관하고 직렬화된 HTTP 응답의 바이트 단위 사본은 저장하지 않는다.
- 교착·잠금·버전 충돌의 자동 재시도는 전체 명령을 같은 멱등 키로 다시 실행할 수 있을 때만 제한적으로 허용하며, 정확한 횟수와 오류 코드는 기능별 동시성 계약에서 확정한다.

### 명시적인 1차 한계

- `idempotency_commands`는 MySQL 내부 공통 기록이며 Valkey를 사용하지 않는다.
- 1차 MVP에서는 멱등 기록을 자동 만료하지 않고 연결된 업무 거래의 보존 기간 동안 유지하며, 같은 주체·명령 범위에서 키를 다시 사용할 수 있게 만들지 않는다.
- HTTP 원문 바이트 보관, TTL 기반 만료, 만료 배치, 장기 장애 복구용 세분화된 상태 머신과 범용 멱등성 프레임워크를 도입하지 않는다.
- 멱등성 기능을 위해 새로운 인프라나 외부 라이브러리를 추가하지 않는다.

### 2차 MVP 검토 조건과 전환 경계

다음 조건이 실제 요구나 측정 결과로 확인될 때 공통 `IdempotencyStore`와 Valkey 기반 구현을 검토한다.

- 다중 서버 또는 비동기 처리가 도입되어 처리 중 명령의 선점과 복구가 필요하다.
- 최초 HTTP 상태와 응답 본문을 정확히 재생해야 한다.
- MySQL 멱등성 기록의 충돌·조회·보관 비용이 측정 가능한 병목이 된다.
- `PROCESSING`, `SUCCEEDED`, `FAILED`의 장기 상태와 장애 후 복구가 필요하다.
- 공통 TTL과 만료·정리 정책이 필요하다.

공개 API의 `Idempotency-Key` 계약을 유지하므로 위 조건이 충족되면 프론트엔드 계약을 바꾸지 않고 내부 저장 방식을 교체할 수 있다. Refresh Token용 Valkey와 멱등성용 저장소는 같은 기술을 사용하더라도 책임, 키 공간, TTL 정책을 분리한다.

### 수용 조건

- E-005가 지정한 재전송 가능한 상태 변경 명령은 멱등성 키가 없으면 실행되지 않는다.
- 표준 UUID 형식이 아닌 키는 업무 트랜잭션을 시작하기 전에 거절된다.
- 같은 주체·명령·키·요청 지문의 동시 또는 순차 재시도로 거래와 자원 변경이 한 번만 발생한다.
- 같은 주체·명령·키에 다른 요청 지문이 들어오면 기존 결과를 덮어쓰지 않고 충돌로 거절된다.
- 예약과 함께 처리되는 메뉴 홀드가 별도 멱등성 키를 요구하지 않는다.
- 취소 재시도로 수용량 또는 메뉴 수량이 두 번 복구되지 않는다.
- 멱등 기록과 업무 변경이 부분 성공으로 나뉘어 커밋되지 않는다.
- 1차 구현에 Valkey, TTL 배치, 직렬화된 HTTP 응답 원문 바이트 저장 또는 범용 멱등성 프레임워크가 포함되지 않는다.
- 2차 기술은 문서에 적힌 검토 조건이 충족된 뒤 별도 결정으로 도입한다.

## C-007 트랜잭션 경계와 제한 재시도

### 트랜잭션 소유권

- 쓰기 트랜잭션은 해당 명령을 조정하는 도메인의 주 Service가 소유한다.
- Controller와 개별 Repository가 전체 유스케이스의 트랜잭션 경계를 소유하지 않는다.
- 다른 도메인의 Entity나 Repository를 직접 수정하지 않고 소유 도메인의 공개 Service 메서드를 같은 트랜잭션 안에서 호출한다.
- 조정 유스케이스의 일부 작업에 실패하면 멱등 기록을 포함한 전체 변경을 롤백한다.
- 조회 전용 Service 메서드는 `readOnly = true` 트랜잭션을 사용할 수 있다.

### 유스케이스별 원자적 경계

- 일반 예약 생성은 멱등 기록, 예약 수용량 점유, 예약, 선택 메뉴 홀드·수량 원장과 결과 연결을 하나의 MySQL 트랜잭션으로 처리한다.
- 일반 예약 취소는 멱등 기록, 예약 상태 전이, 수용량 복구, 메뉴 홀드 해제·수량 복구와 결과 연결을 하나의 MySQL 트랜잭션으로 처리한다.
- 픽업 예약 생성·취소는 멱등 기록, 픽업 거래·항목, 메뉴 재고 변경·원장과 결과 연결을 하나의 MySQL 트랜잭션으로 처리한다.
- 픽업 수령 완료와 수용량·메뉴 수량 설정 명령도 E-005의 잠금 순서와 각 명령의 원장 기록을 같은 트랜잭션에서 확정한다.
- 예약 가능 여부 조회 결과는 생성 성공을 보장하지 않는다. 생성 트랜잭션이 잠금을 얻은 뒤 현재 수용량·재고와 정책을 다시 검증한다.

1차 MVP에서는 내부 HTTP 호출이나 비동기 이벤트로 위 원자적 작업을 분할하지 않는다. 향후 알림 등 외부 연동을 추가할 때도 외부 네트워크 호출을 MySQL 트랜잭션 안에서 실행하지 않고 커밋 이후 전달 방식 또는 별도 후속 계약을 사용한다.

### 격리 수준과 제한 시간

- 경합 자원을 변경하는 명령 트랜잭션의 격리 수준은 `READ_COMMITTED`로 명시한다.
- 명령 트랜잭션 제한 시간은 5초다.
- 정합성을 격리 수준에만 맡기지 않고 E-005의 `SELECT ... FOR UPDATE`, 고정 잠금 순서, 조건부 갱신과 유일 제약을 함께 적용한다.
- E-005가 지정한 자원 유형 순서와 각 유형 내부의 PK 오름차순을 모든 쓰기 경로에서 동일하게 사용한다.

### 자동 재시도

자동 재시도는 최초 실행을 포함하여 최대 3회다.

| 시점 | 대기 시간 |
| --- | --- |
| 첫 번째 실패 뒤 | `100~200ms` 무작위 지터 |
| 두 번째 실패 뒤 | `300~500ms` 무작위 지터 |

- 재시도 대기는 실패한 트랜잭션이 완전히 롤백된 뒤 트랜잭션 밖에서 수행한다.
- 각 시도는 새로운 전체 트랜잭션이며 실패한 Repository 쿼리만 부분 재실행하지 않는다.
- 모든 시도는 최초 요청의 같은 `Idempotency-Key`와 요청 지문을 사용한다.
- 재시도 로직을 위해 Spring Retry, Redis, Valkey 또는 새 외부 라이브러리를 추가하지 않는다.

### 재시도 분류

다음과 같이 전체 명령을 다시 실행해도 안전한 일시적 충돌만 자동 재시도한다.

- 데이터베이스 교착
- 일시적인 행 잠금 획득 실패
- 낙관적 버전 충돌

다음 업무 결과는 일시적인 데이터베이스 충돌이 아니므로 자동 재시도하지 않는다.

- 예약 수용량 부족
- 메뉴 재고 부족
- 허용되지 않은 상태 전이
- 요청값 검증 실패
- 인증·인가 실패
- 이메일 중복 등 업무상 유일성 충돌

최대 3회 안에 확정되지 않으면 성공이나 자원 부족을 추측하지 않고 `409 Conflict`를 반환한다. 구체적인 외부 오류 코드는 공통 오류 카탈로그와 기능별 OpenAPI에서 확정한다.

### 참고 구현과의 차이

참고한 Agora의 활성 구현은 Redisson 분산 락 획득을 최대 2초 기다린 뒤 실패 시 충돌을 반환하며 자동 재시도·백오프를 사용하지 않는다. 이 2초는 재시도 간격이 아니라 분산 락 대기 시간이다.

MiriYum 1차 MVP는 Redis 분산 락을 도입하지 않고 MySQL 행 잠금과 조건부 갱신을 사용하므로 Agora의 락 대기 시간을 복사하지 않는다. 짧은 전체 DB 트랜잭션을 제한적으로 재시도하고 동시에 몰린 요청이 같은 순간에 다시 충돌하지 않도록 지터를 적용한다.

### 검증

- 단위 테스트는 재시도 대상과 제외 대상의 분류, 최대 횟수, 지터 범위와 같은 멱등 키 유지를 검증한다.
- 동시성·교착·롤백 인수 테스트는 H2나 mock을 정합성 증거로 사용하지 않고 Testcontainers MySQL에서 실행한다.
- 병렬 테스트는 마지막 수용량·메뉴 수량에 대한 성공 합계가 한도를 넘지 않는지 검증한다.
- 실패 주입 테스트는 부분 예약, 부분 메뉴 홀드, 부분 복구 또는 결과 없는 멱등 성공 기록이 커밋되지 않는지 검증한다.

### 수용 조건

- 조정하는 도메인의 주 Service 한 곳이 각 명령의 전체 트랜잭션을 소유한다.
- 예약과 메뉴 홀드 또는 픽업과 메뉴 재고가 부분 성공으로 나뉘지 않는다.
- 경합 명령은 명시적인 `READ_COMMITTED`와 5초 제한 시간을 사용한다.
- 재시도는 승인된 일시적 충돌에만 최초 실행 포함 최대 3회 수행된다.
- 각 재시도는 새로운 전체 트랜잭션과 같은 멱등 키를 사용한다.
- 첫 번째와 두 번째 재시도 대기가 각각 승인된 지터 범위 안에 있다.
- 최대 횟수 이후에는 성공으로 처리하거나 무한 재시도하지 않고 충돌 응답을 반환한다.
- 1차 구현에 Redis 분산 락, Spring Retry 또는 새 재시도 인프라를 추가하지 않는다.

## C-008 공개 API 경로·명명과 ID

### 기본 경로

- 1차 MVP 공개 HTTP API의 공통 기본 경로는 `/api/v1`이다.
- URL 경로는 소문자 복수 명사를 사용하고 여러 단어는 kebab-case로 연결한다.
- URL 끝에 후행 `/`를 사용하지 않는다.
- 내부 Java 패키지, Entity 또는 테이블 이름을 공개 URL에 그대로 노출하지 않는다.

```text
/api/v1/stores
/api/v1/menu-holds
```

### 이름 표기

| 위치 | 표기 |
| --- | --- |
| URL 경로 조각 | 소문자 복수 명사, kebab-case |
| 경로 변수 | camelCase |
| 쿼리 파라미터 | camelCase |
| JSON 필드 | camelCase |
| enum 값 | 대문자 snake case |

경로 변수는 `{id}`처럼 의미가 없는 이름 대신 `{reservationId}`, `{storeId}`, `{menuId}`처럼 대상 리소스를 명시한다.

### 외부 ID 표현

- MySQL과 JPA의 내부 식별자는 E-007에 따라 `BIGINT`와 Java `Long`을 사용할 수 있다.
- 공개 JSON 요청·응답과 OpenAPI에서 도메인 식별자는 문자열로 표현한다.
- OpenAPI 스키마는 `type: string`과 숫자 문자열 제약을 사용하며 JavaScript `number`로 변환하도록 요구하지 않는다.
- 프론트엔드는 ID를 산술 연산하지 않고 불투명 식별자로 취급한다.

```json
{
  "reservationId": "123",
  "storeId": "45"
}
```

이 규칙은 JavaScript의 안전한 정수 범위를 넘는 `BIGINT` 값이 반올림되는 것을 방지하고, 향후 공개 식별자 형식을 바꿀 때 클라이언트가 숫자 연산에 결합되지 않게 한다.

### 계정 유형별 경로

- 일반 사용자와 매장 운영자의 회원가입·로그인·재발급·로그아웃은 서로 다른 공개 namespace와 스키마를 사용한다.
- 요청 본문의 `role` 또는 `accountType`으로 계정 유형을 선택·변경·승격하지 않는다.
- 플랫폼 운영자 진입 경로는 해당 기능이 활성화되는 고도화 단계 전까지 1차 MVP OpenAPI에 추가하지 않는다.
- 일반 사용자와 매장 운영자의 정확한 인증 namespace는 `auth-account` 기능 명세에서 별도 승인한다.

### 공개 API 소유권

- 하나의 사용자 유스케이스에는 하나의 공개 API만 둔다.
- 화면 담당자가 다르거나 둘 이상의 도메인 기능을 조정해도 같은 목적의 API를 중복 구현하지 않는다.
- 2단계에서 정한 조정 유스케이스 소유자가 공개 경로와 OpenAPI 정의를 관리한다.
- 다른 도메인은 소유자의 공개 Service 메서드와 DTO를 사용하며 같은 경로를 별도 Controller로 다시 노출하지 않는다.
- 상태 변경에 사용할 구체적인 리소스·명령 경로는 기능별 상태 전이와 권한을 검증한 뒤 각 기능 spec과 OpenAPI에서 확정한다.

### 수용 조건

- 모든 1차 MVP 공개 API가 `/api/v1` 아래에 있다.
- URL 경로에 대문자, underscore 또는 단수 리소스 이름을 새로 사용하지 않는다.
- 공개 요청·응답의 ID가 JSON 문자열이며 OpenAPI도 문자열로 선언한다.
- 일반 사용자와 매장 운영자가 같은 인증 진입점에서 역할 입력값으로 구분되지 않는다.
- 플랫폼 운영자 API가 1차 MVP OpenAPI에 노출되지 않는다.
- 동일 유스케이스의 공개 경로와 Controller가 도메인별로 중복되지 않는다.

## C-009 기능별 spec과 OpenAPI 구조

### 확정 구조

```text
docs/specs/
├─ mvp1-openapi.yaml
│
├─ mvp1-common/
│  ├─ spec.md
│  └─ openapi.yaml
│
├─ auth-account/
│  ├─ spec.md
│  └─ openapi.yaml
│
├─ store-search/
│  ├─ spec.md
│  └─ openapi.yaml
│
├─ reservation/
│  ├─ spec.md
│  └─ openapi.yaml
│
└─ menu-hold-pickup/
   ├─ spec.md
   └─ openapi.yaml
```

승인된 내용이 없는 기능별 파일을 빈 자리표시자로 미리 만들지 않는다. 각 기능의 정책·경로·스키마가 승인되는 시점에 해당 파일을 생성한다.

### 공통 OpenAPI

`docs/specs/mvp1-common/openapi.yaml`은 다음 재사용 계약을 소유한다.

- C-001 성공 응답
- C-002·C-003 오류와 검증 응답
- C-005 페이지네이션
- C-008 문자열 ID
- C-006 `Idempotency-Key`
- JWT 보안 스키마
- 공통 날짜·시간 스키마

기능별 OpenAPI는 공통 스키마를 복사하지 않고 이 파일의 component를 `$ref`로 참조한다.

### 기능별 spec

각 기능의 `spec.md`는 저장소 템플릿의 기존 항목과 다음 내용을 소유한다.

- 관련 정책 ID와 단계 포함·제외 범위
- 사용자 관점의 정상·오류 흐름
- 상태 전이와 권한
- 트랜잭션·동시성·멱등성 적용
- 예외 상황과 기능별 오류 코드
- API·데이터 계약과 호환성 경계
- 검증 가능한 인수 조건

각 `spec.md` 상단에는 다음 메타데이터를 둔다.

```text
문서 상태
적용 단계
도메인 소유자
협업 담당자
관련 정책 ID
OpenAPI 경로
최종 승인일
```

도메인 소유자는 2단계 소유권 표를 따르며 일회성 GitHub Issue 담당자와 구분한다.

### 기능별 OpenAPI

각 기능의 `openapi.yaml`은 해당 기능 소유자가 관리하는 다음 HTTP 계약을 소유한다.

- 공개 경로와 HTTP 메서드
- 경로·쿼리·헤더 파라미터
- 요청·응답 스키마
- 성공·오류 HTTP 상태
- 공개 오류 코드

정책 설명, 트랜잭션 내부 구현과 장문의 인수 시나리오는 OpenAPI에 복제하지 않고 같은 디렉터리의 `spec.md`에서 관리한다.

### 통합 진입점

`docs/specs/mvp1-openapi.yaml`은 프론트엔드 연동과 전체 계약 검증에 사용하는 1차 MVP 통합 진입점이다.

- 기능별 공개 경로를 `$ref`로 조립한다.
- 같은 경로·메서드가 둘 이상의 기능 파일에 중복되지 않게 한다.
- 공통 component와 모든 기능 참조가 정상적으로 해석되어야 한다.
- 결제, 노쇼, 플랫폼 운영자와 그 밖의 고도화 전용 API를 포함하지 않는다.
- 통합 진입점은 공통 계약 소유자가 관리하고 기능별 경로 내용은 2단계에서 정한 각 소유자가 관리한다.

### 수용 조건

- 공통 스키마가 기능별 파일에 복사되지 않고 `$ref`로 연결된다.
- 각 기능의 `spec.md`에 도메인 소유자와 협업 담당자가 명시된다.
- 기능별 OpenAPI 경로가 해당 공개 API 소유권 표와 일치한다.
- 통합 진입점에서 모든 1차 MVP 경로와 공통 component를 해석할 수 있다.
- 동일한 공개 경로·메서드 조합이 두 기능 파일에 존재하지 않는다.
- 고도화 전용 API가 1차 MVP 통합 문서에 포함되지 않는다.

## C-010 OpenAPI 버전과 검증

### 명세 버전

- 1차 MVP OpenAPI 문서는 `openapi: 3.1.0`을 사용한다.
- Schema Object는 JSON Schema Draft 2020-12를 기준으로 작성한다.
- YAML 표현은 YAML 1.2의 JSON 호환 문법을 사용한다.
- 현재 OpenAPI 최신 minor라는 이유만으로 3.2를 도입하지 않는다. Springdoc과 프론트엔드 생성·표시 도구의 호환성을 검증한 뒤 별도 승인으로 올린다.
- OpenAPI Specification의 3.1 patch 버전은 같은 기능 집합이므로 도구가 3.1 patch 표기 차이에 의존하지 않게 한다.

### 검증 도구

- OpenAPI lint와 bundle에는 `@redocly/cli` `2.35.1`을 고정하여 사용한다.
- `latest`, `+`, 버전 범위 또는 실행 시점에 결과가 바뀌는 비고정 태그를 사용하지 않는다.
- Redocly CLI 버전 갱신은 release note, Node 호환성, 현재 문서의 lint·bundle 결과를 검증한 별도 변경으로 진행한다.
- 설정은 저장소 루트의 `redocly.yaml`이 소유한다.
- 기본 규칙은 `recommended-strict`를 사용한다.
- 익명 사용 데이터 전송은 `telemetry: off`로 비활성화한다.
- lint 무시 파일을 자동 생성하거나 실패 규칙을 조용히 끄지 않는다. 예외가 필요하면 이유·범위·만료 또는 제거 조건을 팀이 승인한다.

`2.35.1`은 2026-06-25에 공개된 고정 버전으로, 이번 결정 시점에 막 공개된 `2.40.0`을 바로 채택하지 않는다. 현재 검증 범위에 필요하지 않은 실험적 drift·proxy·generate-spec 기능도 1차 MVP 검증 경로에 사용하지 않는다.

### 검증 대상

- 각 기능의 `openapi.yaml`을 독립 진입점으로 lint한다.
- `docs/specs/mvp1-openapi.yaml`을 lint하여 통합 경로·operationId·component 참조를 검증한다.
- 통합 진입점을 bundle하여 모든 외부 `$ref`가 실제로 해석되는지 확인한다.
- bundle 산출물은 임시 검증 결과이며 저장소에 커밋하지 않는다.
- 공통 component 조각은 이를 참조하는 기능별 문서와 통합 진입점의 lint·bundle 과정에서 검증한다.

### 구현 이후 계약 드리프트

- 정적 `docs/specs/mvp1-openapi.yaml`이 설계 계약의 기준이다.
- Springdoc 런타임 출력은 구현이 정적 계약을 따르는지 확인하는 비교 대상이며 정적 계약을 자동으로 덮어쓰지 않는다.
- 구현 이후 CI에서 경로·메서드·요청·응답·상태 코드의 차이를 검출하는 검증을 추가한다.
- 실험적 자동 추론 기능으로 정적 명세를 재작성하지 않는다.

### 수용 조건

- 모든 OpenAPI 루트 문서가 3.1 계열로 해석된다.
- 고정된 Redocly CLI `2.35.1`로 기능별 lint와 통합 lint·bundle이 성공한다.
- 깨진 외부 참조와 중복 operationId가 검증에서 실패한다.
- 저장소와 CI가 `latest` 태그 또는 비고정 검증 도구 버전을 사용하지 않는다.
- lint 경고를 승인 없는 ignore 파일로 숨기지 않는다.
- 런타임 Springdoc 출력이 정적 계약을 자동 변경하지 않는다.

### 소유 경계

- 인증 자격 증명 실패, 계정 상태·회원정보 오류와 권한 부족의 `401 Unauthorized`, `403 Forbidden`은 인증 도메인의 단일 `AuthErrorCode`가 소유한다.
- 매장·메뉴·예약·메뉴 홀드·픽업 리소스가 존재하지 않는 오류는 각 도메인의 단일 ErrorCode가 소유한다.
- 요청 경로 자체가 존재하지 않는 경우에만 `COMMON_005`를 사용한다.
- 빈 검색·목록 결과는 C-005에 따라 오류가 아니며 `200 OK`와 빈 배열을 반환한다.
- 업무상 중복·상태 위반·수용량·재고 부족은 공통 코드로 평탄화하지 않고 해당 도메인 코드를 사용한다.

### 응답과 재시도

- `COMMON_001`은 C-003의 안전한 필드별 `details`를 포함할 수 있다.
- `COMMON_002`도 안전하게 특정할 수 있는 JSON 필드 경로만 `details`에 포함할 수 있으며 원본 입력값을 노출하지 않는다.
- `429 Too Many Requests`와 `503 Service Unavailable`은 서버가 재시도 가능 시각을 계산할 수 있을 때 `Retry-After` 헤더를 제공한다.
- `COMMON_011`은 내부 예외명, 스택 추적, SQL, 시스템 경로와 비밀 값을 응답에 노출하지 않는다.
- 클라이언트가 재시도할 수 있다는 이유만으로 서버가 성공 여부를 추측하거나 무한 자동 재시도하지 않는다.

### 코드 변경 규칙

- 공개한 외부 코드 번호와 의미는 변경하거나 다른 오류에 재사용하지 않는다.
- 더 이상 사용하는 경로가 없어져도 과거 공개 코드를 새 의미에 할당하지 않는다.
- 새 공통 오류가 승인되면 `COMMON_013`부터 순차적으로 추가한다.
- 실제 1차 MVP 계약에 없는 예상 상황을 위해 코드를 대량으로 미리 만들지 않는다.
- enum 상수명과 기본 메시지를 다듬더라도 외부 코드의 의미와 HTTP 상태 변경은 계약 변경으로 검토한다.

### 수용 조건

- 공통 예외 처리기가 표에 있는 HTTP 상태와 외부 코드를 동일하게 반환한다.
- 인증·도메인 오류가 편의상 `COMMON_011` 또는 공통 404로 변환되지 않는다.
- 빈 목록이 `COMMON_005`로 반환되지 않는다.
- `COMMON_001`·`COMMON_002`의 세부 정보에 원본 민감 입력값이 포함되지 않는다.
- `COMMON_011`이 내부 구현 정보를 노출하지 않는다.
- 공개된 공통 코드 번호가 삭제 뒤 다른 의미로 재사용되지 않는다.

## C-012 성공 응답의 구체 OpenAPI 스키마

### 결정

백엔드 Java 구현은 C-001의 공통 `ApiResponse<T>`를 사용한다. OpenAPI에서는 `data`를 아무 값이나 허용하는 범용 성공 봉투 하나로 모든 API를 표현하지 않고, 공개하는 성공 결과의 형태별로 구체적인 응답 스키마를 선언한다.

예를 들어 예약 상세 조회는 다음과 같이 `data`가 `ReservationDetail`임을 OpenAPI가 직접 검증할 수 있어야 한다.

```yaml
ReservationDetailSuccessResponse:
  type: object
  additionalProperties: false
  required:
    - code
    - message
    - data
  properties:
    code:
      $ref: "../mvp1-common/openapi.yaml#/components/schemas/SuccessCode"
    message:
      $ref: "../mvp1-common/openapi.yaml#/components/schemas/SuccessMessage"
    data:
      $ref: "#/components/schemas/ReservationDetail"
```

이 규칙은 API마다 별도의 Java 성공 봉투 클래스를 만들라는 뜻이 아니다. Java에서는 `ApiResponse<ReservationDetailResponse>`처럼 공통 제네릭을 사용하고, OpenAPI가 그 제네릭의 실제 `data` 타입을 잃지 않도록 문서에서 구체화한다.

### 작성 규칙

- 성공 응답 객체는 `code`, `message`, `data`를 모두 `required`로 선언한다.
- `code`는 공통 `SuccessCode`, `message`는 공통 `SuccessMessage` component를 `$ref`로 재사용한다.
- `data`는 기능별 구체 스키마 또는 페이지 응답 스키마를 `$ref`로 연결한다.
- 결과가 없는 성공 응답은 C-001에 따라 `data`를 빈 객체가 아니라 JSON `null`로 명시한다.
- 목록은 배열 타입과 `items`를, 페이지 응답은 C-005의 `items`와 `page` 구조를 구체적으로 선언한다.
- 객체 스키마는 의도하지 않은 응답 필드가 계약에 조용히 추가되지 않도록 기본적으로 `additionalProperties: false`를 사용한다.
- 필수 응답 필드는 `required`에 명시하며, 실제로 `null`이 가능한 필드만 JSON Schema 2020-12 문법으로 `null`을 허용한다.
- 합성 시 해석 차이와 작성 난도를 높이는 성공 봉투의 `allOf` 조합은 1차 MVP에서 사용하지 않는다.
- HTTP 상태와 `data` 구조까지 동일한 성공 응답은 같은 구체 스키마를 재사용할 수 있다. 이름만 다른 중복 스키마를 만들지 않는다.
- 공통 성공 봉투의 모양만 검사하고 `data: {}`처럼 내부 타입을 비워 두는 스키마는 공개 API 응답에 사용하지 않는다.

### 팀원용 작성 안내

기능별 OpenAPI 작성을 시작하기 전에 `docs/specs/mvp1-common/openapi-guide.md`를 작성한다. 이 안내서는 OpenAPI를 처음 사용하는 팀원이 기존 예시를 복사한 뒤 다음 두 부분만 바꿔도 되도록 구성한다.

1. 성공 응답 스키마 이름
2. `data`가 참조할 기능별 결과 스키마

안내서에는 단건·목록·페이지·생성·본문 없는 성공의 최소 예시, 백엔드 `ApiResponse<T>`와의 대응, 프론트엔드에서 `data` 타입을 읽는 방법, 금지 예시와 제출 전 체크리스트를 쉬운 말로 포함한다. 안내서는 새로운 정책을 정하는 문서가 아니라 이 결정과 C-001·C-005를 적용하는 사용 설명서다.

### 채택 전 비교 검증 기록

이 결정은 다른 프로젝트의 사용 전적만으로 채택하지 않고 2026-07-28에 작은 A/B OpenAPI 예제로 먼저 검증했다.

#### 검증 조건

- OpenAPI `3.1.0`
- `@redocly/cli` `2.35.1`
- `recommended-strict`
- 같은 예약 상세 성공 응답의 정상 예시와 `data`를 문자열로 잘못 작성한 예시
- lint로 예시와 스키마의 일치 여부를 검사하고 정상본은 bundle 가능 여부도 확인

| 비교안 | 정상 예시 lint | 잘못된 `data` 예시 lint | 정상본 bundle | 예제 문서 줄 수 |
| --- | --- | --- | --- | --- |
| A: 공통 봉투의 `data: {}`만 사용 | 성공, 종료 코드 `0` | 성공, 종료 코드 `0` | 성공 | 52줄 |
| B: 성공 결과의 구체 `data` 스키마 사용 | 성공, 종료 코드 `0` | 실패, 종료 코드 `1` | 성공 | 67줄 |

B안의 잘못된 예시는 Redocly의 `no-invalid-media-type-examples` 규칙에서 `data property type must be object` 오류로 검출됐다. A안은 잘못된 문자열도 허용하여 계약 오류를 잡지 못했다.

두 예제의 차이는 15줄이었다. 구체 스키마는 문서량이 늘어나는 단점이 있지만, 공통 component 재사용, 동일 응답 스키마 재사용, 복사형 작성 안내서로 부담을 줄인다. 이 추가 문서량보다 백엔드·프론트엔드·API 문서 사이의 `data` 구조 불일치를 구현 전에 검출하는 이점이 크다고 판단하여 B안을 채택했다.

비교 대상으로 확인한 Agora 저장소에는 공통 Java `ApiResponse<T>` 사용 전적은 있었지만 OpenAPI·Redocly 또는 기능별 구체 성공 응답 스키마 사용 전적은 없었다. 따라서 Agora는 공통 응답 모양의 참고 자료로만 사용하고 C-012 채택 근거로 간주하지 않는다.

이 검증은 OpenAPI 예시와 스키마의 일치 여부를 확인한 것이며 런타임 백엔드 응답까지 자동 보장하지는 않는다. 구현 후 실제 응답과 정적 명세의 차이는 C-010의 계약 드리프트 검증으로 보완한다.

검증에 사용한 임시 예제와 bundle 산출물, npm 캐시는 정책 산출물이 아니므로 커밋하지 않는다. 재현할 때는 같은 고정 버전과 규칙으로 정상본·오류본을 각각 lint하고 정상본을 bundle한다.

### 수용 조건

- 기능별 성공 응답의 `data`가 빈 스키마가 아니라 구체 결과 스키마로 검증된다.
- 잘못된 타입의 성공 응답 예시가 고정된 Redocly lint에서 실패한다.
- Java 구현은 공통 `ApiResponse<T>`를 유지하며 OpenAPI 때문에 기능별 봉투 클래스를 중복 생성하지 않는다.
- 같은 성공 결과 스키마를 불필요하게 복제하지 않는다.
- 성공 봉투 구성에 `allOf`를 사용하지 않는다.
- 객체의 필수 필드와 추가 필드 허용 여부가 명시된다.
- 기능별 OpenAPI 작성 전에 초보자용 작성 안내서가 준비된다.
- 런타임 응답과 정적 계약의 일치 여부를 구현 이후 별도로 검증한다.

## C-013 인증·인가 HTTP 상태와 개인 자원 존재 은닉

### 기존 정책과의 관계

이 결정은 D-002의 토큰 유효기간, D-003의 브라우저 저장·전달·CSRF 경계, D-007의 계정 유형별 물리 분리와 2단계의 도메인 소유권을 변경하지 않는다. 기존 정책이 정한 인증·권한 판정을 모든 기능 API가 같은 HTTP 상태와 조회 방식으로 표현하도록 연결한다.

새 인증 기술, 공통 역할 테이블, 통합 계정 principal, 서버 저장 Refresh Token 또는 고도화 전용 권한 체계를 1차 MVP에 추가하지 않는다.

### 상태 코드 판정표

| 판정 결과 | HTTP | 처리 원칙 |
| --- | --- | --- |
| 공개 API | 해당 성공·도메인 상태 | Access JWT를 요구하지 않는다. |
| Access Token 누락 | `401 Unauthorized` | 보호 API에 유효한 인증 자격이 없다. |
| 토큰 형식·서명·만료 오류 | `401 Unauthorized` | 유효한 인증 자격으로 인정하지 않는다. |
| 토큰 namespace와 API의 계정 유형 불일치 | `401 Unauthorized` | 다른 계정 유형의 토큰을 현재 API의 인증 자격으로 인정하지 않는다. |
| JWT subject에 해당하는 현재 계정을 확인할 수 없음 | `401 Unauthorized` | 인증 주체를 구성하지 않는다. |
| 로그인 자격정보 불일치 | `401 Unauthorized` | 이메일 존재 여부와 관계없이 같은 외부 오류로 응답한다. |
| 유효한 principal이지만 현재 계정 상태가 이용을 허용하지 않음 | `403 Forbidden` | 정지·탈퇴 대기 등 활성 정책의 현재 계정 상태를 적용한다. |
| 유효한 principal이지만 API가 요구하는 계정 유형·권한이 아님 | `403 Forbidden` | 인증 성공과 업무 권한 허용을 구분한다. |
| 매장 운영자가 대상 매장의 대표 운영자가 아님 | `403 Forbidden` | JWT의 클라이언트 제공 매장 목록을 신뢰하지 않고 매장 도메인의 현재 FK를 확인한다. |
| Refresh Token 쿠키가 필요한 요청에서 쿠키가 없거나 유효하지 않음 | `401 Unauthorized` | Access Token 오류와 구분되는 인증 도메인 오류로 표현한다. |
| Refresh·로그아웃 요청의 Origin·Referer·CSRF 검증 실패 | `403 Forbidden` | 자동 첨부 쿠키를 사용한 요청의 권한 검증 실패로 처리한다. |
| 본인만 볼 수 있는 개인 자원이 없거나 다른 사용자의 소유임 | 도메인 `404 Not Found` | 두 경우를 같은 오류 코드·메시지·응답 구조로 처리해 존재 여부를 노출하지 않는다. |
| 공개 매장처럼 존재가 공개된 자원은 있으나 변경 권한이 없음 | `403 Forbidden` | 공개 자원의 존재를 숨기기 위해 거짓 404를 사용하지 않는다. |

`401`은 “현재 요청에 사용할 수 있는 인증 자격이 없다”, `403`은 “인증 주체는 확인됐지만 이 동작은 허용되지 않는다”, 개인 자원의 도메인 `404`는 “이 주체의 조회 범위 안에서 대상이 없다”는 의미다.

### 개인 자원 조회 규칙

일반 사용자의 예약, 예약 결합 메뉴 홀드와 픽업 예약처럼 본인만 볼 수 있는 자원은 먼저 ID로 조회한 뒤 Java 코드에서 소유자를 비교하지 않는다. 저장소 또는 도메인 조회 포트에서 인증된 주체 ID를 조회 조건에 함께 넣는다.

```text
허용:
findByReservationIdAndConsumerAccountId(
    reservationId,
    authenticatedConsumerAccountId
)

금지:
findById(reservationId)
→ 응답 또는 로그로 존재를 드러냄
→ 나중에 consumerAccountId 비교
```

조회 결과가 없으면 실제로 존재하지 않는 경우와 다른 사용자가 소유한 경우 모두 예약 도메인의 같은 `RESERVATION_NOT_FOUND` 계열 오류를 반환한다. 다른 소유자의 ID인지 확인하기 위한 두 번째 조회를 수행하지 않는다.

마이페이지가 이 결과를 사용하더라도 2단계 소유권에 따라 예약 조회 규칙과 404는 예약 도메인이 소유한다. 인증·마이페이지 담당자는 예약 entity나 repository를 직접 조회하지 않고 `ReservationService`의 예약 내역 조회 공개 메서드와 DTO를 사용한다.

### 매장 운영자 권한 판정

매장 운영자 JWT는 `store-operator` namespace와 계정 subject만 증명한다. 대상 매장의 현재 소속과 운영 가능 상태는 매장 명령마다 매장 도메인의 `StoreService` 운영 권한 검증 공개 메서드로 확인한다.

판정 순서는 다음과 같다.

1. Access JWT의 형식·서명·만료와 `store-operator` namespace를 검증한다.
2. subject의 현재 매장 운영자 계정과 이용 가능 상태를 확인한다.
3. 경로의 `storeId`에 대한 현재 소속과 운영 권한을 매장 도메인에서 확인한다.
4. 권한이 확인된 뒤에만 대상 메뉴·예약·수량 등 기능 자원을 조회하거나 변경한다.

1단계가 실패하면 `401`, 2·3단계가 실패하면 `403`이다. 매장 운영자 화면이 전송한 계정 ID, 역할, 관리 매장 목록이나 요청 본문의 소유자 필드는 권한 근거로 사용하지 않는다.

### OpenAPI 표현

- 공통 OpenAPI에 `type: http`, `scheme: bearer`, `bearerFormat: JWT`인 `bearerAuth` Security Scheme을 둔다.
- 보호 API의 각 operation은 `security: [{ bearerAuth: [] }]`를 명시한다.
- 공개 API는 보안 요구가 없음을 `security: []`로 명시한다.
- 보호 API는 가능한 `401`과 `403` 응답을 공통 인증 오류 component로 참조한다.
- 개인 자원 API는 해당 도메인의 `404` 응답을 함께 선언한다.
- 일반 보호 API가 Refresh Token 쿠키를 Access Token의 대체 인증 수단으로 받는다고 선언하지 않는다.
- 계정 namespace별 Refresh Token 쿠키 이름·`Path`, 재발급·로그아웃 경로와 CSRF 헤더 이름은 `auth-account` spec과 OpenAPI에서 함께 확정한다.
- Spring Security 필터에서 발생한 `401`·`403`도 C-002의 JSON 오류 응답 직렬화기를 사용한다.

### AI 구현 지침

AI 또는 팀원이 보호 API를 구현할 때 다음 순서를 건너뛰거나 합치지 않는다.

```text
공개/보호 API 분류
  → 토큰 검증
  → 계정 namespace와 현재 계정 상태 검증
  → 역할·대상 매장 대표 운영자 FK 등 유스케이스 권한 검증
  → 인증된 주체로 범위가 제한된 자원 조회
  → 상태 전이·수용량·재고 등 도메인 규칙 실행
```

다음 구현은 금지한다.

- 요청 본문의 `consumerAccountId`, `storeOperatorAccountId`, `role` 또는 관리 매장 목록을 권한 근거로 사용
- 일반 사용자 토큰을 역할 값만 바꿔 매장 운영자 principal로 변환
- 다른 namespace의 JWT를 서명만 유효하다는 이유로 허용
- 예약 entity를 먼저 조회하고 다른 사람 소유일 때만 `403`으로 존재를 알림
- 권한 오류를 모두 공통 `500`, 공통 404 또는 임의의 `200` 응답으로 변환
- Controller마다 서로 다른 토큰 파싱·오류 JSON 코드를 중복 구현
- 일반 보호 API에서 Refresh Token 쿠키를 읽어 Access Token 없이 인증
- 클라이언트가 전송한 소유자 ID와 JWT subject가 같다는 비교만으로 도메인 소유권·대상 매장 대표 운영자 FK 검증을 대체

새 API를 추가하는 AI 작업 지시에는 최소한 다음 내용을 포함한다.

```text
인증 주체 namespace:
공개 또는 보호 API:
필요한 계정 상태:
필요한 역할·대상 매장 관리 권한:
개인 자원 소유권 조회 조건:
401·403·도메인 404 응답:
OpenAPI security 선언:
```

값을 알 수 없는 항목은 AI가 추측해 채우지 않고 해당 기능 spec·소유권 표의 승인을 먼저 요구한다.

### 기능별 오류 코드 경계

- 인증 자격, 계정 상태와 CSRF·Origin 검증 오류의 외부 코드는 `AuthErrorCode`가 소유한다.
- 대표 운영자 FK·운영 권한 오류는 매장 도메인이 판정하되 외부 `403` 코드의 정확한 소유 위치는 `store-search`와 `auth-account` 명세가 중복 없이 하나로 정한다.
- 개인 예약·메뉴 홀드·픽업 자원의 존재 은닉 404는 각 자원 소유 도메인의 `ErrorCode`가 소유한다.
- 정확한 `AUTH_###` 상수·메시지와 namespace별 인증 경로는 `auth-account` 기능 명세에서 확정한다. C-013만으로 임의 번호를 선점하지 않는다.

### 수용 조건

- 보호 API가 Access JWT Bearer 인증을 사용하고 Refresh Token 쿠키를 대체 인증 수단으로 사용하지 않는다.
- 토큰 누락·위조·만료·namespace 불일치가 `401`로 처리된다.
- 인증된 계정의 상태·역할·대상 매장 관리 권한 부족이 `403`으로 처리된다.
- 개인 자원의 실제 부재와 다른 사용자 소유가 같은 도메인 `404` 응답으로 처리된다.
- 개인 자원 repository·조회 포트가 인증 주체 ID를 조회 조건에 포함한다.
- 공개 자원의 변경 권한 부족을 존재 은닉 404로 바꾸지 않는다.
- Spring Security 필터 오류가 C-002의 오류 응답 형식을 사용한다.
- 기능별 OpenAPI에 공개·보호 여부와 가능한 `401`·`403`·도메인 `404`가 표현된다.
- 요청이 제공한 계정·역할·소유자·관리 매장 값이 권한 근거로 사용되지 않는다.
- AI가 미확정 인증 경로·쿠키 이름·외부 오류 코드 번호를 임의로 생성하지 않는다.

| 본인확인 외부 연동 | 공급자 중립 확인 참조, 실행 환경은 adapter 설정 전 `NOT CONFIGURED` | 확인 정책은 지키되 승인되지 않은 유료 제공업체·요청 형식을 AI가 임의 선택하지 않게 한다. |
| 검색 분류 코드 | catalog 조회 API의 불투명 code 사용 | 정확한 초기 분류값이 승인되기 전에 AI가 enum을 발명하거나 프론트가 별도 목록을 갖지 않게 한다. |
| 정렬 | API별 허용값 enum | 자유 문자열을 SQL·속성명으로 넘기거나 팀마다 다른 기본 정렬을 만드는 문제를 막는다. |
| 예약 중간 상태 | 외부 응답에서 `REQUESTED`, `CAPACITY_HELD` 제외 | 생성 트랜잭션 내부 상태를 사용자·프론트 계약으로 잘못 고정하지 않게 한다. |
| 메뉴 수정 | 전체 표현의 새 버전을 `PUT`으로 게시 | 필수 필드를 모두 받는 요청을 부분 수정 `PATCH`로 오해하지 않게 한다. |
| 운영자 픽업 취소 | 취소 명령 리소스와 중앙 수량 복구 | 범용 상태 PATCH나 수동 재고 수정으로 거래·수량 정합성을 깨뜨리지 않게 한다. |
| 운영자 재고 조회 | 날짜·메뉴 조건의 페이지 조회 | 관리 화면이 DB 직접 조회나 추측한 이전 수량으로 쓰기 요청을 만들지 않게 한다. |
| OpenAPI 서버 URL | 상대 URL `/` | 배포 도메인·포트를 발명하지 않으면서 엄격 검증의 서버 선언 요구를 만족하고 같은 origin의 `/api/v1` 경로를 사용한다. |
| 라이선스 표기 | `LicenseRef-All-Rights-Reserved` | 저장소에 승인된 LICENSE가 없는 상태에서 OpenAPI 도구 통과를 위해 Apache 등 제3자 라이선스를 임의 선언하지 않는다. |
| 검증 도구 | Redocly CLI `2.35.1`, `recommended-strict` 고정 | 검증되지 않은 최신 버전 자동 추종을 피하고 모든 팀원이 같은 규칙으로 재현하게 한다. |

공급자 중립 본인확인과 catalog code는 계약의 추측을 막는 경계다. 구체 제공업체 선택과 초기 catalog seed 승인은 구현 전에 별도 기록이 필요하며, 그전까지 AI는 실제 연동 성공이나 임의 분류값을 가정하지 않는다.
