# 1차 MVP 도메인·담당자 소유권

> 문서 상태: 2단계 도메인·담당자 소유권 완료
> 추적 Issue: [#25](https://github.com/sparta-spring4/Commerce-Final-Project-MiriYum/issues/25)
> 최종 변경일: 2026-07-28

이 문서는 확정된 팀원 분담을 바꾸지 않고, 여러 담당 영역이 만나는 기능의 데이터·상태·파일·API 소유권과 의존 방향을 기록한다. 승인되지 않은 경계는 구현 계약으로 사용하지 않는다.

## 확정 팀원 분담

| 팀원 | 구현 담당 |
|---|---|
| 1번 | 인증, 일반 사용자·매장 운영자 계정, JWT, 사용자 정보, 마이페이지 |
| 2번 | 매장, 검색, 운영자 기본 관리, 운영시간, 예약 시간대 설정 |
| 3번 | 예약 가능 판정, 예약 생성·취소, 예약 상태 전이, 중복·동시 예약 처리 |

이 표는 담당자를 다시 배정하기 위한 표가 아니다. 아래 소유권 결정은 이 분담을 유지하면서 직접 엔티티 수정, repository 공유와 중복 API 구현을 막기 위한 경계다.

## O-001 내 예약 내역 조회

### 담당과 소유권

- 1번 팀원은 마이페이지의 내 예약 내역 화면·사용자 흐름과 마이페이지 진입 경계의 구현을 담당한다.
- 3번 팀원과 예약 도메인은 예약 상태 의미, 내역 포함 범위, 정렬·필터 기준과 예약 조회 데이터 계약을 소유한다.
- 1번 팀원은 인증된 `consumer_account_id`를 예약 도메인의 공개 `ReservationHistoryQueryService`에 전달해 결과를 사용한다.
- 1번 팀원은 예약 entity나 repository를 직접 조회·수정하거나 별도의 예약 상태 해석 규칙을 만들지 않는다.
- 공개 HTTP 경로와 OpenAPI 문서 소유 위치는 `4. 공통 계약과 API 명세`에서 한 번만 확정한다. 인증·마이페이지와 예약 도메인이 같은 기능의 공개 API를 각각 만들지 않는다.

### 의존 방향

```text
마이페이지 화면·진입 경계 (1번)
            │
            ▼
예약 조회 Application Service·DTO (3번)
            │
            ▼
예약 데이터·상태 규칙 (3번)
```

### 변경 규칙

- 예약 내역의 상태 의미, 포함·제외 조건, 기본 정렬과 조회 DTO를 바꾸려면 3번 팀원의 검토가 필요하다.
- 마이페이지 표시·탭 구성·빈 상태·계정 화면 흐름을 바꾸려면 1번 팀원의 검토가 필요하다.
- 두 영역에 영향을 주는 변경은 한쪽이 상대 도메인 내부 파일을 직접 수정하지 않고 공개 계약 변경으로 제안한다.

### 인수 조건

- 마이페이지 예약 내역 구현에서 예약 repository·entity 직접 의존이 발견되지 않는다.
- 예약 상태 이름과 포함·정렬 기준이 예약 도메인의 공개 조회 계약과 일치한다.
- 동일한 목적의 마이페이지 예약 조회와 예약 도메인 조회 API가 중복 노출되지 않는다.

## O-002 매장 조회의 예약 가능 여부

### 담당과 소유권

- 2번 팀원과 매장 도메인은 매장 기본정보·운영시간, 예약을 받는 요일·시간대 설정과 매장 목록·상세·검색 조회 조합을 소유한다.
- 3번 팀원과 예약 도메인은 시간대별 전체 예약 가능 인원·팀 수, 기존 예약이 소비한 수용량, 요청 날짜·시간·인원에 따른 최종 예약 가능 여부를 소유한다.
- “매장이 언제 예약을 받는가”는 매장 도메인, “요청 조건으로 지금 실제 예약 가능한가”는 예약 도메인의 판정이다.
- 2번 팀원은 매장 조회에서 예약 도메인의 공개 `ReservationAvailabilityService`를 사용하고 예약 entity·repository·수용량 원장을 직접 조회하거나 자체 계산하지 않는다.
- 목록·검색의 여러 매장을 판정할 때에는 매장별 반복 호출이 아니라 예약 도메인이 제공하는 일괄 조회 계약을 사용한다.
- 공개 HTTP 경로와 OpenAPI 응답 조합은 `4. 공통 계약과 API 명세`에서 한 번만 확정한다. 매장 도메인과 예약 도메인이 같은 최종 가능 판정 API를 각각 노출하지 않는다.

### 의존 방향

```text
매장 목록·상세·검색 조합 (2번)
              │
              ▼
예약 가능 단건·일괄 조회 Service (3번)
              │
              ▼
예약 수용량·기존 예약·최종 판정 (3번)
```

### 변경 규칙

- 매장 운영시간과 예약 접수 요일·시간대 설정을 바꾸려면 2번 팀원의 검토가 필요하다.
- 예약 인원·팀 수 자원, 잔여 수용량 계산과 최종 가능 판정을 바꾸려면 3번 팀원의 검토가 필요하다.
- 양쪽 입력이 필요한 변경은 도메인 공개 Application Service와 DTO 계약을 먼저 변경하고 상대 도메인의 내부 entity·repository를 직접 수정하지 않는다.

### 인수 조건

- 매장 목록·상세·검색 구현에 예약 repository·entity 직접 의존과 별도 잔여 수용량 계산이 없다.
- 같은 요청 조건에 매장 조회와 예약 생성 사전 검증이 서로 다른 가능 여부를 계산하지 않는다.
- 여러 매장의 예약 가능 여부 조회가 매장 수만큼 반복되는 도메인 호출이나 DB 조회로 구현되지 않는다.

## O-003 메뉴 기본정보와 수량·홀드

### 담당과 소유권

- 2번 팀원과 매장 도메인은 `menu_id`, 메뉴명·설명·가격·카테고리, 대표 메뉴 여부와 검색 노출·게시 상태를 소유한다.
- 4번 팀원과 메뉴 홀드·픽업 도메인은 홀드·픽업 가능 여부, 날짜·시간대별 수량 원장, 잔여 수량, 품절·수량 복구, 메뉴 홀드와 픽업 예약을 소유한다.
- “무슨 메뉴인가”는 매장 도메인, “언제 몇 개를 홀드·픽업할 수 있는가”는 메뉴 홀드·픽업 도메인의 판정이다.
- 4번 팀원은 매장 도메인의 공개 메뉴 조회 계약과 `menu_id`를 사용하고 메뉴 기본정보 entity·repository를 직접 수정하지 않는다.
- 2번 팀원은 현재 홀드 가능 여부나 잔여 수량이 필요하면 메뉴 홀드·픽업 도메인의 공개 `MenuQuantityQueryService`를 사용하고 수량 원장을 직접 조회·계산하지 않는다.

### 상태와 검색 경계

- 메뉴의 검색 노출·게시 상태와 날짜·시간대별 재고·품절 상태를 하나의 enum이나 열로 합치지 않는다.
- 메뉴명·카테고리·대표 메뉴 조건은 2번 팀원과 매장 도메인이 판정한다.
- “현재 홀드 가능”, 잔여 수량과 품절 조건은 4번 팀원과 메뉴 홀드·픽업 도메인이 판정한다.
- 검색·상세 API가 두 결과를 함께 보여 주더라도 공개 HTTP 경로와 응답 조합은 `4. 공통 계약과 API 명세`에서 한 번만 확정한다.

### 의존 방향

```text
메뉴 기본정보·검색 (2번) ── menu_id ──▶ 수량·홀드·픽업 (4번)
          ▲                                  │
          └──── MenuQuantityQueryService ────┘
```

### 변경 규칙

- 메뉴명·가격·카테고리·대표 여부·게시 상태 변경은 2번 팀원의 검토가 필요하다.
- 홀드·픽업 자격, 수량 단위·원장·품절·복구 규칙 변경은 4번 팀원의 검토가 필요하다.
- 한쪽이 상대 도메인의 테이블 열이나 상태 enum을 편의상 추가·변경하지 않고 공개 계약 변경으로 제안한다.

### 인수 조건

- 메뉴 기본정보 entity에 날짜·시간대별 잔여 수량이나 홀드 거래 상태가 저장되지 않는다.
- 메뉴 수량·홀드 구현이 메뉴 기본정보 repository를 직접 수정하지 않는다.
- 게시 중이지만 해당 시간대 수량이 0인 메뉴와, 게시되지 않아 검색할 수 없는 메뉴가 서로 다른 상태로 판정된다.

## O-004 예약 취소와 메뉴 수량 복구

### 담당과 소유권

- 3번 팀원과 예약 도메인은 예약 취소 공개 명령·API, 취소 가능 여부, 예약 상태 전이와 전체 취소 유스케이스의 트랜잭션 조정을 소유한다.
- 4번 팀원과 메뉴 홀드·픽업 도메인은 예약에 연결된 메뉴 홀드 조회, 홀드 해제, 날짜·시간대별 수량 복구와 중복 해제 방지를 소유한다.
- 3번 팀원의 예약 취소 application service는 4번 팀원이 제공하는 공개 `MenuHoldReleaseService`를 호출한다.
- 3번 팀원은 메뉴 홀드·수량 entity나 repository를 직접 수정하지 않고, 4번 팀원은 예약 상태를 직접 변경하지 않는다.

### 트랜잭션과 멱등성

- 예약 취소 상태 전이와 연결 메뉴 홀드 해제·수량 복구는 하나의 MySQL 트랜잭션에서 함께 성공하거나 함께 롤백한다.
- 홀드 해제나 수량 복구가 실패하면 예약 취소도 확정하지 않고 부분 성공을 반환하지 않는다.
- 같은 취소 요청의 재시도는 예약·홀드 관계, 원 취소 사건과 멱등 키를 기준으로 같은 결과에 수렴한다.
- 이미 해제된 홀드의 수량을 다시 더하거나 이미 취소된 예약에 두 번째 취소 상태 전이를 만들지 않는다.
- 경합 자원은 상태 전이와 수량 원장이 정한 고정 순서로 잠그고, 교착·버전 충돌은 전체 명령을 안전하게 다시 실행할 수 있을 때만 제한 재시도한다.

### 의존 방향

```text
예약 취소 공개 명령·트랜잭션 조정 (3번)
                    │
                    ▼
        MenuHoldReleaseService (4번)
                    │
                    ▼
       홀드 해제·수량 원장 복구 (4번)
```

### 변경 규칙

- 예약 취소 자격·상태 전이·공개 요청 계약 변경은 3번 팀원의 검토가 필요하다.
- 홀드 해제·수량 복구·중복 방지 규칙 변경은 4번 팀원의 검토가 필요하다.
- 원자성이나 호출 순서를 바꾸는 변경은 두 담당자가 함께 검토하고 단일 트랜잭션 불변식을 유지한다.

### 인수 조건

- 예약 취소와 홀드 수량 복구 중 어느 하나만 반영된 상태가 커밋되지 않는다.
- 동일 취소 요청을 반복·동시 실행해도 예약은 한 번만 취소되고 홀드 수량은 한 번만 복구된다.
- 예약 도메인에 메뉴 수량 직접 갱신 SQL이 없고 메뉴 홀드·픽업 도메인에 예약 상태 직접 갱신 SQL이 없다.

## O-005 예약 생성과 선택 메뉴 홀드

### 담당과 소유권

- 3번 팀원과 예약 도메인은 일반 예약 생성 공개 API, 날짜·시간·인원·팀 수 수용량 검증과 전체 생성 유스케이스의 트랜잭션 조정을 소유한다.
- 4번 팀원과 메뉴 홀드·픽업 도메인은 선택 메뉴와 매장의 일치, 홀드 가능 여부·잔여 수량 검증, 메뉴 수량 차감과 `MenuHold` 생성을 소유한다.
- 예약 생성 요청의 메뉴 선택은 선택 항목이다. 메뉴를 건너뛰면 빈 메뉴 목록으로 같은 예약 생성 유스케이스를 사용하고 별도 “홀드 없음 예약” API를 만들지 않는다.
- 메뉴가 선택되면 3번 팀원의 예약 생성 application service가 4번 팀원이 제공하는 공개 `MenuHoldReserveService`를 호출한다.
- 3번 팀원은 메뉴 수량을 직접 차감하거나 메뉴 홀드 entity를 생성하지 않고, 4번 팀원은 일반 예약 entity나 예약 수용량을 직접 생성·차감하지 않는다.

### 트랜잭션과 실패

- 일반 예약과 선택 메뉴 홀드는 하나의 MySQL 트랜잭션에서 함께 확정한다.
- 예약 인원·팀 수 자원이나 선택 메뉴 수량 가운데 하나라도 부족하거나 검증할 수 없으면 전체 요청을 롤백한다.
- 예약이 없는 중간 메뉴 홀드, 메뉴 홀드가 누락된 부분 성공 예약과 일부 메뉴만 차감된 상태를 남기지 않는다.
- 동일 멱등 키 재시도는 같은 예약·메뉴 홀드 결과에 수렴하고 새 예약이나 추가 수량 차감을 만들지 않는다.
- 경합 자원은 승인된 고정 순서로 잠그며 구체적인 잠금·조건부 SQL 계약은 `3. 상태 전이와 논리 ERD` 및 `4. 공통 계약과 API 명세`에서 확정한다.

### 픽업 예약 경계

- 베이커리·카페 픽업 예약은 일반 예약 인원·팀 수를 소비하지 않는 별도 거래이며 4번 팀원과 메뉴 홀드·픽업 도메인이 공개 API·상태·수량·트랜잭션 전체를 소유한다.
- 픽업 예약을 만들기 위해 3번 팀원의 일반 예약 entity나 수용량 원장을 생성·호출하지 않는다.

### 의존 방향

```text
일반 예약 생성 공개 명령·트랜잭션 조정 (3번)
                      │
                      ▼
          MenuHoldReserveService (4번)
                      │
                      ▼
         홀드 생성·메뉴 수량 차감 (4번)

픽업 예약·수량·상태 (4번 단독)
```

### 인수 조건

- 메뉴 선택 여부와 관계없이 일반 예약 생성 공개 API는 하나다.
- 일반 예약과 선택 메뉴 홀드·수량 차감 중 일부만 커밋되지 않는다.
- 동일 요청의 반복·동시 실행에도 예약·홀드와 수량 차감이 각각 한 번만 확정된다.
- 픽업 예약 생성으로 일반 예약 행이나 예약 인원·팀 수 차감이 발생하지 않는다.

## O-006 매장 운영자의 예약 관리

### 담당과 소유권

- 2번 팀원과 매장 도메인은 매장 운영자 예약 관리 화면·진입 경로, 현재 운영자와 대상 매장의 소속 정보, 매장 선택·전환 UI를 소유한다.
- 3번 팀원과 예약 도메인은 일반 사용자·매장 운영자용 예약 조회 계약, 예약 확정·완료·방문 완료·취소 상태 전이, 상태 변경 공개 API와 예약 감사 정보를 소유한다.
- 매장 운영자 화면은 예약 도메인의 공개 조회·명령 계약을 사용하고 별도의 운영자용 예약 entity·repository·상태 전이 service를 만들지 않는다.
- 예약 도메인은 매장 도메인이 제공하는 공개 `StoreOperatorAccessService`로 현재 운영자의 대상 매장 소속과 매장 상태를 검증한다.
- 2번 팀원은 예약 상태를 직접 변경하지 않고, 3번 팀원은 매장 운영자-매장 소속 관계를 직접 생성·변경하지 않는다.

### 상태와 API 경계

- 일반 사용자 취소와 매장 운영자 상태 변경은 행위자와 허용 전이가 다르더라도 예약 도메인의 같은 상태 기계가 판정한다.
- 클라이언트가 보낸 역할·매장 ID만으로 운영자 명령을 승인하지 않고 현재 principal, 중앙 소속과 대상 매장 상태를 함께 검증한다.
- 정확한 사용자·운영자 HTTP 경로는 `4. 공통 계약과 API 명세`에서 확정하되 동일한 예약 조회·상태 변경 API를 매장 도메인과 예약 도메인이 중복 작성하지 않는다.

### 의존 방향

```text
매장 운영자 예약 관리 화면 (2번)
               │
               ▼
예약 조회·상태 변경 API와 상태 기계 (3번)
               │
               ▼
     StoreOperatorAccessService (2번)
```

### 변경 규칙

- 운영자 화면·매장 선택 흐름과 소속 데이터 변경은 2번 팀원의 검토가 필요하다.
- 예약 조회 의미·상태 전이·명령 요청과 응답 변경은 3번 팀원의 검토가 필요하다.
- 운영자에게 허용할 새 예약 전이는 예약 상태 기계와 소속 검증 계약을 함께 변경하며 어느 한쪽이 단독으로 우회 경로를 추가하지 않는다.

### 인수 조건

- 매장 도메인 패키지에 예약 entity·repository나 별도 예약 상태 기계가 없다.
- 유효한 매장 운영자 토큰만으로는 다른 매장의 예약을 조회·변경할 수 없다.
- 사용자·운영자 동시 상태 변경에도 예약 도메인의 허용 전이 하나만 확정되고 매장 화면의 로컬 상태가 원장을 덮어쓰지 않는다.

## O-007 매장 운영자 계정과 매장 소속

### 담당과 소유권

- 1번 팀원과 인증·계정 도메인은 `store_operator_accounts`, 매장 운영자 회원가입·로그인, 비밀번호·계정 상태, `store-operator` principal과 JWT namespace를 소유한다.
- 2번 팀원과 매장 도메인은 `stores`, `store_operator_store_affiliations`, 사업자 확인과 매장 등록, 운영자-매장 소속의 생성·변경·종료와 매장 승인·운영 상태를 소유한다.
- “누가 로그인했는가”는 인증·계정 도메인, “어느 매장을 관리할 수 있는가”는 매장 도메인의 판정이다.
- 1번 팀원은 매장 소속 entity·repository를 직접 생성·변경하지 않고, 2번 팀원은 계정 비밀번호·인증 상태·토큰을 직접 생성·변경하지 않는다.

### 가입·등록 흐름

- 매장 운영자 계정 가입과 매장 등록은 별도 단계로 처리한다.
- 1번 팀원의 계정 가입이 성공한 뒤, 2번 팀원의 매장 등록 흐름에서 인증된 `store_operator_account_id`와 새 매장의 소속 관계를 생성한다.
- 매장 등록 실패가 이미 생성된 계정의 비밀번호·인증 상태를 롤백하거나 임의 삭제하지 않는다. 사용자는 유효한 계정으로 매장 등록을 다시 시도한다.
- 같은 계정·매장 신청의 중복 소속 생성은 매장 도메인의 유일 제약과 멱등 계약으로 차단한다.

### 인증과 권한 검증

- JWT는 `store-operator` 계정 유형과 subject를 증명하지만 클라이언트가 선택한 매장 ID나 변경 가능한 매장 목록을 권한 근거로 사용하지 않는다.
- 매장 명령마다 매장 도메인의 공개 `StoreOperatorAccessService`로 현재 계정 상태, 대상 매장 소속과 매장 승인·운영 상태를 검증한다.
- 계정 정지나 토큰 namespace 불일치는 인증·계정 경계에서, 소속 종료·다른 매장·매장 상태 불일치는 매장 권한 경계에서 거부한다.

### 의존 방향

```text
매장 운영자 계정·principal·JWT (1번)
                  │
                  ▼ store_operator_account_id
매장 등록·소속·운영 권한 (2번)
                  │
                  ▼
     StoreOperatorAccessService (2번)
```

### 변경 규칙

- 매장 운영자 가입·로그인·계정 상태·토큰 계약 변경은 1번 팀원의 검토가 필요하다.
- 매장 등록·소속·매장 상태와 매장 명령 권한 변경은 2번 팀원의 검토가 필요하다.
- 계정과 소속을 함께 요구하는 기능은 두 공개 계약을 조합하며 공통 `User` entity나 역할 열을 새로 만들지 않는다.

### 인수 조건

- `store_operator_accounts`에 관리 매장 목록이나 매장별 권한 열을 중복 저장하지 않는다.
- `store_operator_store_affiliations`에 비밀번호·토큰·인증 자격정보를 저장하지 않는다.
- 유효한 운영자 JWT라도 현재 대상 매장 소속이 없거나 매장 상태가 요청을 허용하지 않으면 매장 명령이 거부된다.
- 매장 등록 실패 뒤 계정으로 다시 로그인하고 같은 등록 흐름을 안전하게 재시도할 수 있다.

## O-008 베이커리·카페 픽업 자격

### 담당과 소유권

- 2번 팀원과 매장 도메인은 사업자 정보·공식 진위확인 결과, 중앙 카페·베이커리 자격 상태, 자격 판정에 사용한 정책·매핑 버전과 공개 `StorePickupEligibilityService`를 소유한다.
- 4번 팀원과 메뉴 홀드·픽업 도메인은 픽업 가능 메뉴·수량·시간대, 픽업 예약 생성·취소·상태와 픽업 수량 차감·복구를 소유한다.
- “이 매장이 픽업 기능을 사용할 자격이 있는가”는 매장 도메인, “어떤 메뉴를 언제 몇 개 픽업 예약할 수 있는가”는 메뉴 홀드·픽업 도메인의 판정이다.
- 4번 팀원은 픽업 기능 활성화와 예약 생성 때 2번 팀원이 제공하는 `StorePickupEligibilityService`를 사용하고 사업자 업종을 자체 해석하거나 별도 자격 상태를 만들지 않는다.
- 2번 팀원은 픽업 예약·상태·수량 entity나 repository를 직접 생성·변경하지 않는다.

### 자격과 일반 기능 경계

- 매장·메뉴 검색 카테고리, 태그나 운영자가 선택한 `카페·베이커리` 표시만으로 픽업 자격을 만들거나 변경하지 않는다.
- 공식 진위확인 업종과 버전된 허용 매핑으로 확정한 중앙 자격만 픽업 활성화·생성 근거로 사용한다.
- 픽업 자격이 없거나 검증할 수 없으면 픽업 기능만 실패 폐쇄하고 일반 매장 등록·검색·일반 예약을 중단하거나 취소하지 않는다.
- 픽업 자격 정책·매핑 버전이 바뀌어도 이미 확정된 거래를 임의 변경하지 않고 이후 활성화·생성 요청부터 현재 자격을 검증한다.

### 의존 방향

```text
사업자 검증·픽업 자격 상태 (2번)
                │
                ▼
 StorePickupEligibilityService (2번)
                │
                ▼
픽업 메뉴·수량·예약·상태 (4번)
```

### 변경 규칙

- 사업자 검증 입력, 업종 매핑과 픽업 자격 상태 변경은 2번 팀원의 검토가 필요하다.
- 픽업 메뉴 자격, 시간대·수량·예약 상태와 복구 규칙 변경은 4번 팀원의 검토가 필요하다.
- 픽업 기능을 새 매장 유형에 허용하려면 매장 자격 계약과 픽업 거래 계약을 함께 검토하고 검색 분류만 바꾸어 우회하지 않는다.

### 인수 조건

- 검색 카테고리만 카페·베이커리로 바꿔도 픽업 기능이 활성화되지 않는다.
- 유효한 중앙 자격이 없는 매장의 픽업 예약은 실패하지만 일반 매장 조회와 일반 예약은 계속 가능하다.
- 메뉴 홀드·픽업 도메인에 사업자 업종 자체 판정이나 두 번째 픽업 자격 원장이 없다.

## O-009 파일·패키지·API·마이그레이션 소유권

### 용어와 코드 의존 규칙

- 이 문서의 `도메인 공개 Application Service`는 네트워크 포트가 아니라 다른 도메인이 사용하도록 소유 도메인이 공개한 Java 인터페이스와 DTO다.
- 다른 도메인은 소유 도메인의 `application/api` 계약만 사용하고 entity·repository·내부 service·infrastructure 구현을 직접 참조하지 않는다.
- 필요한 기능이 공개 계약에 없으면 소유 담당자와 인터페이스·메서드·DTO 변경을 합의하고 해당 담당자의 검토를 받는다.
- 아직 제품 런타임이 구성되지 않았으므로 아래 패키지 경로는 소유권만 예약한다. 빈 패키지·entity·API·마이그레이션은 실제 승인 기능 구현을 시작할 때 생성한다.

| 팀원 | 소유 도메인·주요 데이터 | 공개 API 최종 관리 | 예약 패키지 경로 | 기능 명세·OpenAPI |
|---|---|---|---|---|
| 1번 | 일반 사용자·매장 운영자 계정, 인증 자격·계정 상태, 사용자 프로필·마이페이지 진입 | 회원가입·로그인·재발급·로그아웃, 사용자 정보, 내 예약 내역 | `com.miriyum.auth` | `docs/specs/auth-account/` |

정확한 물리 테이블 이름과 FK는 `3. 상태 전이와 논리 ERD`에서 확정한다. 이미 확정된 `consumer_accounts`, `store_operator_accounts`, `store_operator_store_affiliations`, `stores`와 계정 물리 분리 계약은 그대로 사용한다.

### 중복 가능 공개 API의 최종 관리 책임

| 사용자 기능 | OpenAPI 최종 관리 | 함께 검토할 소유자 |
|---|---|---|
| 마이페이지 내 예약 내역 | 1번 `auth-account` | 3번: 예약 상태·조회 조건·예약 DTO |
| 매장 목록·상세·검색의 예약 가능 여부 | 2번 `store-search` | 3번: 예약 가능 판정·가용성 DTO |
| 일반 예약 생성과 선택 메뉴 홀드 | 3번 `reservation` | 4번: 메뉴 홀드 요청·수량·오류 |
| 예약 취소와 메뉴 수량 복구 | 3번 `reservation` | 4번: 홀드 해제·수량 복구·오류 |
| 매장 운영자의 예약 조회·상태 변경 | 3번 `reservation` | 2번: 매장 소속·매장 상태 검증 |
| 베이커리·카페 픽업 예약 | 4번 `menu-hold-pickup` | 2번: 매장 픽업 자격 |

- 최종 관리 담당자는 같은 사용자 목적의 중복 HTTP API를 하나로 정리하고 OpenAPI 파일과 최종 요청·응답 위치를 관리한다.
- 요청·응답에 포함된 다른 도메인의 상태·필드·오류 규칙은 해당 도메인 소유자가 검토하며 최종 관리 담당자가 임의로 바꾸지 않는다.
- 하나의 사용자 명령이 여러 도메인을 변경하면 승인된 조정 유스케이스의 API 하나를 사용하고, 프런트엔드가 도메인별 쓰기 API를 순서대로 호출해 원자성을 대신하지 않는다.

### 마이그레이션과 공통 계약

- Flyway는 하나의 공통 디렉터리를 사용하되 각 테이블의 도메인 소유자가 마이그레이션을 작성하고 검토한다.
- 다른 도메인 테이블을 참조하는 FK·유일 제약·삭제 정책은 양쪽 도메인 소유자가 함께 검토한다.
- 이미 적용된 Flyway 마이그레이션을 수정하지 않고 새 버전의 마이그레이션을 추가한다.
- `docs/specs/mvp1-common/`의 변경은 영향받는 모든 도메인 소유자가 검토한다.
- 공통 성공·예외·검증 응답, 날짜·시간·타임존, 페이지네이션과 멱등성처럼 전체 API에 적용되는 계약은 네 명 모두 검토한다.
- 상대 담당자의 소유 파일 변경이 필요하면 별도 중복 구현을 만들지 않고 변경 목적과 계약 영향을 공유한 뒤 소유자의 검토를 받는다.

### 구조 검증 조건

- 다른 도메인의 entity·repository·내부 service를 직접 import하는 의존이 없다.
- 각 공개 HTTP 경로와 OpenAPI operation은 최종 관리 담당자가 한 명으로 식별된다.
- 동일 사용자 목적의 API와 상태 전이 구현이 서로 다른 담당 패키지에 중복 존재하지 않는다.
- 공통 계약 변경과 교차 도메인 FK에 필요한 공동 검토자가 누락되지 않는다.
