# 기능 명세: 매장·검색·운영자 기본 관리

> 문서 상태: 4단계 승인
> 적용 단계: 1차 MVP, 2차 MVP
> 도메인 소유자: 2번 팀원 — 매장·검색
> 협업 검토: 3번 팀원 — 예약 가용성, 4번 팀원 — 메뉴 수량 가용성
> 관련 정책 ID: STORE-002~STORE-007, STORE-014, OPER-002~OPER-010, S-005, S-007, E-002, C-001~C-013
> OpenAPI: `docs/specs/store-search/openapi.yaml`
> 최종 승인일: 2026-07-31

## 범위

### 포함

- 서울·부산·대구·대전·광주의 공개 매장 목록·검색·상세
- 매장명·메뉴명·지역명 키워드 검색
- 2차 MVP의 결정적 통합 검색·QueryDSL 조건·검증 좌표 반환
- 매장·메뉴 카테고리와 매장 태그 catalog 조회
- 요청 조건이 있을 때 예약 가능 여부 조합
- 매장 운영자의 매장 등록·수정
- 정규 영업시간과 예약 접수 시간대 관리
- 메뉴 기본정보·대표 메뉴·공개·판매 제어 관리

### 제외

- 사용자 현재 위치·거리순·반경 검색
- 이미지·파일 업로드와 S3
- 플랫폼 운영자 심사·사건 큐
- 결제·정산·리뷰·웨이팅
- 메뉴 시간대별 재고 수량과 픽업 거래 상태 관리

## 공개 탐색 계약

`GET /api/v1/stores` 하나에서 다음 조건을 조합한다.

| 조건 | 의미 |
| --- | --- |
| `keyword` | 매장명·게시 메뉴명·지역 표시명에 대한 1차 MVP 텍스트 포함 검색 |
| `region` | `SEOUL`, `BUSAN`, `DAEGU`, `DAEJEON`, `GWANGJU` |
| `storeCategoryCode` | 중앙 catalog에서 받은 매장 주 카테고리 코드 |
| 예약 조건 | `serviceDate`, `startTime`, `partySize`를 모두 보낸 경우에만 가용성 판정 |
| `includesInfants` | 영유아가 한 명 이상 포함되면 `true`, 생략하면 `false` |
| `availableOnly` | 완전한 예약 조건이 있을 때만 `true` 허용 |

예약 조건 일부만 보내거나 `availableOnly=true`인데 완전한 예약 조건이 없으면 `COMMON_001`로 거부한다. 임의 기본 날짜·시간·인원으로 가용성을 추측하지 않는다.
`endTime`은 클라이언트가 보내지 않으며 서버가 해당 매장의 현재 예약 접수 시간대·서비스 소요·전환 정책으로 계산한다. 이 계산은 실제 예약 생성과 같은 예약 도메인 계약을 사용한다.

### 예약 가능 매장 검색 후보 상한

- `availableOnly=true` 검색은 선택한 고정 정렬에서 먼저 매칭되는 공개 후보를 최대 5,000개까지만 예약 가용성 평가 대상으로 삼는다. 서버 설정과 SQL `LIMIT`이 같은 상한을 강제하며 클라이언트가 이 값을 늘릴 수 없다.
- 이 경로의 `totalElements`는 전체 저장소의 매칭 수가 아니라 위 최대 5,000개 후보 안에서 `AVAILABLE`로 판정된 정확한 수다. 페이지 결과도 같은 제한 후보와 정렬을 사용하므로 서로 다른 범위의 합계와 내용을 섞지 않는다.
- 후보 상한은 예약 가용성 평가의 요청당 메모리와 일괄 조회 횟수를 제한하기 위한 1차 MVP 계약이다. 일반 검색과 상세 조회의 공개 여부·필터·정렬 계약을 바꾸지 않는다.
- 운영 관측에서 단일 검색 조건의 공개 후보가 4,000개에 도달하면 별도 가용성 읽기 모델 또는 모든 청크가 공유하는 일관 스냅샷의 설계를 시작한다. 5,000개에 도달하면 다음 배포 전에 전환해 정렬상 뒤쪽 후보가 탐색 범위에서 제외되지 않게 한다.
- 후보 수와 무관하게 전체 매장 기준의 정확한 `totalElements`가 제품 요구가 되거나 검색 응답시간·메모리 사용량이 승인된 운영 기준을 넘으면 같은 전환을 앞당긴다. 전환 전까지 상한을 설명 없이 높이거나 제거하지 않는다.

### 공개 조회 요청 제한

- `GET /api/v1/stores`, `GET /api/v1/stores/{storeId}`, `GET /api/v1/stores/{storeId}/menus`는 `SCALE-005`의 공개 조회 등급을 공유하며 IP당 60초에 60회로 제한한다.
- 세 경로는 경로별 한도를 따로 갖지 않고 같은 IP의 공개 매장 조회 합계를 하나의 중앙 카운터로 계산한다. 1차 MVP에서는 기존 MySQL `rate_limit_windows`의 원자적 갱신을 재사용해 여러 애플리케이션 인스턴스의 합계를 판정한다.
- 한도를 넘은 요청은 컨트롤러와 예약 가용성 조회를 실행하기 전에 `429`, `COMMON_010` 공통 오류 envelope와 다음 허용까지 남은 초를 담은 `Retry-After` 헤더를 반환한다.
- 운영 배포에서는 외부에 열린 Nginx만 원본 IP 헤더를 만들 수 있다. Nginx는 클라이언트가 보낸 값과 무관하게 `X-Real-IP`를 `$remote_addr`로 덮어쓰고, backend 포트는 호스트 loopback과 내부 Docker 네트워크에만 둔다.
- Docker 네트워크에서 Nginx 주소를 고정하고 Spring/Tomcat의 native forwarded-header 처리는 그 주소만 내부 프록시로 신뢰한다. `X-Real-IP`를 remote IP 원본으로 사용하므로 필터의 servlet remote address는 실제 사용자 IP가 되며, 신뢰 프록시 밖에서 직접 보낸 `X-Real-IP`와 `X-Forwarded-For`는 제한 키를 바꾸지 못한다.
- 회귀 검증은 서로 다른 Nginx 전달 원본 IP가 별도 공개 조회 버킷을 사용하고 같은 원본 IP는 세 경로의 한도를 공유하는지, 신뢰 프록시 밖의 위조 헤더가 무시되는지, Nginx·Compose·Spring 설정이 같은 고정 프록시 주소 계약을 갖는지 확인한다.
- 같은 `/api/v1/stores/**` namespace라도 위 세 공개 GET 계약에 해당하지 않는 요청은 공개 조회 한도를 소비하는 대신 기존 보안 체인에서 거부한다.

검색 결과의 `reservationAvailability`는 다음 값을 사용한다.

- `NOT_REQUESTED`: 예약 조건이 없어 계산하지 않음
- `AVAILABLE`: 요청한 모든 구간에서 인원 수와 팀 1건을 확보할 수 있음
- `UNAVAILABLE`: 영업·접수 시간·수용량 가운데 하나 이상이 부족

2번 도메인은 수용량을 직접 계산하거나 저장하지 않고 3번 도메인의 `ReservationService`가 제공하는 예약 가능 일괄 조회 공개 메서드를 사용한다. `partySize`와 `includesInfants`는 이 공개 DTO에 그대로 전달한다. 메뉴 홀드 가능 수량이 상세에 필요하면 4번 도메인의 조회 계약을 사용하며 메뉴 재고 repository를 직접 참조하지 않는다.

### 검색 구현 선택

1차 MVP는 MySQL `utf8mb4_0900_ai_ci` collation과 parameter-bound `LIKE`를 사용한 단순 포함 검색으로 제한한다. 서버는 입력 공백·대소문자와 SQL wildcard를 정규화·escape하고 클라이언트가 SQL 표현이나 정렬 열을 직접 선택하지 못하게 한다. 양쪽 wildcard를 쓰는 포함 검색에는 B-tree가 키워드 탐색을 보장하지 않으므로 이를 검색 인덱스로 오인하지 않는다. V22의 복합 인덱스는 공개 매장 범위·고정 정렬과 현재 게시 메뉴 join 후보를 줄이는 용도이며, 키워드 검색량이 이 방식의 한계를 넘으면 별도 승인된 전문 검색 단계로 이관한다. QueryDSL 고급 필터, 전문 검색 엔진, 위치 검색과 개인화 점수는 뒤 단계다.

이 선택은 검색 품질보다 계약과 소유권을 먼저 검증하고 새 의존성을 억지로 넣지 않기 위한 것이다.

## 2차 MVP 통합 검색 계약

### 기존 API 호환과 입력 모드

`GET /api/v1/stores`는 1차 MVP 페이지 검색과 2차 MVP 통합 검색을 같은 공개 경로에서 제공한다. `searchInput`이 없으면 기존 `keyword`, `region`, `storeCategoryCode`, 예약 조건과 `page` 계약을 그대로 사용한다. 공백이 아닌 1~100자의 `searchInput`이 있으면 다음 통합 검색 계약을 사용한다.

- 통합 검색은 `searchInput`, `includesInfants`, `availableOnly`, `sort`, `cursor`, `size`만 허용한다. 1차 MVP의 `keyword`, `region`, `storeCategoryCode`, `serviceDate`, `startTime`, `partySize`, `page`와 혼용하면 `COMMON_001`로 거부한다.
- `includesInfants=true`와 `availableOnly=true`는 해석 결과에 날짜·시각·인원이 모두 있을 때만 허용한다. 일부 예약 조건은 추측으로 채우지 않고 warning과 남은 일반 키워드로 축소한다.
- 통합 검색의 기본 정렬은 `relevance,desc`, 기본 크기는 20, 최대 크기는 50이다. `recommendation,desc`는 현재 검색 필수 조건을 통과한 후보를 `history-v1`으로 재정렬한다. cursor는 서버 비밀키로 HMAC 인증한 불투명 문자열이며 payload가 변조되거나 정규화 입력 조건, `includesInfants`, `availableOnly`, 정렬, 크기 또는 인증 주체 범위가 달라진 요청에 재사용하면 `COMMON_001`로 거부한다. 인증 주체 범위는 원본 사용자 ID를 payload에 노출하지 않고 별도 HMAC 문맥에서 만든 익명 또는 소비자별 불투명 값으로 결합한다. 서버 비밀키가 회전하면 기존 cursor는 만료된 것으로 취급한다.
- `GET /api/v1/stores`는 인증 헤더가 없는 요청도 허용한다. 유효한 소비자 Access Bearer가 있으면 추천 정렬에 자기 이력을 가산하고, 헤더를 제출했지만 형식·서명·만료·용도·namespace가 유효하지 않으면 익명으로 축소하지 않고 `AUTH_###` 401로 거부한다.
- 통합 검색 응답은 기존 페이지 응답과 구분되는 `IntegratedStoreSearchData`를 사용한다. `items`, `normalizedCondition`, `warnings`, `ruleVersion`, `vocabularyVersion`, `rankingRuleVersion`, `nextCursor`를 반환하고 정확한 전체 건수나 페이지 번호를 추측하지 않는다. `rankingRuleVersion`은 추천 정렬에서 `history-v1`, 다른 정렬에서 `null`이다. 각 항목의 `recommendationReason`은 추천 정렬에서 실제 최고 양의 기여 요인의 코드·문구, 다른 정렬에서 `null`이며 내부 점수·가중치·이용 횟수는 노출하지 않는다.

### 결정적 해석과 승인 사전

- `RuleInterpreter`는 `Asia/Seoul`과 서버 `Clock`을 사용해 상대 날짜를 해석하고, 승인된 Region 및 활성 Catalog의 `code`와 `displayName`만 사전 별칭으로 사용한다.
- Catalog 운영 CRUD가 없는 2차 MVP에서는 승인 seed 버전 `catalog-v1`을 사전 버전으로 사용한다. 코드·표시명·버전이 바뀌는 후속 단계는 사전 버전도 함께 변경해야 한다.
- 해석된 지역·매장 카테고리·메뉴 카테고리·태그·가격·인원·날짜·시각과 남은 일반 키워드를 정규화 조건으로 반환한다.
- 부분·중복·모호 표현은 구조화 조건으로 사용하지 않는다. warning은 민감한 원문 조각 없이 code와 field만 반환하고, 해석하지 못한 표현은 남은 일반 키워드의 매장명·게시 메뉴명·지역·주소 포함 검색으로 보존한다.

### 후보 조회, 최신 상태 재검증과 좌표

1. QueryDSL은 승인된 구조화 조건과 남은 일반 키워드로 MySQL 공개 후보를 조회한다.
2. 관련도는 남은 키워드의 `매장명 정확 일치 → 매장명 포함 → 게시 메뉴명 포함 → 지역·주소 포함 → 구조화 조건만 일치`의 고정 tier로 계산하고, 같은 tier는 매장명 오름차순과 매장 ID 오름차순으로 정렬한다. 임의 실수 가중치나 개인 이력은 사용하지 않는다.
3. 후보를 최대 200개씩 Store 공개 상태와 `ReservationService.getAvailabilities`로 일괄 재검증한다. 응답 직전에 Store 공개·운영·예약 모드를 다시 읽고 불일치, 누락 또는 순서 오류는 해당 후보를 실패 폐쇄한다.
4. `availableOnly=true`는 같은 정적 관련도 순서를 계속 스캔하며 `AVAILABLE` 후보만 응답 크기까지 채운다. 예약 시각은 모든 후보에 동일한 요청 조건이므로 정렬 숫자로 만들지 않는다. 다음 가능 시간 탐색은 Reservation의 별도 공개 계약 없이는 제공하지 않는다.
5. cursor는 마지막으로 스캔한 정적 후보의 관련도 tier·매장명·매장 ID와 검색 fingerprint를 담고 전체 payload를 HMAC-SHA-256으로 인증한다. 최신 가용성 변경은 표시·제외 여부만 바꾸고 seek 순서를 바꾸지 않는다.
6. 공개 좌표는 현재 주소 버전의 `VERIFIED` latitude·longitude만 반환한다. `UNVERIFIED` 또는 주소 버전 불일치 좌표는 `null`이며 검색 요청 중 Kakao Local API를 호출하지 않는다.
7. `recommendation,desc`는 정적 관련도 순으로 최대 5,000개 후보를 같은 요청 스냅샷에서 수집·최신 검증한 뒤 `history-v1`으로 전체 재정렬한다. 추천 cursor는 완전한 추천 동점 키와 검색 fingerprint를 HMAC 인증하며 다음 페이지에서도 같은 bounded 후보 집합을 재계산해 seek한다.

`reservationAvailability`는 조회 시점의 발견 보조 정보이며 수량 확보나 예약 성공을 보장하지 않는다. 실제 예약 생성은 Reservation 도메인의 쓰기 트랜잭션에서 현재 영업·접수 시간·수용량을 다시 검증한다.

### 오류·개인정보·검증

- 빈 입력, 길이 초과, 모드 혼용, 허용하지 않은 정렬, 변조·불일치 cursor는 `COMMON_001` 400이다.
- 예약 일괄 결과의 크기·순서·매장 ID가 요청과 다르거나 최신 Store 상태를 확인할 수 없으면 성공을 추측하지 않고 해당 후보를 제외한다.
- 사용자 현재 위치·위치 권한·정밀 위치는 요청하지 않는다. `searchInput` 원문과 warning 원문 조각은 영속화·감사·애플리케이션 로그에 기록하지 않는다.
- Service 단위 테스트는 해석 fallback, 관련도 tier, cursor, 일괄 결과 불일치와 최신 상태 제거를 검증한다. MockMvc와 OpenAPI 대조는 두 입력 모드·validation·응답 one-of를 검증한다. Testcontainers MySQL은 QueryDSL 후보, 메뉴 포함 검색, 상태 변경 재검증과 `availableOnly` chunk fill을 검증한다.

## 카테고리와 태그 catalog

- 매장은 주 카테고리 코드를 정확히 1개 가진다.
- 메뉴는 주 카테고리 코드 1개와 서로 중복되지 않는 보조 카테고리 코드 0~5개를 가진다.
- 매장 태그는 중앙 허용 catalog에서만 선택한다.
- 메뉴 로컬 태그는 해당 매장에서만 사용하는 텍스트이며 검색 보조 정보다.
- 공식 사업자 주업태명·주종목명과 검색 카테고리·태그는 서로 변환하지 않는다.

정책에 정확한 category code 목록이 아직 없으므로 OpenAPI에서 임의 enum을 발명하지 않는다. 프론트엔드는 다음 catalog API의 `code`를 그대로 제출한다.

- `GET /api/v1/store-categories`
- `GET /api/v1/menu-categories`
- `GET /api/v1/store-tags`

catalog code는 불투명한 문자열이며 클라이언트가 영문 이름을 추측하거나 표시명을 코드로 보내지 않는다. 정확한 seed와 버전은 구현 시작 전 매장 도메인 소유자가 승인해야 하며, 승인되지 않은 값은 `STORE_004`로 거부한다.

## 매장 등록과 상태

- `POST /api/v1/store-operators/stores`는 인증된 매장 운영자 계정으로 새 매장 신청을 만든다.
- 요청의 운영자 ID나 역할 값은 받지 않고 JWT subject를 사용한다.
- 사업자등록번호와 업종 구분 `CAFE`, `BAKERY`, `OTHER`를 구조화 입력한다.
- 1차 MVP는 사업자등록번호 형식과 중앙 영구 중복을 검증한다. 한 번 매장에 귀속된 번호는 폐점 후에도 일반 등록에서 재사용할 수 없으며, 재개·이전·복구는 향후 플랫폼 운영자 전용 절차로 분리한다. 사전 사업자 진위·업종 기준 데이터 비교, 국세청 공식 진위조회와 플랫폼 운영자 심사는 사용하지 않는다.
- 형식과 중복 검사를 통과한 신청은 즉시 `APPROVED`로 매장을 생성한다.
- 사업자등록증 이미지·파일 URL을 받지 않는다.
- 신청자는 `applicantSelfAttested=true`와 `requiredTermsAgreed=true`를 함께 제출해야 한다. 서버는 두 동의 시각과 필수 약관 버전 `STORE_ONBOARDING_REQUIRED_TERMS_V1`을 매장에 기록한다.

입점 검증과 운영 상태는 각각 다음 축으로 반환한다. 픽업 사용 여부는 별도 상태 축 없이 `modes.pickupEnabled`로 반환한다.

| 축 | 값 |
| --- | --- |
| `verificationStatus` | `APPROVED` |
| `operationStatus` | `OPEN`, `TEMPORARILY_CLOSED`, `CLOSED` |
등록 업종과 검색 카테고리·태그는 픽업 사용 여부를 제한하지 않는다. `CAFE`, `BAKERY`, `OTHER` 모두 등록·수정 요청에서 `modes.pickupEnabled=true`를 선택할 수 있다.

## 2차 MVP 주소 검증과 좌표 저장

- 매장 등록과 `address` 또는 `region`을 포함한 기본정보 수정은 외부 지오코딩 결과가 정확히 한 건이고, 요청의 유효 주소 및 `Region`과 일치할 때만 좌표를 저장한다. 정식 주소 뒤에는 층·호·동·실·관·빌딩·건물·상가 형태의 상세주소 token만 허용하고 두 번째 주소나 일반 문장은 거절한다. 주소만 수정하면 현재 `Region`을, `Region`만 수정하면 현재 주소를 함께 검증한다.
- 검색 가능한 결과가 없거나 여러 건이거나 주소·지역이 일치하지 않으면 `COMMON_001` 400으로 전체 명령을 거절한다. 설정 누락, 시간 초과, 한도 초과, 외부 서비스 오류 또는 해석 불가능한 응답은 `COMMON_012` 503으로 거절하며 실패한 매장 행이나 부분 변경을 남기지 않는다.
- 외부 호출은 DB 트랜잭션 밖에서 수행한다. 저장 직전에 주소와 지역의 버전을 다시 확인하고 선행 검증 이후 값이 바뀌었으면 `COMMON_008` 409로 거절한다. 검증 좌표와 매장 변경, 멱등 결과는 하나의 트랜잭션으로 확정한다.
- 기존 매장은 migration에서 `UNVERIFIED`, 좌표 없음, `addressVersion=1`로 이행한다. 운영자 응답의 `geocoding`은 `status`, `latitude`, `longitude`, `verifiedAddress`, `verifiedAt`, `addressVersion`만 공개하고 외부 제공자명·응답 원문·내부 버전은 노출하지 않는다.
- 공개 검색·상세·추천은 저장된 `VERIFIED` 좌표만 사용하며 요청 처리 중 외부 지오코딩 서비스를 호출하지 않는다. `UNVERIFIED` 매장은 좌표가 필요한 기능에서 제외하거나 좌표 없음으로 처리하고 텍스트 기반 1차 MVP 검색은 유지한다.

## 운영 시간과 예약 접수 시간대

### 주간 설정과 매장 시간대

- 영업시간과 예약 접수 시간대는 서로 독립된 불변 버전 스트림이다.
- 두 초안 저장 `PUT`은 7개 요일을 중복 없이 모두 포함한 전체 주간 설정을 받으며, 일부 요일만 조용히 병합하지 않는다. 요일이나 시간 구간 배열의 `null` 요소를 허용하지 않는다.
- 정규 영업시간은 요일별 0개 이상의 `[startTime, endTime)` 구간이다. 영업시간·브레이크타임·예약 접수 구간은 종류별·요일별 최대 48개이며 시각 JSON은 `HH:mm`만 허용한다.
- 브레이크타임은 영업 구간과 별도 구간으로 관리하며 하나의 영업 구간 안에 완전히 포함되어야 한다. 모든 구간은 0 길이와 실제 시간 중첩을 허용하지 않는다.
- 자정을 넘는 구간은 시작 요일에 귀속하며 일요일–월요일 주간 경계까지 실제 시간 중첩을 검사한다.
- 예약 접수 시간대는 실제 영업시간 안에 있어야 하며 브레이크타임과 겹치지 않는다. 예약 접수 버전은 검증에 사용한 영업시간 버전 ID를 보관한다.
- 매장은 IANA `timeZoneId`를 가진다. 신규 매장 등록은 유효한 IANA 값을 필수로 받고 일정 계산에서 JVM·운영체제 기본 시간대나 주소 기반 추측을 사용하지 않는다. 기존 매장은 migration에서 `Asia/Seoul`로 이행한다. 활성·예약 일정의 효력 해석을 바꾸는 일반 매장 수정 API에서는 시간대를 변경하지 않으며 별도 시간대 변경 절차는 후속 범위다.

### 초안·게시·취소 수명주기

- `PUT /api/v1/store-operators/stores/{storeId}/operating-hours`와 `PUT /api/v1/store-operators/stores/{storeId}/reservation-time-slots`는 제출한 전체 주간 설정을 새 불변 `DRAFT` 버전으로 저장할 뿐 게시하지 않는다.
- 초안 내용은 제자리에서 수정하지 않는다. 변경하려면 새 초안 버전을 저장하고, 게시할 버전 번호를 명시한다.
- `POST .../{version}/publications`은 저장된 초안에만 사용할 수 있다. `publicationMode=IMMEDIATE`는 중앙 확정 시각에 활성화하고, `publicationMode=SCHEDULED`는 미래 `effectiveAt`을 예약한다. `effectiveAt`은 오프셋을 포함한 RFC 3339 date-time이며 서버는 이를 중앙 `Instant`로 저장하고 응답에 매장 `timeZoneId`를 함께 반환한다. `SCHEDULED`에는 `effectiveAt`이 필수이고 `IMMEDIATE`에는 허용하지 않는다.
- 게시 명령은 비어 있지 않은 `changeReason`을 항상 요구한다. 초안 저장 자체에는 변경 사유를 요구하지 않지만 게시 감사에 사유를 보존한다.
- `POST .../{version}/publication-cancellations`은 비어 있지 않은 `changeReason`을 받고 아직 효력이 발생하지 않은 `SCHEDULED` 버전에만 사용할 수 있다. 성공하면 예약 시각을 제거하고 버전을 `DRAFT`로 되돌려 내용은 유지한다. 이미 활성화된 버전은 취소할 수 없으며 되돌리려면 이전 내용을 복제한 새 초안을 게시한다.
- 버전 상태는 `DRAFT`, `SCHEDULED`, `ACTIVE`, `RETIRED`, `ACTIVATION_FAILED`를 사용한다. 정상 게시로 새 버전이 `ACTIVE`가 되면 이전 활성 버전은 `RETIRED`가 된다. 권한·매장 상태·시간대 또는 재검증 실패처럼 재시도로 해결되지 않는 자동 게시 실패는 `ACTIVATION_FAILED`로 끝내고 조용히 활성화하지 않는다.
- 영업시간 새 버전이 활성화되면 이전 영업 버전을 기준으로 검증된 예약 접수 버전의 활성 포인터를 해제하고 해당 예약 버전을 `RETIRED`로 전환한다. 이 전환은 원 영업시간 게시와 같은 사유·요청 식별자를 가진 별도 예약-stream 감사 사건으로 남긴다. 예약 접수 시간대는 새 영업 버전을 기준으로 새 초안을 검증·게시하기 전까지 신규 노출·예약에 사용할 수 없다.

### 자동 게시와 동시성

- 자동 게시 작업자는 중앙 `Instant` 기준으로 `effectiveAt`이 지난 `SCHEDULED` 후보 중 매장별 `(effectiveAt, version)` 순서의 가장 이른 버전 하나만 전역 배치에 포함한다. 한 매장의 선두 후보가 일시 실패해도 해당 매장은 배치 슬롯 하나만 사용하며 다른 매장의 도래 후보 처리를 막지 않는다. 후보 조회 중복은 허용하되 각 활성화 트랜잭션은 매장 행, 일정 상태 행 순서로 잠근 뒤 버전 상태를 다시 확인한다.
- 여러 인스턴스가 같은 후보를 처리해도 `SCHEDULED`인 버전 하나만 `ACTIVE`로 조건부 전이한다. 뒤따른 작업은 이미 끝난 상태를 확인하고 새 활성화나 감사 사건을 만들지 않는다.
- 한 스트림에서 같은 `effectiveAt`에는 하나의 버전만 예약할 수 있다. 여러 지난 예약이 있으면 `(effectiveAt, version)` 오름차순의 가장 이른 후보만 잠금 안에서 활성화할 수 있어 작업자 실행 순서가 최종 활성 버전을 뒤집지 않는다.
- 일시적인 DB 잠금·연결 실패는 중앙 상태를 바꾸지 않고 재시도한다. 업무 규칙상 영구 실패는 `ACTIVATION_FAILED` 상태와 실패 감사를 같은 트랜잭션에 남긴다.
- 게시·취소 명령과 자동 게시 모두 활성 포인터, 이전 버전 종료, 버전 상태, 감사 사건과 멱등 결과를 하나의 트랜잭션으로 확정한다.
- 동일 멱등 키와 같은 명령 지문은 저장된 성공 결과를 재생한다. 소유권은 재생 전에도 확인하지만 `verificationStatus`와 `operationStatus`는 신규 실행 callback 안에서만 검사한다.
- 신규 명령 트랜잭션은 매장 행을 먼저 잠그고 일정 상태 행을 잠근다. 잠금·타임아웃과 알려진 일정 제약 충돌은 `STORE_006`으로 반환하며 부분 상태를 남기지 않는다.

### 감사와 영향 거래 경계

- 휴점·폐점과 운영 모드 변경은 이후 신규 거래 후보를 차단하지만 기존 CONFIRMED 예약을 자동 변경하지 않는다. 현재 대표 운영자는 Reservation 소유 계약에 따라 기존 예약을 취소하거나 방문 완료할 수 있다.
- 초안 저장, 즉시 게시, 게시 예약, 예약 취소, 자동 활성화, 활성화 실패마다 append-only 감사 사건을 남긴다.
- 감사 사건은 행위자 유형·식별자, 매장, 일정 종류, 대상 버전, 이전·새 활성 버전, 전후 상태, 매장 시간대, 요청·효력·처리 시각, 변경 사유, 요청 식별자와 결과를 기록한다. 자동 게시 행위자는 `SYSTEM`으로 기록한다.
- 감사 이력은 플랫폼 운영자 승인 여부가 아니다. 1차 MVP에 플랫폼 운영자 환경과 승인 workflow를 추가하지 않는다.
- 기존 확정 예약·메뉴 홀드·행사의 실제 충돌 식별은 각 소유 도메인의 공개 조회 계약이 필요한 #69의 `contract-first` 후속 범위다. #69가 연결되기 전 감사에는 `conflictCheckStatus=NOT_EVALUATED`와 알 수 없는 충돌 수를 남기며 `0건` 또는 `충돌 없음`으로 기록하지 않는다.
- 일정 변경과 게시 자체는 기존 확정 거래를 자동 취소·이동하거나 거래 스냅샷을 바꾸지 않는다.
- 예약 인원·팀 수는 3번 예약 도메인의 수용량 API가 관리하고 이 파일에서 중복 수정하지 않는다.

### 휴무와 예약 서비스 전체 구간 검증

- `windowEndAt`은 예약을 시작할 수 있는 접수 구간의 상한이며 고객 서비스 종료나 실제 점유 종료가 아니다. Reservation은 매장별 시간 정책에 따라 `serviceEndAt = startAt + serviceDuration`, `occupancyEndAt = serviceEndAt + turnoverDuration`으로 두 종료 시각을 각각 계산한다.
- Store는 Reservation이 전달한 서비스 구간 `[startAt, serviceEndAt)` 전체가 하나의 활성 영업 구간 안에 있고 브레이크타임, 정기 휴무, 취소되지 않은 임시 휴점과 겹치지 않는지 판정한다. turnover 구간 `[serviceEndAt, occupancyEndAt)`은 현재 Store 일정 검증 범위와 입력에 포함하지 않으며 Reservation의 수용량·중복 판정에 사용한다.
- 정기 휴무는 요일 반복 또는 특정 날짜의 종일 규칙을 불변 버전으로 관리한다. 명시적으로 게시된 빈 버전은 정기 휴무 없음이며 활성 버전 자체가 없으면 판정은 fail-closed다.
- 임시 휴무는 중앙 `Instant` 반개구간과 등록 시점 매장 `timeZoneId` 스냅샷을 보관한다. 상태는 현재 시각에 따라 `SCHEDULED`, `ACTIVE`, `ENDED`, `CANCELLED`로 파생한다.
- batch 판정은 입력 순서·개수·중복을 보존하며 Store, 활성 영업/예약/정기 휴무 일정, 임시 휴무를 고정된 수의 일괄 조회로 적재한다. 소스 누락·소유자/시간대 불일치·DST의 존재하지 않거나 중복되는 현지 경계는 `NOT_ACCEPTING`이다.
- Store는 기간 계산, turnover, 좌석/인원 수용량, 중복 예약, 예약 스냅샷을 소유하지 않는다. 이 계약은 내부 애플리케이션 계약이며 별도 HTTP 경로를 노출하지 않는다.

## 메뉴 기본정보

- 메뉴 기본정보는 이름, 설명, 가격, 대표 메뉴 여부, 주·보조 카테고리, 로컬 태그, 홀드 선택 허용, 픽업 선택 허용, 구조화된 알레르기·원산지 표시와 주류 여부를 가진다.
- 메뉴 버전은 `DRAFT`, `SCHEDULED`, `PUBLISHED`, `RETIRED`다.
- 메뉴 생성과 수정은 게시하지 않은 `DRAFT`를 저장한다. 즉시 게시와 예약 게시는 저장된 초안에 별도 게시 명령을 실행한다.
- 관리자는 메뉴 목록과 상세에서 현재 초안, 예약 게시 버전, 게시 버전을 함께 조회할 수 있다.
- 예약 게시 취소는 예약 버전을 다시 초안으로 돌리며, 노출·판매 제어·운영 종료와 함께 변경 사유를 필수로 받는다. 예약 이후 생성한 최신 초안이 이미 있으면 그 초안을 보존하기 위해 취소를 `STORE_010` 충돌로 거부한다.
- 초안에는 미등록 알레르기·원산지 상태를 저장할 수 있다. 게시할 때 `REGISTERED` 알레르기 표시는 OPER-008의 중앙 알레르기 코드 중 최소 1개 구조화 항목을 가져야 하고, 같은 메뉴 버전에서 한 코드에는 하나의 상태만 허용한다. 원산지는 등록된 구조화 항목 또는 적용 대상 아님을 명시해야 한다. 승인된 `알레르기 없음` 표현이 없으므로 빈 목록을 안전으로 해석하지 않는다.
- 주류 여부는 추론하지 않고 운영자의 명시 입력을 버전에 저장한다.
- 공개 상태 `VISIBLE/HIDDEN`, 메뉴 전체 수동 판매 상태 `SELLING/SOLD_OUT/PAUSED`를 별도 축으로 관리한다. 수동 `SOLD_OUT`과 `PAUSED`는 운영자가 설정·복구하며 수량 복구로 자동 해제되지 않는다.
- 4번 MenuHold 도메인의 `InventoryAvailabilityStatus.AVAILABLE/SOLD_OUT`은 `menuId + serviceDate + [startTime, endTime) + policyVersion` 단위로 운영자가 제어하는 제공 구간별 수동 가용 상태다. `SOLD_OUT`은 해당 구간의 수동 차단 상태이며, 온라인 가용량은 `ONLINE_HOLD`와 정책상 허용된 `SHARED` 잔여로 별도 계산하고 수량 변화만으로 구간 상태를 자동 변경하지 않는다. 한 구간의 `SOLD_OUT`은 다른 구간이나 메뉴 기본정보의 판매·공개 상태를 변경하지 않는다. Store/Menu는 시간대별 원시 수량·구간 상태·원장을 중복 저장하거나 재계산하지 않고 MenuHold 구간 상태를 반영하는 역방향 쓰기 명령도 제공하지 않는다.
- 유효한 취소·조정의 수량 복구는 원장 정합성을 위해 현재 영업 여부와 무관하게 실제 사용한 원래 풀에 반영한다. 복구만으로 신규 거래 가능 상태가 되지 않으며 `HIDDEN`, `PAUSED`, 수동 `SOLD_OUT`을 해제하지 않는다.
- 신규 홀드·픽업은 `PUBLISHED + VISIBLE + SELLING`인 메뉴에 대해 대상 제공 구간 전체가 적용 가능한 게시 영업 구간 안에 포함되고 브레이크타임·정기 휴무·임시 휴점·폐점·채널 마감과 충돌하지 않으며, 수량 관리 대상이면 #42의 해당 구간 최종 `InventoryAvailabilityStatus`가 `AVAILABLE`이고 온라인 가용량이 양수일 때만 허용한다. 현재 시각이 대상 영업 구간 안일 필요는 없고 영업 구간과 제공 구간의 시작·종료가 정확히 같을 필요도 없다. 미래 유효 구간은 현재 영업 전에도 후보가 될 수 있지만 종료된 구간은 복구돼도 신규 후보가 되지 않는다.
- #85는 Store/Menu의 매장·메뉴 귀속, 게시·공개·수동 판매 상태와 채널 선택 가능성을 검증하고 #42는 제공 구간의 수동 `InventoryAvailabilityStatus`와 온라인 가용량을 검증한다. 신규 거래 쓰기 시점에는 두 공개 계약과 대상 구간의 유효성을 모두 다시 검증한다.
- 가격은 대한민국 원 정수이며 음수를 허용하지 않는다.
- 메뉴 수정은 새 버전을 만들고 기존 거래의 이름·가격·버전 스냅샷을 바꾸지 않는다.
- 생성·수정·즉시 게시·예약 게시·예약 취소·자동 게시·노출 변경·판매 제어 변경·운영 종료는 append-only 감사 사건을 남긴다. 감사에는 행위자, 요청 식별자, 결과, 전후 버전·상태, 변경 필드, 변경 사유와 영향 확인·복구 결과를 기록한다.
- 동일 메뉴의 자동 게시 워커가 여러 인스턴스에서 동시에 실행돼도 DB 잠금으로 한 번만 활성화하며, 감사 저장이 실패하면 포인터와 버전 전이를 함께 롤백한다.
- 이미지 URL이나 파일 필드는 1차 MVP 요청·응답에 없다.

## 대표(인기) 메뉴 3~5개와 표시 순서

- 대표 메뉴와 인기 메뉴는 같은 제품 개념이다. 현재 대표 여부와 공개 순서는 매장별 대표 메뉴 설정 원장이 소유하고 기존 메뉴 버전의 `representative` 값은 과거 버전 재현에만 사용한다.
- 매장 운영자는 자기 매장의 현재 게시·공개 메뉴 중 3~5개를 중복 없이 순서대로 전체 교체한다. 요청은 `expectedVersion`과 `Idempotency-Key`를 사용하며 같은 version의 동시 요청은 하나만 성공한다.
- `SOLD_OUT`과 특정 제공 시간대 재고 0은 대표 선정을 유지한다. 시간대별 품절은 MenuHold·Pickup 가용성 계약이 계산하며 메뉴 전체 상태를 자동 변경하지 않는다.
- `HIDDEN`, `PAUSED`, `RETIRED`, 현재 게시 버전 없음은 대표 목록에서 자동 해제한다. 안전한 숨김·중지·종료 명령은 최소 개수 때문에 거부하지 않으며 3개 미만이면 설정을 `REQUIRES_ATTENTION`으로 표시한다.
- 공개 상세의 기존 `representativeMenus`는 설정 순서로 현재 공개 가능한 항목만 반환한다. 별도 `popularMenus` 필드를 만들지 않는다.
- Payment·Reservation이 예약금 계산에 사용할 때는 Store/Menu 소유 공개 Service·DTO로 setting version과 순서·게시 version·기본 가격을 읽고 Entity·Repository를 직접 참조하지 않는다.

## 권한

- 공개 매장·메뉴·catalog 조회는 비회원도 가능하다.
- 등록·수정·운영시간·접수시간대·메뉴 관리는 `store-operator` Access JWT가 필요하다.
- 모든 매장 관리 요청은 현재 계정 상태, 대상 매장의 `store_operator_account_id` 일치, 입점·운영 상태를 `StoreService`의 운영 권한 검증 공개 메서드에서 확인한다.
- 대상 매장의 대표 운영자가 아니면 `STORE_003` 403을 반환한다.
- 공개 매장은 존재하지만 변경 권한이 없는 경우이므로 거짓 404로 숨기지 않는다.

## 멱등성·트랜잭션·동시성

- 매장 등록·수정, 영업시간·접수 시간대 초안 저장·게시·예약 취소와 메뉴 생성·수정은 `Idempotency-Key`를 요구한다.
- 매장 등록은 멱등 기록, 사업자등록번호의 영구 귀속, 입점 동의 증거, 인증된 운영자 FK를 포함한 매장 생성을 하나의 트랜잭션으로 조정한다.
- 같은 사업자등록번호의 동시·후속 신청은 매장 운영 상태와 무관한 DB 유일 제약으로 한 건만 성공한다.
- 일정 초안 저장·게시·예약 취소와 메뉴 변경은 버전 상태·감사·멱등 결과를 같은 트랜잭션에서 확정한다.
- 공개 검색은 쓰기 트랜잭션이나 잠금을 획득하지 않는다.
- 공개 검색·상세·추천은 저장된 좌표만 읽고 외부 지오코딩 서비스를 호출하지 않는다.
- 운영시간·메뉴 변경이 기존 예약·홀드·픽업 거래 스냅샷을 갱신하지 않는다.

## API 소유권

- 매장 목록·상세·검색과 공개 가용성 조합 경로는 2번이 최종 관리한다.
- 예약 가용성 결과의 계산과 DTO 의미는 3번이 검토한다.
- 메뉴 수량 가용성 결과의 계산과 DTO 의미는 4번이 검토한다.
- 예약 수용량 설정, 메뉴 재고 수량 조정과 픽업 거래 API를 이 파일에 중복 생성하지 않는다.

## Migration·호환성 요구

- 1차 MVP는 `stores.store_operator_account_id` 단일 FK를 사용하며 직원·공동 관리자·명의 양도 API를 제공하지 않는다.
- 다중 운영자·역할·명의 양도가 활성화되는 고도화에서는 기존 FK를 관계 테이블의 최초 `OWNER` 행으로 이관한 뒤 권한 원본을 전환한다.
- 공개 API와 응답에는 내부 운영자 FK를 불필요하게 노출하지 않아 이후 마이그레이션이 클라이언트 계약을 깨지 않게 한다.
- `CLOSED` 매장과 `RETIRED` 메뉴는 공개 신규 선택에서 제외하지만 과거 거래 FK·스냅샷을 보존한다.
- catalog code가 추가돼도 기존 코드의 의미를 다른 분류로 재사용하지 않는다.
- V10 이전 매장 행은 migration에서 `created_at`을 두 동의 시각으로, `STORE_ONBOARDING_REQUIRED_TERMS_V1`을 약관 버전으로 backfill한다. 이는 스키마 이행을 위한 기술적 표시이며 기존 신청자의 법적 재동의를 의미하지 않는다.

## 인수 조건

- 지역 필터가 승인된 다섯 지역만 허용한다.
- 키워드가 매장명·게시 메뉴명·지역 표시명을 검색하고 SQL 표현을 직접 받지 않는다.
- 완전한 예약 조건 없이 가용성을 추측하지 않는다.
- 수용량·재고를 매장 repository에 중복 저장하거나 직접 차감하지 않는다.
- 카테고리와 공식 업종 검증값을 서로 변환하지 않는다.
- 매장 등록 요청에 파일·이미지·플랫폼 운영자 승인 필드가 없다.
- 매장 등록 요청의 자기확약·필수 약관 동의가 필수이며 서버에 동의 시각과 약관 버전이 남는다.
- 세 매장 상태 축이 하나의 enum으로 합쳐지지 않는다.
- 운영시간 변경이 기존 거래를 자동 취소·이동하지 않는다.
- 운영시간과 예약 접수 시간대는 초안을 저장한 뒤에만 즉시 또는 미래 시각으로 게시할 수 있다.
- 예약 게시 취소는 효력 전 버전을 초안으로 되돌리고 이미 활성화된 버전을 소급 변경하지 않는다.
- 다중 인스턴스 자동 게시가 같은 버전을 한 번만 활성화하며 실패를 감사할 수 있다.
- #69 연결 전 실제 충돌 확인 상태를 `NOT_EVALUATED`로 구분하고 충돌 없음으로 표시하지 않는다.
- 메뉴 기본 상태와 시간대별 수량 상태가 분리된다.

# 품절 메뉴 대안 검색

`POST /api/v1/stores/{storeId}/menus/{menuId}/alternative-searches`는 원본 메뉴와 요청 수량을 기준으로 현재 대안을 조회한다. 원본 메뉴는 게시·공개 상태라면 수동 판매 상태가 `SELLING` 또는 `SOLD_OUT`일 때 조회할 수 있지만, 대안 후보에는 `SELLING` 메뉴만 포함한다. 같은 매장의 적격·재고 충분 메뉴가 하나라도 있으면 그 결과만 반환하며, 없을 때에만 원본 매장의 검증 좌표 기준 3km 이내 다른 매장을 검색한다. 알레르기 제외 코드가 있으면 정보가 등록되지 않았거나 `CONTAINS`/`MAY_CONTAIN`인 후보를 제외한다. 이 조회는 재고 확보나 예약 성공을 보장하지 않으며 사용자 현재 위치와 전체 요청 body를 저장하거나 로그로 남기지 않는다.
