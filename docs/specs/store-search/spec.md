# 기능 명세: 매장·검색·운영자 기본 관리

> 문서 상태: 4단계 승인
> 적용 단계: 1차 MVP
> 도메인 소유자: 2번 팀원 — 매장·검색
> 협업 검토: 3번 팀원 — 예약 가용성, 4번 팀원 — 메뉴 수량 가용성
> 관련 정책 ID: STORE-002~STORE-007, STORE-014, OPER-002~OPER-010, S-005, S-007, E-002, C-001~C-013
> OpenAPI: `docs/specs/store-search/openapi.yaml`
> 최종 승인일: 2026-07-31

## 범위

### 포함

- 서울·부산·대구·대전·광주의 공개 매장 목록·검색·상세
- 매장명·메뉴명·지역명 키워드 검색
- 매장·메뉴 카테고리와 매장 태그 catalog 조회
- 요청 조건이 있을 때 예약 가능 여부 조합
- 매장 운영자의 매장 등록·수정
- 정규 영업시간과 예약 접수 시간대 관리
- 메뉴 기본정보·대표 메뉴·공개·판매 제어 관리

### 제외

- 지도 좌표·현재 위치·거리순·반경 검색
- QueryDSL 고급 필터와 개인화 재정렬
- 이미지·파일 업로드와 S3
- 플랫폼 운영자 심사·사건 큐
- 결제·정산·리뷰·웨이팅·추천
- 메뉴 시간대별 재고 수량과 픽업 거래 상태 관리

## 공개 탐색 계약

`GET /api/v1/stores` 하나에서 다음 조건을 조합한다.

| 조건 | 의미 |
| --- | --- |
| `keyword` | 매장명·게시 메뉴명·지역 표시명에 대한 1차 MVP 텍스트 포함 검색 |
| `region` | `SEOUL`, `BUSAN`, `DAEGU`, `DAEJEON`, `GWANGJU` |
| `storeCategoryCode` | 중앙 catalog에서 받은 매장 주 카테고리 코드 |
| 예약 조건 | `serviceDate`, `startTime`, `partySize`를 모두 보낸 경우에만 가용성 판정 |
| `availableOnly` | 완전한 예약 조건이 있을 때만 `true` 허용 |

예약 조건 일부만 보내거나 `availableOnly=true`인데 완전한 예약 조건이 없으면 `COMMON_001`로 거부한다. 임의 기본 날짜·시간·인원으로 가용성을 추측하지 않는다.
`endTime`은 클라이언트가 보내지 않으며 서버가 해당 매장의 현재 예약 접수 시간대·서비스 소요·전환 정책으로 계산한다. 이 계산은 실제 예약 생성과 같은 예약 도메인 계약을 사용한다.

검색 결과의 `reservationAvailability`는 다음 값을 사용한다.

- `NOT_REQUESTED`: 예약 조건이 없어 계산하지 않음
- `AVAILABLE`: 요청한 모든 구간에서 인원 수와 팀 1건을 확보할 수 있음
- `UNAVAILABLE`: 영업·접수 시간·수용량 가운데 하나 이상이 부족

2번 도메인은 수용량을 직접 계산하거나 저장하지 않고 3번 도메인의 `ReservationService`가 제공하는 예약 가능 일괄 조회 공개 메서드를 사용한다. 메뉴 홀드 가능 수량이 상세에 필요하면 4번 도메인의 조회 계약을 사용하며 메뉴 재고 repository를 직접 참조하지 않는다.

### 검색 구현 선택

1차 MVP는 MySQL의 정규화된 검색용 필드와 인덱스를 사용한 단순 포함 검색으로 제한한다. QueryDSL, 전문 검색 엔진, 위치 검색과 개인화 점수는 뒤 단계다. 검색 필드 정규화와 escape를 서버가 수행하고 클라이언트가 SQL wildcard나 정렬 열을 직접 선택하지 못하게 한다.

이 선택은 검색 품질보다 계약과 소유권을 먼저 검증하고 새 의존성을 억지로 넣지 않기 위한 것이다.

## 카테고리와 태그 catalog

- 매장은 주 카테고리 코드를 정확히 1개 가진다.
- 메뉴는 주 카테고리 코드 1개와 서로 중복되지 않는 보조 카테고리 코드 0~5개를 가진다.
- 매장 태그는 중앙 허용 catalog에서만 선택한다.
- 메뉴 로컬 태그는 해당 매장에서만 사용하는 텍스트이며 검색 보조 정보다.
- 공식 사업자 주업태명·주종목명과 검색 카테고리·태그는 서로 변환하지 않는다.

정책에 정확한 category code 목록이 아직 없으므로 OpenAPI에서 임의 enum을 발명하지 않는다. 프론트엔드는 다음 catalog API의 `code`를 그대로 제출한다.

- `GET /api/v1/store-categories`
- `GET /api/v1/menu-categories`
- `GET /api/v1/store-tags`

catalog code는 불투명한 문자열이며 클라이언트가 영문 이름을 추측하거나 표시명을 코드로 보내지 않는다. 정확한 seed와 버전은 구현 시작 전 매장 도메인 소유자가 승인해야 하며, 승인되지 않은 값은 `STORE_004`로 거부한다.

## 매장 등록과 상태

- `POST /api/v1/store-operator/stores`는 인증된 매장 운영자 계정으로 새 매장 신청을 만든다.
- 요청의 운영자 ID나 역할 값은 받지 않고 JWT subject를 사용한다.
- 사업자등록번호와 업종 구분 `CAFE`, `BAKERY`, `OTHER`를 구조화 입력한다.
- 1차 MVP는 사업자등록번호 형식과 중앙 영구 중복을 검증한다. 한 번 매장에 귀속된 번호는 폐점 후에도 일반 등록에서 재사용할 수 없으며, 재개·이전·복구는 향후 플랫폼 운영자 전용 절차로 분리한다. 사전 사업자 진위·업종 기준 데이터 비교, 국세청 공식 진위조회와 플랫폼 운영자 심사는 사용하지 않는다.
- 형식과 중복 검사를 통과한 신청은 즉시 `APPROVED`로 매장을 생성한다.
- 사업자등록증 이미지·파일 URL을 받지 않는다.
- 신청자는 `applicantSelfAttested=true`와 `requiredTermsAgreed=true`를 함께 제출해야 한다. 서버는 두 동의 시각과 필수 약관 버전 `STORE_ONBOARDING_REQUIRED_TERMS_V1`을 매장에 기록한다.

입점 검증, 운영 상태와 픽업 자격은 각각 다음 축으로 반환한다.

| 축 | 값 |
| --- | --- |
| `verificationStatus` | `APPROVED` |
| `operationStatus` | `OPEN`, `TEMPORARILY_CLOSED`, `CLOSED` |
| `pickupEligibility` | `ELIGIBLE`, `INELIGIBLE` |

등록 업종이 `CAFE` 또는 `BAKERY`이면 픽업 자격 `ELIGIBLE`, `OTHER`이면 `INELIGIBLE`로 확정한다. 검색 카테고리·태그는 이 값을 바꾸지 않는다. `OTHER` 매장의 일반 입점·검색·예약 기능은 유지하며 픽업 기능만 실패 폐쇄한다.

등록 요청이 `businessType=OTHER`와 `modes.pickupEnabled=true`를 함께 보내면 서버는 값을 자동 보정하거나 부분 등록하지 않고 `STORE_008`로 전체 요청을 거절한다. 신청자는 `pickupEnabled=false`로 재요청해 일반 매장·예약 기능을 즉시 등록할 수 있다.

## 운영 시간과 예약 접수 시간대

### 주간 설정과 매장 시간대

- 영업시간과 예약 접수 시간대는 서로 독립된 불변 버전 스트림이다.
- 두 초안 저장 `PUT`은 7개 요일을 중복 없이 모두 포함한 전체 주간 설정을 받으며, 일부 요일만 조용히 병합하지 않는다. 요일이나 시간 구간 배열의 `null` 요소를 허용하지 않는다.
- 정규 영업시간은 요일별 0개 이상의 `[startTime, endTime)` 구간이다. 영업시간·브레이크타임·예약 접수 구간은 종류별·요일별 최대 48개이며 시각 JSON은 `HH:mm`만 허용한다.
- 브레이크타임은 영업 구간과 별도 구간으로 관리하며 하나의 영업 구간 안에 완전히 포함되어야 한다. 모든 구간은 0 길이와 실제 시간 중첩을 허용하지 않는다.
- 자정을 넘는 구간은 시작 요일에 귀속하며 일요일–월요일 주간 경계까지 실제 시간 중첩을 검사한다.
- 예약 접수 시간대는 실제 영업시간 안에 있어야 하며 브레이크타임과 겹치지 않는다. 예약 접수 버전은 검증에 사용한 영업시간 버전 ID를 보관한다.
- 매장은 IANA `timeZoneId`를 가진다. 신규 매장 등록은 유효한 IANA 값을 필수로 받고 일정 계산에서 JVM·운영체제 기본 시간대나 주소 기반 추측을 사용하지 않는다. 기존 매장은 migration에서 `Asia/Seoul`로 이행한다. 활성·예약 일정의 효력 해석을 바꾸는 일반 매장 수정 API에서는 시간대를 변경하지 않으며 별도 시간대 변경 절차는 후속 범위다.

### 초안·게시·취소 수명주기

- `PUT /api/v1/store-operator/stores/{storeId}/operating-hours`와 `PUT /api/v1/store-operator/stores/{storeId}/reservation-time-slots`는 제출한 전체 주간 설정을 새 불변 `DRAFT` 버전으로 저장할 뿐 게시하지 않는다.
- 초안 내용은 제자리에서 수정하지 않는다. 변경하려면 새 초안 버전을 저장하고, 게시할 버전 번호를 명시한다.
- `POST .../{version}/publication`은 저장된 초안에만 사용할 수 있다. `publicationMode=IMMEDIATE`는 중앙 확정 시각에 활성화하고, `publicationMode=SCHEDULED`는 미래 `effectiveAt`을 예약한다. `effectiveAt`은 오프셋을 포함한 RFC 3339 date-time이며 서버는 이를 중앙 `Instant`로 저장하고 응답에 매장 `timeZoneId`를 함께 반환한다. `SCHEDULED`에는 `effectiveAt`이 필수이고 `IMMEDIATE`에는 허용하지 않는다.
- 게시 명령은 비어 있지 않은 `changeReason`을 항상 요구한다. 초안 저장 자체에는 변경 사유를 요구하지 않지만 게시 감사에 사유를 보존한다.
- `POST .../{version}/publication-cancellation`은 비어 있지 않은 `changeReason`을 받고 아직 효력이 발생하지 않은 `SCHEDULED` 버전에만 사용할 수 있다. 성공하면 예약 시각을 제거하고 버전을 `DRAFT`로 되돌려 내용은 유지한다. 이미 활성화된 버전은 취소할 수 없으며 되돌리려면 이전 내용을 복제한 새 초안을 게시한다.
- 버전 상태는 `DRAFT`, `SCHEDULED`, `ACTIVE`, `RETIRED`, `ACTIVATION_FAILED`를 사용한다. 정상 게시로 새 버전이 `ACTIVE`가 되면 이전 활성 버전은 `RETIRED`가 된다. 권한·매장 상태·시간대 또는 재검증 실패처럼 재시도로 해결되지 않는 자동 게시 실패는 `ACTIVATION_FAILED`로 끝내고 조용히 활성화하지 않는다.
- 영업시간 새 버전이 활성화되면 이전 영업 버전을 기준으로 검증된 예약 접수 버전의 활성 포인터를 해제하고 해당 예약 버전을 `RETIRED`로 전환한다. 이 전환은 원 영업시간 게시와 같은 사유·요청 식별자를 가진 별도 예약-stream 감사 사건으로 남긴다. 예약 접수 시간대는 새 영업 버전을 기준으로 새 초안을 검증·게시하기 전까지 신규 노출·예약에 사용할 수 없다.

### 자동 게시와 동시성

- 자동 게시 작업자는 중앙 `Instant` 기준으로 `effectiveAt`이 지난 `SCHEDULED` 후보 중 매장별 `(effectiveAt, version)` 순서의 가장 이른 버전 하나만 전역 배치에 포함한다. 한 매장의 선두 후보가 일시 실패해도 해당 매장은 배치 슬롯 하나만 사용하며 다른 매장의 도래 후보 처리를 막지 않는다. 후보 조회 중복은 허용하되 각 활성화 트랜잭션은 매장 행, 일정 상태 행 순서로 잠근 뒤 버전 상태를 다시 확인한다.
- 여러 인스턴스가 같은 후보를 처리해도 `SCHEDULED`인 버전 하나만 `ACTIVE`로 조건부 전이한다. 뒤따른 작업은 이미 끝난 상태를 확인하고 새 활성화나 감사 사건을 만들지 않는다.
- 한 스트림에서 같은 `effectiveAt`에는 하나의 버전만 예약할 수 있다. 여러 지난 예약이 있으면 `(effectiveAt, version)` 오름차순의 가장 이른 후보만 잠금 안에서 활성화할 수 있어 작업자 실행 순서가 최종 활성 버전을 뒤집지 않는다.
- 일시적인 DB 잠금·연결 실패는 중앙 상태를 바꾸지 않고 재시도한다. 업무 규칙상 영구 실패는 `ACTIVATION_FAILED` 상태와 실패 감사를 같은 트랜잭션에 남긴다.
- 게시·취소 명령과 자동 게시 모두 활성 포인터, 이전 버전 종료, 버전 상태, 감사 사건과 멱등 결과를 하나의 트랜잭션으로 확정한다.
- 동일 멱등 키와 같은 명령 지문은 저장된 성공 결과를 재생한다. 소유권은 재생 전에도 확인하지만 `verificationStatus`와 `operationStatus`는 신규 실행 callback 안에서만 검사한다.
- 신규 명령 트랜잭션은 매장 행을 먼저 잠그고 일정 상태 행을 잠근다. 잠금·타임아웃과 알려진 일정 제약 충돌은 `STORE_006`으로 반환하며 부분 상태를 남기지 않는다.

### 감사와 영향 거래 경계

- 초안 저장, 즉시 게시, 게시 예약, 예약 취소, 자동 활성화, 활성화 실패마다 append-only 감사 사건을 남긴다.
- 감사 사건은 행위자 유형·식별자, 매장, 일정 종류, 대상 버전, 이전·새 활성 버전, 전후 상태, 매장 시간대, 요청·효력·처리 시각, 변경 사유, 요청 식별자와 결과를 기록한다. 자동 게시 행위자는 `SYSTEM`으로 기록한다.
- 감사 이력은 플랫폼 운영자 승인 여부가 아니다. 1차 MVP에 플랫폼 운영자 환경과 승인 workflow를 추가하지 않는다.
- 기존 확정 예약·메뉴 홀드·행사의 실제 충돌 식별은 각 소유 도메인의 공개 조회 계약이 필요한 #69의 `contract-first` 후속 범위다. #69가 연결되기 전 감사에는 `conflictCheckStatus=NOT_EVALUATED`와 알 수 없는 충돌 수를 남기며 `0건` 또는 `충돌 없음`으로 기록하지 않는다.
- 일정 변경과 게시 자체는 기존 확정 거래를 자동 취소·이동하거나 거래 스냅샷을 바꾸지 않는다.
- 예약 인원·팀 수는 3번 예약 도메인의 수용량 API가 관리하고 이 파일에서 중복 수정하지 않는다.

## 메뉴 기본정보

- 메뉴 기본정보는 이름, 설명, 가격, 대표 메뉴 여부, 주·보조 카테고리, 로컬 태그, 홀드 선택 허용, 픽업 선택 허용, 구조화된 알레르기·원산지 표시와 주류 여부를 가진다.
- 메뉴 버전은 `DRAFT`, `SCHEDULED`, `PUBLISHED`, `RETIRED`다.
- 메뉴 생성과 수정은 게시하지 않은 `DRAFT`를 저장한다. 즉시 게시와 예약 게시는 저장된 초안에 별도 게시 명령을 실행한다.
- 관리자는 메뉴 목록과 상세에서 현재 초안, 예약 게시 버전, 게시 버전을 함께 조회할 수 있다.
- 예약 게시 취소는 예약 버전을 다시 초안으로 돌리며, 노출·판매 제어·운영 종료와 함께 변경 사유를 필수로 받는다. 예약 이후 생성한 최신 초안이 이미 있으면 그 초안을 보존하기 위해 취소를 `STORE_010` 충돌로 거부한다.
- 초안에는 미등록 알레르기·원산지 상태를 저장할 수 있다. 게시할 때 `REGISTERED` 알레르기 표시는 OPER-008의 중앙 알레르기 코드 중 최소 1개 구조화 항목을 가져야 하고, 같은 메뉴 버전에서 한 코드에는 하나의 상태만 허용한다. 원산지는 등록된 구조화 항목 또는 적용 대상 아님을 명시해야 한다. 승인된 `알레르기 없음` 표현이 없으므로 빈 목록을 안전으로 해석하지 않는다.
- 주류 여부는 추론하지 않고 운영자의 명시 입력을 버전에 저장한다.
- 공개 상태 `VISIBLE/HIDDEN`, 메뉴 전체 수동 판매 상태 `SELLING/SOLD_OUT/PAUSED`를 별도 축으로 관리한다. 수동 `SOLD_OUT`과 `PAUSED`는 운영자가 설정·복구하며 수량 복구로 자동 해제되지 않는다.
- 4번 MenuHold 도메인의 `InventoryAvailabilityStatus.AVAILABLE/SOLD_OUT`은 `menuId + serviceDate + [startTime, endTime) + policyVersion` 단위로 운영자가 제어하는 제공 구간별 수동 가용 상태다. `SOLD_OUT`은 해당 구간의 수동 차단 상태이며, 온라인 가용량은 `ONLINE_HOLD`와 정책상 허용된 `SHARED` 잔여로 별도 계산하고 수량 변화만으로 구간 상태를 자동 변경하지 않는다. 한 구간의 `SOLD_OUT`은 다른 구간이나 메뉴 기본정보의 판매·공개 상태를 변경하지 않는다. Store/Menu는 시간대별 원시 수량·구간 상태·원장을 중복 저장하거나 재계산하지 않고 MenuHold 구간 상태를 반영하는 역방향 쓰기 명령도 제공하지 않는다.
- 유효한 취소·조정의 수량 복구는 원장 정합성을 위해 현재 영업 여부와 무관하게 실제 사용한 원래 풀에 반영한다. 복구만으로 신규 거래 가능 상태가 되지 않으며 `HIDDEN`, `PAUSED`, 수동 `SOLD_OUT`을 해제하지 않는다.
- 신규 홀드·픽업은 `PUBLISHED + VISIBLE + SELLING`인 메뉴에 대해 대상 제공 구간 전체가 적용 가능한 게시 영업 구간 안에 포함되고 브레이크타임·정기 휴무·임시 휴점·폐점·채널 마감과 충돌하지 않으며, 수량 관리 대상이면 #42의 해당 구간 최종 `InventoryAvailabilityStatus`가 `AVAILABLE`이고 온라인 가용량이 양수일 때만 허용한다. 현재 시각이 대상 영업 구간 안일 필요는 없고 영업 구간과 제공 구간의 시작·종료가 정확히 같을 필요도 없다. 미래 유효 구간은 현재 영업 전에도 후보가 될 수 있지만 종료된 구간은 복구돼도 신규 후보가 되지 않는다.
- #85는 Store/Menu의 매장·메뉴 귀속, 게시·공개·수동 판매 상태와 채널 선택 가능성을 검증하고 #42는 제공 구간의 수동 `InventoryAvailabilityStatus`와 온라인 가용량을 검증한다. 신규 거래 쓰기 시점에는 두 공개 계약과 대상 구간의 유효성을 모두 다시 검증한다.
- 가격은 대한민국 원 정수이며 음수를 허용하지 않는다.
- 메뉴 수정은 새 버전을 만들고 기존 거래의 이름·가격·버전 스냅샷을 바꾸지 않는다.
- 생성·수정·즉시 게시·예약 게시·예약 취소·자동 게시·노출 변경·판매 제어 변경·운영 종료는 append-only 감사 사건을 남긴다. 감사에는 행위자, 요청 식별자, 결과, 전후 버전·상태, 변경 필드, 변경 사유와 영향 확인·복구 결과를 기록한다.
- 동일 메뉴의 자동 게시 워커가 여러 인스턴스에서 동시에 실행돼도 DB 잠금으로 한 번만 활성화하며, 감사 저장이 실패하면 포인터와 버전 전이를 함께 롤백한다.
- 이미지 URL이나 파일 필드는 1차 MVP 요청·응답에 없다.

## 권한

- 공개 매장·메뉴·catalog 조회는 비회원도 가능하다.
- 등록·수정·운영시간·접수시간대·메뉴 관리는 `store-operator` Access JWT가 필요하다.
- 모든 매장 관리 요청은 현재 계정 상태, 대상 매장의 `store_operator_account_id` 일치, 입점·운영 상태를 `StoreService`의 운영 권한 검증 공개 메서드에서 확인한다.
- 대상 매장의 대표 운영자가 아니면 `STORE_003` 403을 반환한다.
- 공개 매장은 존재하지만 변경 권한이 없는 경우이므로 거짓 404로 숨기지 않는다.

## 멱등성·트랜잭션·동시성

- 매장 등록·수정, 영업시간·접수 시간대 초안 저장·게시·예약 취소와 메뉴 생성·수정은 `Idempotency-Key`를 요구한다.
- 매장 등록은 멱등 기록, 사업자등록번호의 영구 귀속, 입점 동의 증거, 인증된 운영자 FK를 포함한 매장 생성을 하나의 트랜잭션으로 조정한다.
- 같은 사업자등록번호의 동시·후속 신청은 매장 운영 상태와 무관한 DB 유일 제약으로 한 건만 성공한다.
- 일정 초안 저장·게시·예약 취소와 메뉴 변경은 버전 상태·감사·멱등 결과를 같은 트랜잭션에서 확정한다.
- 공개 검색은 쓰기 트랜잭션이나 잠금을 획득하지 않는다.
- 운영시간·메뉴 변경이 기존 예약·홀드·픽업 거래 스냅샷을 갱신하지 않는다.

## API 소유권

- 매장 목록·상세·검색과 공개 가용성 조합 경로는 2번이 최종 관리한다.
- 예약 가용성 결과의 계산과 DTO 의미는 3번이 검토한다.
- 메뉴 수량 가용성 결과의 계산과 DTO 의미는 4번이 검토한다.
- 예약 수용량 설정, 메뉴 재고 수량 조정과 픽업 거래 API를 이 파일에 중복 생성하지 않는다.

## Migration·호환성 요구

- 1차 MVP는 `stores.store_operator_account_id` 단일 FK를 사용하며 직원·공동 관리자·명의 양도 API를 제공하지 않는다.
- 다중 운영자·역할·명의 양도가 활성화되는 고도화에서는 기존 FK를 관계 테이블의 최초 `OWNER` 행으로 이관한 뒤 권한 원본을 전환한다.
- 공개 API와 응답에는 내부 운영자 FK를 불필요하게 노출하지 않아 이후 마이그레이션이 클라이언트 계약을 깨지 않게 한다.
- `CLOSED` 매장과 `RETIRED` 메뉴는 공개 신규 선택에서 제외하지만 과거 거래 FK·스냅샷을 보존한다.
- catalog code가 추가돼도 기존 코드의 의미를 다른 분류로 재사용하지 않는다.
- V10 이전 매장 행은 migration에서 `created_at`을 두 동의 시각으로, `STORE_ONBOARDING_REQUIRED_TERMS_V1`을 약관 버전으로 backfill한다. 이는 스키마 이행을 위한 기술적 표시이며 기존 신청자의 법적 재동의를 의미하지 않는다.

## 인수 조건

- 지역 필터가 승인된 다섯 지역만 허용한다.
- 키워드가 매장명·게시 메뉴명·지역 표시명을 검색하고 SQL 표현을 직접 받지 않는다.
- 완전한 예약 조건 없이 가용성을 추측하지 않는다.
- 수용량·재고를 매장 repository에 중복 저장하거나 직접 차감하지 않는다.
- 카테고리와 공식 업종 검증값을 서로 변환하지 않는다.
- 매장 등록 요청에 파일·이미지·플랫폼 운영자 승인 필드가 없다.
- 매장 등록 요청의 자기확약·필수 약관 동의가 필수이며 서버에 동의 시각과 약관 버전이 남는다.
- 세 매장 상태 축이 하나의 enum으로 합쳐지지 않는다.
- 운영시간 변경이 기존 거래를 자동 취소·이동하지 않는다.
- 운영시간과 예약 접수 시간대는 초안을 저장한 뒤에만 즉시 또는 미래 시각으로 게시할 수 있다.
- 예약 게시 취소는 효력 전 버전을 초안으로 되돌리고 이미 활성화된 버전을 소급 변경하지 않는다.
- 다중 인스턴스 자동 게시가 같은 버전을 한 번만 활성화하며 실패를 감사할 수 있다.
- #69 연결 전 실제 충돌 확인 상태를 `NOT_EVALUATED`로 구분하고 충돌 없음으로 표시하지 않는다.
- 메뉴 기본 상태와 시간대별 수량 상태가 분리된다.
- 지도·현재 위치·거리·결제·추천 필드가 OpenAPI에 없다.
