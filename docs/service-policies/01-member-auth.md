# 회원·인증·계정 정책

> 문서 상태: 확정
> 정책 범위: `AUTH-001`~`AUTH-012`
> 최종 변경일: 2026-07-28

회원 유형, 로그인, 본인·연령 확인, 토큰, 계정 복구, 탈퇴 및 제재를 다룬다. 상세 설계에는 `00-policy-template.md`의 공통 검토 항목을 적용한다.

## 단계 적용 기준

- `1차 MVP`: 물리적으로 분리된 일반 사용자·매장 운영자 계정별 stateless Access JWT와 Refresh JWT를 사용한다. 정상 토큰 목록, 리프레시 상태나 세션을 애플리케이션 서버·MySQL·Valkey에 저장하지 않는다. 플랫폼 운영자 계정·JWT·API·UI는 구현하지 않는다.
- `고도화`: Valkey 기반 Refresh Token 회전·폐기·재사용 탐지와 일반 사용자 카카오 로그인을 도입한다.
- 이 문서에서 Valkey, 리프레시 상태, 토큰 계열 회전·폐기·재사용 탐지 또는 카카오 로그인을 전제로 한 조항은 별도 단계 표기가 없으면 `고도화`에만 적용한다.
- 어느 단계에서도 이메일·휴대전화 일치, 외부 로그인 성공이나 로그인 수단 연결로 계정 유형·인증 주체·권한을 병합, 전환 또는 승격하지 않는다.

## AUTH-001 지원 회원 유형과 계정 관계

> 정책 상태: 확정

### 현재 확정 사항

- 계정 유형은 `일반 사용자`, `매장 운영자`, `플랫폼 운영자`로 구분한다.
- 세 유형은 각각 `consumer_accounts`/`consumer_account_id`, `store_operator_accounts`/`store_operator_account_id`, `platform_operator_accounts`/`platform_operator_account_id`라는 별도 테이블과 기본 키를 사용한다. 단일 사용자 테이블과 역할 열로 통합하지 않는다.
- 인증 주체와 토큰 네임스페이스는 각각 `consumer:{id}`/`consumer`, `store-operator:{id}`/`store-operator`, `platform-operator:{id}`/`platform-operator`로 분리한다.
- 같은 사람은 서로 다른 유형의 계정을 각각 보유할 수 있지만 기본 키, 인증 상태, 토큰과 권한을 공유하지 않는다.
- 1차 MVP에서 하나의 매장 운영자 계정은 자신을 `store_operator_account_id`로 참조하는 여러 매장을 관리할 수 있다.
- 플랫폼 운영자 계정의 세부 권한 체계는 별도 플랫폼 운영 정책에서 정의한다.
- 매장 직원용 계정은 지원하지 않으며, 매장 관리 시스템에는 매장 운영자 계정으로만 로그인할 수 있다.
- 매장 운영자 계정의 가입·로그인 가능 상태와 매장별 운영 권한은 구분한다.
- 가입·본인 확인을 마친 매장 운영자 계정이라도 해당 매장의 사업자 검증과 입점 승인이 완료되고 매장의 대표 운영자 FK가 해당 계정을 참조하기 전에는 그 매장의 운영 기능을 사용할 수 없다.
- 클라이언트가 전달한 계정 유형, 일반 사용자 계정의 로그인 수단 연결, 외부 로그인 성공과 이메일·휴대전화 일치만으로 계정 유형이나 매장 운영 권한을 생성·변경하지 않는다.
- 모든 매장 관리 요청은 중앙의 계정 유형, 계정 상태, 대상 매장의 대표 운영자 FK 일치와 해당 매장의 승인·운영 상태를 함께 검증한다. 어느 하나라도 확인할 수 없거나 유효하지 않으면 실패 폐쇄한다.
- 매장 운영자 계정은 1인 1계정 사용을 원칙으로 하며, 직원 또는 제3자와의 계정 공유는 지원하지 않는다.
- 일반 사용자 계정과 매장 운영자 계정은 동일한 이메일 및 휴대전화로 각각 생성할 수 있다.
- 다만 동일한 계정 유형 내에서는 이메일과 휴대전화가 중복될 수 없다.
- 비회원은 공개된 매장·메뉴·가격·예약 가능 여부를 탐색하고 조회할 수 있다.
- 비회원 예약, 비회원 웨이팅은 지원하지 않는다.
- 예약, 웨이팅, 메뉴 홀드, 결제 같은 상태 변경 기능은 로그인한 일반 사용자만 사용할 수 있다.


### 정책 근거

- 사용자용 기능과 매장 관리 기능을 분리해서 보안을 높이기 위함이다.
- 일반 사용자 계정에 문제가 생겨도 매장 관리 권한까지 같이 영향받지 않게 하기 위함이다.
- 한 사람이 여러 매장을 운영할 때 계정을 여러 개 만들지 않아도 되게 하기 위함이다.
- 플랫폼 운영자 계정은 서비스 전체를 다루는 계정이므로 일반 이용 계정과 따로 관리하기 위함이다.
- 여러 사람이 하나의 공용 계정을 같이 쓰는 상황을 막고, 누가 어떤 작업을 했는지 확인할 수 있게 하기 위함이다.
- 비회원은 매장 정보를 쉽게 볼 수 있게 하되, 예약이나 결제 같은 중요한 기능은 로그인한 사용자 기준으로 안전하게 관리하기 위함이다.

### 다중 서버·다중 인스턴스 원칙

- 계정 유형과 대상 매장의 대표 운영자 FK는 각 서버가 따로 판단하지 않고, 중앙 기준으로 동일하게 확인한다.
- 어떤 서버에서 요청이 들어오더라도 같은 권한 기준으로 검사해야 한다.
- 계정 유형 간 전환이나 권한 승격으로 해석될 수 있는 요청은 명시적인 인증 경계를 통과해야 한다.
- 공개 가입·로그인·계정 연결 API는 요청 본문의 역할 값을 권한 근거로 사용하지 않으며, 서버가 허용한 계정 유형별 흐름과 중앙 상태만 신뢰한다.
- 1차 MVP의 매장 관리 요청은 매번 대상 매장의 대표 운영자 FK와 승인·운영 상태를 확인한다. 계정 정지 또는 매장 상태 변경 뒤에는 캐시·기존 로그인 상태·인스턴스 로컬 상태로 이전 권한을 계속 인정하지 않는다.
- 로그인 시에는 계정 유형을 함께 구분해서 처리해야 한다.
- 이메일과 휴대전화 중복 여부는 단일 값이 아니라 계정 유형을 포함한 기준으로 검사해야 한다.
- 공개 조회는 다중 서버와 캐시 환경에서도 잘 동작할 수 있어야 한다.
- 비회원 조회 기능은 여러 서버와 캐시 환경에서도 잘 동작할 수 있어야 한다.
- 거래성 요청(예약, 웨이팅, 결제)은 인증된 계정 식별자를 기준으로 멱등성, 중복 제한 및 감사 추적을 적용한다.

## AUTH-002 이메일·소셜·휴대전화 로그인 수단

> 정책 상태: 확정

### 현재 확정 사항

- 일반 사용자와 매장 운영자는 같은 인증 주체나 토큰 네임스페이스를 공유하지 않는다.
- `1차 MVP`에서 일반 사용자와 매장 운영자는 계정 유형별 `이메일 + 비밀번호` 로그인을 사용한다.
- 이메일 일회용 코드나 휴대전화 OTP를 일반 사용자의 기본 보조 로그인 수단으로 사용하지 않는다.
- 1차 MVP에서 일반 사용자와 매장 운영자의 휴대전화는 로그인 수단이 아니라 `MVP 신뢰 연락처`(실제 소유 인증은 생략했지만 1차 MVP에서 사용할 수 있다고 간주한 연락처)로 저장한다.

- 연령 기준을 충족하지 못한 사용자도 일반 식당 탐색·예약 기능은 이용할 수 있다.
- 다만 연령 기준을 충족하지 못한 사용자의 주류 주문·홀드·결제와 주류 행사 예약·참여는 허용하지 않는다.
- 플랫폼의 연령 판정과 매장 현장의 신분 확인 책임은 분리한다.
- 실제 주류 제공 전 현장 나이·본인 확인은 매장 책임으로 하고, 플랫폼은 이를 직접 수행하거나 완료를 보증하지 않는다.
- 플랫폼에는 주류 이용 가능 여부와 확인 시점만 저장하고, 생년월일 원본과 현장 신분증 자료는 저장하지 않는다.
- 연령 기준 미충족 사용자에게는 일반 메뉴 정보와 일반 광고는 노출할 수 있지만, 주류 판촉 광고는 노출하지 않는다.

### 정책 근거

- 주류 기능은 일반 예약 기능보다 법적 책임과 운영 위험이 크기 때문에, 도입 전 기준을 먼저 정해 두는 것이 안전하다.
- 가입 시 이미 완료한 본인 확인 결과를 활용하면 같은 목적의 반복 인증을 줄일 수 있다.
- 일반 탐색·예약과 주류 거래를 분리하면 서비스 접근성을 유지하면서도 주류 이용 제한은 명확하게 적용할 수 있다.
- 플랫폼의 사전 연령 판정과 매장 현장의 실제 신분 확인 책임을 분리하면 책임 경계를 더 분명하게 유지할 수 있다.
- 생년월일 원본이나 현장 신분증 자료를 저장하지 않는 방향은 개인정보 최소 수집 원칙에도 맞는다.

### 다중 서버·다중 인스턴스 원칙

- 주류 기능이 도입되면 연령 판정 기준과 정책 버전은 중앙 기준으로 관리하고, 모든 인스턴스가 같은 기준으로 처리해야 한다.
- 주류 관련 쓰기 요청은 화면 노출 여부와 관계없이 서버 최종 처리 단계에서 연령 제한을 다시 검사해야 한다.
- 여러 인스턴스에서 동시에 같은 요청이 들어와도 주류 이용 제한 검사가 누락되지 않도록 처리해야 한다.
- 주류 이용 가능 여부와 확인 시점만 필요한 최소 범위로 조회하고, 생년월일 원본은 서비스 인스턴스에서 직접 다루지 않는 방향을 유지한다.
- 현장 신분 확인 완료 여부나 신분증 원본 자료는 중앙 저장소와 애플리케이션 로그에 남기지 않는다.
- 법령이나 정책이 바뀌면 특정 서버만 다르게 처리되지 않도록 중앙 정책 기준을 기준으로 일관되게 반영해야 한다.

## AUTH-005 중복 계정 판정과 로그인 수단 연결

> 정책 상태: 확정

### 현재 확정 사항

- 정책상 같은 사람은 `일반 사용자 계정` 1개와 `매장 운영자 계정` 1개를 각각 최대 1개까지 보유할 수 있다.
- 일반 사용자 계정과 매장 운영자 계정은 서로 다른 계정 유형이므로, 같은 사람이 두 유형의 계정을 각각 하나씩 보유하는 것은 허용한다.
- 같은 사람이 같은 계정 유형으로 다시 가입하려는 경우에는 새 계정을 만들지 않고 기존 계정을 안내한다.
- 다만 1차 MVP 일반 사용자는 실제 동일인 확인 수단이 없으므로 이 목표를 완전히 증명할 수 없다. 정규화 연락처 중복만 차단하고, 실제 동일인 기준의 중복 억제는 DI·CI(본인확인 업체가 제공하는 동일인 식별값) 도입 뒤 적용한다.
- `1차 MVP`의 중복 가입 판정은 계정 유형별로 정규화된 휴대전화 번호와 이메일 주소를 기준으로 한다. 일반 사용자의 직접 입력값은 실제 동일인 또는 소유 확인 증거가 아니다.
- 같은 계정 유형 안에서는 정규화된 휴대전화 번호 또는 이메일 주소 중 하나라도 기존 계정과 같으면 신규 계정을 생성하지 않는다.
- 동일한 휴대전화 번호와 이메일 주소를 일반 사용자 계정과 매장 운영자 계정에서 각각 사용하는 것은 허용한다.
- 카카오와 이메일·비밀번호 등 여러 로그인 수단을 사용하더라도 같은 계정 유형에서는 하나의 계정에 연결한다.
- 일반 사용자 계정에 연결된 카카오와 이메일·비밀번호는 모두 같은 계정의 유효한 로그인 방식으로 사용한다.
- 초기 서비스에서는 사용자가 연결된 로그인 수단을 개별적으로 해제하는 기능을 제공하지 않는다.
- 중복 여부는 가입 완료 후가 아니라 신규 계정을 생성하기 전에 확인한다.
- 가입 시도에서 중복이 발견되면 새 계정 생성 대신 기존 계정 안내 또는 로그인 수단 연결 흐름으로 전환한다.
- 로그인 수단 연결은 기존 계정의 본인임을 인증한 뒤에만 허용하며, 이메일 일치 같은 추정만으로 자동 연결하지 않는다.
- 카카오 로그인과 카카오 제공자 식별자 연결은 일반 사용자 계정에만 허용하며 매장 운영자·플랫폼 운영자 계정의 로그인 수단이나 권한 부여 경로로 사용하지 않는다.
- 카카오 제공자 식별자가 이미 연결되어 있으면 새 계정 생성이나 재연결을 시도하지 않고 연결된 일반 사용자 계정의 현재 상태·제재를 적용한다.
- 연결되지 않은 카카오 제공자 식별자를 기존 일반 사용자 계정에 추가하려면 해당 기존 계정의 유효한 재인증을 먼저 완료해야 한다. 카카오가 제공한 이메일과 등록 이메일의 일치만으로 자동 연결하지 않는다.
- 카카오 제공자 식별자가 다른 계정에 이미 연결되어 있으면 연결·이동·병합을 모두 중단하고 계정 복구를 안내한다. 플랫폼 운영자 재량으로 연결 소유 계정을 즉시 바꾸지 않는다.
- 로그인 수단 연결은 계정 유형과 서비스 권한을 변경하지 않으며, 일반 사용자 계정에 카카오를 연결한 결과로 매장 운영자·플랫폼 운영자 권한이 생기지 않는다.
- 입력한 휴대전화 또는 이메일로 계정 중복을 검사하더라도 기존 계정의 식별 정보는 노출하지 않는다. 실제 소유 확인이 없는 1차 MVP 일반 사용자에게는 기존 계정 단서나 로그인 수단 연결을 제공하지 않는다.
- 실제 연락처 소유 확인을 도입한 단계에서만 기존 계정을 찾을 수 있도록 최소한의 계정 단서를 마스킹하여 안내하고, 로그인·계정 복구·로그인 수단 연결 경로를 제공한다.
- 기존 계정의 이메일·휴대전화 전체 값이나 그 밖의 프로필 정보는 중복 가입 안내에 표시하지 않는다.
- 정규화된 휴대전화 번호와 이메일 주소가 같은 계정 유형의 서로 다른 기존 계정을 가리키면 어느 계정도 자동으로 우선하지 않는다. 1차 MVP 입력값은 소유 확인 증거가 아니므로 자동 연결 근거로 사용하지 않는다.
- 서로 다른 계정을 가리키는 충돌이 발생하면 새 계정 생성과 로그인 수단 연결을 모두 중단하고, 계정 복구를 안내하며 플랫폼 운영자 검토 대상으로 기록한다.
- 하나의 매장 운영자 계정으로 여러 매장을 관리하는 것은 중복 계정으로 보지 않는다.
- 플랫폼 운영자가 별도로 발급하는 플랫폼 운영자 계정은 공개 가입 중복 판정 범위에서 제외하고 플랫폼 운영자 정책에서 별도로 관리한다.
- 초기 서비스 범위에는 이미 생성된 두 계정의 데이터 통합 기능을 포함하지 않는다.

### 정책 근거

- 예약, 리뷰, 혜택, 제재 이력이 여러 계정으로 흩어지는 것을 방지하기 위함이다.
- 일반 사용자 계정과 매장 운영자 계정의 권한은 분리하되, 같은 유형 안에서는 계정 관계를 단순하게 유지하기 위함이다.
- 이메일이나 외부 로그인 정보가 우연히 같다는 이유만으로 자동 연결하면 계정 탈취 위험이 커질 수 있으므로 이를 방지하기 위함이다.
- 연락처 소유 확인 전에는 계정 존재를 노출하지 않음으로써 계정 탐색 공격 가능성을 줄이기 위함이다.
- 동일 유형 내 중복 가입을 막고, 필요한 경우에는 새 계정을 만드는 대신 기존 계정에 로그인 수단을 연결하는 방식으로 운영 단순성을 유지하기 위함이다.

### 다중 서버·다중 인스턴스 원칙

- 휴대전화 번호와 이메일 주소는 계정 유형별 중앙 저장소의 일관된 정규화 기준과 유일성 제약으로 관리한다. 실제 확인 여부는 값 자체와 분리된 상태로 관리하여 1차 MVP 입력값을 인증 완료로 오해하지 않는다.
- 중복 확인과 계정 생성은 하나의 원자적 경계에서 처리하여 여러 인스턴스의 동시 가입 요청이나 외부 인증 콜백에도 두 번째 계정이 생성되지 않게 한다.
- 기존 계정 인증 후 로그인 수단 연결은 원자적이고 멱등하게 처리하여 같은 연결 요청이 중복 반영되지 않게 한다.
- 외부 로그인 연결은 제공자와 제공자 식별자의 복합 유일성 제약으로 보호하고, 같은 카카오 식별자가 둘 이상의 중앙 계정에 연결되지 않게 한다.
- 연결 요청 식별자, 대상 계정 버전과 기존 계정 재인증 상태를 하나의 처리 경계에서 검증한다. 중복·역순 콜백에는 이미 확정된 연결 결과를 반환하고 계정이나 연결 관계를 추가 생성하지 않는다.
- 카카오 연결 확정 전후에 계정 유형과 권한 버전이 같음을 검증하며, 불일치하거나 중앙 상태를 확인할 수 없으면 연결을 실패 폐쇄한다.

### 현재 확정 사항

- 일반 사용자와 매장 운영자의 이메일·비밀번호 로그인에 같은 비밀번호 형식 기준을 적용한다.
- 비밀번호는 최소 8자 이상이어야 한다.
- 비밀번호는 최대 64자까지 허용하며 제한을 초과한 값을 자동으로 잘라 저장하거나 검증하지 않는다.
- 공백과 출력 가능한 ASCII 문자 및 유니코드 문자를 허용한다. 유니코드 비밀번호는 길이 판정과 저장 전 NFC 방식으로 정규화하고 유니코드 코드 포인트 하나를 한 글자로 계산한다.
- 영문 대문자, 영문 소문자, 숫자, 특수문자 중 3종 이상을 포함해야 한다.
- 비밀번호 설정 또는 마지막 변경 시점부터 90일이 지나면 변경 권고 경고를 표시한다.
- 90일이 지나도 이메일·비밀번호 로그인과 서비스 이용을 제한하지 않는다.
- 흔하거나 알려진 유출 비밀번호로 판단되면 위험 경고를 표시하되, 사용자가 원하면 설정·변경·재설정을 허용한다.

- 재설정 코드의 재전송은 직전 코드 발급 후 60초가 지나야 허용한다.

- 수동 복구 후 재설정 코드에도 발급 후 10분 유효, 재발급 시 이전 코드 즉시 무효화, 60초 재전송 대기, 최초 발급 포함 동일 이메일 1시간 최대 5회, 코드별 누적 3회 입력 실패 시 해당 코드 무효화 기준을 동일하게 적용한다.
- 새 비밀번호 설정이 성공하면 복구 후 비밀번호 재설정 필요 상태를 해제하되 자동 로그인시키지 않고 새로 로그인하게 한다.
- 수동 복구가 승인되어 등록 이메일이 교체되면 교체 전 기존 이메일에도 등록 이메일 변경 사실을 알리는 보안 알림을 발송한다. 이 알림에는 복구 후 이메일 주소, 제출 증빙과 심사 세부정보를 포함하지 않는다.
- 교체 전 이메일의 변경 보안 알림 발송에 실패해도 수동 복구 승인, 등록 이메일 교체와 기존 리프레시 상태 폐기를 되돌리지 않는다. 최초 발송 실패 후 직전 실패 시점을 기준으로 1분·5분·15분 간격으로 최대 3회 추가 재시도한다.
- 추가 재시도까지 모두 실패하면 최종 실패 상태를 보관하고 권한 있는 플랫폼 운영자에게 경보와 감사 가능한 수동 재발송 경로를 제공하되, 복구된 계정의 이용은 제한하지 않는다.
- 승인과 거절 모두 심사 사건 식별자, 대상 계정 식별자, 담당 플랫폼 운영자 식별자, 증빙별 확인 결과, 결정 결과와 사유, 처리 시각을 중앙 감사 이력에 남긴다.
- 담당 플랫폼 운영자는 자신이 생성한 감사 이력을 수정하거나 삭제할 수 없다. 수동 복구 감사 이력은 심사 처리 완료 시점부터 3년간 보관한 뒤 파기한다.
- 완료된 수동 복구 감사 이력 전체는 슈퍼관리자 또는 별도의 `계정 복구 감사 열람` 권한을 가진 플랫폼 운영자만 열람할 수 있다. `계정 복구` 승인 권한만으로는 완료된 전체 감사 이력을 열람할 수 없다.
- 진행 중인 심사 담당자는 자신에게 배정된 사건을 처리하는 데 필요한 범위만 조회하며, 이 권한을 완료된 전체 감사 이력 열람 권한으로 확대하지 않는다.
- 수동 복구 신청은 접수 후 3영업일 이내에 승인, 거절 또는 보완 요청 가운데 하나로 1차 처리 결과를 안내한다. 보완 요청 후 최종 처리 기한은 보완 자료가 다시 접수된 시점부터 새로 계산한다.
- 이메일·비밀번호 로그인은 같은 계정에서 연속 5회 실패하면 1분 동안 지연하고, 지연 종료 후 다시 실패하면 5분, 이후 다시 실패하면 최대 15분까지 단계적으로 지연한다. 15분 단계 이후의 추가 실패에는 15분 지연을 반복 적용하며 영구 잠금으로 전환하지 않는다.
- 이메일·비밀번호 로그인에 성공하면 해당 계정의 연속 실패 횟수와 지연 단계를 초기화한다. 로그인 지연 중에도 카카오 로그인과 비밀번호 재설정·계정 복구는 허용한다.
- 계정 기준 지연과 별도로 IP·요청 경로의 반복 로그인 시도를 중앙 기준으로 제한하며, 실패 횟수와 지연 상태 또는 계정 존재 여부를 응답으로 노출하지 않는다. 별도 기기 지문 수집이나 유료 봇 방어 서비스는 현재 범위에 포함하지 않는다.
- 플랫폼 운영자의 임시 비밀번호와 최초 변경 기준은 ADMIN-001에서 별도로 관리한다.

### 정책 근거

- 최신 길이 중심 권고보다 사용자에게 익숙한 복잡도 규칙을 우선한다.
- 일반 사용자와 매장 운영자에게 같은 형식 기준을 적용하여 안내와 운영 기준을 단순화한다.
- 90일 주기의 변경 권고로 비밀번호 점검 계기를 제공하되, 강제 변경으로 인한 로그인 중단과 사용자 불편은 피한다.
- 취약한 비밀번호를 강제로 거부하기보다 위험을 알리고 사용자의 선택을 허용하여 설정 과정의 마찰을 낮춘다.
- 소유 확인을 마친 이메일이 있는 계정 유형과 단계에서는 그 이메일을 재사용하여 초기 재설정 절차를 단순화하고 외부 휴대전화 본인확인 사업자에 대한 상시 의존을 피한다. 1차 MVP 일반 사용자는 이 근거가 없으므로 자동 재설정 예외를 적용하지 않는다.
- 숫자 코드는 이메일을 확인한 기기와 비밀번호를 재설정하는 기기가 달라도 입력할 수 있고 사용자에게 익숙한 흐름이다.
- 10분의 유효기간은 정상적인 이메일 확인 시간을 제공하면서 노출된 코드의 악용 가능 시간을 제한한다.
- 재발급할 때 이전 코드를 무효화하여 동시에 유효한 코드를 하나로 제한하고 코드 검증 상태를 단순화한다.
- 60초의 재전송 대기시간은 정상적인 이메일 도착을 기다리게 하면서 중복 발송과 발송 자원 남용을 줄인다.
- 1시간 최대 5회 제한은 정상적인 이메일 지연·유실에 대응할 여유를 두면서 반복 발송에 따른 괴롭힘·비용·트래픽을 억제한다.
- 코드당 3회 실패 제한으로 추측 기회를 줄이되, 계정 전체를 잠그지 않아 제3자가 고의 실패로 일반 로그인을 차단하는 상황을 피한다.
- 재설정 성공 시 계정 단위로 모든 리프레시 상태를 폐기하여 공격자가 이미 확보한 리프레시 토큰이 비밀번호 변경 뒤에도 갱신에 사용되는 상황을 막는다.
- 등록 이메일 보안 알림으로 사용자가 본인이 요청하지 않은 비밀번호 재설정을 인지할 수 있게 한다.
- 이메일 발송 장애를 계정 복구 트랜잭션과 분리하여 외부 이메일 사업자 장애가 비밀번호 재설정을 중단시키거나 결과를 모호하게 만들지 않게 한다.
- 최대 3회의 추가 재시도로 일시적 장애를 흡수하되 무한 재시도와 대규모 작업 적체를 방지한다.
- 1분·5분·15분으로 늘어나는 간격은 짧은 장애에는 빠르게 대응하면서 장애가 지속될 때 이메일 사업자와 작업 큐에 부하가 집중되는 것을 완화한다.

- 등록 이메일 접근 불가 상황을 플랫폼 운영자 수동 심사로 분리하여 자동 복구 경로의 공격 표면을 줄이되, 운영 부담과 사회공학 위험은 구체적인 심사 기준으로 통제해야 한다.
- 등록 휴대전화·복구 후 사용할 이메일 소유 확인을 공통 기준으로 사용하고 매장 운영자에게 사업자등록증을 추가 요구하여 계정 유형별 위험에 맞는 고정 심사 기준을 둔다.
- 일반 사용자의 추가 비교 항목을 기존 등록 이메일 주소로 한정하여 신규·저빈도 사용자도 같은 기준으로 심사하되, 이메일 주소 단독의 낮은 확인 강도는 등록 휴대전화·복구 후 사용할 이메일 소유 확인과 플랫폼 운영자 최종 승인으로 보완한다.
- 기존 이메일 소유를 다시 확인한 경우에는 일반 재설정으로 돌리고, 확인할 수 없는 경우에만 다른 이메일로 교체하여 복구 후 로그인·재설정·보안 알림을 정상적으로 사용할 수 있게 한다.
- 수동 복구 시 모든 기존 리프레시 상태를 계정 단위로 폐기하여 이메일 접근권 상실 과정에서 탈취됐을 수 있는 리프레시 토큰이 복구 뒤에도 갱신에 사용되는 상황을 막는다.
- 수동 복구 후 새 비밀번호를 반드시 설정하게 하여 기존 비밀번호가 노출됐을 가능성까지 차단하고, 그 전에는 카카오 로그인으로 우회하여 계정에 접근하지 못하게 한다.
- 교체 전 이메일에도 민감정보 없는 변경 알림을 남겨 잘못 승인된 복구를 기존 이메일 소유자가 인지할 가능성을 확보한다.
- 이메일 사업자의 일시적 장애와 계정 복구 결과를 분리하고 기존 보안 알림과 같은 재시도·최종 실패 관리 기준을 적용하여 운영 복잡도를 줄인다.
- 매장 운영자는 관리 중인 매장 1곳의 사업자등록번호와 대표자명을 모두 비교하여 핵심 사업자·대표자 관계를 확인하면서 다매장 계정의 서류 부담을 제한한다.
- 등록 이메일과 휴대전화를 모두 사용할 수 없는 상황에서는 대체 증빙을 받지 않아 민감정보 수집과 사회공학 공격 경로를 늘리지 않는다.
- 전용 계정 복구 권한과 변경 불가능한 승인·거절 이력으로 담당 플랫폼 운영자를 명확히 식별하고 단일 승인 방식의 책임소재를 확보한다.
- 복구 승인 권한과 완료된 전체 감사 이력 열람 권한을 분리하여 업무에 필요하지 않은 계정·증빙 결과의 노출 범위를 줄인다.

- 최대 64자와 공백·유니코드 지원으로 긴 암호문 사용과 비밀번호 관리자를 지원하되, 입력을 자동으로 자르지 않아 서로 다른 비밀번호가 같게 처리되는 상황을 막는다.
- 수동 복구의 3영업일 1차 처리 기한으로 승인 품질을 유지하면서 신청자가 처리 상태를 예측할 수 있게 한다.
- 점진적 지연과 기본 IP·요청 경로 제한을 함께 적용하여 분산 추측 공격을 늦추면서 공격자가 고의 실패로 계정 전체를 영구 잠그는 서비스 거부 위험을 줄인다. 기기 지문과 유료 봇 방어를 제외하여 추가 개인정보 수집·비용·구현 복잡도를 피한다.

### 다중 서버·다중 인스턴스 원칙

- 비밀번호 형식 기준과 정책 버전은 중앙 설정을 기준으로 모든 인스턴스에 동일하게 적용한다.
- 비밀번호 길이는 NFC 정규화 후 유니코드 코드 포인트 기준으로 중앙에서 동일하게 판정하고 64자를 초과한 입력은 잘라내지 않고 거부한다.
- 마지막 비밀번호 설정·변경 시점과 90일 경과 및 경고 대상 여부는 중앙 계정 상태와 공통 기준 시각으로 판정하며 애플리케이션 인스턴스의 로컬 시각이나 세션 상태에 의존하지 않는다.
- 90일 경과 경고 여부는 인증 성공과 서비스 권한 판정을 거부하는 조건으로 사용하지 않는다.
- 동시에 발생한 비밀번호 변경 요청은 계정 버전 또는 원자적 갱신 기준으로 하나만 확정되게 한다.
- 흔하거나 유출된 비밀번호의 판정 기준과 경고 문구 버전은 중앙에서 관리하여 모든 인스턴스가 동일한 경고 결과를 제공한다.
- 6자리 숫자 일회용 재설정 코드의 발급·사용·무효화 상태는 중앙에서 관리하고, 여러 인스턴스에서 동시에 사용되더라도 원자적으로 한 번만 성공하게 한다.
- 코드 만료는 중앙 발급 시각과 공통 기준 시각으로 판정하여 모든 인스턴스에서 동일한 10분 유효기간을 적용한다.
- 코드 재발급과 이전 코드 무효화는 중앙에서 하나의 원자적 처리 경계로 수행하여 동시 재발급 요청에도 최신 코드 하나만 유효하게 한다.

## AUTH-007 세션·토큰·기기 관리

> 정책 상태: 확정

### `1차 MVP` 확정 사항

- `1차 MVP`의 일반 사용자·매장 운영자는 계정 유형별로 분리된 stateless Access JWT와 Refresh JWT를 사용한다. 플랫폼 운영자는 고도화에서 별도 계정과 인증 경계를 활성화한다.
- 두 JWT는 서명·만료·발급자·대상·토큰 종류·계정 유형과 허용된 최소 클레임을 검증한다. 계정 유형별 발급자 또는 대상을 혼용하지 않는다.
- 정상 Access JWT 목록, 정상 Refresh JWT 목록, 리프레시 상태, 세션이나 토큰 원문을 애플리케이션 서버·MySQL·Valkey에 저장하거나 요청마다 조회하지 않는다.
- Refresh JWT 갱신은 유효한 서명·만료·발급자·대상·토큰 종류와 계정 유형을 검증한 뒤 같은 계정 유형의 새 Access JWT와 Refresh JWT를 발급한다.
- 서버 저장 상태가 없으므로 개별 Refresh JWT 회전, 서버 측 로그아웃 폐기, 토큰 재사용 탐지, 활성 로그인 목록과 개별 로그인 종료는 제공하지 않는다.
- 로그아웃은 클라이언트가 보유 토큰을 제거하는 경계이며 이미 발급된 JWT를 서버 저장 상태로 폐기했다고 표시하지 않는다. 계정 정지·권한 회수 요청은 현재 중앙 계정·권한 검증이 필요한 보호 명령에서 실패 폐쇄한다.

### `고도화` 확정 방향

- Refresh Token 원문 대신 안전한 해시와 계정·로그인 단위·토큰 계열 식별자, 만료, 폐기·교체 상태와 필요한 최소 기기 표시 정보를 Valkey에 저장한다.
- Refresh Token을 사용할 때마다 기존 토큰을 폐기하고 새 토큰으로 회전한다. 폐기·교체 토큰 재사용을 탐지하면 해당 토큰 계열을 폐기하고 AUTH-012 위험 사건으로 연결한다.
- 로그아웃·계정 정지·권한 회수·개별 로그인 종료·전체 로그인 종료는 대상 로그인 단위나 토큰 계열의 Valkey 상태를 폐기한다.
- 로그아웃은 대상 리프레시 상태의 현재 존재 여부와 관계없이 멱등하게 처리한다. 이미 만료·폐기됐거나 존재하지 않는 상태도 새 로그인 상태를 만들지 않은 채 같은 종료 결과로 수렴한다.
- 모든 계정 유형은 자신의 활성 로그인 목록에서 현재 로그인 여부, 로그인 시각과 필요한 최소 기기 표시 정보를 확인하고 개별 로그인 또는 현재 로그인을 제외한 모든 로그인을 종료할 수 있다.
- 로그인 표시를 위해 정밀 위치나 지속적인 기기 지문을 수집하지 않으며 IP 주소 원문을 사용자 화면에 노출하지 않는다.
- Valkey 상태를 확인할 수 없으면 로그인·갱신·로그아웃처럼 해당 상태 확인이 필요한 요청을 실패 폐쇄하며 MySQL이나 로컬 상태로 우회하지 않는다.
- Valkey 장애 중에도 기존 유효 Access JWT 요청은 서명·만료·현재 계정·권한 검증 경계를 통과한 경우에만 처리한다. Valkey 장애만으로 비회원 공개 조회를 중단하지 않는다.

### 단계 공통 확정 세부

- Access JWT 유효기간은 발급 시각부터 1시간이다.
- Refresh JWT 유효기간은 발급 시각부터 14일이다.
- 현재 활성화된 계정 유형의 분리된 토큰 namespace에 같은 유효기간을 적용한다. 1차 MVP는 일반 사용자·매장 운영자만 해당하며 플랫폼 운영자는 고도화 구현 시 적용한다.
- 로컬·개발·운영 런타임 프로필은 같은 값을 사용하고 만료 경계 테스트에서만 더 짧은 값을 주입할 수 있다.
- 이 유효기간 결정은 1차 MVP의 무저장 JWT, 클라이언트 로그아웃과 고도화의 Valkey 회전·폐기 정책을 변경하지 않는다.
- `1차 MVP`의 로그인·재발급 성공 응답은 Access JWT를 응답 본문으로 전달하고 프런트엔드는 shell별 메모리에만 보관한다. 보호 API는 `Authorization: Bearer` 헤더를 사용한다.
- Refresh JWT는 계정 namespace별 이름과 경로가 분리된 `HttpOnly`, `Secure`, `SameSite=Lax` 쿠키로만 전달하고 응답 본문·Web Storage에 원문을 노출하지 않는다.
- Refresh Token 쿠키를 사용하는 재발급은 동일 Origin의 `POST` JSON 요청과 `Origin`·`Referer` 검증을 요구한다. 로그아웃에는 Spring Security CSRF 보호를 적용하고 shell 메모리의 Access JWT와 해당 namespace 쿠키를 제거한다.
- 하나의 Vite 빌드 안에서도 계정 shell의 인증 상태와 토큰 namespace를 합치지 않는다. 상세 브라우저 계약과 인수 조건은 [1차 MVP 공통 명세 D-003](../specs/mvp1-common/spec.md#d-003-브라우저-토큰-전달저장과-csrf-경계)을 따른다.
- `1차 MVP`에는 계정별 동시 로그인 상한, 활성 로그인 목록, 오래된 로그인 자동 종료, 기기별 종료와 다른 로그인 전체 종료를 두지 않는다. 같은 브라우저·namespace의 Refresh Token 쿠키 교체를 다른 브라우저까지 적용되는 로그인 제한으로 해석하지 않는다.
- 과거 중앙 세션 정책의 계정 유형별 동시 세션 수를 `1차 MVP` JWT에 변환하지 않는다. 정확한 로그인 상한과 초과 처리 순서는 Valkey 로그인 상태를 도입하는 `고도화` 활성화 전에 별도 결정한다.
- 2026-07-21에 확정한 정상 비밀번호·등록 이메일 변경 시 기존 로그인 유지 정책을 단계 변경 없이 적용한다. `1차 MVP`는 정상 변경만을 이유로 이미 발급된 JWT를 폐기하거나 다른 브라우저가 종료됐다고 표시하지 않는다.
- 비밀번호 재설정·수동 계정 복구·탈취 신고·보안 잠금·계정 정지·권한 회수는 정상 변경과 구분하고 각 기존 정책의 단계 경계를 따른다. 고도화에서도 정상 변경의 기본값은 로그인 유지이며 명시적 종료 요청이나 별도 보안 사건에만 Valkey 폐기 정책을 적용한다.
- `1차 MVP`에는 새로운 공통 `auth_time`, 최근 로그인 유효시간이나 추가 인증 토큰을 도입하지 않는다. 보호 명령은 기존 정책대로 현재 계정 상태·계정 유형·권한, 대상 매장의 대표 운영자 FK, 대상 자원 소유권과 매장 상태를 필요한 범위에서 중앙 재검증한다.
- 개별 활성 정책에 이미 재인증이 명시된 작업만 해당 절차를 적용하고 모든 중요 명령에 현재 비밀번호 확인을 새로 확대하지 않는다. 플랫폼 운영자 중요 작업 재인증은 기존대로 `고도화`에서만 활성화한다.
- 2026-07-21에 정한 세션 유휴·절대 만료값은 액세스 토큰이나 리프레시 토큰 수명으로 자동 변환하지 않는다.

### 정책 근거

- `1차 MVP`는 서버 토큰 저장소 없이 계정 유형별 JWT 검증 경계를 먼저 확인하여 운영 요소를 최소화한다.
- `고도화`는 리프레시 상태를 Valkey에 두고 회전·폐기·재사용 탐지를 추가하여 탈취된 토큰 계열의 확산을 제한한다.
- 상세 선택 이유와 검토한 대안은 [ADR-006](../adr/ADR-006-jwt-valkey-refresh-token.md)에서 관리한다.

### 다중 서버·다중 인스턴스 원칙

- `1차 MVP`의 모든 인스턴스는 동일한 계정 유형별 JWT 검증 설정을 사용하고 로컬 세션이나 정상 토큰 목록에 의존하지 않는다.
- `고도화`의 모든 인스턴스는 같은 Valkey 리프레시 상태를 사용한다. 발급·회전·만료·폐기·재사용 탐지는 중앙 상태를 기준으로 처리하며 로컬 캐시나 MySQL로 우회하지 않는다.
- `고도화`에서 리프레시 상태 폐기와 재사용 보안 사건은 계정·로그인 단위·토큰 계열·해시 기반 식별값을 기준으로 멱등하게 기록하며 토큰 원문을 로그나 감사 기록에 남기지 않는다.
- 후속 감사·알림 실패는 확정된 폐기를 되돌리지 않고, 장기 실패는 플랫폼 운영자 경보로 남긴다.

### 관측 가능한 인수 조건

- `1차 MVP`에서 일반 사용자 JWT와 매장 운영자 JWT를 서로 바꾸어 보내면 발급자·대상·계정 유형 검증에서 거부되고, 서버 저장 토큰·세션 상태가 생성되지 않는다. 플랫폼 운영자 토큰은 1차 MVP에서 발급되지 않는다.
- `고도화`에서 같은 Refresh Token으로 동시에 갱신을 요청해도 한 번만 회전하며, 교체 토큰 재사용은 해당 토큰 계열 폐기와 AUTH-012 위험 사건으로 연결된다.
- `고도화`에서 로그아웃을 반복하거나 여러 인스턴스에 동시에 보내도 같은 종료 결과로 수렴하고, 활성 로그인 종료 뒤 해당 로그인은 다시 갱신되지 않는다.
- `고도화`의 활성 로그인 표시에 최소 기기 정보만 남고 정밀 위치·지속적인 기기 지문·IP 주소 원문이 노출되지 않는다.
- `고도화`의 Valkey 장애 중 로그인·갱신·로그아웃은 실패 폐쇄되고, 기존 유효 Access JWT 요청과 공개 조회는 각각 정해진 검증 경계 안에서 처리된다.

## AUTH-008 사용자 이름·닉네임·프로필 규칙

> 정책 상태: 확정

### 현재 확정 사항

- 일반 사용자의 공개 닉네임은 로그인 이메일, 휴대전화, 실명과 분리하며 계정·권한·거래의 식별에는 공개 닉네임이 아닌 변경되지 않는 중앙 계정 식별자를 사용한다.
- 닉네임은 중복을 허용한다. 닉네임을 설정하지 않은 계정에는 내부 계정 식별자를 노출하지 않는 임의의 기본 표시명을 부여한다.
- 닉네임은 NFC 정규화 후 2자 이상 20자 이하로 제한하고 한글·영문·숫자·공백·밑줄·하이픈만 허용한다. 앞뒤 공백을 제거하고 연속 공백은 하나로 정규화한다.
- 이메일 주소·휴대전화 번호·URL 형태, MiriYum·플랫폼 운영자·가게 공식 계정으로 오인하게 하는 예약어와 기본 금칙어는 닉네임으로 사용할 수 없다.
- 일반 사용자는 닉네임을 7일에 한 번 변경할 수 있다. 신고 또는 정책 위반으로 변경된 경우에는 플랫폼 운영자가 즉시 재설정을 요구할 수 있다.
- 프로필 이미지는 선택 사항이며 설정하지 않으면 기본 이미지를 사용한다. 업로드는 JPEG·PNG·WebP 형식과 파일당 5MB 이하로 제한하고 공개 전에 이미지로 재처리하여 원본 메타데이터와 비이미지 내용을 제거한다.
- 일반 사용자의 이메일·휴대전화·본인확인 실명은 공개 프로필에 표시하지 않는다. 매장 운영자가 관리하는 매장명·매장 이미지는 사용자 닉네임·프로필이 아니라 매장 정책에서 관리한다.
- 닉네임·프로필 정책 위반은 무료 내부 예약어·금칙어 목록과 사용자 신고·플랫폼 운영자 검토로 처리하며 유료 외부 콘텐츠 검수 API를 필수로 사용하지 않는다.

### 정책 근거

- 공개 표시명과 내부 계정 식별자를 분리하여 닉네임 변경·중복이 예약·리뷰·신고의 귀속을 바꾸지 않게 한다.
- 제한된 문자·길이와 단순 정규화로 화면 깨짐과 사칭을 줄이면서 팀 프로젝트에서 구현 가능한 범위를 유지한다.
- 실명·연락처 비공개와 이미지 메타데이터 제거로 프로필에 불필요한 개인정보가 노출되는 위험을 줄인다.

### 다중 서버·다중 인스턴스 원칙

- 닉네임 정규화, 예약어·금칙어 버전과 최근 변경 시각은 중앙 상태로 관리하여 모든 인스턴스가 같은 7일 변경 제한과 검증 결과를 적용한다.
- 프로필 변경은 계정 식별자를 기준으로 멱등하게 처리하고, 변경 사건을 기준으로 프로필 캐시를 무효화하여 여러 인스턴스에서 이전·신규 값이 장기간 혼재하지 않게 한다.
- 이미지 검증·재처리가 완료되기 전 파일은 공개하지 않으며 같은 업로드가 중복 처리되어도 공개 프로필에는 하나의 확정 이미지 버전만 연결한다.

## AUTH-009 보호자·미성년자 이용 범위

### 다중 서버·다중 인스턴스 원칙

- 탈퇴 대기 상태, 요청 시각과 삭제 예정 시각은 중앙 계정 상태를 단일 기준으로 관리하며 모든 인스턴스가 즉시 같은 접근 차단 결과를 적용한다.

- 자동 취소 명령은 거래별 멱등 키를 사용하여 여러 인스턴스의 재시도에도 한 번만 확정한다. 모든 대상의 취소 성공을 확인하기 전에는 계정을 탈퇴 대기로 전환하지 않으며, 일부 취소 후 실패한 경우 이미 취소된 거래를 되살리지 않고 남은 거래를 안내한다.

- 장기 미사용 여부를 애플리케이션 인스턴스별 로컬 상태로 관리하거나 권한 판정에 사용하지 않는다. 모든 인스턴스는 중앙 계정 상태와 AUTH-007의 리프레시 상태 만료·폐기 결과를 동일하게 적용한다.

### 현재 확정 사항

- 계정 제재는 `경고`, `특정 기능 제한`, `기간 정지`, `영구 정지`의 단계로 운영한다.
- 일반적인 위반은 위반의 심각도·반복성·피해 범위에 따라 단계적으로 강화한다.
- 사기, 계정 탈취, 결제 악용 또는 심각한 안전 위협처럼 즉시 피해 확산을 막아야 하는 중대한 사건은 앞 단계를 생략하고 기간 정지나 영구 정지를 적용할 수 있다.
- 모든 제재에는 대상 계정, 제재 단계, 적용·종료 시각, 플랫폼 운영자, 사유와 근거를 연결하여 감사 가능한 중앙 이력으로 남긴다.
- 경고·특정 기능 제한·기간 정지는 중앙 권한 저장소에서 `계정 제재` 권한을 가진 플랫폼 운영자 1명이 확정할 수 있다.
- 사기·계정 탈취·결제 악용·심각한 안전 위협의 긴급 차단도 `계정 제재` 권한 플랫폼 운영자 1명이 즉시 기간 정지로 적용할 수 있다.
- 영구 정지는 `계정 제재` 권한 플랫폼 운영자가 제안하고 슈퍼관리자가 추가 승인해야 확정된다. 제안과 추가 승인은 서로 다른 플랫폼 운영자 계정으로 수행하며 슈퍼관리자 승인 전에는 영구 정지로 전환하지 않는다.
- 기간 정지 또는 영구 정지가 확정되면 로그인 방식과 관계없이 모든 리프레시 상태를 즉시 폐기하고 현재 계정 상태 검증으로 기존 액세스 JWT 요청과 이후 로그인을 완전히 차단한다. 정지된 계정에 제재 안내나 이의 제기를 위한 제한 로그인 화면은 제공하지 않는다.
- 기간·영구 정지 확정 직후 등록 이메일로 제재 단계, 적용·종료 시각 또는 영구 정지 여부, 사유 요약과 고객지원 이의 제기 방법을 안내한다. 신고자 신원이나 공개하면 안 되는 내부 증거는 이메일에 포함하지 않는다.
- 이메일 발송 실패는 확정된 제재를 취소하거나 로그인 차단을 지연시키지 않는다. 발송은 비동기로 처리하고 최초 실패 후 1분·5분·15분 간격으로 최대 3회 추가 재시도하며 최종 실패를 플랫폼 운영자 경보와 수동 재발송 대상으로 남긴다.
- 고객지원 이의 제기는 계정에 등록된 휴대전화 또는 등록 이메일 가운데 하나의 소유 확인을 완료하면 접수할 수 있다.
- 소유 확인 전에는 해당 연락처의 계정 존재 여부, 제재 단계·사유·근거와 신고자 정보를 공개하지 않는다. 두 등록 연락수단을 모두 사용할 수 없으면 AUTH-006의 계정 복구로 연락처 소유권을 먼저 회복해야 한다.
