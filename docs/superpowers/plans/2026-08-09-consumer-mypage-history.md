# 소비자 마이페이지 이력 조회 구현 계획

## 목적

Issue #155의 고도화 범위를 결제·환불, 웨이팅, 알림 이력 조회로 구현한다. 이 계획은 1차 MVP의 예약 이력 조회와 섞이지 않도록 고도화 경계와 선행 계약을 고정하기 위한 문서다.

## 현재 확인된 상태

- `ConsumerAccountController`에는 본인 계정 조회와 예약 이력 조회만 있다.
- 예약 이력은 예약 도메인의 공개 조회 계약을 호출하며, 현재 페이지 번호 기반이다.
- `dev`에는 결제·환불, 웨이팅, 알림 원장과 공개 조회 API 구현이 없다.
- 따라서 이 브랜치에서는 결제·웨이팅·알림의 원장, 엔티티, migration, 조회 API를 추측해서 만들지 않는다.

## 구현 경계

### 포함

- 로그인한 일반 사용자의 본인 데이터만 조회
- 결제·환불 이력 조회용 마이페이지 조합 경계
- 현재·과거 웨이팅 이력 조회용 마이페이지 조합 경계
- 예약·취소·환불·웨이팅 호출 알림을 `type`으로 구분하는 알림 이력 조회 경계
- 각 원 도메인의 공개 조회 계약을 호출하는 조합 서비스
- 안정적인 커서 페이지네이션과 커서 경계 테스트
- 빈 결과, 타인 데이터 접근 차단, 상태 필터 테스트

### 제외

- 결제·환불·웨이팅 명령 로직
- 결제·알림 외부 제공자 연동 및 실제 발송
- 새로운 원장 테이블을 마이페이지가 직접 소유하는 구조
- 관리자 통합 조회
- 기존 예약 이력 API의 페이지 번호 계약 변경

## 선행 계약

각 원 도메인 담당자가 아래 공개 조회 계약을 먼저 제공해야 한다.

| 원 도메인 | 필요한 공개 계약 | 마이페이지가 직접 하지 않는 일 |
|---|---|---|
| 결제 | 소비자 계정 ID 기준 결제·환불 이력 조회, 상태·금액·시각·관련 예약 참조 | 결제 상태 확정, 환불 실행, 금액 계산 |
| 웨이팅 | 소비자 계정 ID 기준 현재·과거 웨이팅 조회, 호출·종료 상태와 시각 | 대기 순번 변경, 호출, 취소 |
| 알림 | 소비자 계정 ID 기준 알림 이력 조회, `type` 필터와 전달 상태 | 알림 발송, 재시도, 외부 채널 호출 |

공개 계약에는 최소한 다음을 확정해야 한다.

- 요청 주체는 Access Token의 소비자 계정 ID로 고정한다.
- 다른 계정 ID를 query parameter나 path로 받지 않는다.
- 기본 20개, 최대 50개의 커서 페이지네이션을 사용한다.
- 정렬은 최신 생성 시각 내림차순이며 동률이면 원 도메인 이력 ID 내림차순이다.
- 다음 커서는 불투명 값으로 반환하고, 클라이언트가 내부 ID나 시간 값을 조작해 직접 구성하지 않도록 한다.
- 삭제·마스킹·보존 정책은 원 도메인이 소유하며 마이페이지는 공개 DTO만 조합한다.

## 구현 순서

1. 결제·웨이팅·알림 담당자가 공개 조회 DTO, 필터, 커서 규칙과 소유 범위를 확정한다.
2. 각 원 도메인에 계약 테스트를 추가한다.
3. 마이페이지 조합 서비스가 원 도메인 공개 포트를 호출하도록 연결한다.
4. 마이페이지 응답 DTO와 OpenAPI를 추가한다.
5. 빈 결과, cursor 경계, 타인 접근, 상태 필터와 원 도메인 장애 매핑을 테스트한다.
6. 원 도메인 데이터와 staging 응답을 확인한 뒤 고도화 Draft PR을 Ready로 전환한다.

## 변경 허용 범위

선행 계약이 준비되기 전에는 이 파일과 Issue #155의 계획만 변경한다. 계약이 준비된 뒤 구현 PR에는 다음 경로만 포함한다.

- `backend/src/main/java/com/miriyum/domain/consumer/`
- `backend/src/test/java/com/miriyum/domain/consumer/`
- `backend/src/main/java/com/miriyum/domain/*/port/` 또는 원 도메인이 제공하는 공개 조회 포트 경로
- `backend/src/test/java/com/miriyum/domain/*/`
- `docs/specs/`의 마이페이지 관련 정본
- `frontend/src/shared/api/generated/`는 OpenAPI 생성 결과가 필요한 경우 프론트 담당자와 함께 갱신한다.

## 검증 기준

- 원 도메인 원장을 직접 조회하거나 상태를 변경하지 않는다.
- 소비자 계정 ID가 다른 요청은 조회 결과를 반환하지 않는다.
- 첫 페이지, 마지막 페이지, 잘못된 커서, 만료된 커서를 검증한다.
- 빈 이력은 성공 응답과 빈 목록으로 반환한다.
- 외부 제공자 장애와 원 도메인 조회 장애는 마이페이지 성공으로 숨기지 않고 공통 오류 계약으로 매핑한다.
- 결제·웨이팅·알림 기능이 아직 준비되지 않은 동안에는 이 계획을 근거로 임시 성공 응답이나 가짜 데이터를 만들지 않는다.
