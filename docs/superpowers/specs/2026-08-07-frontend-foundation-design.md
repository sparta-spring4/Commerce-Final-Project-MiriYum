# 프론트엔드 공통 기반 설계

## 목표

GitHub Issue #191의 프론트엔드 공통 실행 기반을 구현한다. 이후 화면 Issue(#192, #37, #38, #193, #194, #195, #196)가 API 호출 방식, 응답 봉투 해석, 오류 코드 판정, 멱등 키 생성, 비동기 상태 표현, 라우팅과 테스트 하네스를 각자 다시 만들지 않게 한다.

화면은 만들지 않는다. 인증 판단(#192)과 기능 화면은 이 범위가 아니며, 이 Issue는 그것들이 꽂힐 자리만 제공한다.

## 범위와 작업 단위

| 영역 | 소유 경로 | 내용 |
| --- | --- | --- |
| 의존성 | `package.json`, `pnpm-lock.yaml` | 이 Issue가 단독 소유. 화면 Issue는 공유 의존성을 직접 추가하지 않는다 |
| 앱 셸 | `src/app/**` | 라우트 표, 공통 레이아웃, 404·권한 없음, 오류 경계, 목적지 보존 |
| API 경계 | `src/shared/api/**` | 생성 타입, HTTP 클라이언트, 오류 매핑, 멱등 키 |
| 공통 표현 | `src/shared/ui/**` | 비동기 상태 표현 |
| 테스트 하네스 | `src/test/**` | MSW 핸들러, setup |
| dev 검증 | `vite.config.ts` | `/api` 프록시는 #197이 이미 제공. 이 Issue는 변경하지 않는다 |

`src/features/**`는 화면 Issue가 소유한다. 이 Issue는 그 아래에 파일을 만들지 않는다.

## 도입 라이브러리 결정

각 결정은 `docs/08-ui-and-frontend-guidelines.md`가 요구하는 동작에서 도출한다. 요구가 없는 편의 라이브러리는 도입하지 않는다.

| 결정 | 선택 | 근거 |
| --- | --- | --- |
| 라우팅 | React Router | 계정 shell별 분리된 route 가드와 목적지 보존이 필요하다. 표준 선택이며 `useNavigate`·`Navigate`로 로그인 복귀 경로를 표현한다 |
| 서버 상태 | TanStack Query | `docs/08`이 `초기·로딩·빈 상태·성공·검증 오류·권한 없음·충돌·결과 불명·재시도 가능·복구 대기` 구분을 요구한다. 7개 기능에서 이 상태 기계를 손으로 반복 구현하는 것보다 낫다 |
| 타입 생성 | openapi-typescript | 인수 조건이 "생성 타입 또는 OpenAPI 기반 클라이언트"를 요구한다. 런타임 client를 만들지 않고 타입만 생성해 `fetch` 위에 얹는다 |
| HTTP | 표준 `fetch` | 프록시가 same-origin을 만들어 주므로 별도 HTTP 라이브러리가 필요 없다 |
| 모의 서버 | MSW | 인수 조건이 미구현 backend 계약을 MSW로만 다루도록 요구한다 |
| UUID | `crypto.randomUUID()` | 브라우저 표준. `Idempotency-Key` 생성에 외부 의존성이 필요 없다 |

디자인 시스템·테마·CSS 프레임워크는 도입하지 않는다. 이 Issue의 범위가 아니며 화면 Issue가 필요를 근거로 별도 판단한다.

## 응답 봉투 설계

backend는 성공과 실패의 본문 모양이 다르다.

```
성공: { code: "SUCCESS", message: string, data: T | null }
실패: { code: "COMMON_001", message: string, details?: ValidationErrorDetail[] }
```

실패는 `ApiResponse`로 감싸지 않는다. 따라서 클라이언트는 HTTP status로 두 모양을 먼저 가른 뒤 `code`를 읽는다. `docs/08`이 요구하는 "HTTP status와 공통 응답 `code`를 함께 평가"가 이 지점이다.

성공 응답에서 `data: null`은 정상적인 응답 데이터 없음이며 오류가 아니다. 빈 배열도 정상 empty result다. 클라이언트는 둘 다 오류 상태로 바꾸지 않는다.

## HTTP 클라이언트 설계

`requestApi`는 성공 시 `data`를 반환하고 실패 시 `ApiError`를 던진다. TanStack Query가 `error` 상태로 받아 화면이 오류 코드별로 분기한다.

`ApiError`는 다음을 보존한다.

- `status` — HTTP status
- `code` — `COMMON_001`~`COMMON_012` 또는 도메인 코드
- `message` — 서버가 준 사용자 표시 문구
- `details` — 필드 오류 목록 또는 없음

클라이언트가 서버 오류 코드를 자체 해석해 성공으로 바꾸지 않는다. 네트워크 실패와 응답 파싱 실패는 서버가 준 코드가 아니므로 별도 판별자로 구분해 "재시도 가능" 상태로 다루고, 서버 코드가 있는 것처럼 위장하지 않는다.

요청 본문은 생성 타입으로 제한한다. backend가 `spring.jackson.deserialization.fail-on-unknown-properties: true`라서 OpenAPI에 없는 필드를 보내면 400이다.

## 인증 이음새

이 Issue는 토큰을 보관하거나 재발급을 판단하지 않는다. #192가 그것을 소유한다. 대신 두 이음새만 제공한다.

1. **Authorization 주입 지점** — 클라이언트가 요청 직전에 호출하는 토큰 공급 함수를 주입받는다. 기본값은 토큰 없음이며, #192가 계정 shell별 공급자를 꽂는다.
2. **401 후처리 지점** — 401 응답에 대해 호출되는 처리 함수를 주입받는다. 기본값은 그대로 `ApiError`를 던지는 것이며, #192가 재발급·복귀를 구현한다.

이음새를 주입으로 두는 이유는 계정 shell이 둘이고 서로 토큰을 공유하지 않기 때문이다. 클라이언트가 전역 단일 토큰을 들고 있으면 `docs/08`의 shell 분리 규칙을 깬다.

## 멱등 키 설계

`Idempotency-Key`는 **HTTP 호출이 아니라 논리적 작업 시도**에 붙는다. 같은 입력으로 재시도하면 같은 키를 유지해야 하고, 사용자가 입력을 바꿔 새로 제출하면 새 키여야 한다. 키를 요청 함수 안에서 매번 생성하면 재시도가 새 키를 받아 `COMMON_007` 없이 중복 실행될 수 있다.

따라서 키 생성은 작업 시작 시점에 한 번 수행하고 재시도 동안 보존한다. 이 기반은 키를 만들고 붙이는 수단만 제공하며, 어떤 작업이 하나의 시도인지는 화면 Issue가 정한다.

## 라우트 표와 목적지 보존

라우트 정의는 `src/app`이 단독 소유한다. 화면 Issue는 자기 route만 이 표에 등록하고 라우터 설정을 각자 만들지 않는다. 계정 shell별 네비게이션 항목도 여기서 분리한다. 1차 MVP에 없는 기능의 항목·링크·자리표시자는 만들지 않는다.

목적지 보존은 인증이 필요한 지점에서 원래 가려던 경로를 기록해 두는 수단이다. 복귀 여부와 교차 namespace 차단은 #192가 판단한다. 이 Issue는 보존과 조회 수단만 제공한다.

## 오류 처리

| 계층 | 처리 |
| --- | --- |
| 네트워크·파싱 실패 | 서버 코드가 아님을 구분하고 재시도 가능 상태로 표시 |
| `4xx`·`5xx` 응답 | `ApiError`로 변환해 `status`·`code`·`message`·`details` 보존 |
| 렌더링 예외 | 오류 경계가 잡아 빈 화면으로 끝나지 않게 함 |
| 없는 경로 | 404 화면 |
| 권한 없는 접근 | 404와 구분된 화면 |

오류 메시지는 서버가 준 `message`를 우선 사용한다. 권한·개인정보·다른 사용자의 경쟁 상태를 노출하지 않는다.

## 테스트 전략

- MSW 핸들러는 생성 타입을 사용해 응답을 만든다. 손으로 쓴 응답 모양이 계약과 어긋나는 것을 타입이 막는다.
- 재현할 상태: 성공, 빈 결과, `data: null`, 400, 401, 403, 404, 409, 429, 503.
- 멱등 키 유지: 같은 작업의 재시도가 같은 키를 보내는지 확인한다.
- 라우팅: 없는 경로와 권한 없는 접근이 서로 다른 화면으로 가는지, 오류 경계가 렌더링 예외를 잡는지 확인한다.
- `mvp1-openapi.yaml`에 있으나 backend에 없는 경로(`POST /api/v1/reservations`, 픽업 전체 등)는 MSW로만 다룬다. production 코드에서 성공을 가정하지 않는다.

## 생성 타입 관리

생성 결과를 저장소에 커밋한다. 두 가지 이유다.

1. CI와 기여자가 생성 단계 없이도 타입 검사를 실행할 수 있다.
2. OpenAPI 변경이 diff로 드러나 계약 변경을 리뷰에서 놓치지 않는다.

CI에 재생성 후 diff 없음을 확인하는 step을 추가한다. OpenAPI를 고치고 타입을 다시 만들지 않은 상태를 실패로 잡는다. 이 step은 #199가 만든 `frontend-ci.yml`에 더한다.

## 완료 기준

- `pnpm run dev`에서 `/api/v1/store-categories`가 same-origin으로 backend에 도달한다.
- 생성 타입만 사용하고 응답 타입을 수동 선언하지 않는다.
- 성공 봉투의 `code`·`message`·`data`를 구분하고 `data: null`과 빈 배열을 오류로 만들지 않는다.
- 오류를 HTTP status와 `code`로 함께 판정한다.
- 멱등 키를 작업 단위로 생성하고 재시도에 보존한다.
- 열 가지 비동기 상태를 표현하는 공통 수단이 있다.
- 라우트 표, 공통 레이아웃, 404, 권한 없음, 오류 경계, 목적지 보존이 존재하고 테스트로 고정된다.
- MSW로 성공·빈 결과·400·401·403·404·409·429·503을 재현하는 테스트가 있다.
- 1차 MVP 범위 밖 SDK·환경변수·route가 번들과 설정에 포함되지 않는다.
- `pnpm run typecheck`, `pnpm test`, `pnpm run build`가 통과한다.
