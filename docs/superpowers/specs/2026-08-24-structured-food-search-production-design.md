# 구조화 음식 검색 production 설계

> 상태: 구현 전 승인 설계
> 소유 Issue: [#625](https://github.com/sparta-spring4/Commerce-Final-Project-MiriYum/issues/625)
> 기준 브랜치: `origin/dev` (`dc9c8c250d35162ebf065b861f933113e703e20e`)
> 성격: 구현 절차를 위한 비정본 설계 문서. 제품 계약은 구현 PR에서 `docs/specs/store-search/spec.md`, `docs/specs/store-search/openapi.yaml`, `docs/specs/store-recommendation/spec.md`, `docs/adr/ADR-009-hybrid-semantic-search-qdrant.md`에 반영한다.

## 1. 목적

현재 검색은 사용자가 메뉴명을 직접 입력한 경우에는 강하지만, `얼큰하고 국물 있는 고기 음식`처럼 맛·재료·국물·조리법으로 말한 질의를 메뉴 및 실제 매장 후보로 연결하는 능력이 부족하다. 평가에서 이 손실을 줄인 simulated G 구조는 acceptable Recall@20을 79.80%에서 91.20%로 높였다.

production 변경의 목적은 다음 세 단계를 실제 통합 검색에 반영하는 것이다.

1. 자연어를 메뉴명과 음식 속성으로 분리한다.
2. 현재 MySQL의 메뉴명·설명·카테고리·태그로 후보를 넓힌다.
3. 개인 이력보다 먼저 음식 관련도를 적용해 첫 페이지 20개를 정렬한다.

91.20%는 완전한 속성 manifest를 사용한 simulated evidence 결과다. production 메뉴 메타데이터에는 속성이 빠져 있을 수 있으므로 동일 수치를 구현 완료 수치로 간주하지 않는다. 병합 전 동일한 2,000개 고유 질의와 5회 체크포인트를 actual application predicate로 재평가한다.

## 2. 범위와 비범위

### 포함

- 결정적 음식 어휘와 구조화 증거 모델
- 기존 LLM 의미 확장의 strict structured output
- 기존 메뉴 테이블의 현재 공개 버전에서 구조화 증거를 계산하는 QueryDSL predicate와 정적 정렬 키
- 일반 정렬 및 추천 정렬의 음식 관련도 우선순위
- 커서의 정렬 키 확장과 이전 커서의 명시적 무효화
- 검색·추천 정본 문서와 OpenAPI 설명 갱신
- 최소 단위 테스트, 영향받은 repository 통합 테스트 클래스, 2,000×5 actual 재평가

### 제외

- embedding 또는 외부 검색 인덱스 도입
- Flyway 및 DB 스키마 변경
- 메뉴 데이터 자동 보강·마이그레이션
- 공개 요청·응답 필드 추가 또는 삭제
- 기존 평가 manifest의 gold 수정
- 개인 이력 점수 산식 자체의 변경

## 3. 불변 조건

- 매장과 메뉴는 현재 공개·검색 가능 상태여야 한다. 폐점·비공개 매장과 비공개·과거 메뉴 버전은 후보와 증거 양쪽에서 제외한다.
- 지역·가격·업종·가용성 등 사용자가 지정한 필터는 관련도보다 강한 필수 조건이다.
- 사용자가 직접 입력한 메뉴명 또는 결정적 별칭 일치는 LLM 추론보다 우선한다.
- `면`, `탕`, `국`, `밥` 같은 일반 형태 토큰 하나만으로 후보를 만들지 않는다.
- 속성의 역방향 부분 문자열 매칭은 하지 않는다. 예를 들어 짧은 일반 토큰이 긴 메뉴명 안에 있다는 이유만으로 속성 증거로 인정하지 않는다.
- API 키, 인증 헤더, 원본 이력은 로그·응답·평가 산출물에 기록하지 않는다.

## 4. 내부 모델

### 4.1 `StructuredFoodEvidence`

검색 내부 전용 불변 값으로 다음 필드를 갖는다.

- 원문에서 추출한 span
- 명시 메뉴 계열 `menuFamilies`
- `ingredients`
- `tastes`
- `broths`
- `methods`
- `aromas`
- `textures`
- `forms`
- 각 값의 출처 `DETERMINISTIC` 또는 `LLM`

값은 정규화된 vocabulary ID로 보관하고, 같은 차원 안에서는 중복 제거한다. `forms`는 분석 정보로 기록하지만 `면/탕/국/밥` 같은 일반 형태 하나만으로 후보 자격이나 두 차원 임계값을 만족시키지 못한다.

### 4.2 `FoodEvidenceVocabulary`

코드에 포함하는 고정된 결정적 사전이다. 다음을 버전과 함께 제공한다.

- 대표 메뉴 계열과 별칭: `짬뽕`, `불향 해물 짬뽕`, `옛날 짬뽕`; `뼈해장국`, `뼈다귀 해장국`; `잔치국수`, `멸치국수` 등
- 재료·맛·국물·조리법·향·식감·형태의 대표어와 동의어
- 단독 증거로 금지할 일반 토큰 denylist
- 서로 다른 표현이 같은 ID로 귀결되는 정규화 규칙

사전 항목은 사람이 검토 가능하고 테스트에서 version과 대표 별칭을 고정한다. 운영 중 외부 API나 평가 대상 LLM이 사전을 생성하지 않는다.

## 5. 자연어 해석

### 5.1 결정적 추출

정규화된 질의에서 긴 표현부터 우선해 vocabulary를 매칭한다. 겹치는 span은 더 긴 표현을 채택하고, 같은 차원의 같은 ID는 한 번만 센다. 메뉴 계열·별칭과 음식 속성을 분리하므로 `칼칼한 마라탕`은 `마라탕`을 명시 메뉴 계열로, `칼칼한`을 맛으로 기록한다.

결정적 메뉴명 또는 별칭이 검출되면 `explicitMenu=true`로 취급한다. LLM이 같은 계열을 제안하더라도 명시 메뉴 여부를 만들거나 승격시킬 수 없다.

### 5.2 LLM 보충

기존 exact-first와 보충 호출 정책을 유지한다. 첫 페이지의 결정적 후보가 부족할 때만 LLM을 호출하며, strict JSON schema로 메뉴 계열과 음식 속성 차원을 각각 받는다. 현재 temperature, system instruction, 요청 모델, 반환 모델, 토큰·지연 기록 정책은 유지한다.

LLM 결과는 다음 규칙으로 병합한다.

- 결정적 값은 삭제하거나 다른 차원으로 이동할 수 없다.
- 허용된 vocabulary ID로 정규화되는 값만 추가한다.
- LLM이 추론한 메뉴 계열은 `LLM` 출처이며 `explicitMenu`가 아니다.
- 잘못된 형식, timeout, 429, 5xx, 빈 응답, 모르는 값은 해당 보충값만 포기한다.
- 실패 시 결정적 검색 결과를 그대로 반환한다.

이 정책은 LLM이 자유 문장으로 만든 `불향 해물 짬뽕` 때문에 실제 `짬뽕`을 잃는 문제와, 추론값이 사용자의 직접 입력보다 강해지는 문제를 막는다.

## 6. 후보 자격

각 매장은 반드시 같은 **현재 공개 메뉴 한 건**에서 음식 증거를 충족해야 한다. 서로 다른 메뉴의 `매운맛`과 `고기`를 합쳐 한 메뉴가 두 차원을 만족한 것처럼 계산하지 않는다.

후보 자격은 강한 순서로 다음과 같다.

1. 사용자가 직접 입력한 메뉴명 또는 결정적 별칭이 현재 메뉴의 이름과 exact/forward/안전한 alias로 일치한다.
2. 정규화된 메뉴 계열이 현재 메뉴의 이름·설명·카테고리·태그와 일치한다.
3. 메뉴명이 없는 음식 설명 질의는 같은 메뉴에서 재료·맛·국물·조리법·향·식감 중 서로 다른 차원 두 개 이상이 일치한다.

`forms`는 보조 정렬 증거로만 사용할 수 있고 3번의 두 차원에는 포함하지 않는다. 속성 일치는 정규화 ID의 결정적 별칭/동의어 매칭만 허용하며 일반 substring 역방향 매칭을 허용하지 않는다.

매장명, 지역/주소 등 기존 후보 경로는 유지한다. 단, 음식 조건이 구조화된 경우 음식 증거가 없는 매장은 음식 후보로 승격하지 않는다. 모든 경로에 기존 공개 상태·현재 버전·가용성·지역·가격·카테고리 predicate를 동일하게 적용한다.

## 7. 정렬과 커서

### 7.1 정적 음식 관련도 키

`IntegratedStoreSearchCandidate`에 정적 음식 관련도 키를 추가한다. 키는 최소한 다음 요소를 비교 가능한 순서로 표현한다.

1. 명시 메뉴 exact/alias 여부
2. 명시 메뉴 forward 여부
3. 메뉴 계열 일치 여부
4. 서로 다른 음식 차원 일치 수
5. 기존 `relevanceTier`
6. 기존 sort value
7. `storeId`

구체적인 정수 packing은 구현 계획에서 테스트 가능한 상수로 정하되, 위 사전식 순서를 보존하고 오버플로를 허용하지 않는다. LLM 출처라는 이유만으로 명시 메뉴 점수를 부여하지 않는다.

### 7.2 QueryDSL과 cursor

음식 관련도는 첫 페이지를 가져온 뒤 Java에서만 재정렬하지 않는다. QueryDSL의 정적 order와 seek predicate에 포함하고 cursor payload에도 넣는다. 그래야 첫 페이지에서 밀려난 강한 후보가 다음 페이지에서 영구히 건너뛰어지는 문제가 없다.

cursor 계약 버전을 올려 이전 버전 cursor를 `COMMON_001`로 거부한다. 새 cursor는 기존과 같이 검색 fingerprint·정렬·크기·인증 주체 범위를 HMAC으로 보호하며 원본 질의나 사용자 ID를 노출하지 않는다.

## 8. 일반 검색과 추천 검색

### 8.1 `relevance,desc`

정적 음식 관련도 키가 기존 정렬 앞에 위치한다. 명시 메뉴 일치가 가장 먼저 나오고, 메뉴명이 없는 질의에서는 같은 메뉴에서 더 많은 서로 다른 음식 차원을 만족한 후보가 먼저 나온다.

### 8.2 `recommendation,desc`

추천도 음식 관련도 그룹을 먼저 고정한다. 기존 `history-v1` ranker의 계산식과 recommendation reason 선택은 변경하지 않고, **같은 음식 관련도 그룹 안에서만** 개인 이력으로 순서를 바꾼다. 따라서 개인 이력이 낮은 음식 관련도 후보를 높은 음식 관련도 후보 위로 올릴 수 없다.

전체 순서의 의미가 달라지므로 응답의 `rankingRuleVersion`을 `food-evidence-v1+history-v1`로 갱신한다. 공개 응답 shape는 그대로이며 문자열 값과 OpenAPI 설명만 변경한다. 추천 cursor는 음식 관련도 그룹과 기존 완전 동점 키를 모두 인증·seek한다. 비추천 정렬의 `rankingRuleVersion`은 계속 `null`이다.

## 9. exact-first와 보충 후보

- 기존 결정적 검색을 먼저 수행한다.
- 첫 페이지가 충분하면 LLM을 호출하지 않는다.
- 부족할 때만 구조화된 LLM 증거로 최대 200개 보충 후보를 조회한다.
- 보충 후보도 동일한 현재 공개 메뉴·매장·필터 predicate와 음식 관련도 키를 사용한다.
- 기존 exact 후보와 store ID로 중복 제거하며 더 강한 정적 키를 보존한다.
- 최종 첫 페이지와 다음 cursor는 하나의 정렬 계약으로 만들어야 하며, 단순 append 순서에 의존하지 않는다.

## 10. 장애·보안·성능

- LLM 비활성화, timeout, 429, 5xx, format 오류는 검색 실패가 아니라 보충 포기다.
- 재시도·회로 차단·latency 경고는 기존 정책을 유지한다.
- 원문 자연어 외 실제 사용자·매장 비밀정보를 LLM 요청에 추가하지 않는다.
- 입력 길이 100자, 보충 후보 200개, 추천 후보 5,000개의 기존 상한을 유지한다.
- QueryDSL은 메뉴별 `exists`/집계 표현으로 같은 메뉴 증거를 계산하고, 애플리케이션에서 후보×메뉴×속성을 순회하는 삼중 루프를 만들지 않는다.
- embedding, 외부 vector index, 외부 cache는 추가하지 않는다. 이번 평가에서 large embedding은 2,000개 중 1개만 추가 회수했고 운영 복잡도 대비 이득이 작았다.

## 11. 호환성과 마이그레이션

- DB migration은 없다.
- 공개 요청·응답 schema 변경은 없다.
- 추천 응답의 `rankingRuleVersion` 문자열이 바뀌며 이전 cursor는 계약 버전 변경으로 만료된다.
- 기능 flag 또는 기존 LLM expansion 비활성 설정으로 구조화 보충을 끌 수 있어야 한다. rollback 시 결정적 기존 검색으로 안전하게 축소한다.
- 정본 문서는 새 후보·정렬·추천 버전·cursor 의미와 embedding 비도입 결정을 함께 갱신한다.

## 12. 검증

### 12.1 TDD 단위 검증

- 긴 별칭 우선, 띄어쓰기 정규화, 차원별 중복 제거
- `칼칼한 마라탕`의 메뉴/맛 분리
- `면/탕/국/밥` 단독 금지
- 결정적 값 우선 및 LLM fill-only 병합
- LLM 메뉴 계열이 explicit으로 승격되지 않음
- strict schema 오류와 provider 실패 시 결정적 fallback
- 음식 관련도 사전식 비교 및 recommendation group 우선
- cursor encode/decode, 변조·구버전·fingerprint 불일치 거부

### 12.2 repository 통합 검증

- 두 차원이 같은 현재 공개 메뉴에서 일치할 때만 후보가 됨
- 서로 다른 메뉴의 증거를 합산하지 않음
- 폐점·비공개 매장과 과거·비공개 메뉴가 후보/증거에서 제외됨
- exact/forward/alias/구조화 속성의 순서
- 지역·가격·카테고리·가용성 필터 유지
- 첫 페이지와 다음 cursor 사이 누락·중복 없음
- 추천에서 음식 관련도 그룹을 개인 이력이 뒤집지 못함

로컬에서는 관련 단위 테스트와 `IntegratedStoreSearchRepositoryIT` 등 영향받은 통합 테스트 클래스만 실행한다. 전체 backend suite는 GitHub CI를 authoritative 결과로 사용한다.

### 12.3 actual application 재평가

동일한 manifest와 이미 완료된 2,000×5 체크포인트를 재사용해 새 LLM 과금 없이 actual application predicate를 계산한다. 다음을 이전 D/E/G simulated 결과와 분리해 보고한다.

- strict/acceptable Recall@1/@3/@5/@8/@20/@50/전체 후보
- exact/forward/reverse/alias 및 구조화 evidence 회수·오탐
- true-no-answer 및 전체 음성 질의 false-positive
- 폐점·비공개·과거 메뉴 누출과 필터 위반
- 후보 풀 회수와 ranking 손실
- 질의 유형별 실패 사례

성공 기준은 actual acceptable Recall@20의 개선, 기존 명시 메뉴 회수의 비회귀, true-no-answer 오탐 0 유지, 전체 음성 오탐과 상태/필터 누출의 비증가다. 91.20%는 비교 목표이지 사전 합격 보장이 아니다.

## 13. 구현 순서와 rollback

1. 정본 계약과 테스트에서 새 의미를 먼저 고정한다.
2. 음식 vocabulary와 결정적 추출을 구현한다.
3. LLM schema와 fill-only 병합을 구현한다.
4. repository 후보·정렬·cursor를 구현한다.
5. 추천을 음식 그룹 우선으로 연결한다.
6. 최소 로컬 검증과 actual 재평가를 수행한다.
7. CI가 전체 회귀 검증을 완료한 뒤에만 병합 판단을 한다.

문제가 발생하면 구조화 보충을 비활성화해 기존 결정적 검색으로 되돌린다. cursor 계약은 구버전을 계속 거부하고, 추천 버전은 실제 적용 중인 규칙과 항상 일치시킨다.

## 14. 알려진 한계

- 합성 manifest는 음식 속성이 완전하지만 운영 메뉴의 설명·카테고리·태그는 비어 있거나 일관되지 않을 수 있다.
- DB schema를 바꾸지 않으므로 vocabulary가 메뉴 텍스트에 없는 속성을 복원할 수 없다.
- LLM은 후보를 보충하지만 허용 vocabulary 밖의 새 개념을 즉시 검색 증거로 사용할 수 없다.
- 음식 관련도 우선은 검색 의도 보존에는 유리하지만 개인화가 순서를 바꿀 수 있는 범위를 의도적으로 줄인다.
- actual 재평가와 CI가 끝나기 전에는 simulated 91.20%를 production 성공률로 표현하지 않는다.
