# MiriYum 프론트 인계·정본 문서 정렬 설계

## 1. 목적

일반 사용자·매장 운영자·플랫폼 운영자용 디자인 인계서 3개와 풀스택 구조·연결 인계서 3개뿐 아니라, 이 인계서가 따라야 하는 저장소의 활성 제품 정본·서비스 정책·기능 명세·통합 계약을 최신 제품 범위와 실제 연결 원칙에 맞게 함께 정렬한다. 인계서와 기존 정본은 역할, 단계, 상태, 용어와 기능 노출 조건이 서로 충돌하지 않아야 한다.

이번 변경은 프론트 또는 백엔드 기능을 구현하지 않는다. 인계 문서가 디자인 AI와 풀스택 AI에 서로 다른 책임을 정확히 전달하도록 만드는 문서 작업이다.

## 2. 기준 우선순위

### 제품 범위와 단계 분류

이 작업에서 사용자가 2026-08-10에 확정하고 후속 대화로 보완한 범위를 최우선 제품 기준으로 사용한다. 기존 인계 문서나 활성 제품·정책 정본이 이 범위와 다르면 해당 소유 문서를 함께 고친다. 현재 OpenAPI와 백엔드 구현이 새 제품 정책과 다르면 구현을 문서만으로 바꾼 것처럼 쓰지 않고, 제품 정본에는 목표 정책과 runtime 차단 사유를 기록하며 구현 사실을 설명하는 계약에는 실제 상태를 보존한다.

확정 제품 단계는 `1차 MVP`, `2차 MVP`, `고도화` 세 가지다. 기존 `향후 고도화`에 있던 기능은 자동으로 고도화에 편입하지 않는다. 이번에 사용자가 고도화로 확정한 기능만 이동하고, 나머지는 현재 확정 제품 범위 밖의 후보로 명시하여 API·화면·상태·의존성의 근거로 사용하지 않는다.

### 실제 연결 가능성

풀스택 AI는 작업 시점의 저장소에서 다음 항목을 모두 확인한다.

1. 현재 Issue와 허용 경로
2. 저장소 및 프론트엔드 AI 지침
3. 활성 기능 명세와 OpenAPI
4. 실제 Controller·Service 구현
5. 통합 테스트 또는 동등한 호출 가능 증거
6. 현재 발표·배포 범위

화면의 활성 조건은 단계명이 아니다. 위 항목의 교집합으로 실제 연결 가능한 기능만 메뉴, 라우트, 탭, 버튼, 데이터 요청과 액션에 포함한다.

- 1차 MVP 기능이어도 실제 API가 없으면 숨긴다.
- 2차 MVP나 고도화 기능이어도 실제 구현과 현재 배포 승인이 모두 확인되면 연결할 수 있다.
- OpenAPI만 있고 Controller가 없거나, Controller만 있고 승인된 계약이 없으면 활성화하지 않는다.
- 비활성 버튼, 준비 중 화면, 가짜 성공, production mock으로 미구현 기능을 대신하지 않는다.

## 3. 역할별 문서 책임

### 디자인 인계서

- 저장소를 보지 못하는 디자인 AI가 문서 하나만으로 해당 역할의 전체 화면을 설계할 수 있어야 한다.
- 1차 MVP, 2차 MVP, 고도화의 확정 기능을 모두 화면·상태·사용자 흐름으로 설계한다.
- 단계별 모듈을 독립적으로 분리하여 실제 연결 단계에서 숨겨도 핵심 흐름이 깨지지 않게 한다.
- API 경로, DTO, DB, 로컬 파일 경로와 내부 문서 확인 지시를 포함하지 않는다.
- 아직 정책이 확정되지 않은 기능의 화면, 상태, 버튼 또는 수치를 발명하지 않는다.

### 풀스택 구조·연결 인계서

- 저장소의 활성 정본과 실제 구현을 확인하는 순서와 연결 게이트를 제공한다.
- 디자인에 존재하는 기능을 곧바로 runtime 기능으로 간주하지 않는다.
- 기능별 지원 여부를 독립적으로 판단하고 일부만 구현됐으면 해당 모듈만 노출한다.
- 제품 범위와 현재 API가 충돌하면 임의 보정하지 않고 충돌을 보고하며 해당 기능을 숨긴다.
- 서버 enum, 오류 코드, 경로와 상태 전이를 추측하지 않는다.

## 4. 단계별 제품 범위

### 1차 MVP

#### 인증·계정

- 일반 사용자와 매장 운영자의 분리된 회원가입·로그인
- Spring Security와 JWT 기반 Access Token·Refresh Token
- 두 계정 유형의 권한·인증 namespace 분리
- 사용자 정보 조회·수정과 내 예약 내역

#### 매장·검색

- 서울·부산·대구·대전·광주 지역 카테고리
- 지역·매장 카테고리·완전한 예약 조건에 따른 매장 목록과 예약 가능 여부
- 매장명·메뉴명·지역명 키워드 검색
- 매장 상세, 기본정보, 운영시간, 대표 메뉴, 예약 가능 시간대

#### 일반 예약과 메뉴 홀드

- 날짜·시간대·성인·아동·영유아 인원 기반 즉시 확정 예약
- 예약 가능 여부, 생성, 조회, 취소
- 예약 완료·방문 완료·취소 상태
- 중복 예약 방지와 동시 예약 충돌 처리
- 대표 메뉴 사전 선택 또는 메뉴 없이 예약
- 홀드 가능한 메뉴 수량 조회
- 전체 성공 또는 전체 실패
- 품절 처리와 취소 시 원래 메뉴 홀드 재고 복구

#### 픽업 예약

- 업종과 무관하게 픽업 기능을 활성화한 매장에서 사용
- 픽업 날짜·시간·메뉴·수량 선택
- 일반 좌석 예약과 다른 거래 및 상태 흐름
- 생성·조회·취소·수령 완료

#### 매장 운영

- 매장 등록·수정과 승인 대기 없는 즉시 관리 진입
- 운영시간과 예약 가능 시간대 관리
- 일반 예약 메뉴 홀드 재고 관리
- 픽업 재고 관리
- 예약 내역 조회, 매장 취소, 방문 완료
- 픽업 내역 조회, 매장 취소, 수령 완료

### 2차 MVP

- 자연어 요청에서 분위기·메뉴 카테고리·거리·가격대 조건 추출
- 조건에 맞는 매장·메뉴 추천
- 이전 예약과 최근 메뉴 홀드 이력을 반영한 개인화 추천
- 품절 시 같은 카테고리 대체 메뉴 추천
- 같은 매장에 대체 메뉴가 없으면 반경 3km 주변 매장 추천
- 메뉴 카테고리·가격대·거리·예약 가능 여부 기반 우선순위
- 카카오맵 연동

2차 MVP는 일반 사용자 탐색 기능이 중심이다. 별도 운영자 계약이 확정되지 않은 추천 관리 화면을 매장 운영자에게 만들지 않는다.

### 고도화

- Redis 기반 Refresh Token 관리와 카카오 소셜 로그인
- 예약금·메뉴 홀드 결제, 결제 성공·실패·취소·환불, PortOne·Webhook 동기화
- 결제·환불·웨이팅·알림 내역 마이페이지
- 사업자등록증·매장·메뉴 이미지 업로드, S3와 파일 메타데이터
- 예약 완료·취소·메뉴 품절·방문 시간·웨이팅 호출·대체 추천 알림
- 일반 예약 취소 시 대기 순서 기반 취소표 자동 승계
- 웨이팅 등록·순번·예상 대기·취소·호출·입장 완료·미응답과 SSE
- QR·일회용 번호 체크인과 노쇼 처리
- 매장 운영 대시보드, 예약률·취소율·노쇼·웨이팅 통계
- 매장별 대표·추천 메뉴 3~5개 관리와 사용자 화면 우선 노출
- 플랫폼 운영자의 회원·입점·매장·예약·웨이팅 관리
- 입점 승인·반려
- 슈퍼관리자 전용 플랫폼 운영자 관리
- 웨이팅 기반 거리 추천

## 5. 서비스별 재고 경계

1차 MVP에서는 일반 예약 메뉴 홀드 재고와 픽업 재고를 서로 독립적으로 관리한다.

- 일반 예약 메뉴 홀드는 예약 전용 재고만 차감하고 취소 시 같은 재고로 복구한다.
- 픽업은 픽업 전용 재고만 차감하고 취소 시 같은 재고로 복구한다.
- 한 서비스의 가용량·품절·복구가 다른 서비스 재고를 자동 변경하지 않는다.
- 화면에서 두 재고를 하나의 공유 수량처럼 합산하지 않는다.

서비스 간 재고 이전은 향후 추가할 수 있으나 현재 확정 범위가 아니다. 이전 방향, 수량 제한, 동시성, 감사, 취소와 복구 정책이 확정되기 전에는 이전 버튼·상태·API·가짜 흐름을 설계하거나 구현하지 않는다.

## 6. 현재 저장소와의 연결 주의점

기준 브랜치는 작업 시작 뒤 최신화한 `origin/dev`이며, runtime 사실은 커밋 해시를 영구 지원표로 사용하지 않고 실제 작업 시점마다 다시 확인한다.

- 공개 픽업 가용성, 일반 사용자 픽업 생성·상세·취소, 매장 운영자 픽업 목록·상세·취소·수령 완료 Controller는 현재 존재한다. 그러나 이 구현은 일반 예약 메뉴 홀드와 픽업이 `ONLINE_HOLD`와 허용된 `SHARED` 수량을 공유하므로 확정된 서비스별 독립 재고 정책과 충돌한다. 독립 픽업 재고 계약·구현·테스트·릴리스 증거가 생길 때까지 픽업 제품 모듈은 숨긴다. 일반 사용자 픽업 목록 Controller도 별도 확인 전에는 노출하지 않는다.
- 공개 메뉴 홀드 수량 조회 Controller가 현재 없다. 예약 생성이 메뉴 선택을 받을 수 있더라도 수량 조회가 연결되기 전에는 메뉴 사전 선택 모듈을 완전 지원으로 표시하지 않는다.
- 매장 운영자의 일반 예약 방문 완료 Controller·Service·focused test는 현재 존재한다. 그래도 실제 프론트 활성화는 작업 시점의 계약·구현·검증·릴리스 교집합을 다시 통과해야 하며 예약 목록·상세·취소와 독립적으로 게이트한다.
- 현재 메뉴 재고 계약은 일반 예약 메뉴 홀드와 픽업의 온라인 수량 공유를 전제로 한다. 이번에 확정한 서비스별 독립 재고 정책과 충돌하므로 픽업 재고 계약으로 사용하지 않는다.
- 운영시간·예약 접수 시간대의 초안·즉시/예약 게시·게시 취소, 정기·임시 휴무, 예약 시간 정책은 현재 구현 범위에 존재하므로 매장 운영자 문서에서 누락하지 않는다.
- 현재 계정 가입은 실제 이메일·휴대전화 소유 인증이 아니라 MVP 신뢰 연락처를 사용한다. 디자인과 풀스택 문서가 이를 인증 완료로 표현하지 않는다.
- 매장 등록은 플랫폼 승인 대기 없이 즉시 관리로 이동하되, 이는 별도 자동 승인 API를 새로 만들라는 뜻이 아니다.

이 목록은 영구 지원표가 아니다. 풀스택 AI는 실제 작업 시점마다 같은 검사를 다시 수행한다.

## 7. 파일별 변경 방향

### `handoff/design/01-consumer-design.md`

- 회원가입의 신뢰 연락처와 만 14세 이상 자기 확인을 바로잡는다.
- 검색 조건, 일반 예약, 메뉴 홀드, 전 업종 픽업을 완전한 화면 흐름으로 보완한다.
- 2차 추천과 고도화 마이페이지·결제·웨이팅·알림·체크인 화면을 독립 모듈로 정리한다.

### `handoff/design/02-store-operator-design.md`

- 운영자 계정 정보 화면과 매장 등록 필수 흐름을 보완한다.
- 운영시간·예약 접수 시간대·휴무·예약 시간 정책의 상태와 게시 흐름을 설계한다.
- 일반 예약 메뉴 홀드 재고와 픽업 재고를 분리한다.
- 전 업종 픽업, 예약·픽업 관리와 고도화 운영 기능을 정렬한다.

### `handoff/design/03-platform-operator-design.md`

- 플랫폼 운영자 전체가 고도화임을 유지한다.
- 회원·입점·매장·예약·웨이팅·추천 메뉴와 슈퍼관리자 운영자 관리 범위를 보강한다.

### `handoff/fullstack/01-consumer-fullstack.md`

- 단계와 runtime 활성 조건을 분리한다.
- 인증·검색·예약·메뉴 홀드·픽업을 실제 구현 단위로 게이트한다.
- 서비스별 재고와 현재 미구현 Controller를 명시한다.

### `handoff/fullstack/02-store-operator-fullstack.md`

- 운영자 셸 bootstrap, 계정, 매장, 일정, 휴무, 예약 시간 정책, 메뉴와 서비스별 재고를 실제 계약에 맞춰 분리한다.
- 방문 완료와 픽업 전체를 독립 capability로 게이트한다.

### `handoff/fullstack/03-platform-operator-fullstack.md`

- 현재 전체 셸 숨김을 유지한다.
- 고도화 구현 조건에 추천 메뉴와 필요한 운영 계약을 포함한다.

## 8. 검수와 검증

문서 수정 후 다음을 확인한다.

1. 각 역할 문서에 다른 역할의 화면이 섞이지 않았는지 확인한다.
2. 1차·2차·고도화 확정 기능의 누락과 잘못된 단계 분류를 확인한다.
3. 디자인 문서에 저장소 경로·API 구현 지시가 없는지 확인한다.
4. 풀스택 문서가 미구현 기능을 비활성 버튼이나 준비 중 화면으로 남기지 않는지 확인한다.
5. 전 업종 픽업과 서비스별 독립 재고가 여섯 문서에서 일관적인지 확인한다.
6. 재고 이전 기능과 미확정 평균·시간 수치·상태값을 발명하지 않았는지 확인한다.
7. 플랫폼 운영자 기능이 1차·2차 MVP에 노출되지 않는지 확인한다.
8. `git diff --check`와 문서별 필수·금지 문구 검색을 실행한다.
9. 하위 에이전트의 파일별 검수 뒤 전체 브랜치 교차 검수를 별도로 수행한다.

## 9. 기존 정본 문서 교정 범위

### 단계와 runtime

- `README.md`, `CONTRIBUTING.md`, `ai/document-routing.md`, `ai/integration-contracts.md`와 `docs/00`~`09`의 단계 설명을 세 단계 제품 분류와 runtime 증거 축으로 분리한다.
- 제품 단계는 전체 디자인·계획 범위를 분류한다. 실제 프론트·백엔드 연결은 단계와 무관하게 승인된 계약, 구현된 Controller·Service, 호출 증거와 릴리스 승인의 교집합으로 판단한다.
- `ai/integration-contracts.md`는 backend 제품 API가 존재하지 않는다는 오래된 문구를 제거하되, 조합된 cross-end runtime이 검증되지 않았으면 그 상태는 계속 `NOT CONFIGURED`로 둔다.

### 1차 MVP 등록·역할·예약

- 1차 MVP는 매장 운영자가 매장 생성 요청을 성공시키면 생성 응답의 매장을 바로 관리하는 흐름이다. 별도 입점 신청 aggregate, 승인 대기 화면, 플랫폼 심사, 자동 승인 API를 만들지 않는다.
- 현재 구현·OpenAPI의 `APPROVED` 같은 필드는 실제 계약 사실로 남길 수 있지만, 이를 사용자에게 보이는 승인 절차나 별도 자동 승인 endpoint로 해석하지 않는다. 필드 제거는 backend migration과 함께하는 별도 작업이다.
- 일반 사용자와 매장 운영자의 권한은 분리한다. 구체적인 authority 문자열이나 JWT claim은 실제 Security 구현·OpenAPI에 없는 값을 발명하지 않는다.
- 1차 MVP의 공개 예약 상태와 액션은 실제 구현 계약을 기준으로 확정·취소·방문 완료를 다룬다. 내부 트랜잭션 단계나 아직 없는 변경·거절·만료·대기 상태를 UI·API·enum placeholder로 승격하지 않는다.

### 서비스별 재고와 계약 충돌

- 제품 정본은 일반 예약 메뉴 홀드 재고와 픽업 재고의 독립 소유권, 동일 서비스 취소 복구, 교차 차감·집계·복구 금지를 명시한다.
- 현재 `ONLINE_HOLD`·`ONSITE`·`SHARED` OpenAPI와 schema·Service는 구현 사실을 나타내므로 문서만으로 독립 재고 계약처럼 바꾸지 않는다. 제품 정책과 구현 충돌을 명시하고 픽업 runtime을 차단한다.
- 독립 재고용 OpenAPI·migration·Controller 변경은 별도 backend 소유 contract-first 작업이다. 이번 PR은 그 구현을 완료했다고 주장하지 않는다.
- 서비스 간 재고 이전은 미정이다. 이전 버튼·API·상태·enum·table·event·감사·수량 제한·placeholder를 만들지 않는다.
- 이 금지는 일반 예약 취소로 반환된 예약 수용량을 대기 순서에 따라 승계하는 고도화 기능과 무관하다. 취소표 자동 승계는 유효한 일반 취소에만 시작하며 노쇼에서는 절대 시작하지 않는 확정 범위로 유지한다.

### 단계별 기능 소유 문서

- 인증 정책과 ADR의 고도화 저장소 명칭은 사용자가 확정한 `Redis`로 정렬한다. 현재 구현이 없으므로 Redis runtime이 구성됐다고 주장하지 않는다.
- 매장 등록, 매장·메뉴·운영시간·예약 가능 시간대, 검색·5개 지역, 사용자 정보, 예약·메뉴 홀드·픽업과 운영자 관리 범위를 1차 MVP 소유 문서에 빠짐없이 명시한다.
- 2차 MVP 자연어·취향·품절 대체·3km 주변 매장·카카오맵은 일반 사용자 경험으로 소유한다. 별도 운영자 추천 관리 기능을 만들지 않는다.
- 고도화는 Redis Refresh Token, 카카오 로그인, 결제·환불, 알림, 웨이팅·SSE, 일반 취소표 승계, 체크인·노쇼, 파일·이미지, 통계·대시보드, 대표·추천 메뉴 3~5개와 우선 노출, 웨이팅 지도 1~5km, 플랫폼 운영자를 포함한다.
- 코스·구독·리뷰·광고·Pro·LLM 채팅 등 이번에 확정되지 않은 기존 후보는 `향후 고도화`라는 네 번째 출시 단계로 유지하지 않고 확정 범위 밖으로 분리한다.

### 기능 명세와 OpenAPI

- 기존 기능 명세는 제품 목표와 현재 구현 사실을 구분한다. 미구현 메뉴 홀드 가용성 path는 OpenAPI 존재만으로 활성 API라고 쓰지 않는다.
- 통합 `mvp1-openapi.yaml`은 실제 구현·승인된 source OpenAPI 경로를 빠뜨리지 않도록 재생성·검증하되, 별도 구현이 없는 추천·지도·독립 재고 계약은 추가하지 않는다.
- 2차 소비자 탐색은 계획 기능 명세를 가질 수 있지만 Controller가 없는 OpenAPI를 runtime 계약처럼 등록하지 않는다.

## 10. 검수와 검증 추가 기준

기존 8개 파일 단위 기준에 더해 다음을 검증한다.

1. 활성 정본에 1차 MVP 입점 신청·승인 대기·플랫폼 승인·자동 승인 API 흐름이 남지 않았는지 확인한다.
2. 실제 구현 필드를 설명하는 문서에서 `APPROVED`를 제거한 것처럼 거짓말하지 않으면서도 사용자 흐름으로 노출하지 않는지 확인한다.
3. 서비스별 독립 재고가 제품 정본에 명시되고, 현재 공유 재고 OpenAPI·구현이 runtime 차단 사유로 남는지 확인한다.
4. 재고 이전 금지와 일반 취소표 자동 승계가 서로 다른 개념으로 유지되는지 확인한다.
5. 세 단계 분류와 구현 Controller/API 기반 runtime 활성화가 분리됐는지 확인한다.
6. Redis, 카카오, 3km, 1~5km, 대표·추천 메뉴 3~5개, SSE, 노쇼 제외 승계 경계가 소유 문서마다 일치하는지 확인한다.
7. OpenAPI bundle lint와 source path 완전성, backend/frontend 테스트·빌드와 `git diff --check`를 실행한다.
