# 단계별 로드맵과 문서 재구성 설계

> 문서 성격: 구현 전 승인 설계 산출물
>
> 이 문서는 현재도 미래에도 제품 요구 탐색의 기본 라우팅 대상이나 제품 정본이 아니다. 이번 구현 계획 작성과 사용자 검토 목적으로만 읽는 산출물이다. 구현 시 활성 정본인 `docs/00~09`, 관련 `service-policies`, ADR, `CONTRIBUTING.md`와 `ai/document-routing`을 갱신한다.

## 1. 목적·배경·비목표

현재 문서군에 섞인 초기·후속 범위와 과거·현재 판단을 정리한다. 기존 정본 소유 구조를 유지하면서 로드맵을 `1차 MVP`, `2차 MVP`, `고도화`, `향후 고도화`로 재배치하고 기능·기술·전환 증거·문서 책임을 정렬한다.

비목표는 다음과 같다.

- 이 spec을 정본으로 만들거나 후속 기능을 현재 기능처럼 표현하지 않는다.
- 파일 시점으로 정본을 판단하거나 정확한 버전·수명·시간·횟수·기간·임계치를 발명하지 않는다.
- 기존 ADR을 삭제·폐기하거나 실제 증거 없이 백엔드를 분리하지 않는다.

## 2. 문서 재구성 접근

기존 정본 구조를 유지한다. 번호 문서는 상위 경계, `service-policies`는 상세 상태·예외·권한, ADR은 지속 기술 결정을 소유한다. 규칙을 복제하지 않고 소유 정본으로 연결한다.

모든 활성 정본에는 필요한 범위에서 네 단계 축을 적용한다.

- **1차 MVP:** 최소 기술로 거래 정확성과 기본 흐름을 제공한다.
- **2차 MVP:** 1차 원장에 규칙 해석·이력 추천·원 매장 기준 대안을 추가한다.
- **고도화:** 인증 상태·파일·웨이팅·실시간·결제·환불·알림·관리 기능을 반드시 구현한다.
- **향후 고도화:** 앞 단계 검증 뒤 시간이 남을 때만 진입한다.

문서의 정책 상태와 단계 포함 여부는 분리한다. 확정 정책이라도 해당 단계에서 진입 경로를 제공하지 않을 수 있으며, 향후 후보가 문서에 있다는 이유만으로 의존성·인프라·권한을 활성화하지 않는다.

## 3. 절대 불변식

### 3.1 계정 물리 분리

세 계정 유형은 공통 계정 행·역할 열로 합치지 않는다. 각 유형은 전용 테이블·PK·principal·토큰 namespace를 가진다. 참조·감사는 유형과 PK를 함께 기록한다. 클라이언트 역할 값·이메일·외부 로그인으로 유형·권한을 바꾸지 않으며 매장 명령은 계정·소속·매장 상태를 MySQL에서 검증한다.

### 3.2 방식 A

1차·2차와 고도화는 하나의 Spring Boot와 MySQL을 사용한다. 각 단계에는 실제 기능 모듈만 둔다. 1차는 `auth`, `store`, `booking` 중심이고 `payment`, `notification`은 고도화에서 추가한다. 빈 패키지·설정·의존성을 미리 만들지 않는다. 모듈은 공개 service/application 포트를 사용하며 MySQL은 활성 업무의 원장이다.

### 3.3 예약 모델과 용어

사용자 행위는 `예약`으로 통일한다. 자원은 날짜·시간대별 총 인원수와 총 팀 수이며 한 예약이 둘을 함께 소비한다. 겹치는 모든 시간대가 두 수용량을 만족해야 하고 하나라도 부족하면 전체 실패한다. 개별 배치 식별자는 요구·노출하지 않는다.

### 3.4 매장 운영 모드

- `예약만`: 인원수와 팀 수 수용량만 사용한다.
- `예약+메뉴 홀드`: 메뉴를 건너뛰면 수용량만, 선택하면 수용량과 모든 메뉴 수량을 한 MySQL 트랜잭션에서 확정한다. 부분 성공은 없다.
- `카페·베이커리 픽업 예약`: 승인된 업종만 날짜·픽업 시간대·메뉴·수량을 사용하며 인원수·팀 수를 차감하지 않는다.

모드 변경은 효력 이후 신규 요청에만 적용하고 기존 확정 건을 자동 변경하지 않는다.

### 3.5 카테고리와 추천 기준점

매장은 주 카테고리 1개, 메뉴는 주 1개와 중복 없는 보조 0~5개를 가진다. 서버가 내부 코드의 공개·활성을 검증한다. 1차의 5개 지역 카테고리는 별도 탐색 코드다.

거리 기준은 원 매장의 검증 좌표다. 사용자 현재 위치는 요청·저장·사용하지 않는다. 후보는 점수보다 먼저 최신 영업·판매·수량·예약 가능 조건을 통과한다.

## 4. 단계별 기능 범위와 기술 스택

### 4.1 1차 MVP

일반 사용자와 매장 운영자의 가입·로그인, 매장·상품 키워드 검색, 5개 지역 탐색, 기본 프로필·예약 내역, 예약 가능 조회·생성·상태·취소, 세 운영 모드와 매장 관리 기능을 제공한다. 플랫폼 운영자 화면, 리뷰, 웨이팅, 결제, 알림, 파일, 지도, AI와 실시간 전송은 제외한다.

기술은 Java 21, Spring Boot 4.1.0, Gradle Wrapper 9.6.1, Spring MVC, Spring Data JPA, Spring Security, Flyway, MySQL과 Testcontainers MySQL을 사용한다. 프런트엔드는 Node.js 24.18.0, pnpm 11.17.0, React 19.2.8, TypeScript 7.0.2, Vite 8.1.5, Vitest 4.1.10과 React Testing Library 16.3.2를 사용한다. 정확히 확인되지 않은 MySQL·Testcontainers 버전은 적지 않는다.

Access JWT와 Refresh JWT는 서버 정상 목록·폐기 목록을 두지 않는 구조로 시작한다. 토큰 유형·서명·만료·발급자·대상·계정 namespace를 검증하고 보호 명령은 현재 계정·매장 권한을 MySQL에서 확인한다. 수용량·메뉴 수량은 DB 유일 제약, 비음수 조건, 고정 잠금 순서, 조건부 SQL과 멱등 키로 보호한다. 일반 조회는 JPA, 고경합 쓰기는 repository 경계의 좁은 명시적 SQL을 허용한다.

Valkey, QueryDSL, 카카오맵 API, SSE, PortOne, S3, Kafka, Outbox, 검색엔진과 마이크로서비스는 1차에 넣지 않는다.

### 4.2 2차 MVP

1차 구조와 원장을 유지하면서 AI 없이 자연어 조건을 해석한다. `RuleInterpreter`가 정규화, 명시적 시간대와 `Clock`, 가격, 승인된 분위기·카테고리 사전, 남은 키워드를 결정적으로 처리한다. 모호한 입력은 추측하지 않고 경고한다.

유효한 과거 예약과 확정 메뉴 선택을 MySQL에서 요청 시 집계하고 Java 점수 계산기가 설명 가능한 순위를 만든다. 2차에 존재하는 취소·실패·단순 조회는 선호 신호가 아니다. 고도화에서 노쇼 상태가 생긴 뒤에도 노쇼는 선호 신호에서 제외한다. 품절 또는 마지막 수량 경합 실패 뒤 별도 동기 읽기 API가 같은 매장 메뉴를 먼저 제안하고, 없으면 원 매장의 저장 좌표를 기준으로 bounding box와 Java Haversine을 사용해 3km 후보를 판정한다. 사용자의 명시적 수락 전에는 원 거래를 바꾸지 않는다.

2차 진입 시 선택 조합과 projection에는 QueryDSL을 도입한다. `store.recommendation`이 후보·점수를 소유하고 `booking`의 공개 `BulkAvailabilityPort`를 사용한다. Kakao Local REST는 입점·주소 변경 때 좌표 변환 포트 뒤에서만 호출하고 지도 SDK는 표시와 매장 운영자의 좌표 확인에만 사용한다. 추천 요청 중 외부 지도 호출은 없다.

AI/LLM, Spring AI, 벡터 DB, 검색 클러스터, 메시지 브로커, 별도 추천 서비스·DB, 공간 DB와 추천 캐시는 금지한다.

### 4.3 고도화

고도화는 반드시 구현한다.

- Valkey 기반 Refresh 상태, 매 갱신 회전·폐기·재사용 탐지와 로그인 단위 종료
- 일반 사용자 카카오 로그인과 추정 자동 연결·권한 승격 차단
- S3 사업자등록증·매장/메뉴 이미지와 DB 메타데이터, 비공개 암호화 자료 경계와 객체 대사
- 예약·취소·품절·도착 예정 시각·웨이팅 호출·대체 추천·결제·환불·승계 알림
- 웨이팅 등록·순번·예상 대기·취소·호출·상태와 SSE 실시간 반영
- 유효한 일반 취소로 반환된 예약 가능분의 자동 승계
- QR 체크인, 짧은 일회 확인번호, 유예와 노쇼 판정
- PortOne V2 예약금·메뉴 홀드 결제, Webhook 검증, 환불·멱등성·대사
- 매장 운영자 대시보드·통계·설정과 대표/추천 메뉴 3~5개
- 플랫폼 운영자의 회원·입점·매장·예약·웨이팅 관리와 승인·감사
- 마이페이지의 결제·환불·알림·웨이팅 이력

노쇼 후보·확정·정정은 자동 승계, 예약 가능분 반환 원장과 일반 가용 재공개를 만들지 않는다. 자동 승계는 일반 취소로 반환된 예약 가능분에만 적용한다. 알림·승계·결제 복구는 업무 상태와 같은 트랜잭션에 기록한 기능별 MySQL 내구성 작업, DB 임대·fencing, 멱등 키, 제한 재시도, 격리와 대사를 최소안으로 사용한다. SSE와 Valkey Pub/Sub은 전달 보조이며 MySQL 원장을 대체하지 않는다.

### 4.4 향후 고도화

시간이 남을 때만 인기·시간대·대표 메뉴 추천, 사용자·사업자 구독, AI 요약·FAQ·예약 안내·리포트·RAG, 플랫폼 운영자 기능 확장, 제공자 중립 포트 뒤의 카카오톡 알림, 예약 기준 1:1 채팅, 리뷰·신고·어뷰징, 코스·테이스팅과 외부 본인확인을 검토한다.

추천 후보·필터·점수·순위·TOP3는 결정적 코드가 담당한다. LLM은 확정 결과의 설명만 만들고 실패 시 템플릿으로 대체한다. 이 범위를 근거로 AI 파이프라인, 벡터 DB, 채팅 인프라와 추가 외부 제공자를 미리 설치하지 않는다.

## 5. 기술 선택·전환 기록 규칙

모든 기술 선택은 다음 항목을 빠짐없이 기록한다.

1. 처음 문제와 단계 제약
2. 검토 대안
3. 초기 선택과 이유
4. 대안별 거절 이유
5. 알려진 단점
6. 다음 판단에 사용할 관측 신호
7. 먼저 시도할 단순 개선
8. 개선 뒤 비교할 다음 후보
9. 결과·성능·장애·보안 검증
10. 마이그레이션 방법과 새 선택의 단점

전환은 두 종류로 구분한다. **계획된 단계 전환**은 새 단계의 승인 요구 자체가 원인이며, 2차 진입 시 JPA 조회에 QueryDSL을 추가하는 결정처럼 단계 진입 조건·계약·마이그레이션 검증을 충족하면 실행한다. **증거 기반 전환**은 현재 선택의 관측 지표가 기준을 지속 초과하고 단순 개선으로 해결되지 않을 때 후보 비교 뒤 실행한다. 어느 전환도 이전 문제·선택·거절 이유·단점과 실제 증거를 삭제하지 않는다.

| 계정 | 세 계정 유형 물리 분리 | 공통 `USERS`+role | 승격·사고 영향 분리 | 유형별 인증·복구 중복 |

| 1차 데이터 접근 | JPA+좁은 명시적 SQL | QueryDSL·전체 native SQL | 단순 조회와 원자 쓰기 최소 분리 | 두 접근 방식·스키마 결합 |
| Refresh | 1차 무상태, 고도화 Valkey | MySQL·초기 Valkey 상태 | 최소 운영 뒤 폐기 요구에 전환 | 1차 즉시 폐기 불가, 이후 Valkey 의존 |
| 1차 검색 | MySQL 키워드 | 검색엔진 | 원본 직접 조회로 충족 | 오타·자동완성·관련도 한계 |
| 수량 정합성 | MySQL 조건부 갱신·락 | Valkey 원장 | 원본·수량을 한 트랜잭션으로 보호 | 락·DB 부하 |
| 2차 동적 조회 | QueryDSL | Specification·native SQL | 다중 조건·projection 타입 안전성 | annotation processing 관리 |
| 조건 해석 | `RuleInterpreter` | 형태소 분석·AI | 결정적이며 외부 전송 없음 | 사전 유지 비용 |
| 추천 점수 | Java 점수화 | SQL·ML | 설명 가능·결정적 순위 | CPU·heap·over-fetch |
| 거리 | bounding box+Haversine | 공간 인덱스·Kakao 실시간 호출 | 외부 호출 없는 원 매장 기준 | 밀집 지역 과다 후보 |
| 추천 전달 | 동기 읽기 API | 비동기 작업 | 거래와 분리된 즉시 응답 | tail latency·요청 취소 |
| 후속 작업 | 기능별 MySQL 내구성 작업 | Kafka·범용 Outbox | 단일 DB에서 상태·작업 유실 방지 | polling·테이블·락 비용 |
| DB 통합 검증 | Testcontainers MySQL | mock·H2·수동 공유 DB | 1차부터 MySQL 제약·락·격리 검증이 필요하며 선도입이 아님 | 컨테이너 환경·실행 시간 |

대표 전환선은 JPA→QueryDSL/명시적 SQL, 저장소 없는 JWT→Valkey, MySQL 검색→검색 읽기 모델, 요청 시 집계→MySQL 스냅샷, Java 점수화→DB projection, 단일 Vite 앱→복수 앱, 방식 A→선택적 분리다. 각 전환은 원 결과 동등성, 성능, 장애 복구와 롤백을 검증한다.

## 7. 고도화·향후 고도화 기술 격리

고도화에서도 Kafka, 범용 Outbox, 마이크로서비스, WebSocket과 검색 클러스터를 선도입하지 않는다. 알림·자동 승계·결제 복구는 기능별 MySQL 내구성 작업으로 시작한다. WebSocket은 양방향 저지연 상호작용 요구가, Kafka·범용 Outbox는 다수 독립 소비자·장기 재생·DB polling 병목이, 검색 클러스터는 오타·관련도·부하의 측정 실패가 확인될 때만 후보가 된다.

백엔드 분리는 모듈별 배포 지연, 한 기능 때문에 발생하는 전체 과잉 확장, 격리 뒤에도 반복되는 SLO 침해, 서로 다른 규제·복구 경계, 독립 팀 소유와 데이터 단일 소유가 실제로 확인될 때 재검토한다. 분리 전 모듈 API, 작업 풀, 쿼리·연결 격리, 별도 worker와 읽기 모델을 먼저 개선한다.

향후 고도화는 고도화 인프라를 자동 상속하지 않는다. 기능 승인, 데이터·개인정보 계약, 실패 대체 경로와 운영 기준을 각각 다시 확인한다.

## 8. ADR 규칙

같은 결정 주제는 기존 ADR에 날짜별 개정 이력으로 이어 쓴다. 최초 선택과 당시 근거를 삭제하지 않고 변경 이유, 증거, 검증, 마이그레이션과 새 단점을 추가한다. 새로운 지속적 주제만 새 ADR을 만든다.

구현 단계에서 ADR-001~007 전체를 현재 단계 축과 정렬되는지 검토한다. 검토만으로 개정하지 않고 같은 주제의 실제 결정이 바뀔 때만 기존 파일에 날짜별 개정을 추가한다. ADR-001은 방식 A, ADR-002는 점진 인프라·전환, ADR-003은 S3의 고도화 배치, ADR-004는 Testcontainers 등 검증 의존성, ADR-005는 PortOne의 고도화 배치, ADR-006은 무상태 JWT에서 Valkey로의 전환, ADR-007은 규칙 기반 검색·MySQL 조회를 다룬다. 고도화로 위치를 바꾸더라도 기존 결정을 삭제하지 않는다.

## 9. 활성 정본 allowlist와 과거 문서 제외

활성 정본 allowlist는 파일 시점이 아니라 현재 승인 기준으로 다음 경로군에서 구성한다.

- `docs/00-index.md`~`docs/09-quality-operations-and-rules.md`
- 현재 승인 기준과 정렬된 `docs/service-policies/`
- 현재 유효 상태의 `docs/adr/`
- `docs/05-functional-requirements.md` 또는 소유 정책이 명시적으로 연결한 현재 기능 명세 `docs/specs/<feature>/spec.md`

`docs/specs/`의 현재 템플릿은 요구사항 정본이 아니다. `README.md`, `CONTRIBUTING.md`와 `ai/` 계약은 제품 사실이 아니라 사람·AI의 진입·라우팅을 소유한다.

`docs/superpowers/specs/`, `docs/superpowers/plans/`, `miriyum-service-blueprint.md`, `miriyum-service-decisions.md`, `superseded`·`retired` ADR과 승인 기준에 연결되지 않은 작업 산출물은 현재 승인 기준을 소유하지 않는 과거 설계·계획·변경 기록이므로 기본 제품 라우팅에서 제외한다. 제외는 즉시 삭제를 뜻하지 않는다. 사용자가 과거 판단 검토를 명시적으로 요청할 때만 해당 과거 문서를 읽는다. 이 spec도 이번 구현 계획과 사용자 검토 외의 제품 요구 탐색에서는 기본 라우팅 대상이 아니다.

## 11. 검증·인수 기준

- 세 계정 유형의 테이블·PK·principal·token namespace가 물리적으로 분리되고 교차 토큰·자가 승격이 거부된다.
- 세 운영 모드, 수용량·메뉴 수량과 모드 변경 불변식이 MySQL 동시성 테스트를 통과한다.
- Testcontainers MySQL에서 Flyway, 유일 제약, 조건부 SQL, 교착·병렬 요청, 전체 롤백과 정확히 한 번 복구를 검증한다.
- 2차 규칙 해석은 고정 한국어 질의셋에서 결정적 결과·모호성 반환·회귀를 검증한다.
- 추천은 동일 스냅샷에서 동일 순위·설명을 만들고 최신 MySQL 자격, 원 매장 기준 거리와 사용자 수락 경계를 지킨다.
- Valkey 회전·폐기·재사용, S3 객체 대사, SSE 재연결, Webhook 위조·중복·역순, 내구성 작업 중단·재개를 장애 주입으로 검증한다.
- 노쇼 처리에서 자동 승계, 반환 원장과 일반 가용 재공개가 생성되지 않는 회귀 테스트를 고정한다.
- 구조 테스트는 모듈 간 repository/entity 직접 접근과 순환 의존을 차단한다.
- 금지 기술이 해당 단계 의존성·설정·빈 패키지·배포 전제로 들어오지 않는다.
- 문서 검증은 중복 소유, 깨진 링크, 단계 표기, allowlist와 ADR 개정 이력을 확인한다.
