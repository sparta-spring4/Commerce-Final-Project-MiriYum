# JWT·Valkey 인증과 통합 검색 정책 설계

> 문서 상태: 구현·검증 반영
> 결정자: 이병우
> 수정자: Codex
> 결정일: 2026-07-27
> 최종 정리일: 2026-07-27
> 범위: `AUTH-007`, `ADS-007`, `ADS-008`, 인증·검색 아키텍처와 연계 문서

## 1. 목표

새 1차 MVP의 액세스 토큰·리프레시 토큰 요구와 하나의 검색창에서 일반 키워드·자연어 검색을 함께 제공하려는 제품 방향을 현재 정본에 반영한다.

이번 변경은 다음 두 결론을 확정한다.

1. 인증은 Spring Security 기반 액세스 JWT·리프레시 토큰 구조로 전환하고 리프레시 토큰의 서버 상태는 Redis 호환 Valkey에서 관리한다.
2. 검색창은 하나만 제공한다. 결정적 규칙과 선택적 외부 AI로 키워드·구조화 조건을 함께 추출한 뒤 MySQL을 조회하며, OpenSearch와 Meilisearch는 1차 MVP 검색 경로에 도입하지 않는다.

정책 결정 상태와 MVP 포함 여부는 독립적으로 관리한다. 이번 결정으로 제외된 OpenSearch·Meilisearch는 `확정된 MVP 제외 기술`이며 미결정 상태로 내리지 않는다.

## 2. 인증 결정

### 2.1 확정 범위

- 일반 사용자, 식당 대표자와 플랫폼 운영자의 인증 API는 Spring Security 기반 액세스 JWT를 사용한다.
- 액세스 토큰은 애플리케이션 서버나 Valkey에 정상 토큰 목록으로 저장하지 않고 서명, 만료, 발급자, 대상과 허용된 최소 검증 항목을 확인한다.
- 리프레시 토큰은 토큰 원문이 아니라 안전한 해시, 계정 식별자, 로그인 단위 식별자, 토큰 계열 식별자, 만료, 폐기·교체 상태와 필요한 최소 기기 표시 정보를 Valkey에 저장한다.
- 리프레시 토큰을 사용할 때마다 기존 토큰을 폐기하고 새 액세스 토큰·리프레시 토큰을 발급하는 회전 방식을 사용한다.
- 폐기되거나 이미 교체된 리프레시 토큰의 재사용이 확인되면 해당 토큰 계열을 폐기하고 `AUTH-012` 위험 사건으로 연결한다.
- 로그아웃, 사용자의 개별·전체 로그인 종료, 계정 정지와 권한 회수는 대상 리프레시 토큰 또는 토큰 계열을 Valkey에서 폐기한다.
- Valkey 장애 중에는 로그인·리프레시 토큰 갱신·로그아웃처럼 리프레시 토큰 상태 확인이 필요한 요청을 실패 폐쇄한다. 이미 발급된 액세스 토큰을 사용하는 일반 API 요청은 서명·만료·현재 계정/권한 검증 경계 안에서 처리한다.
- 실제 서버 제품과 버전은 `Valkey 8.1.x`, 애플리케이션 접근 계층은 `Spring Data Redis + Lettuce`로 표기한다. 문맥상 프로토콜·라이브러리를 가리킬 때만 Redis 호환이라는 표현을 사용한다.

### 2.2 기존 정책에서 변경되는 내용

- `AUTH-007`의 Spring Session Data Redis 중앙 서버 세션과 무작위 세션 ID 쿠키를 현재 인증 원본으로 사용하는 결정을 폐기한다.
- 브라우저에서 액세스 JWT·리프레시 토큰을 사용하지 않는다는 기존 결정을 폐기한다.
- 계정별 활성 세션 목록과 개별·전체 종료는 Spring Session 인덱스가 아니라 Valkey의 리프레시 토큰 로그인 단위 상태를 기준으로 제공한다.
- 기존 세션의 유휴·절대 만료 값은 액세스 토큰·리프레시 토큰 수명으로 자동 변환하지 않는다. 새 토큰 수명 결정을 별도로 받아야 한다.

### 2.3 선택 이유와 대안 비교

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| 서명만 검증하는 완전 무상태 리프레시 JWT | 저장소가 필요 없고 구현·확장이 단순하다. | 로그아웃·계정 정지·특정 기기 종료·탈취 토큰 폐기와 재사용 탐지가 만료 전까지 어렵다. | 결제·운영자 권한이 있는 서비스의 통제 요구에 부족하여 미채택 |
| 액세스 JWT + MySQL 리프레시 상태 | 내구성·감사·트랜잭션이 좋고 별도 저장소가 없어도 된다. | 짧은 수명 상태의 만료 정리와 잦은 회전 처리가 DB 업무 원장에 섞이며, 이미 운영할 Valkey와 책임이 중복된다. | Valkey를 다른 초기 기능에서도 운영하므로 미채택 |
| 액세스 JWT + Valkey 리프레시 상태 | 액세스 요청의 무상태 검증을 유지하면서 자동 만료, 원자 회전·폐기, 기기별 로그인과 재사용 탐지를 제공한다. 이미 캐시·속도 제한·임시 선점·실시간 전파에 사용하는 기반 시설을 재사용한다. | Valkey 장애 시 신규 로그인·갱신이 제한되고 서버 상태·운영이 필요하다. | 채택 |
| Spring Session Data Redis | 즉시 중앙 폐기와 브라우저 쿠키 구조가 단순하다. | 모든 인증 요청이 중앙 세션 저장소에 의존하고 새 MVP의 액세스·리프레시 JWT 요구를 충족하지 않는다. | 기존 확정에서 변경 |
| 외부 인증 제공자·독립 인증 서버 | 표준 인증 기능과 운영 책임을 위임하거나 여러 서비스를 통합하기 좋다. | 현재 단일 제품 MVP에 별도 비용·운영·외부 종속을 추가하고 Spring Security JWT 구현 목표와 겹친다. | 현재 미채택 |

Valkey를 채택한 이유는 Redis라는 이름을 먼저 선택했기 때문이 아니다. 서버에서 변경 가능한 리프레시 토큰 상태가 필요한 보안 요구와, Valkey를 이미 다른 초기 기능의 공용 기반 시설로 운영한다는 조건을 함께 만족하기 때문이다.

### 2.4 이번 승인에 포함되지 않은 현재 MVP 결정

다음 값은 구현 전에 결정해야 하지만 이번 승인만으로 임의 확정하지 않는다.

- 액세스 토큰 만료시간
- 계정 유형별 리프레시 토큰 유효기간
- 리프레시 토큰의 브라우저 전달·저장 방식과 CSRF 경계
- 동시 로그인 상한을 기존 일반 사용자 5개·식당 대표자 3개·플랫폼 운영자 1개로 유지할지 여부
- 정상 비밀번호·이메일 변경 시 다른 리프레시 토큰을 유지할지 폐기할지 여부
- 액세스 토큰 만료 전 즉시 차단이 필요한 명령의 중앙 계정·권한 재검증 범위

이 항목은 현재 MVP에 필요하므로 `TODO`로 숨기지 않고 `팀원 상의 필요` 또는 `변경 필요`로 추적한다.

## 3. 통합 검색 결정

### 3.1 확정 범위

- 사용자에게 일반 검색과 자연어 검색을 나눈 별도 입력창·모드 선택을 요구하지 않고 하나의 검색창을 제공한다.
- 입력을 키워드 검색 또는 자연어 검색 중 하나로 배타 분류하지 않는다. 한 입력에서 키워드와 지역·카테고리·분위기·가격·거리·인원·시각·예약 가능 여부 같은 구조화 조건을 함께 추출한다.
- 숫자·단위·시각·지역·카테고리·태그는 MiriYum 사전과 결정적 규칙으로 먼저 해석한다.
- 규칙으로 해석하지 못한 모호한 표현만 Spring AI 외부 AI 연동 계층에 전달한다. AI는 매장 목록을 생성하지 않고 허용된 검색 조건 JSON만 반환한다.
- AI 반환값은 허용 필드, 코드, 숫자 범위와 조합 규칙을 서버에서 검증한다. 실패·시간 초과·형식 오류에는 규칙 결과만 사용하고, 유효한 조건이 없으면 전체 또는 남은 문구를 일반 키워드 검색으로 처리한다.
- 키워드와 구조화 조건을 공통 통합 검색 조건으로 병합하고 MySQL에서 매장·메뉴·지역과 현재 가용 조건을 조회한다.
- MySQL은 검색과 예약·웨이팅·메뉴 상태의 현재 원본이다. 표시와 예약·홀드 확정 전에 같은 원본의 최신 영업·품절·수용량 상태를 검증한다.
- OpenSearch와 Meilisearch는 1차 MVP 검색 요청 경로와 필수 인프라에서 제외한다.

### 3.2 검색 입력 처리 예시

| 입력 | 공통 검색 조건 |
|---|---|
| `파스타` | `keyword=파스타` |
| `성수 파스타` | `region=성수`, `keyword=파스타` |
| `성수에서 조용한 파스타집` | `region=성수`, `atmosphere=QUIET`, `keyword=파스타` |
| `지금 근처 2명 예약 가능한 3만원대 식당` | 현재 위치, `partySize=2`, 예약 가능, 가격대 3만원 |
| `부모님 모시고 가기 좋은 곳` | 규칙의 미해석 표현만 AI가 허용된 분위기·목적 태그로 변환 |

### 3.3 선택 이유와 대안 비교

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| 일반 검색과 자연어 검색을 별도 모드로 분리 | 구현 흐름과 사용자 의도가 명확해 보인다. | `성수 조용한 파스타`처럼 키워드와 조건이 섞인 실제 입력을 한쪽으로 잘못 분류하고 사용자가 모드를 선택해야 한다. | 미채택 |
| 통합 입력 + 규칙 우선·AI 보조 + MySQL | 하나의 사용자 경험에서 결정적 조건과 모호한 표현을 함께 처리하고, AI 비용·지연·오류를 제한하며 최신 업무 원본을 직접 조회한다. 별도 검색 인덱스 동기화가 없다. | MySQL만으로 오타 허용·자동완성·고급 관련도·대규모 전문 검색 품질을 높이는 데 한계가 있다. | 채택 |
| OpenSearch 읽기 모델 | 한국어 분석기, 전문 검색, 위치·벡터 후보, 복잡한 관련도와 대규모 확장에 강하다. | 별도 클러스터와 MySQL 색인 동기화·재색인·장애 복구가 필요하고 현재 MVP 규모와 초기 아키텍처보다 복잡하다. | MVP 제외 확정, 측정 후 재평가 |
| Meilisearch 읽기 모델 | 애플리케이션 검색 설정이 비교적 단순하고 오타 허용·접두어·검색 즉시성과 키워드/의미 혼합 검색을 제공한다. | 역시 별도 인덱스와 동기화가 필요하고 예약·품절 같은 강한 조건은 MySQL 재검증이 필요하다. | MVP 제외 확정, 검색 UX 병목이 확인되면 우선 비교 후보 |
| AI가 결과 매장을 직접 생성 | 자연스러운 응답과 의미 이해를 빠르게 시연할 수 있다. | 존재하지 않는 매장·메뉴, 오래된 가용성, 설명 불가능한 누락과 개인정보·비용 위험이 있다. | 금지 |
| 순수 의미·벡터 검색 | 표현이 달라도 의미가 비슷한 후보를 찾기 좋다. | 정확한 매장명·메뉴명과 가격·거리·인원·예약 가능 같은 강한 조건을 놓칠 수 있다. | 현재 미채택 |

OpenSearch와 Meilisearch는 미결정 기술이 아니다. 현재 MVP에서는 도입하지 않기로 확정했으며, 오타·자동완성·전문 검색 품질이나 검색 부하가 MySQL 기준을 넘는다는 측정 결과가 생길 때만 ADR을 새로 갱신한다.

### 3.4 구현 계약으로 남길 범위

다음은 채택한 구조 안에서 기능 명세·API 계약 단계에 확정한다.

- MySQL 키워드 검색의 정규화 열, 인덱스와 전문 검색 방식
- 공통 통합 검색 조건의 정확한 필드·열거형·범위
- 규칙 해석 신뢰도와 외부 AI 호출 조건
- 외부 AI 요청에서 제외할 개인정보와 위치 정밀도
- 검색 정렬, 커서와 동률 처리의 전송 계약
- 검색 품질·지연·AI 호출률을 측정할 인수 기준

## 4. 문서 소유권과 연계 수정 범위

### 기술 선택 근거 관리 방식

기술 선택 이유와 경쟁 대안 비교는 중앙 변경 기록에 모두 복제하지 않고 `docs/adr/`에서 결정별 파일로 관리한다.

- `ADR-006`: Spring Security 액세스 JWT와 Valkey 리프레시 토큰 상태 관리
- `ADR-007`: 단일 검색창의 규칙 우선·AI 보조 해석과 MySQL 직접 조회

각 ADR은 맥락, 결정, 채택 이유, 검토한 대안별 장단점, 감수할 단점, 재검토 조건과 연계 정본을 소유한다. 정책 문서는 현재 적용할 규칙을, 시스템 아키텍처는 현재 구성과 책임을 소유하며 ADR의 비교표를 복제하지 않는다.

`miriyum-service-decisions.md`의 중앙 변경 이력에는 결정자·수정자·날짜·변경 대상·짧은 변경 이유와 해당 ADR 링크만 남긴다. 중앙 기록은 변경을 찾는 색인이고 ADR이 기술 선택 근거의 단일 원본이다.

## 6. 검증 기준

- 현재 MVP 정본에 `Spring Session Data Redis 중앙 서버 세션`, `브라우저 JWT 미사용`, `OpenSearch 조회`, `Meilisearch를 추가하지 않는다`가 활성 현재형 요구로 남지 않는다.
- Valkey는 리프레시 토큰 상태·캐시·속도 제한·임시 선점·실시간 전달의 보조 기반 시설이며 MySQL 업무 원장을 대체하지 않는다.
- 액세스 토큰 정상 요청이 매번 Valkey 정상 토큰 목록을 조회하도록 문서화되지 않는다.
- 리프레시 토큰 원문, 액세스 토큰 원문과 민감한 검증 항목을 저장·기록하도록 문서화되지 않는다.
- 자연어와 키워드 입력은 하나의 통합 검색 조건으로 합쳐지고 최종 검색 대상이 MySQL로 일관된다.
- AI가 매장 결과나 현재 가용성을 결정하지 않고 허용된 조건만 제안한다.
- OpenSearch와 Meilisearch는 `확정 + MVP 제외`이며 미결정 상태로 잘못 분류되지 않는다.
- 중앙 변경 이력에 요청·결정자 `이병우`, 수정자 `Codex`, 변경 날짜, 대상, 짧은 이유와 ADR 링크가 남는다.
- 경쟁 대안의 장단점과 선택 이유는 각 ADR에만 상세히 남고 정책·중앙 기록에 중복되지 않는다.
