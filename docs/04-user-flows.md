# 04. 핵심 사용자 흐름

## 문서 사용법

이 문서는 사용자 관점의 시작·종료 조건과 적용 단계를 요약한다. 정책 결정 상태와 단계 포함 여부는 별도 축이며, 확정 정책도 지정 단계 전에는 UI·API·권한·상태 진입 경로를 만들지 않는다. 규칙의 예외, 권한, 동시성, 감사와 재시도 기준은 링크된 상세 정책을 따른다.

## 네 단계 흐름 매트릭스

| 단계 | 진입 가능한 대표 흐름 | 비진입 경계 |
|---|---|---|
| `1차 MVP` | 분리된 계정의 이메일 로그인, 입점·매장 소속 확인, 매장·메뉴 기본 탐색, `예약만`·`예약+메뉴 홀드`·승인된 카페·베이커리의 `픽업 예약` | 웨이팅, 결제·환불, 체크인·노쇼, 자동 승계, 플랫폼 운영자 업무 화면과 알림 발송을 활성화하지 않는다. |
| `2차 MVP` | `RuleInterpreter` 규칙 해석, QueryDSL 조회, 이력 기반 결정적 Java 재정렬, 품절 대안과 지도 탐색 | 외부 AI·LLM이 조건·후보·순위·TOP3를 결정하지 않으며 웨이팅·결제 흐름에 진입하지 않는다. |
| `고도화` | 웨이팅·SSE, 예약금 결제·취소·환불, 체크인·노쇼, 일반 취소 자원 승계, 플랫폼 운영자 업무, 거래·운영 알림, Free 기본 운영 통계, Valkey 토큰 통제와 일반 사용자 카카오 로그인 | 코스·구독·리뷰·AI 설명·채팅을 활성화하지 않는다. |
| `향후 고도화` | 코스·테이스팅, 사용자 구독·매장 Pro, 리뷰, 결정적 TOP3에 대한 LLM 설명과 채팅형 탐색 | LLM이 검색 조건·후보·순위·TOP3 또는 거래 결과를 결정하지 않는다. |

## 1. 회원 가입·로그인

- **적용 단계:** `1차 MVP` 기본 이메일 로그인, `고도화` Valkey 토큰 통제·일반 사용자 카카오 로그인.
- **시작 조건:** 사용자가 회원 가입 또는 로그인을 선택하고, 필요한 인증 수단을 제공한다.
- **주요 흐름:** 서비스는 물리적으로 분리된 계정 유형과 인증 수단을 확인하고, 본인 확인과 만 14세 이상 가입 가능 여부를 검증한다. `1차 MVP`는 서버 저장 상태 없는 Access/Refresh JWT를 발급하고, `고도화`에서 Valkey 회전·폐기·재사용 탐지와 일반 사용자 카카오 로그인을 추가한다. 주류 이용 연령 확인은 현재 흐름에 포함하지 않는다.
- **성공 종료:** 사용자가 자신의 계정 유형 네임스페이스에 유효한 Access/Refresh JWT를 발급받아 서비스를 이용할 수 있다.
- **실패 종료:** 검증 실패, 잠금 또는 복구 절차가 필요하면 인증 상태를 만들지 않는다. `고도화`의 Valkey 상태가 필요한 로그인·갱신·로그아웃에서 Valkey를 확인할 수 없으면 실패 폐쇄하되 비회원 공개 조회는 중단하지 않는다.
- **관련 정책 ID:** AUTH-001, AUTH-002, AUTH-003, AUTH-006, AUTH-007, AUTH-009, AUTH-012, PRIV-002.

## 2. 식당 입점 신청

- **적용 단계:** `1차 MVP`.
- **시작 조건:** 인증된 사업자 대표자가 식당 입점 신청을 시작한다.
- **주요 흐름:** 신청자는 사업자·대표자·매장 확인 자료와 기능 선택을 제출하고, 서비스는 심사 또는 보완 요청 상태를 제시한다.
- **성공 종료:** 심사를 통과한 매장이 허용된 기능과 대표자 권한으로 운영을 시작한다.
- **실패 종료:** 필수 자료 부족, 소유권 불일치 또는 심사 거절 시 신청은 보완·거절·재신청 가능한 상태로 끝난다.
- **관련 정책 ID:** STORE-001, STORE-003, STORE-004, STORE-005, STORE-006, STORE-008, STORE-009, STORE-011, STORE-012, ADMIN-003.

## 3. 식당 탐색

- **적용 단계:** `1차 MVP` 단어·구조화 기본 탐색, `2차 MVP` 규칙 해석·이력 추천·품절 대안·지도 탐색, `향후 고도화` 설명·채팅.
- **시작 조건:** 사용자가 하나의 검색창에 위치, 조건, 식당·메뉴 이름이나 자연어 표현을 입력해 탐색을 요청한다.
- **주요 흐름:** `2차 MVP`의 `RuleInterpreter`가 숫자·단위·시각·지역·카테고리·태그를 결정적 규칙으로 해석하고, 서버가 허용한 조건만 QueryDSL predicate로 조립해 MySQL을 조회한다. 예약·메뉴 홀드 이력과 현재 요청 맥락은 결정적 Java 점수화에만 사용한다. 품절 대안은 같은 매장을 먼저 찾고, 없으면 품절 메뉴가 속한 원 매장 좌표를 기준으로 반경 3km의 다른 매장을 찾는다.
- **성공 종료:** 서비스가 결과 표시 직전에 MySQL의 최신 영업·품절·가용 상태를 다시 검증하고, 사용자가 현재 이용 가능한 식당 정보를 보고 다음 행동(상세 보기·예약)을 선택할 수 있다. 웨이팅은 `고도화`에서 활성화한다.
- **실패 종료:** 규칙으로 해석하지 못한 표현은 단어 검색으로 남기고, 조건에 맞는 결과가 없거나 위치 권한이 없으면 결과 부재 또는 지역 직접 선택을 안내한다. `향후 고도화`의 LLM 설명이 실패하면 결정적 결과와 템플릿 설명을 유지하며 LLM 실패로 후보·순위·TOP3를 바꾸지 않는다.
- **관련 정책 ID:** OPER-002, OPER-003, OPER-005, OPER-006, OPER-009, ADS-007, ADS-008, PRIV-004.

## 4. 예약

- **적용 단계:** `1차 MVP` 기본 예약, `고도화` 예약금 결제·취소·환불 연결.
- **시작 조건:** 인증된 사용자가 운영 중인 식당의 예약 가능 시간과 인원을 선택한다.
- **주요 흐름:** 서비스는 영업시간, 날짜·시간 구간별 전체 예약 가능 인원·팀 수, 중복 예약 여부와 임시 선점을 검증한다. `예약+메뉴 홀드`에서 메뉴를 선택하면 메뉴 수량을 같은 선점 그룹에 결합하고, 메뉴를 건너뛰면 예약 자원만 즉시 확정한다. `고도화`에서 예약금이 활성화된 거래만 검증된 결제 성공 뒤 확정한다.
- **성공 종료:** 사용자와 식당이 예약 상태, 방문 정보 및 필요한 다음 행동을 확인하고 예약 안내를 받는다.
- **실패 종료:** 수용량 부족, 선점 만료, 중복 예약 또는 영업 상태 변경 시 예약을 확정하지 않는다. `고도화`의 결제 실패·불명확 결과는 결제 정책에 따라 실패 또는 대사 상태로 격리한다.
- **관련 정책 ID:** RES-001, RES-004, RES-006, RES-010, RES-014, RES-015, HOLD-004, PAY-001, PAY-005, PAY-007, NOTI-004, SCALE-007.

## 5. 카페·베이커리 픽업 예약

- **적용 단계:** `1차 MVP`.
- **시작 조건:** 로그인 사용자가 픽업 예약을 활성화한 카페·베이커리의 메뉴와 픽업 구간을 선택한다.
- **주요 흐름:** `booking`은 업종 자격, 메뉴 수량, 영업·픽업 구간과 사용자 제한을 검증하고 메뉴 수량만 임시 선점한 뒤 픽업 예약을 확정한다. 홀 운영 여부는 자격 조건이 아니며 예약 인원·팀 수를 만들거나 선점하지 않는다.
- **성공 종료:** 사용자는 확정 수량·픽업 구간·수령 조건을 확인하고 매장은 같은 메뉴 수량 원장에서 준비 상태를 관리한다.
- **실패 종료:** 업종 부적격, 기능 미활성, 비영업, 무재고, 선점 만료 또는 상태 불일치에는 확정하지 않고 수량을 안전하게 반환한다.
- **관련 정책 ID:** HOLD-001, HOLD-003, HOLD-005, HOLD-007, HOLD-009, HOLD-010, HOLD-013.

## 6. 웨이팅

- **적용 단계:** `고도화`.
- **시작 조건:** 사용자가 현장 또는 원격 웨이팅이 가능한 식당에서 대기 등록을 요청한다.
- **주요 흐름:** 서비스는 위치·일행·중복 조건을 확인하고 순번과 예상 대기 정보를 부여한 뒤 호출 시점에 응답을 받는다.
- **성공 종료:** 사용자가 호출에 맞춰 도착·입장 처리되거나, 대기 상태를 스스로 종료한다.
- **실패 종료:** 위치 확인 불가, 중복 등록, 호출 기한 경과 또는 응답 없음이면 등록·호출은 정책상 허용된 종료 상태로 처리되고 결과를 안내한다.
- **관련 정책 ID:** WAIT-001, WAIT-002, WAIT-004, WAIT-007, WAIT-009, WAIT-010, WAIT-011, WAIT-012, WAIT-016, WAIT-017, NOTI-004.

## 7. 결제·취소

- **적용 단계:** `고도화`.
- **시작 조건:** 사용자가 예약에 필요한 결제를 진행하거나, 이미 확정된 예약·홀드의 취소를 요청한다.
- **주요 흐름:** MiriYum 내부 결제 레코드와 내부 주문 준비 → 내부 주문에서 일대일 파생한 고객사 채번 PortOne `paymentId`로 V2 SDK 결제 요청 → 브라우저가 보낸 상태·금액·`transactionId`를 무시하고 서버가 알려진 `paymentId`를 조회해 상태·정확한 금액/통화·내부 주문 매핑과 PortOne 채번 시도별 `transactionId` 검증 → 동일 멱등 확정 경로로 예약 반영. 브라우저는 준비된 `paymentId`와 인증된 내부 결제 참조만 조회 선택자로 전달하며, 검증된 웹훅도 `paymentId`, `transactionId`, 이벤트 유형과 타임스탬프 또는 메시지 식별자를 구분해 같은 경로를 호출한다. 취소 시 귀책·수수료·환불 조건에 따라 환불과 수량 복구를 조정한다.
- **성공 종료:** 결제 또는 환불의 최종 상태가 예약·홀드 상태와 일치하고, 사용자에게 결과가 전달된다.
- **실패 종료:** 브라우저 성공 응답만으로 결제를 확정하지 않는다. 결제·웹훅·환불 처리 실패나 상태 불일치가 발생하면 완료로 표시하지 않고, 결과가 불명확하거나 장시간 지속되는 `CONFIRMING` 거래는 다른 전이에서 격리한 채 서버 조회·중앙 복구 또는 운영 검토 경로로 남긴다.
- **관련 정책 ID:** PAY-003, PAY-004, PAY-005, PAY-006, PAY-008, PAY-009, PAY-010, PAY-014, PAY-015, RES-009, HOLD-010, ADMIN-005, ADMIN-006, NOTI-004.

## 8. 취소 자리·수량 자동 승계

- **적용 단계:** `고도화`.
- **시작 조건:** 자동 승계가 활성이고, 확정 예약의 유효한 일반 취소로 예약 자원이 반환됐거나 유효한 메뉴 홀드 취소의 수량 복구가 완료됐으며 해당 자원에 유효한 대기 등록자가 있다.
- **주요 흐름:** 서비스는 등록 순번이 가장 빠른 유효 후보에게 5분 제안을 보낸다. 사용자가 기한 안에 수락하면 자원을 10분 동안 선점하고 원 거래와 같은 예약·홀드의 검증·결제·확정 흐름으로 전환한다.
- **성공 종료:** 수락한 사용자의 예약 또는 홀드 전환이 최종 확정되고 사용하고 남은 인원·수량은 일반 가용으로 반환된다.
- **실패 종료:** 명시적 거절, 제안 만료, 자격 재검증 실패 또는 검증된 결제 실패에는 정책과 날짜 경계에 따라 다음 유효 후보 제안 또는 일반 가용 처분으로 진행한다. 결제 결과가 불명확하면 자원을 공개하거나 다음 후보로 넘기지 않는다. 노쇼 후보·노쇼 확정은 일반 취소가 아니므로 승계·반환 원장·일반 가용 재공개를 만들지 않는다.
- **관련 정책 ID:** TRANSFER-001, TRANSFER-002, TRANSFER-003, TRANSFER-004, TRANSFER-005, TRANSFER-006, TRANSFER-007, TRANSFER-008, TRANSFER-009.

## 9. 알림 수신

- **적용 단계:** `고도화`.
- **시작 조건:** 예약·웨이팅·결제 처리 등에서 사용자에게 전달할 확정 사건이 발생한다.
- **주요 흐름:** 서비스는 수신 동의, 필수성, 수신자와 채널을 확인한 뒤 중복 없이 알림을 전달하고 실패 시 정책상 재시도 또는 대체 채널을 적용한다.
- **성공 종료:** 사용자가 허용된 채널에서 해당 사건의 알림 또는 알림 이력을 확인한다.
- **실패 종료:** 동의·수신자 검증 실패, 공급자 장애 또는 전달 실패는 잘못된 대상 발송 없이 실패·재시도 상태로 종료한다.
- **관련 정책 ID:** NOTI-001, NOTI-002, NOTI-003, NOTI-005, NOTI-006, NOTI-007, NOTI-008, NOTI-010, PRIV-002, PRIV-009.

## 10. 체크인·노쇼

- **적용 단계:** `고도화`.
- **시작 조건:** 확정 예약의 사용자가 체크인을 요청하거나 지각 허용시간 뒤 권한 있는 매장 운영자가 미도착을 확인한다.
- **주요 흐름:** 서비스는 회전형 QR 또는 허용된 보조 처리의 예약·매장·시각·재사용 여부를 검증한다. 노쇼는 정책상 직접 확인 또는 보완 절차로만 확정하며 시간 경과만으로 임의 확정하지 않는다.
- **성공 종료:** 체크인은 방문 완료로, 검증된 미도착은 노쇼로 기록되고 환불·제재는 각 소유 정책의 입력으로만 전달된다.
- **실패 종료:** 잘못된 매장·만료·재사용 토큰, 권한·상태 불일치나 불명확 증거에는 상태를 바꾸지 않는다. 노쇼 후보·확정은 예약 취소나 자원 반환으로 해석하지 않는다.
- **관련 정책 ID:** CHECK-001, CHECK-003, CHECK-005, CHECK-006, CHECK-007, CHECK-009, CHECK-010, PAY-009.

## 11. 플랫폼 운영자 업무

- **적용 단계:** `고도화`.
- **시작 조건:** 별도 플랫폼 운영자 계정으로 로그인한 담당자가 배정 사건과 업무 권한 범위 안에서 심사·분쟁·복구·장애 대응을 요청한다.
- **주요 흐름:** 서비스는 플랫폼 운영자 계정 상태, 세부 권한, 사건 배정, 추가 인증과 대상 버전을 검증하고 멱등 명령으로 처리한다.
- **성공 종료:** 허용된 결정과 후속 작업이 감사 원장에 남고 당사자에게 필요한 결과가 전달된다.
- **실패 종료:** 권한·배정·추가 인증·중앙 상태를 확인할 수 없으면 실패 폐쇄하며 일반 사용자나 매장 운영자 계정으로 우회하지 않는다.
- **관련 정책 ID:** ADMIN-001, ADMIN-003, ADMIN-004, ADMIN-005, ADMIN-006, ADMIN-007, ADMIN-010, ADMIN-011, ADMIN-012.
