# 02. 사용자와 권한

## 플랫폼 운영자 인증 활성 계약

- 기능 플래그가 켜진 환경에서만 `/api/v1/platform-operators/**`를 노출하며 기본값 OFF에서는 실제 404를 반환한다.
- 플랫폼 운영자는 공개 가입 없이 V39의 별도 계정 원장과 `platform-operator` JWT namespace를 사용한다.
- 중앙 세션은 유휴 30분, 절대 8시간, 계정당 1개다. 최초 비밀번호 변경 전에는 변경 API 외 업무 접근을 막고 계정 중지·권한 버전·세션 버전 변경 시 기존 세션을 무효화한다.
- 역할은 고정 catalog의 세부 권한 묶음이며 모든 업무 요청은 현재 MySQL 권한 version을 다시 검증한다. 고위험 명령은 현재 권한·사건 배정·현재 비밀번호 기반 일회 승인이 모두 있어야 한다.

## 회원지원 활성 계약

- 회원지원 운영자는 `MEMBER_READ_MINIMAL`, `MEMBER_RECOVERY`, `ACCOUNT_APPEAL_REVIEW`의 필요한 권한만 사용하고 제재 운영자는 `ACCOUNT_SANCTION`을 사용한다.
- 영구 정지는 제안자와 다른 `SUPER_ADMIN`이 `ACCOUNT_PERMANENT_SANCTION_APPROVE`와 별도 일회 재인증으로 추가 승인해야 한다.
- 권한 검사는 계정 조회보다 먼저 수행한다. 존재하지 않는 ID와 요청 계정 유형이 다른 ID는 같은 결과로 정규화하며 이메일·휴대전화·인증정보를 회원지원 응답에 노출하지 않는다.
- 외부 개인인증을 연결하지 않는 단계에서는 목적·계정에 결속된 mock 확인을 사용하고 인증 비밀 원문은 응답·로그·감사에 남기지 않는다. 상세 계약은 [회원지원 기능 명세](specs/member-support/spec.md)를 따른다.

## HTTP audience namespace

- 일반 사용자 인증·계정·예약·픽업 경로는 `/api/v1/consumers/**`를 사용한다.
- 매장 운영자 인증·계정·매장 관리 경로는 `/api/v1/store-operators/**`를 사용한다.
- 인증이 필요 없는 매장·카탈로그·가용성 조회는 `/api/v1/stores/**` 등 공개 자원 경로를 유지한다.
- JWT namespace와 refresh/CSRF 쿠키 Path는 각 audience 경로와 일치해야 하며, 구 단수·기능별 root는 호환 경로로 남기지 않는다.

## 핵심 참여자

- 일반 사용자는 매장과 메뉴를 탐색하고 로그인 후 자신의 예약·메뉴 홀드·픽업 등 방문 경험을 관리한다.
- 매장 운영자는 사업자 검증과 매장 소속 확인을 마친 뒤 자신에게 연결된 매장의 운영 자원만 관리한다.
- 플랫폼 운영자는 `고도화`에서 입점 증빙·제한 기능 심사, 고객지원·분쟁, 결제 예외, 장애와 어뷰징 대응을 맡는다. `1차 MVP` 정상 입점은 플랫폼 운영자 권한 없이 자동 확인한다.

## 물리적 계정 분리

세 계정 유형은 하나의 사용자 테이블과 역할 열로 합치지 않는다. 각 유형은 별도 테이블, 별도 기본 키, 별도 인증 주체와 별도 토큰 네임스페이스를 가진다.

아래 표는 최종 분리 목표를 함께 보여 준다. 1차 MVP Flyway·코드·JWT에는 일반 사용자와 매장 운영자만 포함하며 플랫폼 운영자 행은 고도화에서 추가한다.

| 계정 유형 | 물리 테이블 | 기본 키 | 인증 주체 | 토큰 네임스페이스 |
|---|---|---|---|---|
| 일반 사용자 | `consumer_accounts` | `consumer_account_id` | `consumer:{consumer_account_id}` | `consumer` |
| 매장 운영자 | `store_operator_accounts` | `store_operator_account_id` | `store-operator:{store_operator_account_id}` | `store-operator` |
| 플랫폼 운영자 | `platform_operator_accounts` | `platform_operator_account_id` | `platform-operator:{platform_operator_account_id}` | `platform-operator` |

- 한 사람이 여러 계정 유형을 각각 보유할 수 있지만 기본 키, 로그인 상태, 토큰과 권한은 공유하지 않는다.
- 같은 이메일·휴대전화가 서로 다른 계정 유형에 존재할 수 있다. 이메일 일치, 휴대전화 일치, 외부 로그인 성공이나 로그인 수단 연결은 계정 유형·인증 주체·권한을 생성, 병합, 전환 또는 승격하지 않는다.
- 매장 운영자 계정은 개인별 계정이다. 직원용 계정, 매장 공용 계정이나 다른 계정 유형의 인증정보 공유로 대체하지 않는다.

## 매장 운영자와 매장 관리 관계

1차 MVP에서 각 `stores` 행은 `store_operator_account_id` FK로 현재 대표 운영자 한 명을 직접 참조한다. 한 운영자가 여러 매장을 관리할 수 있지만 한 매장에는 대표 운영자 한 명만 연결한다. 직원·공동 관리자·역할별 권한·명의 양도·소속 이력은 제공하지 않는다.

다중 운영자나 명의 양도를 도입하는 고도화에서는 별도 관계 테이블로 마이그레이션한다. 그때 기존 FK 값을 각 매장의 최초 `OWNER` 관계로 이관한 뒤 권한 조회 구현을 교체하며, 1차 MVP 공개 API에는 운영자 FK를 불필요하게 노출하지 않는다.

모든 매장 관리 요청은 다음 네 조건을 함께 검증한다.

1. 요청의 인증 주체가 `store-operator` 네임스페이스의 유효한 매장 운영자 계정인지
2. 매장 운영자 계정 상태가 활성인지
3. 대상 매장의 `store_operator_account_id`가 인증된 운영자 계정과 일치하는지
4. 대상 매장의 입점 승인·운영 상태가 요청한 기능을 허용하는지

하나라도 확인할 수 없거나 유효하지 않으면 실패 폐쇄한다. 클라이언트가 보낸 계정 유형, 오래된 캐시나 다른 매장의 소속으로 이 검증을 우회하지 않는다.

## 역할별 권한 경계

- 비회원은 공개된 매장·메뉴·가격·예약 가능 여부를 탐색하고 조회할 수 있지만 거래 상태를 만들거나 변경할 수 없다.
- 일반 사용자는 자신의 거래만 관리하며 다른 일반 사용자, 매장이나 플랫폼 운영 영역을 관리할 수 없다.
- 매장 운영자는 자신을 대표 운영자로 참조하는 매장에 한해 등록·운영 설정과 예약·메뉴 홀드·픽업 자원을 관리한다. 일반 사용자 계정이나 다른 매장·플랫폼 운영 영역을 대신 관리할 수 없다.
- 플랫폼 운영자는 `고도화`에서 부여된 업무 권한 안의 심사, 분쟁, 수동 복구와 장애 대응을 수행한다. 민감한 접근과 대량 작업은 업무 범위·승인·감사 경계를 따른다.

## 단계별 인증 경계

- `1차 MVP`는 일반 사용자와 매장 운영자에게 각각 별도 네임스페이스의 stateless Access JWT와 Refresh JWT를 발급하며 서버에 정상 토큰이나 리프레시 상태를 저장하지 않는다. 플랫폼 운영자 계정·JWT·API·UI는 고도화에서 별도 활성화한다.
- `고도화`에서 Valkey 기반 Refresh Token 회전·폐기·재사용 탐지와 일반 사용자 카카오 로그인을 도입한다.
- 단계가 바뀌어도 계정의 물리적 분리와 이메일·외부 로그인에 의한 권한 불변 원칙은 유지한다.

## 상세 정책 연결

가입, 로그인, 토큰, 복구와 계정 제재는 [회원·인증·계정 정책](service-policies/01-member-auth.md)에서 정한다. 매장 등록과 소속 확인은 [매장 입점·심사·매장 운영자 권한 정책](service-policies/02-store-onboarding.md), 플랫폼 운영자 심사·분쟁·수동 복구는 [플랫폼 운영자·분쟁·수동 복구 정책](service-policies/15-admin-operation.md), 개인정보와 민감 정보 접근 경계는 [개인정보·보안 정책](service-policies/17-privacy-security.md)에서 정한다.
