# ADR-001: 단일 애플리케이션과 도메인별 3계층 패키지

- 상태: Accepted
- 결정일: 2026-07-24

## 배경

초기 MiriYum은 예약과 결제처럼 정합성이 중요한 흐름을 빠르게 구현하면서도 도메인 책임과 HTTP·유스케이스·영속성 경계를 분명히 해야 한다.

## 결정

초기 백엔드는 하나의 Spring Boot 애플리케이션으로 구성한다. 각 도메인은 `controller`, `service`, `repository`의 3계층을 기본 경계로 두고, 실제 필요가 생길 때 `entity`, `dto`, `exception` 등의 하위 패키지를 해당 도메인 안에 추가한다.

`controller`는 HTTP 경계, `service`는 유스케이스와 트랜잭션 경계, `repository`는 영속성 접근을 담당한다. 도메인 간 협력은 공개된 service 경계를 통해서만 이루어진다.

## 검토한 대안

- 초기부터 마이크로서비스로 분리: 배포·관측·데이터 정합성의 운영 복잡도가 초기 요구보다 크다.
- 기술 계층별 전역 패키지 구성: 도메인 책임과 변경 범위가 흩어진다.
- controller에서 repository 직접 호출: 유스케이스와 트랜잭션 정책의 위치가 불명확해진다.

## 긍정적 결과

- 하나의 트랜잭션 모델 안에서 핵심 흐름의 정합성을 구현할 수 있다.
- 기능 변경이 도메인 경계 안에 머물러 탐색과 테스트가 쉬워진다.
- HTTP, 유스케이스, 영속성 책임을 분리할 수 있다.

## 부정적 결과

- 애플리케이션 규모가 커지면 배포 단위가 커질 수 있다.
- 도메인 간 service 협력 경계를 지속적으로 점검해야 한다.

## 재검토 조건

독립 배포, 독립 확장, 별도 데이터 소유 또는 비동기 통합 요구가 실제로 검증되면 모듈러 모놀리스 유지 또는 분리를 별도 ADR로 재검토한다.

## 2026-07-27 날짜별 개정

### 개정 결정

- 최초 결정과 본문은 당시의 아키텍처 판단 기록으로 보존한다. 현재 계획은 **방식 A**, 즉 1차 MVP·2차 MVP·고도화까지 하나의 Spring Boot 애플리케이션과 하나의 MySQL을 유지하는 것으로 구체화한다.
- 단일 애플리케이션 안에서도 일반 사용자, 매장 운영자, 플랫폼 운영자는 각자의 계정 테이블, PK, principal, 토큰 namespace를 사용한다. 세 계정 유형을 공통 계정 행이나 하나의 역할 값으로 합치지 않는다.
- 프론트엔드는 계정 유형별 로그인 화면, route shell, 권한 실패 처리를 분리한다. 백엔드도 각 인증 진입점에서 예상한 principal 유형을 검증해 다른 유형의 토큰을 거부한다.
- 1차 MVP는 계정·매장·예약 모듈, 2차 MVP는 검색·규칙 기반 추천 모듈, 고도화는 결제·웨이팅·알림·플랫폼 운영 기능을 같은 배포 단위 안에서 단계적으로 활성화한다.

### 결과와 이행

- 도메인 공개 포트와 저장소 소유권을 유지하므로 향후 분리 가능성은 남지만, 현재 단계에는 네트워크 경계·분산 트랜잭션·중복 데이터 모델을 만들지 않는다.
- 독립 배포·확장 요구가 계측으로 확인되기 전에는 MSA, Kafka, 범용 Outbox를 도입하지 않는다. 재검토 시에는 분리 대상, 데이터 소유권, 장애 복구, 비용과 되돌림 계획을 함께 승인한다.
- 물리적 계정 분리로 인증·마이그레이션·테스트 조합은 늘어나지만 계정 유형 간 권한 혼동과 ID 결합 위험을 줄인다. 세 유형의 교차 토큰 거부와 route 격리를 계약 테스트로 검증한다.
