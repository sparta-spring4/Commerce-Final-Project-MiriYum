# ADR-007: 단일 검색창과 MySQL 기반 통합 검색

- 상태: Accepted
- 결정일: 2026-07-27

## 배경

사용자는 `성수 파스타`처럼 일반 키워드와 지역 조건을 섞거나 `지금 근처 2명 예약 가능한 식당`처럼 여러 구조화 조건을 자연스럽게 함께 입력한다. 일반 검색과 자연어 검색을 별도 모드로 나누면 한 입력을 어느 한쪽으로 잘못 분류하거나 사용자가 검색 방식을 먼저 선택해야 한다.

현재 MVP는 별도 검색 인덱스의 동기화와 운영 부담을 추가하지 않으면서 최신 매장, 메뉴와 예약 가능 상태를 조회해야 한다. 외부 AI의 해석 능력은 활용하되 존재하지 않는 매장이나 오래된 가용성을 결과로 만들지 못하도록 책임을 제한해야 한다.

## 결정

- 사용자에게 검색창 하나만 제공하며 일반 검색과 자연어 검색을 나눈 별도 모드를 두지 않는다.
- 입력을 키워드 또는 구조화 조건 중 하나로 배타 분류하지 않는다. 한 입력에서 키워드와 지역, 카테고리, 분위기, 가격, 거리, 인원, 시각과 예약 가능 여부 같은 구조화 조건을 함께 추출한다.
- 숫자, 단위, 시각, 지역, 카테고리와 서비스가 관리하는 태그는 결정적 규칙으로 먼저 해석한다.
- 규칙으로 해석하지 못한 표현만 Spring AI를 통한 외부 AI 연동에 전달한다.
- AI는 서버가 허용한 검색 조건만 제안하며 매장, 메뉴 또는 현재 가용성 결과를 생성하지 않는다.
- AI가 제안한 조건은 허용 필드, 코드, 값 범위와 조합 규칙을 서버에서 검증한다. 실패하거나 유효한 조건이 없으면 규칙으로 해석한 조건과 남은 키워드만 사용한다.
- 키워드와 구조화 조건을 하나의 통합 검색 조건으로 합치고 최종 매장 조회는 MySQL에서 수행한다.
- OpenSearch와 Meilisearch는 미결정 항목이 아니라 도입하지 않기로 확정한 MVP 제외 기술이다.

## 검토한 대안

### 일반 검색과 자연어 검색의 별도 모드

입력 처리 흐름과 사용자 의도가 명시적으로 나뉜다는 장점이 있다. 반면 키워드와 조건이 섞인 입력을 한쪽으로 잘못 분류하기 쉽고 사용자가 검색 전에 모드를 선택해야 한다. 하나의 검색창에서 두 종류의 정보를 함께 추출하는 방식을 선택했다.

### OpenSearch 읽기 모델

전문 검색, 언어 분석, 위치 후보와 복잡한 관련도 조정에 유리하다. 반면 별도 클러스터와 MySQL 색인 동기화, 재색인, 장애 복구와 운영 관측이 필요하다. 현재 MVP에서는 제외하기로 확정하고, 측정 결과가 MySQL 기준을 넘을 때만 재검토한다.

### Meilisearch 읽기 모델

오타 허용, 접두어 검색과 자동완성을 비교적 단순하게 제공할 수 있다. 반면 별도 인덱스와 동기화가 필요하며 예약과 품절 같은 현재 상태는 다시 MySQL에서 검증해야 한다. 현재 MVP에서는 제외하기로 확정하고 검색 사용성 병목이 측정될 때 비교 후보로 재검토한다.

### AI 직접 결과 생성

모호한 표현을 자연스럽게 처리하고 결과 설명을 빠르게 구성할 수 있다. 반면 존재하지 않는 매장이나 메뉴, 오래된 가용성과 설명하기 어려운 누락을 만들 수 있다. AI에는 허용된 조건 제안만 맡기고 결과 생성은 금지한다.

### 순수 의미·벡터 검색

표현이 달라도 의미가 비슷한 후보를 찾는 데 유리하다. 반면 정확한 매장명과 메뉴명, 가격, 거리, 인원과 예약 가능 여부 같은 강한 조건을 놓칠 수 있고 별도 색인 책임도 생긴다. 규칙과 키워드, 구조화 조건을 결합한 MySQL 조회를 우선한다.

## 긍정적 결과

- 사용자는 검색 종류를 선택하지 않고 한 입력에서 키워드와 조건을 함께 사용할 수 있다.
- 결정적 규칙을 먼저 적용해 외부 AI 호출 비용, 지연과 실패 영향을 제한한다.
- AI가 허용된 조건만 제안하므로 검색 결과의 존재와 현재 상태를 MySQL 원본에 근거해 설명할 수 있다.
- 별도 검색 인덱스 동기화, 재색인과 클러스터 운영 책임을 MVP에서 피할 수 있다.
- AI 연동이 실패해도 규칙 결과와 키워드 검색으로 대체할 수 있다.

## 부정적 결과

- MySQL만으로 오타 허용, 자동완성, 전문 검색 관련도와 대규모 검색 부하를 처리하는 데 한계가 있을 수 있다.
- 규칙 사전, 조건 병합과 AI 반환값 검증 규칙을 애플리케이션에서 관리해야 한다.
- 외부 AI를 호출하는 입력에는 추가 지연과 비용이 발생하며 실패 대체 처리가 필요하다.
- 별도 검색 엔진을 제외하므로 향후 측정 결과에 따라 읽기 모델을 새로 설계하고 동기화해야 할 수 있다.

## 재검토 조건

OpenSearch와 Meilisearch는 다음 측정 결과 중 하나가 MySQL에 대해 합의한 품질·성능 기준을 넘을 때만 재검토한다.

- 오타 허용과 자동완성 부재가 검색 성공률이나 검색 이탈률에 허용할 수 없는 영향을 준다.
- 전문 검색 품질과 관련도 평가가 MySQL 기반 개선만으로 목표 기준을 충족하지 못한다.
- 검색 부하, 응답 지연 또는 데이터 규모가 MySQL 검색의 운영 기준을 지속해서 넘는다.

재검토하더라도 예약, 품절과 가용성 같은 최종 업무 상태는 MySQL에서 다시 검증한다.

## 2026-07-27 날짜별 개정

### 단계 개정

- 최초 통합 검색 결정과 외부 자연어 해석 본문은 당시 판단 기록으로 보존한다. 현재 합의에서는 외부 AI 부분을 향후 고도화로 이동한다.
- **1차 MVP:** MySQL의 기본 키워드·조건 조회만 제공한다.
- **2차 MVP:** 결정론적 `RuleInterpreter`가 자연어를 허용된 조건으로 변환하고 QueryDSL이 매장·메뉴·지역·가격·시간 조건을 MySQL에 적용한다. 추천은 매장·예약 이력과 검색 조건 규칙을 사용하며 예약 모듈의 동기 `BulkAvailabilityPort`로 최종 가용성을 확인한다.
- 2차 MVP에는 Spring AI, 외부 AI/LLM, 벡터 DB, OpenSearch, Meilisearch, 추천 결과 캐시, 메시지 브로커를 두지 않는다. 해석 실패는 명시적 경고와 일반 키워드 검색으로 축소한다.
- 거리 계산의 출발지는 검색 결과를 여는 매장의 저장 좌표다. 사용자 현재 위치를 요청·저장하지 않는다. Kakao Local API는 매장 입점·주소 변경 시 지오코딩, 지도 SDK는 결과 표시와 매장 운영자의 좌표 확인에만 사용하며 추천 요청 중 외부 지도 호출을 하지 않는다.

### 검증·이행·재검토

- 규칙 해석은 버전된 회귀 데이터셋으로 동일 입력·동일 결과, 모순 조건, 알 수 없는 표현, SQL injection 방지와 fallback을 검증한다.
- QueryDSL 통합 테스트는 Testcontainers MySQL에서 조건 조합, 정렬·커서 안정성, 품절·예약 수용량 재검증과 개인정보 비노출을 확인한다.
- 외부 AI를 향후 검토하려면 규칙 기반 방식으로 해결되지 않는 측정된 품질 문제, 최소 정보·법률 검토, 비용·지연·실패 fallback, 모델 변경 회귀와 사용자 고지를 별도로 승인해야 한다. 검색 엔진도 MySQL 부하·지연이 승인 기준을 지속적으로 넘는 증거와 재색인·장애 복구·되돌림 계획이 필요하다.
- 규칙과 MySQL만 사용하면 표현 범위와 대규모 검색 확장성이 제한될 수 있지만, 2차 MVP의 결과를 재현·설명하고 예약 원장과 동기적으로 맞출 수 있다.
